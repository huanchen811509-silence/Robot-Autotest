## 1. 需求原文与解读

### 1.1 原文

> 1 项目看板 和新建项目（向导式） 需要 拆分为2个独立菜单 并且每个用户下（前提是有权限） 都要支持创建项目 ，及时选了项目 对应的这个菜单也需要呈现
> 2 如果项目的测试资产已经分配了 程序需要 支持自动获取焊接与拓扑对应的信息 （如果是多个项目均用共同的资产 在一定时间范围间隔内可以复用获取结果）； 也要支持手工触发获取
> 3 请对以上需求进行评估 编写评估报告

### 1.2 解读（含原文笔误校正）

| 编号 | 解读 | 说明 |
|---|---|---|
| R1 | 「项目看板」（`/overview`）与「新建项目（向导式）」（`/projects/new`）在侧栏各占**一个独立菜单项**，不再是一个入口藏在账户下拉、另一个在侧栏 | 「独立菜单」= 两个可点击的叶子项，而非「一个分组 + 一个跳转」 |
| R1-a | 「每个用户下（前提是有权限）都要支持创建项目」= **有创建权限的角色都能看到并创建**，不受「是否已选中某项目」影响 | 关键是把「有权限」定义清楚（见 §8 D2） |
| R1-b | 「及时选了项目」按笔误处理为「**即使**选了项目」：已处于某项目上下文时，「新建项目」菜单**仍需呈现**，不能因为「当前已有项目」而隐藏 | 现状向导创建成功后会自动把新项目设为当前项目，故该场景真实存在 |
| R2 | 项目测试资产**已分配**（引用/共享生效）后，程序**自动获取**该资产的「焊接」与「拓扑」信息；多项目共用同一资产时，在**时间窗口内复用**获取结果；同时提供**手工触发**刷新 | 自动 + 可复用 + 可强制刷新，三者都要 |
| R3 | 对 R1/R2 做可行性、影响面与方案评估，输出本报告 | 不改代码 |

## 4. R1 方案设计

### 4.1 设计要点

1. 两个项都是**叶子**：`项目看板`（不变，`/overview`）+ `新建项目`（新增，`/projects/new`）。
2. 新增能力码 `project:create`，侧栏叶子 `capability: 'project:create'`，路由 `meta.capability = 'project:create'`。
3. 账户下拉里的「新建项目」保留为**快捷入口**，但显隐改为 `project:create`；与侧栏同口径，不再出现「看得到点不了」。
4. 「是否已选项目」不参与任何显隐判断 —— 满足 R1-b，并补测试。

### 4.2 菜单层级：两案对比

| 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| A（推荐） | 在 `workbench` 组内并列新增叶子 `workbench-create` → `/projects/new` | 一级仍 7 组；组内 ≥2；图标集合不变；改动集中 | 需改 C-02 子路径断言 + 角色快照 | **采纳** |
| B | 把「项目看板」与「新建项目」提升为两个**一级菜单**（一级变 9 组） | 字面最贴近「拆分为 2 个独立菜单」 | 破坏 C-01/C-03/C-04，需改 PRD IA 与全部一级断言；一级从 7→9 会稀释现有信息架构 | 不推荐 |

> 注：R1 字面要求「拆分为 2 个独立菜单」。方案 A 满足「两个独立可点击菜单项」，且不破坏既定 IA 基线；
> 若大师坚持「一级菜单」语义，再按方案 B 走 PRD 变更（需评估 7→9 组的导航容量与后续扩展位）。

### 4.3 权限口径设计

| 角色 | 现状 `PROJECT/CREATE` | 建议 | 理由 |
|---|---|---|---|
| ADMIN | 有 | 保持 | 管理员本就全权 |
| PM | **无** | **建议授予** | 「有权限用户都能建项目」的最小可满足解读；PM 是项目生命周期的天然责任人 |
| ENGINEER | 无 | 保持无（可选扩展） | 工程师建项目会产生大量孤立项目，治理成本高；如业务确有需要再单列决策 |
| VIEWER | 无 | 保持无 | 只读角色 |

> 若最终决定「只有 ADMIN 可建」，则 R1 的「每个有权限用户」在语义上已被满足（有权限=ADMIN），
> 但需要明确写进 PRD，避免后续反复；同时仍须修 G2 的口径错位（这是缺陷，不是取舍）。

## 5. R2 方案设计

### 5.1 两条路径

| 路径 | 做法 | 可行性 | 范围可控性 | 结论 |
|---|---|---|---|---|
| A | 「连接/拓扑」由**平台内部资产派生**：读设备/端口（含网卡归属）/链路，组装成结构化连接明细与拓扑图；事件驱动 + TTL 缓存复用 | 高（数据已在库内） | 高 | **采纳** |
| B | 对接外部「布线/焊接管理系统」拉取真实连接数据 | 取决于接口/认证/网络可达性（当前无任何接口信息） | 低 | 不适用（口径已澄清为内部派生），仅保留 provider 抽象位 |

> 路径 B 的前置信息缺失（接口协议、鉴权方式、部署网络、数据粒度、更新频率），
> 本文**不做工作量评估**，只保留接口位（`AssetInfoProvider` 抽象），后续按需插入实现。

### 5.2 口径与模型设计（路径 A）

**连接（Connections，原文「焊接」）**：定义为**设备 → 网卡 → 接口的连接明细**，一行 = 一条链路端点对：

| 字段 | 含义 | 现状来源 |
|---|---|---|
| `linkId / linkName` | 所属链路 | `Link` |
| `aDevice / aNic / aPort` | A 端设备、网卡、接口 | `Link.aDeviceId/aPortId` + 端口网卡归属字段 |
| `bDevice / bNic / bPort` | B 端设备、网卡、接口 | 同上 |
| `protocol / speedGbps / mtu` | 链路与端口属性 | `Link` / `DevicePort` |
| `macAddress / ipAddress / portStatus` | 接口地址与状态 | `DevicePort` |
| `nicName / nicIndex`（**新增**） | 网卡归属 | 迁移：`device_port` 增两列（可空） |
| `alias`（**不入缓存**） | 本项目对资产的自定义名 | `project_asset.alias`，组装期套用 |

**网卡建模（已定）**：不新建实体表；在 `device_port` 上补 `nic_name` / `nic_index`，把同一设备下的端口按网卡分组，
即可表达「设备 → 网卡 → 接口」三级，改动面最小。

**拓扑（Topology）**：设备-网卡-接口级连接图，节点 = 设备/网卡/接口，边 = 链路。
输出为 `nodes[] + edges[] + stats`，不落新表；资产变更后重新派生。

### 5.3 触发时机（自动 vs 手工）

| 触发 | 时机 | 是否"自动" | 说明 |
|---|---|---|---|
| T1 分配事件 | `share` / `reference` / `unreference` **事务提交后** | 是 | 通过 `@TransactionalEventListener(AFTER_COMMIT)` 发布变更，异步刷新该项目聚合 |
| T2 资产变更 | 设备/端口/链路写操作提交后 | 是 | 失效该项目 + 相关资产片段缓存 |
| T3 首次读懒加载 | `GET asset-info` 命中缺缓存或已过期 | 是 | 懒加载刷新，避免后台定时任务 |
| T4 手工刷新 | `POST asset-info/refresh`（`force=true` 绕过 TTL） | 否 | 幂等 + 单飞去重 + 审计 |

**边界声明**：T1–T3 全部是**库内派生**，不发起任何远端命令，因此**不违反**「采集为显式触发、不在后台自动跑」原则（F-24）。
若未来接路径 B 的远端拉取，远端动作只能由 T4 手工触发或明确授权的定时任务执行。

### 5.4 缓存与复用设计（核心）

```
L1 片段缓存：key = "{assetType}:{assetId}:{contentHash}"
             value = 该资产的连接明细 + 拓扑片段（不含 alias，不含 projectId 前缀）
L2 项目聚合缓存：key = "project:{projectId}:{assetSetFingerprint}"
             assetSetFingerprint = hash(排好序的 {type,id,contentHash} 列表)
```

- **多项目共用同一资产**：L1 命中即复用，天然跨项目共享；L2 因 `assetSetFingerprint` 不同而各自独立。
- **别名隔离**：`alias` 在**组装输出阶段**按 `project_asset` 套用，绝不进 L1/L2，避免串项目名字。
- **复用窗口**：TTL 默认 **12h（43200s，可配 `asset-info.cache.ttl-seconds`）**，L1 与 L2 同窗口；
  资产变更走事件**立即失效**，不等窗口到期；`force=true` 时跳过两级缓存并重算。
- **失效**：`contentHash` 变化 → 指纹变 → L2 自然失效；同时 T2 事件主动逐出该项目 L2（防止指纹碰撞误命中）。
- **并发**：按 `projectId` 单飞（in-flight map，参考 F-23），并发 refresh 只产生 1 次重算；其余请求等待并复用同一结果。
- **降级**：缓存组件不可用时退化为直算（只影响性能，不影响正确性）。

**为什么不能直接复用现有 `TtlCache` 默认值**：默认 30s 与 12h 差三个数量级，达不到「按小时复用」的目的；
且能力缓存与资产聚合的容量特征不同，建议**独立配置段**，避免调 TTL 影响权限缓存行为。

### 5.5 接口草案

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/projects/{projectId}/asset-info?scope=connections,topology` | `ASSET/READ` | 返回聚合结果 + `meta{generatedAt, cacheHit, source, expired}` |
| POST | `/api/projects/{projectId}/asset-info/refresh?scope=connections,topology&force=true` | `ASSET/UPDATE` | 手工触发；返回与 GET 同结构；写审计 `asset-info.refresh` |

响应示例（结构示意，非最终契约）：

```json
{
  "generatedAt": "2026-11-10T10:00:00Z",
  "meta": { "cacheHit": true, "source": "internal", "expired": false },
  "connections": { "items": [ { "linkId": 1, "aDevice": "sw-01", "aNic": "nic0", "aPort": "eth1", "bDevice": "srv-01", "bNic": "nic0", "bPort": "eth0" } ], "count": 1 },
  "topology": { "nodes": [ { "id": "dev:1", "name": "sw-01", "type": "switch", "parent": null } ], "edges": [ { "from": "dev:1/nic0/eth1", "to": "dev:2/nic0/eth0", "linkId": 1 } ], "stats": { "deviceCount": 2, "linkCount": 1 } },
  "empty": false
}
```

**空态**：项目未分配任何资产 / 无链路 → `200` + `empty=true` + 前端提示「尚未分配资产或无连接数据」，不返回 4xx。

### 5.6 前端设计

- 落点：`环境与拓扑` 组内新增「连接与拓扑」页（或 `AssetsView` 增加同名 Tab，二选一，建议独立页，避免资产页继续膨胀）。
- 展示：拓扑图（设备 → 网卡 → 接口三级，复用 `AssetsView` 的 `linkChains` 渲染思路）+ 连接明细表（可导出）。
- 元信息条：生成时间 / 数据来源 / 是否命中缓存 / 已过期提示。
- 操作：`重新获取` 按钮（`ASSET/UPDATE` 才渲染），点击走 refresh，带二次确认（因可能触发重算）。
- 多项目复用提示：当 `cacheHit=true` 时显示「复用窗口内结果」，让用户理解"不是实时"。

## 9. 结论与版本建议

1. **R1 可行，范围小但前置决策重**。真正的难点不是加一个菜单，而是把「谁能建项目」定义清楚；
   当前「PM 可见入口但后端 403」是既有缺陷，必须借本次一并修正。放开范围须同步 PRD §3.1、
   `authz-matrix.yaml`、`PermissionMatrixTest` 三处，否则门禁必红（C-06/C-07）。
2. **R2 在路径 A 下可行，规模中等**。核心不是"抓数据"，而是**缓存语义**：资产级片段缓存 + 项目级指纹缓存，
   `alias` 严格排除在缓存之外。原「焊接」口径已澄清为「设备-网卡-接口的连接」，外部系统对接不再在范围内。
3. **不建议**为 R1 把一级菜单从 7 组扩到 9 组；也不建议为 R2 引入后台定时远端采集（与既有原则冲突）。
4. **版本归属建议**：作为 `v4.3.0` 候选拆两条 FR ——
   `FR-v4.3-01 项目创建菜单与创建权限口径统一`、`FR-v4.3-02 测试资产连接与拓扑信息自动获取与复用`。
5. **本文不改任何业务代码**。评审通过后再按七道流程产出 PRD → DEV-PLAN → TEST-PLAN → 实装。

### 9.1 问卷结论（2026-11-10）

1. 「焊接」为笔误，实指**设备、网卡和接口的连接**；由平台内部资产派生。
2. 「有权限的用户」= **管理员 + 项目经理**（工程师与访客不可建）。
3. 菜单留在**「工作台」组内**，新增独立叶子项；一级仍 7 组。
4. 复用窗口默认 **12 小时**，可配置；资产变更**立即失效**，并支持手工触发刷新。
