## 0. 结论先行

| # | 问题 | 结论 |
|---|---|---|
| 1 | 用例↔脚本的绑定底座有没有 | **有，且是唯一可信源**：`case_script_binding` 表（唯一键 `project_id+case_id+kernel`），扫描 pytest-cases 工程后由 `PytestBindingSyncService` 落库。RF 侧明确无关联列、显示 `NOT_APPLICABLE` `[已核实]` |
| 2 | 「有脚本」这件事在界面上看得到吗 | **看得到但不能筛**：项目库/公共库列表、用例集成员表都有脚本列（`CasesView.vue:361-383`、`GlobalCasesView.vue:214-227`），但 4 个筛选维度里没有脚本维度 `[已核实]` |
| 3 | 执行前会拦无脚本用例吗 | **三套口径并存、互相矛盾**：v5.1 整单 400、v5.23 预测跳过但可跑、预览记 `skipReasons` 不拦截。大师本轮裁定收敛为「软校验 + 确认跳过」 `[已核实 + 已裁定]` |
| 4 | 能快速筛出已有脚本的用例组集吗 | **不能**：全链路无 `bindingState` 过滤参数；唯一“按条件组集”是场景页按分类（`CategoryTree.vue:122-147`），且不按脚本、不在用例库页 `[已核实]` |
| 5 | 做不做得起 | **有条件可行**。改造集中在“列表查询加脚本过滤 + 一个通用批量入集端点 + 执行预检收敛”，不需要新表、不需要动绑定表结构；条件见 §10 前置清单 |
| 6 | 版本落位 | 本轮只出评估 + PRD，FR 用临时前缀 `FR-READY-xx`；**进 `docs/release/` 前统一替换为 `FR-vX.Y-xx`**（`detect_prefix` 只认 `v<数字>`） |

**一句话**：这是「最后一公里的可用性补齐」——绑定数据、展示件、同步链路都已存在，缺的是**把「有脚本」从一列展示升级为可筛选、可组集、可在执行前统一裁决的平台能力**。

## 1. 需求理解与可判定拆解

大师四点指示拆为 8 条可判定需求；每条标注 `case_code`-级证据与完成判据。

| # | 用户动作 / 意图 | 完成判据（可观察） | 证据等级 |
|---|---|---|---|
| N1 | 在项目用例库看到每条用例有没有脚本 | 项目库列表脚本列显示 4 态之一，且与 `case_script_binding` 逐条一致 | `[已核实]` 列已有，需核一致性 |
| N2 | 在公共用例库同样看到 | 公共库脚本列同样 4 态，口径与项目库同一函数产出 | `[已核实]` 装配走 `GlobalCaseService:266-278` |
| N3 | 在项目/公共**用例集**看到成员脚本覆盖情况 | 集成员表有脚本列 + 集合级「已绑定 X/Y」概览 | `[已核实]` 成员有列；`[推断]` 无概览 |
| N4 | 执行前知道哪些用例无脚本 | 发起页弹出清单：已绑定 N / 未绑定 M（列名、编号、原因） | `[已核实]` 现有 willSkip 只是数字预测（`PytestNicRunController.java:456-458`） |
| N5 | 无脚本用例默认不跑、用户可确认跳过 | 勾选确认后，真正下发的 nodeid 清单中不含未绑定项；run.log 有跳过清单 | `[已核实]` 现有 `PytestCommandPlanProvider.java:56-66` 会 continue，但无用户确认环节 |
| N6 | 按「有脚本」筛出一部分用例 | 列表新增脚本状态筛选，返回集与绑定表一致（含分页、总数） | `[已核实]` 后端无该参数 |
| N7 | 把筛选结果快速做成用例集 | 勾选 →「加入用例集」→ 新建/追加，一次完成，成员 seq 连续 | `[已核实]` 用例库页无此动作 |
| N8 | 公共/项目两端都能做 N6–N7 | 两端页面与 API 都具备；platform 单例项目的绑定查询口径一致 | `[已核实]` 公共集页当前只能填数字 ID 单条加（`GlobalCaseSetsView.vue:230-240`） |

**术语澄清（重要）**：大师原话「用例集有没有对应脚本」在物理上不是集本身有脚本——`test_set` 表无任何脚本字段，脚本绑定只挂在 `test_case` 上（`V11_47__case_script_binding.sql:18-45`）。本评估把它解释为**「用例集的成员脚本覆盖率」**，即集内用例中有可信绑定的比例。该解释列入 PRD 开放项 O-1 请大师确认。

## 2. 一手取证：现状能力边界

### 2.1 绑定底座（已核实）

| 事实 | 证据 |
|---|---|
| `case_script_binding` 结构：`project_id/case_id/kernel/script_path/node_id/script_sha256/verified/resolve_source`，唯一键 `(project_id, case_id, kernel)` | `db/migration/V11_47__case_script_binding.sql:18-45` |

| 路径 | 无脚本时的行为 | 证据 |

## 5. 隐藏需求（大师要求重点挖掘）

| ID | 隐藏需求 | 为什么必须做 | 证据 |
|---|---|---|---|
| H1 | **「有脚本」的门槛口径**，不是有行就算 | `verified` 有 0/1 两态，`script_sha256` 用于漂移检测；`BOUND_UNVERIFIED` 是自动解析默认态，未经人工确认 | `V11_47__case_script_binding.sql:27,29`；`CaseScriptView.java:25-29` |
| H2 | **绑定失效识别**：绑定行在但脚本文件已删/改名/内容漂移 | 组集时若只看行存在，会选进「看着有脚本、实际跑不了」的用例，重演「平台不解释」事故 | `PytestBindingSyncService.java:128-144`（sha256 跟随）；UX 报告 P0-2 |
| H3 | **跳过结果可追溯**：K（跳过数）要有落点 | `SKIP` 只来自 junit `<skipped>`（`PytestResultNormalizer.java:325-327`），平台不会为「无脚本」生成结果行；软校验跳过若不记，四元组 N/M/K/T 对不上 | `FR-v5.23-09`；`PytestCommandPlanProvider.java:56-66` |
| H4 | **执行 filter 白名单休眠**：按脚本筛完要能直接发执行 | `RunTrustJdbcStore.FILTER_COLUMNS` 无脚本键，且前端未传 filter；若不做，用户筛完只能组集、不能「筛完就跑」 | `RunTrustJdbcStore.java:41-46`；`ExecutionPlansView.vue:243-247` |
| H5 | **跨内核判定**：一条用例可有多个内核绑定 | 唯一键含 kernel，项目内核优先（`id` 最小兜底）；用例集跨项目时「有无脚本」随内核而变 | `CaseScriptLookup.java:72-97`；`CaseScriptView.java:17,24-31` |
| H6 | **成员 seq 续排** | `test_set_item` 唯一键 `(test_set_id, seq_no)`，批量追加若从 1 重排会撞键 | `V1__baseline.sql:320-334` |
| H7 | **筛选条件持久化** | 保存视图 payload 无脚本字段，用户每次重选；公共库筛选走 URL query，需同步 | `useSavedViews.ts:28-37`；`GlobalCasesView.vue:122-135` |
| H8 | **公共库绑定来源**：platform 单例项目的绑定如何产生 | 公共库列表已装配脚本（`GlobalCaseService:266-278`），但绑定同步是按 `pytest-suite` 项目加载 `pytest.repo_path` 跑的；platform 项目何时同步、同步谁的仓库，现无明确入口 | `PytestBindingSyncService.java:100-104`；`GlobalCaseService.java:43,190` `[部分推断]` |

## 7. 门禁与验收判据（本轮为 PRD 定义，尚未执行）

| 门禁 | 判据 |
|---|---|
| 二进制兼容 | 不改 `case_script_binding` 表结构；既有绑定数据零迁移 |
| 筛选正确性 | 四种 bindingState 各取 ≥1 条样本，筛选结果与绑定表逐条一致；分页总数与 SQL COUNT 一致 |
| 双端一致 | 同一 `case_code` 在项目库与公共库的脚本状态文案逐字相同（同一函数产出） |
| 执行收敛 | 三入口（通用/CI、pytest fake、pytest real）在无脚本时行为一致：清单可见 + 默认剔除 + 确认后继续；real 的 fail-closed 安全闸保留但走同一清单 |
