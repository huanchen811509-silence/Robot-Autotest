## 1. 背景与目标

### 1.1 背景

1. 主程序（`Robot-Autotest`）已具备项目 / 资产 / 用例 / 执行 / 报告五域，且 v2.7 起有 pytest 内核通道（`PytestKernel` / `PytestRunAdapter` / `KernelSelector` / 六态映射 / pytest 报告入库）。
2. 真正的执行程序是自研框架 `nic-test-platform`（V1.2：`SSHConnection → Host → NIC` + Adapter + AW + pytest 编排 + Fake Plan + 证据树），真源在 Synology Git（`yangfulai@10.202.54.201:git/nic-test-platform.git`）。
3. 真正的用例是公共用例库 **469 条**（`基本功能导入测试v0.2.9.9.xlsx`），要求**每条库用例对应一个 py 执行文件**；现状 **61 条已实现（13.0%）**。
4. 评估结论（`RA-EVAL-51-001`）：现有 pytest 内核在本用例库上**启动即失败**（`--json-report` 未声明），且资产无法渲染 inventory、用例无法绑定 py、结果无法回落到用例库。

### 1.2 目标（可度量）

| 目标 | 可度量结果 |
|---|---|
| G1 能跑 | 选定 ≥2 条已实现用例（含 1 条双端）→ 真实执行成功，`run_status` 与实际结论一致 |
| G2 能追溯 | 报告每条用例显示**库编号**（如 `IM-NET-131`）+ `COMMIT_SHA` + 实际执行设备对（`host_key/netdev`） |
| G3 能绑定 | 库内 469 条用例**逐条**有绑定状态；覆盖率可按分类/优先级统计，误差 0 条 |
| G4 能拦截 | 未绑定、资源不足、环境不健康三类情形**在执行前**整单拒绝，并列出编号与原因 |
| G5 能取证 | 每条用例可下钻到「步骤 → 命令 → 原始回显」；证据文件与 `run_id` 一一对应 |
| G6 不出假通过 | Fake/Plan-only 预检结果为 `PLANNED`，**不进通过率**，不显示绿色 PASS |
| G7 不回归 | RF/pabot 路径 argv 与既有门禁读数**逐字不变** |

### 1.3 非目标

不承诺 408 条缺口脚本的产量；不承诺框架 AW 能力（RDMA/QoS/PFC/CCL）的补齐。

## 4. 术语与契约（实现的唯一依据）

### 4.1 资源键规则（冻结）

| 对象 | 规则 | 示例 |
|---|---|---|
| `host_key` | `<device.name>@<device.management_ip>`，写入 `device.host_key` 后**冻结** | `gpu01@10.202.54.101` |
| `nic_key` | `<host_key>/<device_port.nic_name>` | `gpu01@10.202.54.101/ens17np0` |
| `target 选择串` | `nic:<nic_key>` / `gpu:<gpu_key>` | `nic:gpu01@10.202.54.101/ens17np0` |
| 资源池顺序 | `resource_pool.hosts` / `nics` 的顺序**即 `first/second` 语义** | 顺序变更必须留审计 |

### 4.2 用例标识规则

| 项 | 规则 |
|---|---|
| 文件名 | `tests/nic/<分类目录>/test_<code 小写、`-`→`_`>.py`，如 `IM-NET-131` → `test_im_net_131.py` |
| 用例函数 | `test_<同名>_<语义后缀>`，如 `test_im_net_131_rx_checksum_offload` |
| `node_id` | `<相对路径>::<函数名>`，绑定表存**相对路径**，不存绝对路径 |
| `case_key` | 同 `node_id`（与 RF 的 `suitePath.caseName` 同语义，供跨 run 对比） |
| 唯一性 | `(project_id, node_id)` 唯一；一个 `case_code` 允许多 node_id（参数化），但看板标「多绑」 |

### 4.3 执行命令契约（pytest-nic）

```
<python_bin> -m pytest <node_id ... | <path ...>>
  --env_config <runDir>/run_env.yaml
  --mode real|fake
  [--host <host_key>]...
  [--target nic:<nic_key>]...
  [--traffic_direction forward|reverse]
  [--target_slot first|second]
  -p qa_platform_plugin
  --junitxml <runDir>/kernel-pytest-nic-0/junit.xml
  -q
```

| 规则 | 说明 |
|---|---|
| R1 | **禁止** `--json-report`、`--metadata`、`-n/--numprocesses`（用例库无这些依赖，且明确禁并行） |
| R2 | 工作目录 = 仓库工作区根（保证 `addopts`/`pythonpath=src`/`config/` 相对路径成立） |
| R3 | `run_env.run_id` 必须等于平台 `run.run_id`（证据目录即 `<repo>/artifacts/<RUN_ID>/`） |
| R4 | 证据位置不假定在 `runDir`：登记时按 `<repo>/artifacts/<RUN_ID>/` 采集 |
| R5 | argv 不含口令；环境变量注入（见 FR-v5.1-03） |
| R6 | `-p qa_platform_plugin` 由平台注入到工作区，`PYTHONPATH` 指向该目录 |

### 4.4 退出码口径

| 退出码 | 判为 | run 结论 | 是否登记产物 |
|---|---|---|---|
| 0 | 执行成功 | 按用例结论 | 是 |
| 1 | 执行成功、有业务失败 | 按用例结论（有 FAIL） | 是 |
| 2 | 执行中断 | 失败（`interrupted`） | 尽力 |
| 3 | 框架内部错误 | 失败（`framework_error`） | 尽力 |
| 4 | 用法错误（参数/配置不认） | 失败（`usage_error`） | 否 |
| 5 | 未收集到用例 | 失败（`no_tests_collected`） | 否 |

> 「执行失败」与「用例失败」必须分开：前者进 infra 失败分类、可重试；后者是产品结论。

### 4.5 结果状态映射

| junit/pytest | 平台六态 | 报告四态 | 进通过率 |
|---|---|---|---|
| passed | PASS | PASS | ✓ |
| failure | FAIL | FAIL | ✓ |
| error | ERROR | FAIL | ✓（计失败） |
| skipped（业务 skip） | SKIP | SKIP | ✗ |
| skipped（Plan-only 全 skip） | **PLANNED** | SKIP | ✗（**不计通过**） |
| xfail / xpass | XFAIL / XPASS | SKIP / FAIL | 沿用 `KernelStatusMapper` |

## 6. 功能需求

### FR-v5.1-01 执行内核 `pytest-nic`

**描述**：注册独立内核 `pytest-nic`，与通用 `pytest` 内核分离；不得复用通用 pytest 内核的 argv 模板。

**规则**

| # | 规则 |
|---|---|
| R1 | 内核名 `pytest-nic`；`KernelRegistry` 注册后 `KernelSelector` 可选中；`run.kernel` 记快照 |
| R2 | 选择粒度沿用「项目默认 → 用例集 → 用例」，页面必须能解释「生效来源」与「是否被覆盖」 |
| R3 | 通用 `pytest` 内核行为**不变**（其 argv 与本次新增无关），RF 路径严禁触碰 |
| R4 | 内核能力矩阵新增三项探测：`python>=3.11`、`import nic_platform`、`collect 数 > 0` |
| R5 | 若项目绑定 `pytest-nic` 但仓库未绑定 → 执行前拒绝，报 `repo_unbound` |

**边界**：不改 `PabotCommandBuilder` / `PabotOrchestrator` 语义；不新增分片合并逻辑。

**验收**：A1、A2、A17。

### FR-v5.1-02 运行环境渲染（资产 → inventory + run_env）

**描述**：按本次选择的设备与用例，渲染一份**一次性**的 `inventory.yaml` 与 `run_env.yaml` 到 `runDir`，作为 `--env_config` 输入。

**规则**

| # | 规则 |
|---|---|
| R1 | `inventory.hosts` 的键必须是 `device.host_key`；`host` 段由 `device` 渲染：`management_ip`、`username`（`device.account`）、`password=${ENV:<VAR>}`、`ssh_port`（`device.login_mode` 解析，缺省 22）、`os_family`（`operating_system` 归一为 ubuntu/centos，无法判定即拒绝）、`known_hosts_policy`（项目配置，默认 `reject`） |
| R2 | `devices.nics` 键 = `device_port.nic_name`；必填 `netdev`、`vendor`、`product_model`、`pci_bdf`、`driver`、`rdma_device`、`capabilities`；`counter_patterns` 可空（空则该型号按通用解析） |
| R3 | `product_model` 必须命中 `device_specs.yaml` 的 `nics` 键（归一化后），否则**渲染失败**并列出型号（不允许跑到运行期才 `KeyError`） |
| R4 | `resource_pool.hosts` 顺序 = 本次选择顺序；顺序写入 `execution_selection` 冻结快照并记 sha256；报告展示「实际顺序」 |
| R5 | `selected_targets` 由选择的 nic/gpu 生成；**平台只渲染白名单，再用 CLI 收窄**，不用 CLI 扩大 |
| R6 | `run_id` = 平台 `run.run_id`；`mode` = 本次请求（默认 `fake`） |
| R7 | 渲染产物落 `runDir/env/`，同时登记 `run_artifact`（kind `pytest_env`，可选），报告可查「这次给框架喂了什么」（脱敏后） |
| R8 | 渲染失败一律**执行前**拒绝，`failure_reason=env_render_failed`，不产生空跑 |

**边界**：不写回资产表（渲染是单向派生）；`nic_name` 为空的端口不得进池。

**验收**：A3、A4、A5。

### FR-v5.1-03 凭据注入与明文防护

**描述**：把 `credential.secret_ref` 解析为环境变量名，通过进程 env 注入；任何落盘产物与报告中不得出现明文口令。

**规则**

| # | 规则 |
|---|---|
| R1 | `credential.secret_ref` 形如 `ENV:ROBOT_CRED_12`；渲染 inventory 时写 `${ENV:ROBOT_CRED_12}` 字面量，**不写真实值** |
| R2 | 取值来源优先级：进程环境变量 → 系统密钥配置（`system_setting`，加密存储）→ 未取到即拒绝执行（`credential_unresolved`） |
| R3 | 注入只作用于子进程 env；不写 `run.log`、不写 argv、不写 `run_artifact` 内容 |
| R4 | 渲染产物机检：正则扫 `password:\s*(?!\$\{ENV:)` 命中即判失败（发布前门禁 + 运行后巡检） |
| R5 | 报告/导出沿用既有字段白名单（`ReportFieldWhitelist`），新增字段必须显式登记 |
| R6 | 资产页「口令」列一律掩码；后端返回仅 `keyMasked` 前缀（沿用既有口径） |

**边界**：本期不做凭据轮换自动化（归运维/大师）；不引入外部密钥管理服务。

**验收**：A6、A7。

### FR-v5.1-04 用例 ↔ 脚本 1:1 绑定

**描述**：把库内每条用例绑定到唯一 `node_id`；绑定是「按用例执行」与「报告回落」的前置。

**规则**

| # | 规则 |
|---|---|
| R1 | 解析优先级：① 手工绑定（`MANUAL`）→ ② docstring `用例编号: <code>`（`DOCSTRING`）→ ③ 文件名 `test_<code>.py`（`FILENAME`）→ ④ `@pytest.mark.case("<code>")`（`MARKER`，本期可选） |
| R2 | 三级都未命中 → 该用例 `bind_status=MISSING`；脚本无对应库用例 → `ORPHAN` |
| R3 | 同一 `case_code` 命中多个 `node_id` → 全部保留，`bind_status=DUPLICATE`，看板标黄，**不阻断执行**（参数化用例合法） |
| R4 | 同步任务以「仓库 ref 的 commit」为快照：先更新 `repo_commit`，再整体替换该 commit 下的绑定集合（失败回滚） |
| R5 | 一个 py 文件恰好一个用例编号（硬约束）；一个文件内多个 `test_` 函数视为多 node，需 `DUPLICATE` 复核 |
| R6 | 用例文件被删除 → 绑定点标 `MISSING`，不物理删行（保留历史与趋势） |

**边界**：不改脚本内容；不自动修复命名（只报告 + 给建议路径）。

**验收**：A8、A9、A10。

### FR-v5.1-14 并发与租约

**描述**：pytest-nic 单 run 内串行；跨 run 通过租约互斥，避免同设备互踩。

**规则**

| # | 规则 |
|---|---|
| R1 | `concurrency` 强制 1；请求 >1 时降级并告警（`xdist_disabled`），不得传 `-n` |
| R2 | 租约键覆盖 **host 级 + nic 级**：`host:<host_key>`、`nic:<nic_key>`；一个双端 run 同时持有两端，全有或全无 |
| R3 | 申请失败（等待超时）→ 执行前拒绝，`failure_reason=lease_timeout`，不进入 RUNNING |
| R4 | 租约 TTL/心跳沿用现有参数；进程异常退出后由孤儿清扫释放 |
| R5 | 跨 run 并发允许（资源不相交时），但 `maxParallel` 不得因 pytest-nic 而提高（框架无锁） |

**边界**：不实现框架内资源锁（框架明确不做）；不做跨设备池的自动编排。

**验收**：A32、A33。
