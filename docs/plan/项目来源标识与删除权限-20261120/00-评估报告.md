## 2. 一手取证（代码级证据，均已回看）

### 2.1 现有标识字段盘点

**结论：没有任何可复用的「自带 vs 自建」字段。** 已核实：

- `Project.java:11-21` — record 分量仅 `id / code / name / description / enabled / ownerId / visibility / testKernel / kind / codeChangedAt`；无 `origin / builtIn / isDemo / source`。
- `Project.java:37-40` — `public boolean platform() { return "platform".equalsIgnoreCase(kind); }` 是**派生方法**，不是独立标识。
- `ProjectRepositoryJdbc.java:28-37` — MAPPER 与 SELECT 到 `kind, code_changed_at` 为止，不读 `is_demo`。
- `domain/iam/ProjectCard.java:22-40` 与 `frontend/src/api/projectCards.ts:12-41` — 卡片 DTO 两端字段一一对应，**均无 origin / platform**，前端当前根本拿不到来源信息。

**迁移历史（project 表所有列）**：

| 脚本:行 | 动作 |
|---|---|
| `V1__baseline.sql:20-32` | CREATE TABLE project（基础列） |
| `V2_1__iam_fields.sql:27-29` | ADD owner_id, visibility |
| `V11_16__project_test_kernel.sql:5-6` | ADD test_kernel |
| `V11_31__ui_mode_platform_project.sql:2-5` | ADD kind（standard/platform） |

**`is_demo` 不能复用（已核实）**：`V11_65__demo_flag.sql:6-9` 明确写「is_demo 只表示这条记录由开发/演示创建，不改变任何权限与可见性逻辑；默认 0；删除只认这一位」；`v5.9.0/PRD.md:48,286-288,363` 把演示数据定义为 `is_demo=1`，且发版前可整批 DROP。用它当「自带」会把内置项目标成「待清理演示数据」，语义反转。

**`platform` 不能复用（已核实）**：`PlatformProjectService.java:16,25-38` 单例 `CODE="PLATFORM-LIB"`，`ProjectRepositoryJdbc.java:74-77` 用 `WHERE kind='platform' LIMIT 1` 识别；`ProjectService.java:190-197,315-317,351-353` 对它做不可停用/不可改码/不可删保护。它是「公共库载体」语义，且只有一个，无法表达「多个自带项目」。

> 旁证：内置概念在工程里已有先例但用于**角色** —— `V2_1__iam_fields.sql:24` `idx_role_built_in (built_in)`，可作为新增列的命名参照。

### 2.2 删除链路与级联现状

**后端删除校验（`ProjectService.java:345-363`，已核实）**：

```
:347  access.bindProject(projectId)
:348  access.require(PROJECT, DELETE)         // 仅 ADMIN
:349-350 findById，无 → 404
:351-353 if (existing.platform()) → 409 "平台项目不可删除"
:354-358 busyCounts 非空 → 409 "…只能停用（归档），不能彻底删除"
:359   projects.delete(projectId)
:360-362 审计
```

- `busyCounts` 实现：`ProjectRepositoryJdbc.java:207-228`，从 `information_schema.columns` **动态发现**所有含 `project_id` 的表（ORDER BY table_name），跳过 `BUSY_IGNORED = {project_setting, project_label, project_member, project_member_role, audit_log, slo_daily}`（`:49-51`），逐表 `SELECT COUNT(*)`，>0 入 map。
- `ProjectController.java:122-126` 删除端点**只有 `projectId` 一个参数**，无 force / skip 后门。

**现有 `projects.delete()` 只删 5 张关系表（已核实）**：`ProjectRepositoryJdbc.java:198-204` —— `project_member_role / project_setting / project_label / project_member / project`，**不删任何业务子表**。

**级联真删的真实难点（这是 D1 的核心风险）**：

- 外键普查：`v5.17.0/DEV-PLAN.md:221-222` — **26 张表 RESTRICT 引用 `project(id)`，仅 `project_asset` / `project_group_role` 是 CASCADE**；正确删除顺序 `test_report → test_result → run → test_case → test_set → 再删项目`。
- 间接子表无 `project_id`，不在 busyCounts 扫描范围：`scripts/ops/purge-temp.sh:164-167` 明列 `test_case_step / case_requirement / case_requirement_version / case_script_binding / manual_execution / test_set_item` 只能经 test_case/test_set 间接定位（与项目记忆 v5.18 一致）。
- 历史事故：`v5.17.0/DEV-PLAN.md:218` D-67-01-3 — 有从属数据时 `DELETE FROM project` 报 1451 且成员关系已删 → **半删状态**；`:219` D-67-01-4 —「走项目删除接口」是死路（409 只许归档）。
- 运维脚本已有可复用骨架：`scripts/ops/purge-temp.sh:177-205` 按「间接子表 → 含 project_id 表（多轮循环）→ project」顺序删，并有计数校验；但它**绕过应用层**、需人工授权，不能直接当用户自助删除入口。

**结论**：级联真删不是「把 busyCounts 关掉」这么简单，必须新增**事务性级联清理服务**，否则会重现 1451 半删与孤儿行 —— `docs/design/EHT-命令证据与删除契约.md:95`「物理删除不得留下有外键子表的孤儿行」是硬判据。

## 6. 结论

**有条件可行，且必须先补齐级联清理能力再放行 removal 判据。** 判断依据：

1. **底座有、标识无**：项目已有 `kind` / `is_demo` 但语义都不匹配，新增 `origin` 列是最小侵入方案，全链路改动点清晰（见本报告 §2.1、前端取证 A/B 表）。
2. **删除能力是真正缺口**：现网删除是「防孤儿设计」——只清关系表、有数据一律 409。要让 USER 项目带数据真删，必须新增事务性级联清理服务，**不能靠关掉 busyCounts 实现**（会重现 v5.17 半删事故）。
3. **权限放大要堵**：ADMIN 切换 origin 是本次最大的安全面；必须两段式（切换 + 删除各自确认与审计），且 platform 硬保护优先、origin 不得开后门。
4. **本轮范围**：大师裁定 D4 —— 仅本文（评估）与 PRD，零代码零迁移；DEV-PLAN / TEST-PLAN / 实施 / 真库 marking 待批准后进入第 ④⑤ 环。

**放行前置（进入开发前必须满足）**：PRD 的 FR 全部写出可判定验收命令；级联清理的删除顺序与孤儿校验写成硬判据；备份与 dry-run 清单有证据形态；两个 demo 的「双无出路」风险大师已阅知。
