## 0. 结论摘要

四块需求**都不是从零开始**：菜单已是 8 组两级结构，主题已有 3 模式 × 6 强调色 × 2 密度，工作台已有单项目看板。真正的缺口是三处**结构性错位**加一处**完全缺失**：

| 需求 | 现状定性 | 结论 |
|---|---|---|
| ① 菜单命名与排序 | 结构在，命名有真缺陷，排序无依据；且「报告」是叶子冒充分组、`/test-reports` 是孤儿页 | 改名 6 处 + 重排 + **「执行」与「报告」合并为 1 组（一级 8 → 7）** |
| ② 工作台项目总览卡牌 | 完全没有；后端也无聚合读数 | 新增只读聚合端点 + 卡牌页，切换语义复用现有 store |
| ③ 顶栏右侧排版 / 排序 / 美工 | 控件放得下，但**高度差 4px、`.app-project` 样式零定义、排序无逻辑**（16 条具体问题） | 统一 28px 栅格 + 四段排序 + 美工统一，**不砍入口、不新增组件** |
| ④ 主题 / 强调色 / 滚动条 | 主题与强调色已相当完整；**滚动条样式零实现** | 只补滚动条与对比度门槛，**不加第 7 个强调色** |

四条硬结论：

1. **命名有一处「同页两名」的实缺陷**：侧边栏该项词条是 `menu.workspace`＝「工作台」，页面 `<h1>` 用的是 `menu.overview`＝「总览」。这不是审美问题，是同一个页面在两个位置叫两个名字。
2. **滚动条是全仓零实现**：`frontend/src` 下 `-webkit-scrollbar` 命中 **0 个文件**，而应用有至少 5 处滚动容器（侧栏、主区、AI 抽屉、AI 消息列表、数据网格表体）。暗色下靠 `color-scheme` 拿到的是浏览器原生亮灰条，与主题不匹配；且没有 `scrollbar-gutter`，内容从短变长时会横向跳一下。
3. **项目卡牌不能靠前端拼**：`GET /api/projects` 只返回 `id/code/name/description/enabled/ownerId/visibility`，**没有任何统计读数**。若在卡牌里逐个项目去调 `/api/projects/{id}/overview`，N 个项目就是 N 次多表聚合请求。必须新增一个批量聚合端点，这是本轮唯一需要动后端的地方。
4. **「执行 + 报告」合并成立，但理由不是「侧栏变短」**：合并后二级项从 24 增到 27、侧栏总行数从 32 增到 34，**并不会更短**。成立的理由是：两者同源同构（`test_report.run_id` → `run.run_id`）、构成「跑完看报告」的一个动作闭环、合并能顺手给 `/test-reports` 孤儿页一个入口、并消除「报告叶子冒充分组」这个形态缺陷。详见 §4.1.1。

**倾向方案**：菜单从 8 组降为 7 组——「执行」与「报告」合并为「执行与报告」（组内 6 项：运行记录 / 测试计划 / 执行节点 / 报告列表 / 报告模板 / 对外报告），并按新顺序重排；工作台升级为分组，内含「项目总览」（卡牌）与「项目看板」；顶栏按「上下文 → 工具 → 偏好 → 账户」四段重排并统一 28px 栅格，不砍任何入口；主题只做滚动条与对比度，不动预设清单。

#### 2.1.1 「执行」与「报告」各自的真实页面构成

这一节是回答「两者能否合并」的事实基础。路由表 `router/index.ts:39-104` 与视图文件对得上：

| 一级项 | 二级入口 | 路由 | 页面职责（实测） |
|---|---|---|---|
| 执行（分组，`capability: execution:read`） | 运行记录 | `/runs` | 运行列表（runId / 状态 / 测试数 / 设备范围 / 失败原因 / 起止时间）+ 手动执行表单 + WebSocket 实时日志面板 |
| 执行 | 测试计划 | `/plans` | 计划列表；下挂 `/plans/groups`（计划组）、`/plans/graph`（依赖图） |
| 执行 | 执行节点 | `/nodes` | 执行节点管理 |
| 执行（`alsoMatch` 下钻） | — | `/runs/failure-clusters` | 失败聚类，从运行列表失败数下钻 |
| 报告（叶子，**无 capability**） | — | `/reports` | 报告列表（runId / 状态 / 计数 / 开始时间 / 可导出）+ 保留策略 + 模板入口 |
| 报告（同叶子 `alsoMatch`） | — | `/reports/templates` | 报告模板 |
| 报告（同叶子 `alsoMatch`） | — | `/reports/:runId` | 报告详情（趋势 / 本轮 vs 基线对比） |
| 报告（`public` 路由） | — | `/reports/:runId/print` | A4 打印页，靠一次性 token 授权 |
| **报告（孤儿）** | **无任何菜单入口** | `/test-reports` | 对外测试报告列表（冻结快照，可脱离源 run 渲染） |

由此得到两条对合并评估起决定作用的事实：

1. **「报告」是叶子冒充分组**：它有 4 个真实页面（列表 / 模板 / 详情 / 打印），却在导航树里只有 1 个叶子，靠 `alsoMatch: ['/reports', '/test-reports']` 把点亮关系硬拉在一起。这就是 I2「形态不统一」的具体实例。
2. **`/test-reports` 是孤儿页**：路由存在、视图存在、`alsoMatch` 里也写了它，但 `NAVIGATION` 里**没有任何一项的 `path` 等于 `/test-reports`**，所以用户在界面上找不到入口，只能手输 URL。这是 v2.2 遗留的真实可用性缺陷，不是设计取舍。

另外注意权限口径的差异：`runs` 分组带 `capability: 'execution:read'`，`reports` 叶子**不带 capability**。这意味着 `viewer` 角色现在**看不到「执行」但看得到「报告」**（`navigation.spec.ts:124` 断言 `viewer` 不含 `runs`）。任何合并方案都必须处理这条，否则会静默收回 viewer 的报告入口。

#### 2.3.4 美工维度的硬伤

| 编号 | 美工问题 | 证据 |
|---|---|---|
| V1 | 主题按钮**三态循环**：dark → system 要点两次，中间必闪一次 light，用户无法预判下一次点击结果 | `toggleTheme()` 实现，图标随态变（sun/moon/monitor） |

**方案 B 的排序依据（必须明说这是推演不是数据）**：仓库无埋点，无法用频次证明顺序。B 的顺序按「一次完整测试循环的先后」排，再按「配置类后置」收尾：

> 工作台（入口） → 执行（跑） → 报告（看结果） → 用例（写/改） → 资产（铺环境） → 环境与拓扑（采数） → 维护与恢复（出事才来） → 系统设置（几乎不改）

这个顺序有一个可证伪的优点：**前四项构成日常闭环**，后四项是支撑与兜底。PRD 里会把「排序待实测校准」写成显式遗留项，不假装是数据结论。

### 4.1.1 追加评估：「执行」与「报告」能否合并为一个一级菜单（大师 2026-11-08 第 1 问）

**先给结论：可以合并，而且建议合并。但理由不是「侧栏会变短」——合并后二级项反而从 24 增到 27，侧栏总行数从 32 增到 34。真正的理由是流程内聚 + 修掉两个形态缺陷。**

#### 依据：两者是同一业务流程的上下游，不是两件事

| 依据 | 事实 | 证据 |
|---|---|---|
| 数据同源 | 报告实体 `test_report.run_id` 指向 `run.run_id`，报告是 run 的下游产物；`ReportDetailView` 的「趋势 / 本轮 vs 基线」全部按 runId 取数 | `db/migration`、`ReportRepositoryJdbc`、第 13 步浏览器回归 |
| 列表同构 | `RunsView` 列 = runId / 状态 / 测试数 / 设备范围 / 失败原因 / 起止时间；`ReportsView` 列 = runId / 状态 / 计数 / 开始时间 / 可导出。**同一批 run 的两个视角**，主键完全相同 | 两文件的 `DataTableColumns` 定义 |
| 用户动作闭环 | 「跑完看报告」是一个动作，不是两个任务。分两个一级项意味着每次要跨项跳转 | 交互推演 |
| 已有事实上的合并 | `reports` 叶子的 `alsoMatch` 里写着 `/reports`、`/test-reports`，说明作者本来就把它们当一组 | `navigation.ts` |

#### 四个方案

| 方案 | 做法 | 一级项数 | 二级项数 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|---|---|
| A 不合并，只把「报告」升级为分组 | 8 组：执行(3) 与 报告(3) 各自成立 | 8 | 24 | 改动最小；`/test-reports` 能补入口 | 流程仍被切成两段；一级项仍 8 个 | 可行但次优 |
| B 合并为「执行与报告」，6 项平铺 | 一级 7 组；组内顺序：运行记录 → 测试计划 → 执行节点 → 报告列表 → 报告模板 → 对外报告 | 7 | 27 | 流程内聚；孤儿页有家；叶子冒充分组消除；一级 8→7 贴近扫读上限 | 单组最重（6 项）；二级总数反增 3 | **推荐** |
| C 合并 + 组内引入三级 | 「执行与报告」下再分「运行」「报告」两个子分组 | 7 | 27（分两层） | 子域最清晰 | `NavGroup` 只有一层 children，要改导航数据结构、渲染、选中判定、能力过滤、4 处单测——工作量翻倍 | 否决（成本收益不成立） |
| D 把报告降级为运行列表的页签 | 取消报告页独立入口 | 7 | 24 | 最短 | 报告模板、对外报告、打印页无处安放；与 v2.2 已交付的 5 个报告页面冲突 | 否决 |

#### 推荐方案 B 的完整落点

一级菜单 7 组，顺序为：

> 工作台 → **执行与报告** → 用例 → 资产 → 环境与拓扑 → 维护与恢复 → 系统设置

合并后组内 6 项（顺序即推荐顺序）：

| 序 | 二级项 | 路由 | 子域 |
|---|---|---|---|
| 1 | 运行记录 | `/runs` | 运行态 |
| 2 | 测试计划 | `/plans` | 运行态 |
| 3 | 执行节点 | `/nodes` | 运行态 |
| 4 | 报告列表 | `/reports` | 报告态 |
| 5 | 报告模板 | `/reports/templates` | 报告态 |
| 6 | 对外报告 | `/test-reports` | 报告态 |

**命名**：推荐「执行与报告」。备选「运行与报告」（更贴 `run` 的语义）、「测试执行」（会丢报告语义，不推荐）。不造新词，两个词都是用户已熟悉的现有名称。

#### 三个必须一并解决的连带问题（否则合并会引入回归）

| 编号 | 问题 | 处理方式 |
|---|---|---|
| C-1 | **权限回归**：`runs` 组带 `execution:read`，`reports` 叶子无 capability。直接合并会让 `viewer` 失去报告入口（现在能看） | 合并后分组**不带**组级 capability，改为按子项分别设：运行/计划/节点用 `execution:read`，报告 3 项不带。这样 viewer 仍看得到报告 3 项，与现状一致。PRD 会把这条写成显式验收判据 |
| C-2 | **断言重写**：`navigation.spec.ts:99` 断言 `toHaveLength(8)`、`:101` 列 8 个 key、`:166-173` 把 `reports` 当 `NavLeaf` 用 `isLeafActive(reports, ...)` | 全部改为按新结构断言；`reports` 相关用例改成「分组内第 4 项」的定位方式，不允许删断言了事 |
| C-3 | **组内可读性**：6 项平铺，两个子域之间没有视觉区隔 | 给 `NavGroup` 增加可选 `section?: string` 字段（纯前端渲染用途，不参与选中判定与能力过滤），在 section 切换处渲染一条细分隔线。成本约 20 行 + 2 条单测，比引入三级层级便宜得多 |

#### 与「一级项 8 组」原有结论的关系

v1.0 的 FR-UI-01 写的是「一级菜单固定 8 组」。合并后应变 **7 组**。这不推翻 v2.2 已交付的证据：v2.2 MENU-01 的证据是「8 组 IA 与业务域隔离机检」（`hasBusinessDomainAsTopLevel` 等谓词仍然成立），合并只动分组数量与归属，**不动「6 个业务能力域不建一级菜单」这条核心约束**。WBS 分母不变。

推荐 DOM 顺序（= 视觉顺序 = Tab 顺序）：

| 段 1 上下文 | 项目选择器（显示当前项目名 + 启用状态点） | 全局上下文，一切页面数据都受它影响，必须最靠左 |
| 段 2 工具 | 命令面板、AI 助手 | 「我要去做事」，执行类动作 |
| 段 3 偏好 | 外观（主题 + 强调色 + 密度）、语言 | 「我要调整它长什么样」，低频 |
| 段 4 账户 | 用户名（含角色标识）、登出 | 身份与退出，最右 |

三条位置调整（都是 O 类问题的直接解）：

1. **侧栏折叠按钮移出顶栏**，改放到侧栏头部（与产品名同行）。它是外壳控制，不属于「上下文 / 工具 / 偏好 / 账户」任何一段，留在中间会打断阅读顺序（O1）。
2. **「关于」按钮从顶栏移除**。它已经在侧栏「系统设置 > 关于」（`settings-about` → `/about`）有入口，顶栏这个是重复入口（与 I6 同类）。这是**去重复**，不是砍功能。
3. **「语言」保留独立入口但统一造型**。不改成一键循环（循环本身就是 V1 那个缺陷），只给它套统一控件壳 + `language` 图标。

**第三层：美工（解决 V1–V4）**

| 项 | 做法 | 机检 |
|---|---|---|
| 主题按钮三态循环 | 改**二态**（light ↔ dark），`system` 只在外观弹层选 | 断言点击一次 `data-theme` 只在 light/dark 间翻转 |
| 侧栏折叠图标 | 用 `chevronRight` + 折叠时 `rotate(180deg)`，并加 `aria-expanded`；不再与分组箭头同形义混 | 断言图标元素带旋转类且 `aria-expanded` 存在 |
| 项目选择器造型 | **独立样式**（不再借用 `.app-lang`）：白底/面板底 + 强边框 + 前置 `dashboard` 图标 + 项目名 + 状态点，最大宽 180px 超长省略 | 断言 `.app-project` 在样式文件中有独立定义块（`grep` 命中 ≥ 1），且与 `.app-lang` 不共用规则 |
| 语言控件 | 前置 `language` 图标 + 统一壳；中/英双语显示为 `中 / EN` | 视觉走查 + `data-testid` 断言存在 |
| 登出 | 前置 `logout` 图标 + `danger` 类（已有 `.btn-ghost.danger` 样式，直接复用）+ 与账户段同组 | 断言登出按钮含 `danger` 类 |
| hover / active 三态 | 图标按钮 hover 用 `--surface-hover`、active 用 `--surface-selected`、focus-visible 用 `--focus-ring`（均已存在） | `check_states.py` 通过 |
| 分隔线 | 1px `--border`，仅段间出现，段内不出现 | 断言分隔线数量 = 3 |

#### 关于「不引入新组件」的判断

v1.0 曾计划新增 `UserMenu.vue` 与 `ProjectSwitcher.vue` 两个组件。按本次澄清，这两者都不是必需：

- 用户菜单：保留平铺后不需要；
- 项目切换面板：需求 ② 的「工作台项目总览卡牌」已经承担了带搜索的切换入口，顶栏只需一个触发器式选择器，不必再做一个独立面板。

因此本需求**零新增组件**，只改 `App.vue` 模板 + `main.css` 样式段 + 必要的 i18n 键。这显著降低了风险面。

### 4.4 主题 / 强调色 / 滚动条（需求 ④）

| 子项 | 现状 | 方案 | 结论 |
|---|---|---|---|
| 亮/暗模式 | 已实现三模式 + 实时跟随 + 首帧防闪 | 不改机制，只补「暗色三级层（surface/elevated/border）+ hover/active/selected 三态」的对比度实测 | 补强 |
| 强调色 | 6 预设 × 2 主题，7 处清单联动校验 | **不加第 7 个预设**：`check_accent_presets.py` 要求七处一致，新增一个预设要改 7 个文件 + 12 段 CSS 变体块，收益（多一种颜色）远低于成本 | 否决新增 |
| 强调色质量 | 有 `check_contrast` 与 `gen_accent_tokens --check` | 把「6 预设 × 2 主题」的 `--accent` / `--accent-soft` / `--accent-contrast` 全部拉到 WCAG AA（正文 4.5:1、图形与大字 3:1），并以机检锁死 | 采纳 |
| 滚动条 | **零实现** | 统一 5 类滚动容器：宽 8px 细条、thumb 用语义变量派生、track 透明、hover 加深；同时补 `scrollbar-width: thin` + `scrollbar-color`（Firefox）与 `scrollbar-gutter: stable`（防横向跳动） | **采纳（本需求主体）** |
| 密度 | 已实现 2 档 | 不动 | 不改 |
| 高对比/减少动效 | 无 | `prefers-reduced-motion` 与 `forced-colors` 支持 | 列为非目标（本轮） |

**滚动条要注意的硬约束**：`check_colors.py` 只允许 `theme.css` 定义色值，所以滚动条颜色必须写成语义变量的派生（如 `color-mix` 或 `--w7-border` 系列），**不能写字面色**；宽度值会进 px 白名单（现有 8px、6px 已在表内，可复用），不得引入新档位。
