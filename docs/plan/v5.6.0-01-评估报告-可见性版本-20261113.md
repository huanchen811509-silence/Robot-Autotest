## 1. 结论摘要（先给结论，再给理由）

| 编号 | 结论 | 把握 |
|---|---|---|
| C-1 | 菜单「少很多」**不是缺陷，是 `FR-v5.2-07` 的刻意裁剪**：pytest 工程 4 组 11 项，标准工程 7 组 30 项 | 已核实 |
| C-2 | 但裁剪**过头了 3 项**（资产设备、资产凭证、对外报告），且很可能还漏 4 项（存量同步、测试计划、环境采集、链路） | 3 项已核实，4 项待验 |
| C-3 | **不建议全量对齐**。pytest 工程补上资产/环境拓扑/维护恢复全 30 项，会把它变回「新用户以为要先配台架才能跑 pytest」的那棵树 | 评估判断 |
| C-4 | 根因不是「树少一项」，是**信息架构与能力模型脱节**：`kind` 只裁菜单，不描述能力；差异靠复制常量维护，加一种工程类型就要再抄一棵 | 已核实（§2.3 证据） |
| C-5 | 本轮真实执行暴露的 P0（GPU 资产缺失、执行入口 UI 不可达、同步阻塞无进度）与菜单问题**同源**：都是「能力有、入口/表达缺」 | 已核实 |
| C-6 | 因此本版主线定为**「让已有的能力被看见、被用上、被信任」**，而不是加新功能 | 建议 |

一句话：**这一版不该再加功能，该把已经能跑的能力摆到台面上**——59 条用例真机跑通了，但界面上发不起执行；GPU 资产表里没有实体，但渲染器天天要它；报告能导出三种格式，但对外报告页没入口。

## 2. 问题一：菜单差异的评估

### 2.1 事实（同 `00-RESEARCH.md` §2，此处只留结论）

| 问题 | 答案 |
|---|---|
| 为什么少 | `kind=pytest-suite` 走 `PYTEST_SUITE_NAVIGATION`，该树按设计只保留「看覆盖/绑脚本/发起执行/看报告」四件事 |
| 少多少 | 一级 7→4，叶子 28→9，含设置共 30→11 |
| 是不是不能用 | 不是。路由不按 `kind` 设防，后端 `ProjectKind` 不参与鉴权，**页面全部可达，只是没入口** |
| 改动成本 | 小（补叶子 + 改一条单测断言 + 改 `EXPECTED_LEAVES` 39），但**必须先定策略**，否则下版本又漂 |

### 2.2 三个方案对比

| 维度 | 方案 A 全量对齐 | 方案 B 按需补齐 + 规则驱动 | 方案 C 只补三项不重构 |
|---|---|---|---|
| 做法 | pytest 直接用 `NAVIGATION` | 保留差异化，补齐真实缺口；可见性改由规则表派生 | 手工往 pytest 树加 3 个叶子 |
| 用户能否找到设备页 | 能 | 能 | 能 |
| 新用户是否被噪音干扰 | **严重**（节点/拓扑/维护/工作区全在） | 轻（只多 3–7 项，且都是它真要用的） | 轻 |
| 加新工程类型时 | 不用改 | 只加规则行 | 又要抄一棵树 |
| 与 `FR-v5.2-07` 设计意图 | 冲突，等于回滚 | 兼容并修正 | 兼容但只修一半 |
| 工作量（相对） | 低 | 中 | 最低 |
| 长期正确性 | 差 | **好** | 差（技术债留存） |
| 结论 | 否 | **推荐** | 仅作降级预案 |

**为什么不选 A**：`/nodes` 对 pytest 工程没有对象（执行在本机起子进程，不派发到执行节点）；`/environment/topology`、`/maintenance/*` 同理。全量对齐会让「少即是多」的设计归零，并且**与用户抱怨的方向相反**——用户抱怨的是「找不到该有的」，不是「没看到用不上的」。

**为什么 B 要带「规则驱动」**：`00-RESEARCH.md` §2.4 已核实，当前是「一种 kind 一棵常量树」。只要再加一种工程类型（例如 `platform` 真的启用），就得再抄一棵，而两棵树之间的差异**没有任何机制保证是故意的**。规则表能把「为什么这项可见」变成一行可读声明。

### 2.3 补齐清单（按证据强度）

| 优先 | 项 | path | 证据强度 | 补的理由 |
|---|---|---|---|---|

## 3. 问题二：六维现状评分与目标

评分口径：1–5 分，5 = 行业良好实践水平。**分数是相对本平台成熟度的自评，不是对外评级**；每格必须能追到 §4 的事实。

| 维度 | 现状 | 本版目标 | 差距主因 |
|---|---|---|---|
| 系统架构 | 3.0 | 3.5 | 能力模型与信息架构脱节（`kind` 只裁菜单） |
| 软件设计 | 3.5 | 4.0 | 报告链路完整，但可见性/入口设计靠硬编码 |
| 程序实现 | 3.0 | 4.0 | 渲染资产恒空、固定开销 30s、执行同步阻塞 |
| 测试体系 | 3.5 | 4.0 | 门禁齐全，但性能门禁无采样即 SKIP（假绿） |
| UI/UX | 3.0 | 3.5 | 报告版式退化（59 条展开 59 标题）、xlsx 无明细 |
| 用户体验 | 2.5 | 4.0 | **执行入口 UI 不可达**，这是最大单点 |
| 运维保障 | 3.0 | 3.5 | 构建覆盖运行中 jar 导致登录超时，靠人记 |
| 智能化 | 3.0 | 3.5 | AI 归因吃脱敏指纹，垃圾进垃圾出 |

对应大师给的版本目标：

| 目标 | 落到哪条主线 | 本版能否有可见提升 |
|---|---|---|
| 易用性 | IA-01/02/04（菜单与可见性） | 能，立刻可见 |
| 实用性 | RP-01/02/03（报告可用）、AS-01（GPU 资产） | 能 |
| 界面美观度 | UX-01/02/03（一致性、长列表、三态） | 部分 |
| 操作便捷性 | EX-01/02/03/04（UI 发起、进度、取消、预检） | 能，最大收益 |
| 运行效率 | EX-05（固定开销 30s→≤10s）、OP-03 | 能 |
| 智能化 | AI-01/02（归因可用、补判助手） | 部分（依赖 RP-02） |

## 5. 风险与前置条件

| 编号 | 风险/前置 | 影响 | 处置 |
|---|---|---|---|
| R-1 | 补菜单会触发 `navigation.spec.ts` 的禁用断言与 `EXPECTED_LEAVES=39` 基线 | 门禁红 | 同一次提交改三处（树/断言/基线），并在提交说明写清「补了哪几项、为什么」 |
| R-2 | `/plans`、`/sync` 对 pytest 工程是否真能跑**未验证** | 可能补了个点进去报错的入口 | DEV-PLAN 前置 W56-00「可行性验证」，验不过则本版不补，只登记 |
| R-3 | 执行异步化若直接改 `/runs` 语义，会打断已有证据脚本与外部调用方 | 回归风险 | 新增异步端点，旧端点保留并标注 deprecated |
| R-4 | GPU 资产实体涉及新表/迁移 | 迁移不可回退（已应用不可改） | 走「加可空→回填→收紧」，新迁移号顺延 |
| R-5 | 报告命令采集需用例库框架配合输出约定行 | 平台单方面做不成 | 平台侧先落「解析 + 缺省提示」，真源侧改动列入依赖 |
| R-6 | 本版若同时做六维，范围必然失控 | 交付风险 | 见 D-03，建议本版聚焦 IA+EX+RP+OP，AS/AI 深度排 v5.7 |

## 6. 不做假声明

- 本报告**没有**做过任何 UI 端到端截图验收；UI 结论来自源码与接口行为。
- 六维分数是自评，**不是**第三方评级，也没有行业基准样本。
- `/sync`、`/plans`、`/environment/collect`、`/assets?tab=links` 四项「待验」，本报告**不假装已确认**。
- 效果类指标（Top8 成功率、create P95、fps）仍未测量，本版把它列为需求而非已达成项。
