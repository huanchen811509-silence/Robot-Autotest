> 流程位置：② 评估报告（`docs/process/版本开发流程.md` §2.2）。**无本报告不得开 PRD**；本报告给出结论后，PRD 才允许立项。
> 输入：`00-RESEARCH.md`（证据清单）、`docs/plan/v5.5.0-EHT真实执行-评估与改进报告-20261113.md`（59 条真实执行）。

## 1. 结论摘要（先给结论，再给理由）

| 编号 | 结论 | 把握 |
|---|---|---|
| C-1 | 菜单「少很多」**不是缺陷，是 `FR-v5.2-07` 的刻意裁剪**：pytest 工程 4 组 11 项，标准工程 7 组 30 项 | 已核实 |
| C-2 | 但裁剪**过头了 3 项**（资产设备、资产凭证、对外报告），且很可能还漏 4 项（存量同步、测试计划、环境采集、链路） | 3 项已核实，4 项待验 |
| C-3 | ~~不建议全量对齐~~ → **改为采纳全量对齐**。原顾虑「会变回要先配台架的那棵树」被业务事实推翻：事实上就是要先配台架 | **大师拍板（D-01）** |
| C-7 | 一致性的代价要用**空态**来还：全量后「节点/拓扑/维护」在 pytest 工程里没有对象，必须由空态说明正面回答「是没配还是不支持」，不能靠隐藏回避 | 评估判断 |
| C-4 | 根因不是「树少一项」，是**信息架构与能力模型脱节**：`kind` 只裁菜单，不描述能力；差异靠复制常量维护，加一种工程类型就要再抄一棵 | 已核实（§2.3 证据） |
| C-5 | 本轮真实执行暴露的 P0（GPU 资产缺失、执行入口 UI 不可达、同步阻塞无进度）与菜单问题**同源**：都是「能力有、入口/表达缺」 | 已核实 |
| C-6 | 因此本版主线定为**「让已有的能力被看见、被用上、被信任」**，而不是加新功能 | 建议 |

一句话：**这一版不该再加功能，该把已经能跑的能力摆到台面上**——59 条用例真机跑通了，但界面上发不起执行；GPU 资产表里没有实体，但渲染器天天要它；报告能导出三种格式，但对外报告页没入口。

## 2. 问题一：菜单差异的评估

### 2.1 事实（同 `00-RESEARCH.md` §2，此处只留结论）

| 问题 | 答案 |
|---|---|
| 为什么少 | `kind=pytest-suite` 走 `PYTEST_SUITE_NAVIGATION`，该树按设计只保留「看覆盖/绑脚本/发起执行/看报告」四件事 |
| 少多少 | 一级 7→4，叶子 28→9，含设置共 30→11 |
| 是不是不能用 | 不是。路由不按 `kind` 设防，后端 `ProjectKind` 不参与鉴权，**页面全部可达，只是没入口** |
| 改动成本 | 小（补叶子 + 改一条单测断言 + 改 `EXPECTED_LEAVES` 39），但**必须先定策略**，否则下版本又漂 |

### 2.2 方案对比与最终选择

| 维度 | 方案 A 全量对齐 | 方案 B 按需补齐 | 方案 C 只补三项 |
|---|---|---|---|
| 做法 | 删掉第二棵树，pytest 工程用同一套菜单 + 保留 `/pytest-workbench` | 保留差异树，只补真实缺口 | 手工加 3 个叶子 |
| 用户能否找到设备页 | 能 | 能 | 能 |
| 跨工程切换是否迷路 | **不会**（同一套菜单） | 会（两套结构不同） | 会 |
| 无对象页面怎么处理 | 空态自解释 | 不存在（仍隐藏） | 不存在（仍隐藏） |
| 与「先配台架才能跑」的业务事实 | **一致** | 部分一致 | 部分一致 |
| 加新工程类型时 | 不用改菜单 | 要维护差异 | 又要抄一棵 |
| 长期维护成本 | 低 | 中 | 高 |
| 结论 | **采纳（D-01）** | 备选 | 否 |

**为什么改成 A（记录取舍，不掩饰）**：

- 原推荐 B 的核心论据是「pytest 工程没有台架资产，这些页是噪音」。**这个前提是错的**：该工程同样要登记 DUT 与网口、配 SSH 凭据、拉起环境，才可能执行——v5.5.0 的真实执行就是这么做的（只是当时绕过了界面）。
- 一致性本身是产品价值：同一产品两套菜单，用户在标准工程与用例库工程之间切换时需要重新建立空间记忆，这类成本不会出现在任何一次验收里，但会持续消耗。
- 全量后唯一的真实风险是「点进去是空页」，那就用**空态说明**把「为什么空、能做什么」讲清楚（C-7），而不是把入口藏掉——藏掉让人连提问的机会都没有。
- 保留一个必要例外：`/pytest-workbench`（健康/覆盖率/绑定/配置）是该工程类型的落地面，并入「工作台」组首位；这是「同一套菜单 + 一处增量」，不是「另写一套」。

### 2.3 全量补齐清单与空态要求

**原则**：28 项全部可见（与标准工程逐项一致），仅 `/pytest-workbench` 作为增量并入「工作台」组。
对「在 pytest 工程确实没有对象」的页面，逐页指定空态要求——这是全量方案的配套，不是可选项。

| 组 | 项 | path | 在 pytest 工程是否有对象 | 空态/说明要求 |
|---|---|---|---|---|
| 工作台 | 工作台总览 | `/workbench` | 有（跨项目总览） | — |
| 工作台 | **pytest 工作台（增量）** | `/pytest-workbench` | 有（本工程落地面） | — |
| 工作台 | 项目工作区 | `/workspace` | 有（导入导出） | — |
| 工作台 | 项目看板 | `/overview` | 有 | — |
| 工作台 | 新建项目 | `/projects/new` | 有 | — |
| 执行 | 即时发起 / 运行列表 / 内核页 | `/execution-plans`、`/runs`、`/kernels` | 有 | — |
| 执行 | 测试计划 | `/plans` | 待验 | 无计划时给「新建计划」引导 |
| 执行 | 执行节点 | `/nodes` | **无**（pytest 本机起子进程） | 说明「本工程类型的执行在本机直接启动，不派发到执行节点」+ 可跳运行列表 |
| 执行 | 报告列表 / 模板 / 对外报告 | `/reports`、`/reports/templates`、`/test-reports` | 有 | — |
| 用例 | 列表 / 用例集 / 总表 | `/cases`、`/cases/sets`、`/cases/board` | 有 | — |
| 资产 | 设备 / 链路 / 凭证 | `/assets?tab=*` | **有（执行前置）** | 无设备时给「登记第一台 DUT」引导 |
| 环境 | 总览 / 采集 / 拓扑 / 准备 / 分析 / 连接 | `/environment/*` | 部分有 | 无数据页说明「尚未采集」+ 跳采集页 |
| 维护 | 原则 / 记录 / 恢复 / 存量同步 | `/maintenance/*`、`/sync` | 部分有 | 无记录时说明「本工程暂无维护记录」 |
| 设置 | 用户管理（我）/ 关于 | `/settings/users`、`/about` | 有 | — |

**判定口径**：上表「无对象」只有一处（`/nodes`）。这意味着**其余 27 项都必须在 pytest 工程里有真实内容**——
凡是打不开或长期空白的，按缺陷登记，而不是用「反正点了也没用」解释。

## 3. 问题二：六维现状评分与目标

评分口径：1–5 分，5 = 行业良好实践水平。**分数是相对本平台成熟度的自评，不是对外评级**；每格必须能追到 §4 的事实。

| 维度 | 现状 | 本版目标 | 差距主因 |
|---|---|---|---|
| 系统架构 | 3.0 | 4.0 | 能力模型与信息架构脱节（`kind` 只裁菜单）；全量后收敛为单一菜单源 |
| 软件设计 | 3.5 | 4.0 | 报告链路完整，但可见性/入口设计靠硬编码 |
| 程序实现 | 3.0 | 4.0 | 渲染资产恒空、固定开销 30s、执行同步阻塞 |
| 测试体系 | 3.5 | 4.0 | 门禁齐全，但性能门禁无采样即 SKIP（假绿） |
| UI/UX | 3.0 | 3.5 | 报告版式退化（59 条展开 59 标题）、xlsx 无明细 |
| 用户体验 | 2.5 | 4.5 | **执行入口 UI 不可达**（最大单点）+ 跨工程菜单不一致 |
| 运维保障 | 3.0 | 3.5 | 构建覆盖运行中 jar 导致登录超时，靠人记 |
| 智能化 | 3.0 | 3.5 | AI 归因吃脱敏指纹，垃圾进垃圾出 |

对应大师给的版本目标：

| 目标 | 落到哪条主线 | 本版能否有可见提升 |
|---|---|---|
| 易用性 | IA-01/02/04（菜单与可见性） | 能，立刻可见 |
| 实用性 | RP-01/02/03（报告可用）、AS-01（GPU 资产） | 能 |
| 界面美观度 | UX-01/02/03（一致性、长列表、三态） | 部分 |
| 操作便捷性 | EX-01/02/03/04（UI 发起、进度、取消、预检） | 能，最大收益 |
| 运行效率 | EX-05（固定开销 30s→≤10s）、OP-03 | 能 |
| 智能化 | AI-01/02（归因可用、补判助手） | 部分（依赖 RP-02） |

## 5. 风险与前置条件

| 编号 | 风险/前置 | 影响 | 处置 |
|---|---|---|---|
| R-1 | 删掉第二棵树会让 `navigation.spec.ts` 那条「禁止出现资产/环境/维护」断言**反向失效** | 门禁红或断言变成空转 | 把断言反转成「叶子集合 = 标准集合 ∪ {/pytest-workbench}」，并在提交说明写清推翻依据 |
| R-7 | 全量后多个页面在 pytest 工程里长期空白，用户觉得「打开了没东西」 | 体验倒退，比隐藏更糟 | 逐页落空态（§2.3 表）；空白页按缺陷登记 |
| R-2 | `/plans`、`/sync` 对 pytest 工程是否真能跑**未验证** | 可能补了个点进去报错的入口 | DEV-PLAN 前置 W56-00「可行性验证」，验不过则本版不补，只登记 |
| R-3 | 执行异步化若直接改 `/runs` 语义，会打断已有证据脚本与外部调用方 | 回归风险 | 新增异步端点，旧端点保留并标注 deprecated |
| R-4 | GPU 资产实体涉及新表/迁移 | 迁移不可回退（已应用不可改） | 走「加可空→回填→收紧」，新迁移号顺延 |
| R-5 | 报告命令采集需用例库框架配合输出约定行 | 平台单方面做不成 | 平台侧先落「解析 + 缺省提示」，真源侧改动列入依赖 |
| R-6 | 本版若同时做六维，范围必然失控 | 交付风险 | 见 D-03，建议本版聚焦 IA+EX+RP+OP，AS/AI 深度排 v5.7 |

## 6. 不做假声明

- 本报告**没有**做过任何 UI 端到端截图验收；UI 结论来自源码与接口行为。
- 六维分数是自评，**不是**第三方评级，也没有行业基准样本。
- `/sync`、`/plans`、`/environment/collect`、`/assets?tab=links` 四项「待验」，本报告**不假装已确认**。
- 效果类指标（Top8 成功率、create P95、fps）仍未测量，本版把它列为需求而非已达成项。
