### 1.2 推断

| # | 推断 | 依据 |
|---|---|---|
| I-01 | 把 `pr.yml` 直接搬到 `ubuntu-latest` 跑不通：它 `make test` 需要真 MySQL 与 `DB_PASSWORD` Secret，`make db-reset` 还会 DROP 测试库；GitHub-hosted runner 没这套环境 | F-05、F-06 + `Makefile` |
| I-02 | 目标部署机不该需要 Maven / npm / 源码；交付物应是**构建产物 + 运维脚本 + 文档**，把依赖收敛到 JDK / Node / MySQL 三个运行时 | F-01、F-09、交付常识 |
| I-03 | 拆卸最大风险不是删不干净，而是误删数据库或误把家目录当安装根；因此拆卸必须「先备份、逐项删、数据库不动、目标须有 MANIFEST.json」 | F-03、运维红线 |
| I-04 | 若脚本在源码树与交付包各写一套，路径迟早漂移（本项目已多次踩「源码对齐 ≠ 部署对齐」）；应共用一份 `common.sh` 按布局判定 | 项目长期记忆「systemd 跑 backend/target/*.jar」教训 |

### 1.3 假设

| # | 假设 | 若不成立 |
|---|---|---|
| A-01 | 目标机为 linux-x64，有 JDK 21 / Node.js 22+ / MySQL 8.0，且已由 DBA 建好空库与账号 | `doctor.sh` 报 FAIL，安装中止；不自动装系统依赖 |
| A-02 | 使用者可接受 Actions artifact（需登录 GitHub）作为「可下载」渠道；公开 Release 属对外口径，本轮不做 | 如需匿名 wget，须大师授权后另加 Release job |
| A-03 | WSL2 / Ubuntu 上 `systemd --user` 可用（WSL 需 `systemd=true` 与 `enable-linger`） | 降级为 `nohup`，`ctl.sh` 已实现双托管 |
| A-04 | 首次安装面对的是空库；已有数据的库走 Flyway | `db-migrate.sh` 默认拒绝非空库 |

## 3. 方案比较

| 方案 | 做法 | 优点 | 代价 / 否决理由 | 结论 |
|---|---|---|---|---|
| A 只写文档 | 把命令抄进 OPS 手册 | 零代码 | 「文档写了但没人接线」正是本项目反复踩的坑；无护栏、无验收 | 否 |
| B 脚本各写一份 | 源码树一套、交付包一套 | 直观 | 路径必然漂移（I-04），两套护栏难以同步 | 否 |
| C **同源脚本 + 布局判定**（采纳） | `common.sh` 按 `MANIFEST.json` 判 bundle/source；打包时 `scripts/ops/*` 原样复制成 `bin/*` | 一份代码两处跑；机检可直接对源码断言；改一处两边生效 | 需要把产物路径抽象成变量 | **是** |
| D 打成 deb / rpm | 走系统包管理器 | 卸载与依赖管理规范 | 需要维护仓与签名；WSL 上 `apt` 权限与 systemd 差异大；本轮范围外 | 排 v3.12 候选 |
| E CI 里跑全量门禁 | ubuntu-latest 上装 MySQL + Chrome + 真库 | 一次到位 | 需要 Secret、真浏览器与自托管资源；与「尝试 CI 构建」目标不符，且会与本地门禁口径冲突 | 否 |

### 3.1 前置条件

1. WSL 权威副本 `~/robot-autotest` 已完成 `scripts/build.sh`，产物齐备（`backend/target/*.jar`、`frontend/dist/index.html`、`frontend/dist/CHANGELOG.md`）。
2. `VERSION` 与 `frontend/public/CHANGELOG.md` 一致（版本四副本由门禁第 23 步守护）。
3. 本机有 `python3`、`tar`、`sha256sum`、`git`；CI 用 `ubuntu-latest` 自带的同款工具。
4. `gh`（Windows 侧）已登录且有 `workflow` scope，用于观察 Actions 真实运行结果。
5. 目标机满足 A-01；凭据文件由部署方准备，仓库与交付包都不含明文口令。

### 3.2 明确不做

- 不自动创建数据库 / 账号、不自动迁移非空库、不自动启动服务、不自动 enable systemd unit；
- 不在交付包里放任何凭据、日志、运行数据、源码依赖目录；
- 不创建 GitHub Release、不 bump 版本号、不产生对外发版口径（归大师）；
- 不改动既有 `pr.yml`、`deploy.sh`、`build.sh`、`gates.sh` 既有 29 步语义；
- 不做 deb/rpm、Docker 镜像、Windows 原生安装包；
- 不在 CI 里跑真 MySQL / 真浏览器 / 全量门禁。

### 3.3 风险与处置

| # | 风险 | 处置 |
|---|---|---|
| R-01 | 交付包路径与源码树不一致导致入口找不到 dist | `ENTRY_DIST` 显式化；`doctor.sh` 断产物；`ctl.sh` 双布局；unit 样例单列 `deploy/release/` |
| R-02 | 拆卸误删数据 | 目标须有 MANIFEST.json；拒绝系统目录/家目录；先备份；数据库不动；逐项删 + 每 10 项校验 |
| R-03 | 凭据泄漏 | `load_env()` 逐行解析不 source；`MYSQL_PWD` 传口令；备份只导键名；打包断言无 `env`/日志；两个既有密钥扫描器继续扫 `scripts/` |
| R-04 | CI 假绿（只 build 不验包） | workflow 里解包自检 + `check_delivery_bundle.py`；本地同序列复跑；`gh run` 观察真实结论 |
| R-05 | `pr.yml` 继续排队占额 | 保留但不动；文档写明它是「待现场」项；新增独立 `delivery.yml` 用 GitHub-hosted runner |
| R-06 | 门禁步骤数从 29 变 30，下游解析脚本要同步 | `CHANGELOG.md` 记为口径变更；`gates.sh` 结构自检同步加「删第 30 步必变红」 |
| R-07 | 文档与实现漂移 | ⑦ 文档回写：`DELIVERY-GUIDE.md`、`bin/README.md`、`README.md`、`CHANGELOG.md`、下一轮计划同步更新 |
| R-08 | **误停全局 systemd unit**（真拆卸实测前发现） | `install.sh --systemd` 写 `var/systemd-managed`；`ctl.sh` / `uninstall.sh` 无标记只动本安装根 pid 文件；机检加负向样本；实测前后 `:8081` / `:8001` 均 200 |
