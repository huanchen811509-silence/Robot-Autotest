## 0. 结论先行

1. **Excel 是事实上的交换格式，不是「一次性导入模板」**。它同时承载用例正文、分类、测试资源、执行结果与看板汇总，且已经有了版本号（`v0.5.0.0`）。因此必须按「格式契约」对待：列序、表头别名、sheet 命名、分节结构都要兼容，并做**双向**（导入 → 平台 → 导出）round-trip 校验。
2. **样本实测**：5 张明细表、**730 条用例、编号零重复**、**32 个一级分类**；但两张表用了不同表头（`测试编号`/`测试用例` vs `用例编号`/`用例名称`），另有 `当前测试环境` 是**分节多表**（服务器 8 台 → 交换机 → 端口）。所以解析器必须「别名 + 分节」双能力，不能按固定列号读。
3. **demo 平台已有可复用的完整实现**：`testcase_parser.py`（多格式 + 表头别名 + 无编号稳定 hash）、`case_workspace.py`（文件 sha → 套件 → 用例 upsert → 过程版本按内容 sha 不可变）、`progress_workbook.py`（反向导出 xlsx）、`resource_import.py`（预览/提交两段式 + `preview_sha256` + `idempotency_key`）。**算法与表结构可以照搬，代码不能直接搬**（Python/FastAPI + SQLite 语义 vs 本项目 Java/Spring + MySQL + 多租户作用域）。
4. **需求 5（存量项目跟随最新用例/资产）不能做成「导入后全库覆盖」**。必须区分「引用源」与「项目内本地修改」：有本地修改的用例不能被静默覆盖，表格里被删掉的行不能直接硬删（会打断正在跑的计划）。默认策略：**新增/更新自动同步，删除软失效，冲突进待办列表**。
5. 本报告只做评估与设计，不写代码；PRD 由两份评估报告合并后产出。

| `backend/niclab/api/resource_import.py` | 预览 → 提交，带 `preview_sha256` + `idempotency_key` | **两段式契约**、幂等键、预览统计结构 | 资产字段不同（本项目的 device/link/port/credential 模型更细） |

## 3. 导入设计：三层幂等

### 3.1 第一层：文件级幂等（同一次上传重复提交不产生副作用）

```
POST /api/global/imports/preview   (multipart: file, scope)
   → 计算 fileSha256，落 import_batch(status=PREVIEW)
   → 返回 { batchId, fileSha256, previewSha256, summary }
POST /api/global/imports/commit    { batchId, previewSha256, idempotencyKey }
   → previewSha256 必须与库内一致（防止预览后文件被换）
   → idempotencyKey 相同且有成功批次 → 直接返回上次结果（200，不重复写）
```

规则：

- 同 `(fileSha256, scope)` 已成功导入过 → 预览页直接提示「该文件已于 <时间> 导入过，本次将复用结果」，并给「强制重新导入」开关（会生成新批次，但行级 upsert 仍不会产生重复数据）；
- 预览与提交之间文件变化（重新算 sha 不一致）→ 409，要求重新预览；
- 提交失败（解析/校验/写库）→ 批次置 `FAILED`，`idempotencyKey` 不占用，可重试。

### 3.2 第二层：行级幂等（重复导入同一行不会多一条）

业务键优先级：

1. `external_id`（表格里的 `用例编号`/`测试编号`）——样本 730 条全部有值且唯一；
2. 缺编号时：`sha1(一级分类|二级分类|用例名称|测试步骤|预期结果)` 生成 `content_key` 兜底（demo 平台已验证该做法能避免「导入两次变两倍」）；
3. 两者都没有 → 该行拒绝，进「错误行」清单（带行号与原因）。

落库语义：`INSERT ... ON DUPLICATE KEY UPDATE`（唯一键 `(source_id, external_id)`），只更新内容列，不动项目内引用关系。

### 3.3 第三层：版本级幂等（内容没变就不产生新版本）

```
case_version(case_id, content_sha, payload_json, created_at)
UNIQUE KEY (case_id, content_sha)
```

- 内容 sha 相同 → 复用已有版本，不新增行；
- 内容 sha 变化 → 新增不可变版本行，`case.current_version_id` 指向最新；
- 项目引用可配置「跟随最新」或「锁定版本」（默认跟随，见 §7）；
- 好处：执行记录能说清「这条用例当时是哪个版本跑的」。

### 3.4 变更集与预览

预览不是「解析了就完事」，要给出可决策的差异：

```
新增 412 / 更新 96 / 未变 222 / 失效 8 / 错误 2
其中：一级分类新增 3 个；优先级变化 12 条；测试资源引用缺失 5 条
```

差异口径：按业务键对齐后逐字段比较，字段级列出变化（名称/步骤/预期/优先级/分类/资源），供用户勾选「本次不应用某几条」。

## 4. 分类体系与筛选

### 4.1 落库

```sql
ALTER TABLE test_case
  ADD COLUMN category_l1 VARCHAR(64) NULL,
  ADD COLUMN category_l2 VARCHAR(64) NULL,
  ADD KEY idx_case_category (project_id, category_l1, category_l2);

CREATE TABLE case_category (
  id        BIGINT PRIMARY KEY AUTO_INCREMENT,
  scope     VARCHAR(16) NOT NULL,        -- global | project
  project_id BIGINT NULL,
  level     TINYINT NOT NULL,             -- 1 | 2
  name      VARCHAR(64) NOT NULL,
  parent_id BIGINT NULL,
  sort_no   INT NOT NULL DEFAULT 0,
  UNIQUE KEY uk_category (scope, project_id, level, name)
);
```

### 4.2 用途（这三点是用户明确要的）

1. **筛选**：用例列表 / 用例集编辑 / 场景编辑统一加「一级 → 二级」联动筛选；URL 上带 `categoryL1/categoryL2`，可分享；
2. **批量建集**：勾选一级分类 → 「加入用例集」/「生成测试场景」，默认按 `一级/二级` 分组生成条目顺序；
3. **看板**：导入预览页展示「分类 × 数量」矩阵，与样本 `测试用例看板` 的口径对齐。

### 4.3 分类归一化

- 空值：`category_l1` 为空的行 → 归入「未分类」，不阻断导入；
- 脏值：首尾空格、全角空格、`/` 分隔的多级（如 `A/B`）→ 归一化后再判重，别名映射表可配置；
- 一级分类改名：不自动改历史用例，提供「批量改分类」动作并写审计。

## 5. 测试资产导入（`当前测试环境` 分节表）

### 5.1 解析策略

该 sheet 是**多段表**：每段有独立表头、段间有空行与说明。解析器按「遇到含关键词的表头行即开新段」切分：

| 段 | 表头关键词 | 映射目标 |
|---|---|---|
| 服务器 | 主机名、管理IP、角色、型号、操作系统、内核、BMC 地址、网口数、网卡配置、登录方式、账户 | `device`（服务器） + `credential` 引用 + `device_port`（网口数汇总需人工确认后展开） |
| 交换机 | 交换机、管理IP、型号、端口数 | `device`（交换机） |
| 端口/链路 | 设备、端口、速率、对端设备、对端端口 | `device_port` + `link` |

### 5.2 幂等键

| 对象 | 业务键 |
|---|---|
| 设备 | `管理IP`（唯一） + `主机名`（展示） |
| 端口 | `(设备管理IP, 端口名)` |
| 链路 | `(A端设备IP, A端口, B端设备IP, B端口)` 排序后取 hash |
| 凭据 | `(设备管理IP, 登录方式, 账户)`；**密码不落明文**，只存引用与掩码 |

### 5.3 与项目的关系

- 导入的资产进「公共资产池」（v4.4 全局模式）；
- 项目通过 `project_asset` 引用，不复制实体；
- 表格里消失的资产 → **软失效**（`enabled=0`），并在引用它的项目里显示「来源已下架」，不硬删。

## 6. 反向导出（幂等导出 + round-trip）

### 6.1 目标

导出的 xlsx 必须能被**同一个导入器原样再导入**，且差异为 0。这是验收硬指标。

### 6.2 规则

- **列序与表头**：严格按样本 v0.5 的 14 列顺序，表头用「正名」（`用例编号`/`用例名称`），别名只在导入侧兼容；
- **sheet 结构**：按一级分类分 sheet？还是保持「一个来源一个 sheet」？——建议**按来源批次 + 一级分类前缀命名**，保持与样本一致的「一张明细表一类业务」结构，看板单独重建；
- **结果列**：导出时把平台内的执行结果写回 `测试结果`（`通过/失败/阻塞/未执行`），`测试资源` 写引用名；
- **导出批次幂等**：同 `(scope, 筛选条件, 数据版本)` 重复导出 → 内容 sha 相同，直接复用上次文件（缓存 24h），避免用户反复导出得到不同字节；
- **回写通道单向**：导出文件只用于线下评审/汇报；执行结果回写走**导入**（可选「只更新结果列」模式），不做「上传即双向合并」，避免冲突不可解释。

### 6.3 round-trip 判据

```
导出 → 不做任何修改 → 重新导入
  期望：新增 0 / 更新 0 / 未变 730 / 失效 0 / 错误 0
```

## 7. 存量项目同步（需求 5）

### 7.1 同步模型

```
case_source(project_id, case_id, source='import', source_batch_id, version_id, mode='track-latest'|'pinned', local_override=0)
```

- 默认 `track-latest`：导入提交后，把该来源的变更传播到所有引用项目；
- 项目内手工改过的用例 → `local_override=1`，**不再被自动覆盖**，进入「待确认」列表，由项目经理决定「采用新版本 / 保留本地」；
- 删除型变更（表格里整行消失）→ 标记 `deprecated_in_source=1`，不硬删；引用它的用例集/场景显示「源已移除」，执行计划可选择跳过；
- `pinned`：给合规要求高的项目用，导入新版本时只提示、不自动升。

### 7.2 同步执行

```
import commit
  → 生成 sync_job（异步）
  → 计算受影响项目（引用该来源的全部项目）
  → 逐项目应用：新增引用 / 升级版本 / 标记失效 / 记录冲突
  → 结果写入 sync_job_item，页面可查看与回滚
```

失败与回滚：单个项目失败不影响其他项目；`sync_job` 支持「按项目回滚到上一批次」（保留两代版本快照）。

### 7.3 资产同步

资产不做「项目内副本」，所以同步 = 更新公共池 + 失效标记；项目侧只展示变化提示（「你引用的 3 台设备信息已更新」）。

## 9. 后端数据模型（建议）

```sql
-- 导入批次（文件级幂等）
CREATE TABLE import_batch (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  scope VARCHAR(16) NOT NULL,            -- global | project
  project_id BIGINT NULL,
  kind VARCHAR(16) NOT NULL,             -- case | asset
  file_name VARCHAR(255) NOT NULL,
  file_sha256 CHAR(64) NOT NULL,
  preview_sha256 CHAR(64) NULL,
  idempotency_key VARCHAR(64) NULL,
  status VARCHAR(16) NOT NULL,           -- PREVIEW | COMMITTED | FAILED | ROLLED_BACK
  summary_json JSON NULL,
  created_by BIGINT NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_import_idem (idempotency_key),
  KEY idx_import_file (file_sha256, scope, kind)
);

-- 导入明细（行级结果，含错误行）
CREATE TABLE import_item (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  batch_id BIGINT NOT NULL,
  sheet_name VARCHAR(128) NULL,
  row_no INT NOT NULL,
  business_key VARCHAR(200) NULL,
  action VARCHAR(16) NOT NULL,           -- CREATE | UPDATE | UNCHANGED | DEPRECATE | ERROR
  error TEXT NULL,
  payload_json JSON NULL
);

-- 用例版本（版本级幂等）
CREATE TABLE case_version (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  case_id BIGINT NOT NULL,
  content_sha CHAR(40) NOT NULL,
  payload_json JSON NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_case_version (case_id, content_sha)
);

-- 来源与项目引用
CREATE TABLE case_source (
  project_id BIGINT NOT NULL,
  case_id BIGINT NOT NULL,
  batch_id BIGINT NOT NULL,
```

## 12. 非功能要求

| 项 | 目标 | 做法 |

| 大文件 | 上传 ≤ 20 MB / 5 万行不 OOM | POI 事件模型（SAX）流式读；分批写库（500 行/批） |

## 13. 测试策略

1. **幂等重放**：同一文件连续提交 2 次 → 第二次「新增 0 / 更新 0 / 未变 730」；
2. **乱序与重复**：行顺序打乱、同文件内重复行 → 结果一致，重复行报告；
3. **表头别名**：把 `用例编号` 改成 `测试编号`、`用例名称` 改成 `测试用例` → 解析结果一致；
4. **缺编号**：删掉某行编号 → 走内容 hash，重复导入不新增；
5. **空/脏分类**：空分类归「未分类」；`A/B` 归一化；
6. **round-trip**：导出 → 原样导入 → 差异 0；
7. **分节资产表**：服务器/交换机/端口三段各自 upsert，IP 冲突行给 409 级错误；
8. **存量同步**：导入新版 → 引用项目用例数、版本、失效标记正确；`local_override` 不被覆盖；
9. **回滚**：回滚批次 → 项目引用回到上一版本，无孤儿行；
10. **权限**：ENGINEER 调导入接口 403；VIEWER 调导出 200 但数据只读。

排序理由：解析与分类是地基；没有预览/提交就谈不上同步；导出依赖导入的数据模型（业务键一致才能 round-trip）。
