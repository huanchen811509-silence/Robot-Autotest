## 0. 结论先行

| # | 结论 |
|---|---|
| 1 | 91 条 TC 覆盖 35 条 FR 与 93 条验收 A/B/C/D；**每条 TC 有唯一判据与固定证据形态**，写不出判据的不算 TC。TC 与验收非一一映射（交叉覆盖）。 |
| 2 | 有一处**规范缝隙必须先补**：项目硬规矩要求 `output.xml` 带 6 项 metadata，而 pytest 不产生 `output.xml`。本计划确立 **metadata 等价物**（sidecar `run_metadata.json` + junit `<properties>` 双载体），并扩展现有 `tools/check_output_metadata.py` 支持双形态（§5）。 |
| 3 | 5.1 线的测试主体是**契约面**（渲染产物能否被框架 `load_*` 读、参数是否被接受、结果能否回落），不是「代码有没有覆盖」。单测绿不构成放行理由。 |
| 4 | 全量 16 版本中，只有 **8 条 TC 需要真实设备**（5.1.0 三条执行 + 样板 + 双端预约 + 长跑窗口），其余全部可在 Fake 模式或脚本层完成 —— 这是本线能保持节奏的关键。 |
| 5 | 门禁读数必须分两段记：原 36 步（对齐 v5.0.0 基线）+ 新增 12 步（37–48）。**两段不得相加成「全绿」**。 |
| 6 | 每个新增机检必须有负向自检：真注入 → 判红 → 还原 → 复跑绿。`skip=N` 式跳过一律不计。 |

## 2. 测试分层与准入准出

### 2.1 分层策略

| 层 | 名称 | 手段 | 覆盖 TC | 单次耗时量级 |
|---|---|---|---|---|
| L1 | 静态机检 | `tools/*.py`、`check_md_tables.py` | 约 22 条 | 秒级 |
| L2 | 单元测试 | `mvn test` / `vitest run` | 约 18 条 | 分钟级 |
| L3 | 契约层 | 渲染产物过框架 `load_inventory`/`load_run_env` 实读、参数探测、junit 解析 | 约 12 条 | 分钟级 |
| L4 | 集成 | `-Pit` + 真实 MySQL + API 调用 | 约 14 条 | 十分钟级 |
| L5 | 端到端真实执行 | 真机 + 真框架 + 真用例 | **8 条** | 小时级 |
| L6 | 跨内核回归 | RK-1~5 黄金样本比对 | 5 条 | 分钟级 |
| L7 | 负向注入 | 故障注入 F1–F12 | 12 项 | 分钟级 |
| L8 | 界面走查 | 大屏/抽屉/雷达/手工执行页人工确认 | 约 6 条 | 人工 |

> 同一 TC 可跨层（如 TC-v5.1-27 同时属 L2 与 L8），**各层计数不可相加**（相加会大于 91）；分层只用于排执行顺序与资源。

### 2.2 准入准出

| 闸 | 判据 |
|---|---|
| 准入（进测试） | 该包 DoD 前 3 条满足（代码合入、单测绿、验收命令有输出）；迁移已在空库重放成功 |
| 准出（该版本可判定） | 该版本全部 TC 状态为 PASS 或已登记 `BLOCKED/PARTIAL`（附原因与所需条件）；无 `FAIL` 未处置；RK 全绿 |
| 不通过 | 存在 `FAIL` 未处置；或 TC 判据靠"人工看一眼"而无证据；或用例库/框架被改动以"让它通过" |

### 2.3 TC 状态字典（沿用 v5.0 台账，不新增第七态）

| 状态 | 含义 |
|---|---|
| `PASS` | 判据满足，证据齐全 |
| `PARTIAL` | 部分满足，缺口写明（如仅 Fake 未真机） |
| `NOT-RUN` | 有执行条件但本轮未排入执行窗口 |
| `BLOCKED` | 缺前置条件（写明缺什么） |
| `FAIL` | 判据不满足 |

## 5. metadata 等价物（本项目硬规矩在 pytest 侧的落法）

### 5.1 为什么必须单列这一节

项目硬规矩（USER.md / `AGENTS.md` §4.1）要求：**所有测试项目的原始报告必须带 metadata**，必填 6 项 `CASE_ID`/`RUN_ID`/`QA_PROJECT`/`DUT`/`LINK`/`SW_BUILD`，推荐 4 项 `BASELINE`/`OPERATOR`/`STARTED_AT`/`CASE_KIND`，键全大写、值 ≤40 字符、不得含凭据。这条规矩是按 RF 的 `output.xml` 写的；**pytest 不产生 `output.xml`**，直接套用会得到「规矩还在、载体没有」的空转。

### 5.2 双载体定义

| 键 | pytest 侧载体 | 生成方 | 校验 |
|---|---|---|---|
| `CASE_ID` | sidecar `case_id`（逐用例） | 框架侧 sidecar 插件 | 逐用例非空 |
| `RUN_ID` | junit `<properties><property name="RUN_ID">` + sidecar 顶层 | 平台渲染期注入 | 两载体同值 |
| `QA_PROJECT` | 同上 | 平台 | 与项目编码一致 |
| `DUT` | 同上（双端记 `A+B`） | 平台渲染期注入 | 个数与端数一致 |
| `LINK` | 同上 | 平台 | 可解析 |
| `SW_BUILD` | 同上（= `COMMIT_SHA`） | 平台按 ref 解析 | 与 `run_metadata.git.commit` 一致 |
| 推荐 4 项 | 同上 | 平台/框架 | 缺失只告警 |

### 5.3 落法与机检

| # | 动作 | 判据 |
|---|---|---|
| 1 | `check_output_metadata.py` 扩展为**双形态**：RF 读 `output.xml`，pytest 读 sidecar `run_metadata.json` + junit `<properties>` | 两种形态都能判，缺键判红 |
| 2 | 键名全大写、值 ≤40 字符、不得含凭据的规则对 sidecar 同样生效 | 造超长值/含口令 → 判红 |
| 3 | 一条 TC 专测这条缝隙：`TC-v5.1-28`（见 §5.4） | 见 §5.4 |
| 4 | 若框架侧未提供 sidecar 插件，平台在渲染期写「只含 run 级 6 项」的 sidecar，逐用例 `CASE_ID` 由 junit `testcase` 名 + 绑定表补齐 | 两种情况都必须满足 6 项非空 |

### 5.4 两条专项 TC 的去向（纯说明，不重复计数）

- `TC-v5.1-27`（步骤树 + 命令抽屉）：验收项 A22、A23 属 5.1.3 的 FR-v5.1-09，但 5.1.0 的产物就要求含明细，因此这条**跨版本**。已并入 §3.1 表尾，不另立编号段。
- `TC-v5.1-28`（metadata 等价物）：它验证的是项目硬规矩在本技术栈的落法，不绑定任何产品 FR。已并入 §3.1 表尾，是本规范缝隙的唯一验证项。

> 两条均已计入 §3.1 的 33 条。本文总数口径为 **91 条**（33 + 22 + 20 + 16）。
