# v5.5.0 EHT pytest 真实执行 · 平台能力评估与改进报告

- 报告日期：2026-11-13
- 执行对象：项目 95 `EHT-PYTEST-LIB`（`kind=pytest-suite` / `test_kernel=pytest`）
- 执行载体：gpu01 `10.202.54.101`、gpu02 `10.202.54.102`（各 2×RTX PRO 6000，ConnectX-7 `ens17np0` 400G，固件 28.44.1036）
- 授权：大师 2026-11-13 21:42 授权对 61 条可执行用例做真实测试，优先 gpu01/gpu02，gpu03 备用，**暂不使用 gpu04**
- 证据目录：`docs/evidence/v5.5.0/eht/real/raw/`

## 1. 结论摘要

1. **全流程闭环已通**：平台内「资产台账 → 渲染 inventory → 真实 SSH 执行 → junit 归一 → 产物登记 → 报告解析 → PDF/DOCX/XLSX 导出」跑通，不再依赖平台外手工命令。
2. **59 条真实执行结果：57 PASS / 1 FAIL / 1 ERROR**（另 2 条 SR-IOV 被 ADR-0013 安全闸拦下，未执行）。用例总耗时 297.7 s，中位 1.2 s，P90 9.9 s，最长 62.3 s。
3. **能力现状是「能用，但不好用」**：执行入口在界面上不可达、执行同步阻塞无进度、GPU 资产模型缺失、报告命令列恒空、失败摘要不可读——五处直接影响可视化与便捷性。
4. **本轮修掉 5 个真实缺陷**（均在平台侧，未改用例库源码）：real 模式入口与安全闸、fake 端点静默降级、产物登记缺失、请求 metadata 不落库导致报告不可导出、junit 失败消息退化成 `"FAIL"`。
5. **2 条不通过各有归因，不是「平台跑不动」**：`IM-MIX-011` 因平台渲染的 `resource_pool.gpus` 恒空（平台资产缺口）；`IM-RDM-022` 因真源断言把期望优先级写死（用例库缺陷）。

## 2. 执行范围与风险分级

61 条已绑定脚本全部导入时落 `safety_level=LX`（未判定），而 ADR-0013 规定 LX 与 L2 一律 `blocksExecution`。因此真实执行前先做**人工补判**：只读脚本实际调用的动作方法，而不是看标题。

| 分级 | 条数 | 判定依据（脚本实际调用） | 本轮处置 |
|---|---|---|---|
| L0 只读 | 41 | 无 `set_*` / 无写型命令，只有采集与判定 | 执行 |
| L1 可逆配置 | 18 | `set_offload` / `set_ring` / `set_channels` / `set_mtu` / `set_link_state` / `set_fec` / `set_pfc`，或脚本内含 `ethtool -K/-L/-G/-A` | 执行 |
| L2 高危 | 2 | `set_sriov_numvfs`（建 VF，可能扰动宿主网卡） | **保持 LX，未执行** |

补判走平台既有唯一合法入口 `POST /api/projects/{id}/cases/batch`（`action=setSafetyLevel`），并保留 `undoToken` 可回滚。补判后项目安全级分布：L0 41 / L1 18 / LX 410（410 = 408 条未绑定 IM + 2 条 SR-IOV）。

**不通过的 2 条**

| 用例 | 结论 | 直接原因 | 归因方 |
|---|---|---|---|
| `IM-MIX-011` GDS 平台 | ERROR（setup） | `pytest.UsageError: 资源池中没有可用的 GPU` | **平台**：渲染的 inventory 里 `devices.gpus` 恒为 `{}` |
| `IM-RDM-022` 双 UP PFC 计数 | FAIL | 期望优先级 `3,6`，实际 `3,4,6` | **用例库**：`target_mask = original ∪ {3,6}`，但断言期望值写死 `"3,6"`，基线含 UP4 必红 |

**抖动验证**：`IM-NET-002`（光模块 DDM）在同一环境连续三次执行结果为 FAIL → PASS → PASS，失败时模块报 `Laser tx power low alarm` / `bias current low alarm`（通道 2–6）。平台只记录单次结论，没有重试与稳定性标记，这条抖动会被当成确定性失败进入对外报告。

**耗时结构**：平台单次执行固定开销约 30 s（渲染 inventory + 契约探测 + 进程启动），同样 3 条只读用例直跑 pytest 3.5 s、走平台 36.0 s。适合批量跑，不适合按条点跑。

## 5. 缺陷清单与改进建议

### P0（直接影响能否用起来）

| 编号 | 缺陷 | 影响 | 建议 |
|---|---|---|---|
| P0-1 | 渲染 inventory 的 `gpus/cpu/ovs/storage` 四类恒为空，资产表无 GPU 实体 | GPU、存储、虚拟化类用例一律 setup 失败 | 资产模型补 GPU/CPU 实体与「型号字典」关联，渲染按下发；短期至少支持 `pytest.gpu_pool` 手工声明 |
| P0-2 | EHT 执行入口在 UI 上不可达 | 用户只能靠脚本调 API，违背「便捷化」目标 | 「便捷操作」页加「发起执行」：选批次/选机/模式，带二次确认 |
| P0-3 | 执行同步阻塞，无进度、无逐用例状态 | 长批次像卡死；无法判断「跑到哪、错在哪」 | 改为异步提交 + `GET /runs/{runId}` 轮询；进度按已完成 junit 事件推进；开放 cancel |
| P0-4 | real 模式下 nodeId 拼错或未绑定时，安全闸直接跳过该条（fail-open） | **可绕过 ADR-0013 直连 DUT**：实测 `test_im_vir_001_sriov_basic` 未绑定仍返回 200 并真的起了 pytest（`exitCode=4`） | 改为 fail-closed：不能确定风险就拒跑 |

### P1（影响报告质量与治理成本）

| 编号 | 缺陷 | 影响 | 建议 |
|---|---|---|---|
| P1-1 | 报告「下发命令」列恒为 `NONE` | 对外报告无法回答「下发了什么命令」 | 用例库框架按约定输出 `$ <cmd>` 行（RF 内核已有口径），平台解析 junit `system-err` 落 `command_text` |
| P1-2 | 摘要 `topFailures` 显示脱敏指纹（`步骤<n>：…11be`） | 失败聚类不可读 | 聚类键与展示名分离：展示首个样本原文 |
| P1-3 | 安全级默认 LX，469 条中 410 条未判定 | 真实执行前人工补判成本高 | 补判助手：静态扫描脚本动作 → 建议 L0/L1/L2 → 批量确认留痕 |
| P1-4 | 无失败重试与抖动标记 | 抖动被当确定性失败写入对外报告 | 支持 `retry=1` 与 `flaky` 标记，报告区分「首次失败/复测通过」 |
| P1-5 | xlsx 导出仅 15 行汇总键值 | 评审要逐条明细时不可用 | 增「用例明细」sheet（编号/结论/耗时/失败原因） |

### P2（体验与可信度）

| 编号 | 缺陷 | 建议 |
|---|---|---|
| P2-1 | 资产台账与真机无一致性校验（`inventory_lab.yaml` 写 `0000:31:00.0`，真机 `0000:45:00.0`） | 增加资产巡检：渲染前比对 `pci_bdf/mac/firmware`，不一致给黄牌 |
| P2-2 | 报告套件树按「一用例一套件」展开，59 条生成 59 个二级标题 | 同脚本目录归并成一层，或用表格 + 过滤替代树 |
| P2-3 | 摘要缺首现/复现率 | 结合历史 run 计算复现率，标出「疑似环境抖动」 |

### 用例库侧（平台不改真源，仅反馈）

| 编号 | 问题 | 建议 |
|---|---|---|
| C-1 | `IM-RDM-022` 期望优先级写死，与 `target_mask` 推导不一致 | 期望值改为从 `target_mask` 派生 |
| C-2 | `IM-NET-002` 对光模块告警零容忍，模块瞬变即红 | 判定改为「持续 N 次采样异常」，与平台重试配套 |

## 6. 本轮已修复（平台侧）

| 修复 | 说明 |
|---|---|
| `POST /api/projects/{id}/pytest/runs` | 新增 real 模式；必须 `confirmReal=true`，且目标用例全部通过 ADR-0013 安全闸（LX/L2 拒跑并点名编号） |
| `/runs/fake` 不再静默降级 | 显式传 `mode=real` 直接 400，避免「以为跑了真机」 |
| 产物登记 | 执行后登记 `junit_xml` / `pytest_report_json`，多批合并 `junit.xml`，报告侧才找得到产物 |
| metadata 落 `run_metadata` | 请求里的十项 metadata 走 HRD-02 补录机制落库，报告不再判「元数据缺失」、导出不再 400 |
| `PytestKernel.fromJunit` 失败消息 | 取 junit `message` 属性（缺省取正文首行），不再把状态名 `FAIL` 当原因 |
| 资产台账 | 按真机画像登记 gpu01/gpu02（host_key、OS、SSH 端口、每台 2 个网口的 15 项 NIC 画像） |
| 安全闸 fail-closed（对应 P0-4） | real 模式下 `nodeIds` 先行映射用例；映射不到的一律 400 点名拒跑，不再「找不到就跳过」——静默跳过等于把未判定风险的用例放进真机 |
| 重复 runId 返回 409（对应本轮发现的 500） | 执行前 `findByRunId` 判重，抛 `CONFLICT`，不再让唯一键冲突以 500 暴露；产物目录也不会被同 runId 二次写入污染 |

单测：`PytestNicRunControllerTest` 9 例（含安全闸放行/拦截、未绑定 nodeId 拒跑、重复 runId 冲突、fake 端点拒 real、通过率口径）、`PytestKernelTest` 新增失败消息用例；后端全量 1799 例 0 失败 0 错误（4 跳过）。

回归探针 `regression_gate.py`（可重复执行，结果落 `eht-real-regression-gate.json`）覆盖五条入口判据，本轮结果 **5/5 PASS**：fake 新 runId → 200 且 `planOnly=true`；同 runId 重放 → 409；real 缺 `confirmReal` → 400；real 打未绑定 nodeId → 400（fail-closed）；real 请求打到 fake 端点 → 400。

## 7. 与版本计划的关系

- `FR-v5.5-08` 此前只有 Fake/Plan-only 证据，本轮补上**真实执行证据**：链路层 15 项判据继续成立，用例层 59 条结果为 57/1/1。建议将状态由「降级达成」回写为「真实链路已验证；用例层 2 条不通过，归因分别为平台资产缺口与真源断言缺陷」——**状态变更需大师确认后落文档**。
- 新增遗留（建议编号 L-55-08 起）：真实执行入口 UI 不可达、执行无进度、GPU 资产实体缺失、报告命令列空、摘要指纹不可读、xlsx 无明细、无重试与抖动标记、410 条安全级未判定。

## 8. 未做与不做假

- **未执行 2 条 L2（SR-IOV）**：ADR-0013 拦截，需单独授权后按「建 VF → 验证 → 归零」流程执行。
- **未做 UI 端到端截图验收**：本机无 CDP 客户端依赖，不拿「接口 200」冒充界面验收。可视化结论来自接口行为与前端源码核查，UI 交互验证列为遗留。
- **未测量效果类指标**（超时基线、每用例预期耗时、Top8 成功率）：本轮只采集了单次耗时，样本不足以定基线。
- gpu03 未启用（gpu01/02 满足 2 台资源池需求）；gpu04 按要求未使用。
