## 2. 菜单差异的事实底数

### 2.1 两棵树的结构 [核实]

前端菜单唯一真源是 `frontend/src/config/navigation.ts`，其中并存三棵树：

| 常量 | 行号 | 用途 | 一级组数 | 叶子数 |
|---|---|---|---|---|
| `GLOBAL_NAVIGATION` | 131 | 跨项目（`/g/*`） | 5 | 见 §2.4 |
| `NAVIGATION` | 232 | 标准工程（`kind=standard/platform`） | 7 | 28 |
| `PYTEST_SUITE_NAVIGATION` | 484 | pytest 用例库工程（`kind=pytest-suite`） | 4 | 9 |

选择入口是 `navTreeFor(mode, kind)`（第 591 行），只有一个三元判断：

```ts
return kind === 'pytest-suite' ? PYTEST_SUITE_NAVIGATION : NAVIGATION
```

项目 95 `EHT-PYTEST-LIB` 的 `kind = pytest-suite`，所以拿到的是 4 组 9 项那棵树。**这就是「感觉少很多」的直接原因**：一级菜单少 3 组（7→4），叶子少 19 项（28→9），加两侧各 2 项「系统设置」后为 **30 项 vs 11 项**。

### 2.3 「只是没入口」还是「真的不能用」[核实]

这一条决定了改造成本，必须查清：

| 检查项 | 结论 | 证据 |
|---|---|---|
| 路由是否按 `kind` 设防 | **否**。`src/router/index.ts` 全文 82 处 `path:`，`grep -n "kind" src/router/index.ts` **零命中** | 命令输出 |
| 前端除导航外是否用 `pytest-suite` 做分支 | 除 `navigation.ts` / `App.vue` 注释 / `navigation.spec.ts` 外**无其他用法** | `grep -rn "pytest-suite" src/` |
| 后端 `ProjectKind` 是否参与鉴权或接口裁剪 | **否**。仅 `ProjectService:122` 建项目时落库 + `ProjectKind.of()` 校验取值 | `grep -rn "ProjectKind" backend/src/main/java` |
| 结论 | **页面全部可达，只是没有菜单入口**。pytest 工程手输 `/assets` 能正常打开并增删设备 | 推导自以上三条 |

也就是说：*差异 100% 在「入口可见性」，0% 在「能力可用性」*。这既是好消息（补入口成本低），也暴露一个真问题——**用户不知道这些页面存在**，因为界面上根本没有路标。

### 2.4 为什么当初要这么做 [核实]

`PYTEST_SUITE_NAVIGATION` 的设计注释（第 468–483 行）写明了动机，对应的需求号是 `FR-v5.2-07 / W52-08`：

> `pytest-suite` 工程里没有台架资产、没有环境拓扑、没有维护恢复——这些页面对它是纯噪音，还会让新用户以为「要先配资产才能跑 pytest」。

这个判断**一半成立、一半不成立**（见 §3）。同时它被两处机制钉住：

| 机制 | 内容 | 影响 |
|---|---|---|
| 单测 `navigation.spec.ts` | 有一条 `pytest 树不出现资产/环境/维护/节点/计划入口`，**显式禁止** `/assets`、`/environment`、`/maintenance`、`/nodes`、`/plans`、`/sync` 六个前缀 | 补入口必须同步改断言 |
| 门禁 `tools/check_nav_kind.py` | `EXPECTED_LEAVES = 39`（三棵树叶子去重后的总数）+ 孤儿叶子检测 | 叶子数变化必须显式改基线，**这是好事**：入口变少/变多都会留下可见提交 |

## 3. 被裁掉的项，对 pytest 工程到底有没有用

判定口径：**看这个 pytest 工程在真实链路上有没有产生对应的数据/约束**，而不是看「这页属于哪个域」。

### 3.1 确认是缺口的三项 [核实]

| 项 | 为什么 pytest 工程需要它 | 硬证据 |
|---|---|---|
| 资产-设备 | 真实执行前必须登记 DUT 与网口画像；`PytestEnvRenderer` 渲染的 `inventory.yaml` 直接来自 `device` / `device_port` 表 | 本次 EHT 真实执行，61 条用例要跑就得先入库 gpu01/gpu02 + 4 个网口；我是**绕过 UI 直接调 `POST /api/devices`** 完成的（`docs/evidence/v5.5.0/eht/real/raw/setup_real_assets.py`） |
| 资产-凭证 | `PytestEnvRenderer` 写 `${ENV:PYTEST_SSH_USER/PASSWORD}` 引用，但「哪个工程用哪套凭据」需要有人配 | 后端 systemd 靠 `EnvironmentFile` 手工注入；界面上无处可配 → 换机器就得改 systemd 单元 |
| 报告-对外报告 | 大师本轮目标原话就含「执行报告 / 测试报告的生成和质量评估」；`/reports` 是内部分析报告，`/test-reports` 才是对外口径页 | pytest 树只有 `/reports`；`export_reports.py` 只能调 API 导出 pdf/docx/xlsx |

### 3.2 疑似缺口、需实测确认的四项 [推断]

| 项 | 疑点 | 待验动作 |
|---|---|---|
| `/sync` 存量同步 | 页面语义是「用例库预览→冲突→执行→回滚」，pytest 工程有 469 条台账要跟真源同步，正是它 | 用工程 95 调 `projectSyncApi` 预览，看是否返回正常差异集 |
| `/plans` 测试计划 | pytest 树里保留了 `/cases/sets`（用例集），而计划编排的对象就是用例集；有集无计划＝只能手动点跑 | 建一个 pytest 工程的定时计划，看派发是否走 pytest 内核 |
| `/environment/collect` | 采集页是核对真机与台账差异的正规入口；本轮已发现 `inventory_lab.yaml` 的 PCI 地址与真机漂移（`0000:31:00.0` vs `0000:45:00.0`） | 打开工程 95 的采集页，看是否按 `kind` 被拦 |
| `/assets?tab=links` | 用例 metadata 的必填项 `LINK` 需要链路字典；没有链路页，`LINK` 只能写自由文本 | 查 `LINK` 取值是否有字典约束 |

### 3.3 裁掉是对的 [核实]

以下项在 pytest 工程里确实是噪音，**不建议补**：`/nodes`（pytest 在本机起子进程，不派发到执行节点）、`/maintenance/{principles,records,recover}`（平台级兜底）、`/environment/{topology,prepare,analysis,connections}`（台架拓扑与连接对纯用例库无意义）、`/projects/new`（项目内再建项目）、`/workspace`（项目搬迁导出，用例库走 git 同步）。

### 3.4 小结：问题的真答案

「少」是**设计使然**，但设计里有 **3 个硬缺口 + 4 个待验项**。所以答案不是「全量对齐」，而是：

1. **该补的补**（资产设备/凭证、对外报告、存量同步、可能还有计划与采集）；
2. **该藏的继续藏**（节点、维护、环境拓扑）；
3. **把「硬编码第二棵树」升级成「规则驱动」**——否则每加一个工程类型就要复制一棵树，差异永远靠人肉维护，下次还会有人问同样的问题。

## 4. 六维现状盘点（承接 v5.5.0 真实执行评估）

来源：`docs/plan/v5.5.0-EHT真实执行-评估与改进报告-20261113.md`（59 条真实执行 57/1/1）+ 本次补充核实。

| 维度 | 现状（已核实事实） | 主要短板 | 证据 |
|---|---|---|---|
| 系统架构 | `kind` 只做界面裁剪，不做能力协商；三棵树靠常量维护；内核 SPI 已解耦（`kernel.default=pytest`） | 信息架构与能力模型脱节：**能力有、入口无** | §2.2、§2.3 |
| 软件设计 | 报告链路 `parse→detail→tree→summary→export` 完整；安全闸 ADR-0013 已 fail-closed | 菜单可见性是硬编码，非规则派生 | `db10f39`、`navigation.ts` |
| 程序实现 | 执行入口 `POST /runs` real 双闸；失败消息取 junit `message`；重复 runId 409 | 渲染 `gpus/cpu/ovs/storage` 恒空；固定开销 ~30s；执行同步阻塞 | v5.5.0 报告 §5/§6 |
| 测试体系 | 后端 1799 例全绿；API 契约 405/336；门禁 52 步；`check_nav_kind` 有基线 | 性能门禁**无采样时 SKIP 即绿**（假绿风险）；UI 无 E2E 冒烟 | `check_perf_budget.py` 头注释 |

## 5. 行业最佳实践对标

> 本节为 **[推断]** 级：属通用工程实践认知，未在本仓库逐条实测。写在这里的作用是给 PRD 的验收判据找参照，不是结论。

| 主题 | 通行做法 | 本平台现状差距 | 落到哪条 FR |
|---|---|---|---|
| 信息架构 | 导航由「能力/数据」驱动（RBAC + 特性开关），而非按产品线复制菜单 | 硬编码第二棵树 | FR-v5.6-01 |
| 渐进披露 | 首屏只给闭环必需项，其余按使用浮现并可搜索（Cmd+K） | 无搜索、无「为什么不显示」解释 | FR-v5.6-04 |
| 长任务交互 | 提交即返回 `202 + taskId`，进度事件流（SSE/轮询），支持取消 | 同步阻塞，无进度、无取消 | FR-v5.6-11~13 |
| 可观测性 | 关键路径 RED 指标（Rate/Errors/Duration）+ 明确 SLO | 有慢查询日志，无执行链路 SLO | FR-v5.6-41 |
| 测试报告 | 报告是**可审计产物**：命令、原始输出、附件、指纹一致 | 命令列恒 `NONE` | FR-v5.6-21 |
| AI 增强 | AI 只做「有证据的归纳」，不产出无源结论（fact-verifier 兜底） | 已有 `AiFactVerifier`，但输入被指纹污染 | FR-v5.6-31 |
| 发布工程 | 构建产物内嵌构建信息，部署后自动校验版本一致性 | 靠人工记得重启（已踩过坑） | FR-v5.6-44 |

## 8. 落位说明（为什么暂时放 `docs/plan/`）

`docs/process/版本开发流程.md` §3 要求六份产物放在 `docs/release/<version>/`。本版当前**只完成 ①~⑤**，
第 ⑥ 道测试报告按大师指令尚未开工。若提前建 `docs/release/v5.6.0/` 目录，`tools/check_release_docs.py`

因此按仓库既有先例（v5.1–v5.5 的计划文档同样在 `docs/plan/`）先落此处；待大师授权、第 ⑥ 道执行完成后，
五份文档整体迁入 `docs/release/v5.6.0/` 并补 `05-TEST-REPORT.md`。迁入动作本身列入 DEV-PLAN 阶段五。
