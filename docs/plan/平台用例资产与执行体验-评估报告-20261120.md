## 0. 结论先行

**一句话**：这 13 条不是 13 个孤立的功能点，而是同一个结构病的 14 个症状——**「用例资产」没有一等对象，导致同一批数据被三套页面用三种口径呈现；「执行可信」没有单一裁决点，导致状态显示与执行拦截各说各话；「全局/项目」各写一套，导致同一功能两套行为。**

**四条最硬的结论**：

1. **用例跑不起来不是感觉，是三条硬拦截同时成立**：新建用例默认 `LX`（阻断执行）→ 未绑定脚本整单 400 → 绑定状态 `BOUND_VERIFIED` 在运行期不可达（无确认入口）。三条都在后端强制执行，前端无任何按钮能解开任何一条 `[已核实]`。
2. **优先级列已经在承载两套语义**：EHT 用例库 469 条里，`T0/T1/T2/待评审` 共 469 条（100% 非 `P0–P3`）。代码注释声称导入时已归一（`CaseImportService.java:66,266-273`），**库内实际未归一**——这是「文档说做了、数据里没有」的又一起同类事故 `[已核实]`。
3. **「我参与的项目」少项目是可定位的 SQL 口径差**：可见性 SQL 是「成员 ∪ 负责人 ∪ 用户组授权」三源，而卡牌的 `own/joined` 只覆盖前两源，经用户组授权进来的项目被静默剔除 `[已核实]`。
4. **拓扑页没有图**：`/environment/topology` 全文无 `<svg>`、无 Canvas、无坐标，只有 CSS 圆点图例 + 边表，文案却写「图上 N 条」。真正在画图的是 `/environment/connections` 的手写 SVG（固定网格、无缩放拖拽）`[已核实]`。

## 3. 逐条评估

### R01 公共用例与 EHT pytest 库：组织与呈现不一致

**诉求**：两边用例的组织方式、呈现形式、详情字段应一致。

**现状**（`[已核实]`）：

| 维度 | 全局公共用例 `/g/cases` | EHT pytest 用例库 `/eht/cases` |
|---|---|---|
| 组件 | `global/GlobalCasesView.vue` | `eht/EhtCaseLibraryView.vue`（全文 131 行） |
| 数据源 | project 88（`kind=platform`），730 条 | project 95（`kind=pytest-suite`），469 条 |
| 布局 | 中栏分类树 + 右表 + 表下详情 | 单张平铺表 + 表外复选框列表 |
| 列 | 8 列（编号/标题/脚本/分类/优先级/状态/版本/操作） | 4 列（编号/标题/优先级/评审态） |
| 筛选 | 关键词 + 生命周期 + 脚本状态 + 分类 | 关键词 + 优先级 |
| 分页 | 服务端分页 | **固定 `size: 50`，无分页 UI** |
| 详情 | `DetailDock` + `CaseDetailPanel`（27 字段） | **无详情** |
| 批量 | 无勾选 | 勾选只用于「已选 N 条」文案 |

证据：`router/index.ts:109-120,330-333,486-498`（三个独立组件，无 alias）；`GlobalCaseService.java:189-247`（`WHERE project_id = ?` 硬绑平台单例）；`EhtCaseLibraryView.vue:38,63-68,101-112`。

**根因**：EHT pytest 工程是 v5.1 的「工程只读视图」，从未纳入「用例资产」域；公共库又硬绑 `kind=platform` 单例，`pytest-suite` 项目天然进不来。**不是漏做，是缺一个「用例库」对象。**

**判定**：未达成。

**方案要点**：把「用例库」提为一等对象（`library = 项目` 的一种视图），抽 `CaseLibraryView` 统一渲染，用 `libraryId` 切换（公共库 / ED202 / EHT pytest 工程 / 项目库）；后端 `/api/case-libraries/{id}/cases` 复用同一查询与同一 DTO。详情可直接复用 `CaseDetailPanel`——它本来就是全局/项目两边共用的（`CaseDetailPanel.vue:76-145`），这是现成的最佳基线。

**邻近影响**：EHT 库「469 总数只显示 50 行」本身是独立缺陷（见 O08），统一后自动消失。

### R02 筛选后按选中用例建集

**诉求**：筛完用例后，把选中的用例直接建成用例集。

**现状**（`[已核实]`）：

- 项目库 `/cases` **已有**：表头三态勾选 + 跨页选择（`useServerSelection`）+ `SelectionBar` 里的 `AddToSetButton`，支持「加入已有集 / 新建集」；提交流程是 `create` 建空集 → 再 `batchAddItems` 或 `addByBindingFilter`（`CasesView.vue:963-993,1487-1503`；`AddToSetButton.vue:66-78`）。
- 公共库 `/g/cases` **完全没有**：无勾选列、无 `SelectionBar`、无建集入口，行点击只开详情（`GlobalCasesView.vue:200-207`）。
- 平台集**加成员只能填数字 caseId**（`GlobalCaseSetsView.vue:366-379`），没有搜索多选。
- 后端有「批量加成员」「按绑定条件加成员」，但**没有「建集并写入成员」的原子接口**：`create` 只收 `setCode/name/description`（`TestSetController.java:106-111`；`TestSetService.java:114-145`）。

**判定**：部分达成（项目侧达成，公共侧未达成）。

**方案要点**：① 组件级复用 `useServerSelection` + `AddToSetButton`，不要复制；② 后端补事务化的 `createWithItems`，避免「建了空集、加成员失败」留下脏集；③ 平台集补 `binding-filter` 版本，使「按脚本状态筛出来的用例」也能一键成集。

**邻近影响**：`FR-v5.24-01` 已规划同一能力（判据「≤3 个 API 调用」），本项应并入 v5.24 而不是新开——否则同一功能两条线。

### R03 示例用例集改「001-中文名」

**诉求**：`SAMPLE-XX` 改成 `001-中文类名称`；用例集与成员用「中栏列表 + 右栏成员」。

**现状**（`[已核实]`）：

- 32 个样例集，编号 `SAMPLE-1` … `SAMPLE-32`，名称 `<一级分类> · 样例`（数据库实读）。
- 命名不是硬编码也不是种子 SQL，而是**运行时派生**：`SampleSetSeeder` 按 `case_category` 一级分类逐条生成 `SAMPLE-n` 与「分类名 · 样例」（`SampleSetSeeder.java:67-71,92-99,116-125`）。
- 触发入口是全局用例集页的「按一级分类重建样例集」（`GlobalCaseSetsView.vue:286-288` → `PlatformCaseSetController.java:122-127`）。
- 排序隐患：按字符串排 `SAMPLE-10` 会排在 `SAMPLE-2` 前面。

**判定**：未达成（命名不符）；且因为编号是派生的，改名必须同时改 Seeder 与存量数据。

**方案要点**：`set_code` 用 3 位序号 `001`–`032`（保留唯一键），`name` 用纯中文分类名。Seeder 改成「先按分类取稳定序号，再拼 code」，迁移脚本重写 32 条存量并保留回滚。新建集的自动编号与 `FR-v5.24-05`（前缀+序号）同源，**编号生成器只能有一个实现**。

### R04 用例集「中栏集列表 + 右栏成员 + 成员详情」

**诉求**：中栏是用例集列表，右栏是成员列表，成员可打开看详情。

**现状**（`[已核实]`）：

- 布局是两栅格 `320px + minmax(0,1fr)`（`CaseSetWorkspace.vue:107-113`），≤1400px 时右区整体变抽屉（`:33-56,141-150`）。
- 成员列表是**手写 `<ul>` + 8 列 grid**，不是表格组件（`CaseSetsView.vue:1045-1063,1310-1313`）。
- 成员详情是**内联停靠区**，注释明确写「不是弹窗 / 抽屉 / 跳页」（`CaseSetsView.vue:1100-1103`）；点击行后在列表下方展开。
- 成员列配置有独立文件（`config/caseSetMemberColumns.ts:67-78`），但**两个用例集页面都没有引用它**，列表标记是手写的——配置与实现已经脱钩。

**判定**：基本达成（三块能力都在），形态与用户预期不符：长列表里点行后详情出现在下方，用户会觉得「点了没反应」。

**方案要点**：成员详情改为**右侧抽屉**（overlay），与用例详情同构；列表保留一行摘要（编号/标题/脚本态）；窄屏回落为全屏抽屉。顺手把 `caseSetMemberColumns` 接回列表，消除「配置写一套、渲染写一套」。

### R05 执行计划与测试计划合并

**诉求**：两个概念合并，合并后可手工发起执行，也可按计划发起。

**现状**（`[已核实]`）：

- 库里**只有一个实体** `execution_plan`（`PlanRecord.java:13-29`），状态只有 `ENABLED/PAUSED`（`PlanStatus.java:6-23`）。
- `/plans`（菜单叫「测试计划」）= 持久化计划：cron、时区、依赖 DAG、暂停/恢复、批量启停、立即触发（`PlansView.vue:581-609,630-637`）。
- `/execution-plans`（菜单叫「执行计划」）= **无状态即时发起台**：预检 → 预览 → 确认发起，只写选择快照，不建计划（`ExecutionPlansView.vue:250-283`；`RunLaunchController.java:129-150`）。
- 代码注释把口径钉死了：「本页 = 现在就把这一批用例跑一遍；`/plans` = cron 定时编排。两套模型不同，所以是两页，**不合并**」（`ExecutionPlansView.vue:5-6`）。
- 菜单两个词条并存：`executionPlans: '执行计划'`、`runsPlans: '测试计划'`（`zh-CN.ts:479-482`）。

**判定**：未达成（用户视角就是一件事被拆成两个菜单）。

**方案要点**：以 `execution_plan` 为唯一实体，`/plans` 合并为「计划」页，行内提供「立即执行」；把「临时跑一批（不建计划）」收成页面顶部一个按钮，复用同一确认面板（`FR-v5.24-04`）。数据模型不用改——`cron` 本来就可空。

**风险**：现存的计划里有一个 `cron='0 * * * * *'`（每秒）且已 `paused`。合并前必须补 cron 校验与「未来 3 次」预览，否则误配会把执行队列打爆。这条单列为 O04。

### R06 执行内核：状态观察、自动/手工移除、节点固化复用

### R09 脚本状态机与优先级「失控」

**诉求**：状态机、优先级等状态失控，前端没按钮，后端不知有没有处理逻辑，导致用例无法执行。

**现状**（`[已核实]`，四个独立断点）：

**断点 1：有一个死字段。** `test_case.status TINYINT DEFAULT 1` 只在校验 INSERT 时写死 1，SELECT 从不读、从不更新（`V1__baseline.sql:278`；`TestCaseRepositoryJdbc.java:32-38,274-278`）。它没有任何语义，但存在于表结构里，容易被误当成「启用/停用」。

**断点 2：评审态有按钮、执行不看。** `review_status` 四态齐全，前端有「提交/通过/驳回」（`CasesView.vue:715-773`；`TestCaseService.java:305-335`），但 `application/execution/**` 里**没有任何 `review_status` 判断**——「已批准」对能不能跑毫无影响。

**断点 3：验证态不可达。** 绑定四态 `BOUND_VERIFIED/BOUND_UNVERIFIED/UNBOUND/NOT_APPLICABLE`（`CaseScriptView.java:24-31`），但同步写入时 `verified` 写死 `false`（`PytestBindingSyncService.java:170-172`），仓储的 `update` **全仓零调用**，也没有任何「确认绑定」的端点。结果：61 条绑定全是 `BOUND_UNVERIFIED`，`BOUND_VERIFIED` 在运行期**永远不可能出现**。

**断点 4：筛选条件被静默丢弃。** 「按筛选执行」的后端白名单只认 `domain/priority/status/caseKind`（`RunTrustJdbcStore.java:42-46`），非白名单键直接跳过（`:258-265`）；而前端会带 `reviewStatus`、`bindingState`（`CasesView.vue:454-455,1036-1037`）。**用户以为按条件跑了一部分，实际跑的范围更大**——这是比「跑不了」更危险的失效。

**再加上优先级词表分裂**：EHT 469 条全是 `T0/T1/T2/待评审`，而 `Priority` 枚举只认 `P0–P3`，非法值直接抛（`Priority.java:9-20`）。导入代码的注释声称「T0/T1/T2 归一为 P0/P1/P2，原值保留」（`CaseImportService.java:66,266-273`），但**库内数据没有归一**——文档承诺与数据事实不一致。且「待评审」被塞进优先级列，承担了本该由 `review_status` 承担的职责（覆盖率统计直接按「优先级=待评审」取数，`PytestCoverage.java:10-19`）。

**判定**：失控确认，且能定位到四个具体断点 + 一个词表分裂。

**方案要点**：
1. **先定词表**（D-05）：`T0→P0`、`T1→P1`、`T2→P2`；「待评审」迁到 `review_status=pending`，`priority` 置空或 `P3`；
2. 补「人工确认绑定」接口 + UI，让 `BOUND_VERIFIED` 可达；
3. 评审态二选一：要么接入执行门禁（`approved` 才可跑），要么从执行链路彻底移除——**不能「显示有状态但不生效」**；
4. 执行筛选与列表筛选同源（`reviewStatus`、`bindingState` 必须生效，或前端不展示）；
5. 删除死字段 `test_case.status`，或给它真语义。

**这是「用例跑不起来」的主因链**：LX 默认阻断 → 未绑定整单 400 → 验证态不可达 → 用户无任何按钮可解。

### R13 公共用例分类树：子项跑到母项左边

- 另有两处布局债：外层栅格 `220px` 而组件写死 `width: 240px`，横向溢出 20px；`GlobalCasesView.vue:573-608` 还留着上一代侧栏的死样式（模板已不引用）。
- 该缩进**没有任何测试约束**（`CaseCategoryNav.spec.ts` 未覆盖 padding/indent）。

**判定**：缺陷确认。

**方案要点**：二级 `<ul>` 给 `24px` 缩进或给二级行补一个 `20px` 占位（与 caret 同宽），使文字基线对齐；宽度统一为 `220px` 或栅格改 `240px`；删死样式；补一条视觉回归断言（子项文字 x > 母项文字 x）。

### R14 「我参与的项目」与项目总览不一致

**诉求**：要把与我有关的全部项目列出来，至少和项目模式的项目总览一致。

**现状**（`[已核实]`，根因已定位到 SQL）：

- 两处**调的是同一个接口** `/api/projects/cards?window=7d&current=`（`projectCards.ts:50-52`），不存在「不同接口」问题。
- 「我参与的」过滤在**前端内存**里做：`card.own === true || card.joined === true`（`WorkbenchView.vue:58-64`）。
- 后端可见性是**三源并集**：`project_member` ∪ `project.owner_id` ∪ `project_group_role`（经用户组授权）（`ProjectVisibilitySql.java:24-38`）。
- 但卡牌的 `own/joined` 只来自 `project.owner_id` 与 `project_member`（`ProjectCardRepositoryJdbc.java:70-72`；`ProjectCardService.java:106-107`）。
- 所以：**仅通过用户组授权进来的项目，`own=false`、`joined=false`，在「我参与的」里被静默剔除**。
- 附带口径差：管理员在项目总览看到全量（`AccessControlService.java:179-185`），在「我参与的」只看到自己的 `own||joined` 子集——文案里已注明，但用户仍会认为「不一致」。
- 现成正确实现已经存在：`PROJECTS_OF_USER` 三源 + `OWNER/MEMBER/GROUP` 来源标注（`ProjectVisibilitySql.java:96`），经 `/api/iam/relations` 暴露，只是没被「我参与的」用。

**判定**：缺陷确认。

**方案要点**：后端加 `?scope=mine`，直接用三源查询并返回来源标注；前端删掉内存过滤；管理员在「我参与的」里明确文案「管理员的全平台可见项目不在此列」，或干脆给管理员单独一个「全部项目」页签。

## 5. 双轨台账（全局 vs 项目）

> 判据：**同名能力、同一目的、两套实现** = 双轨；**同一能力、不同作用域** = 合理差异，但交互必须同构。

| 能力 | 全局侧 | 项目侧 | 性质 | 处置 |
|---|---|---|---|---|
| 用例列表 | `/g/cases`（GlobalCasesView） | `/cases`（CasesView） | 双轨（同一目的） | 统一组件（R01） |
| 用例集 | `/g/case-sets`（手写列表） | `/cases/sets`（DataTable） | 双轨 + 功能鸿沟 | 统一工作区（R12） |
| 资产 | `/g/assets`（采集/批量删） | `/assets`（端口/链路/拓扑） | 作用域差异 + 操作列不一致 | 保留差异，统一操作列顺序与空态 |
| 项目 | `/g/projects` | `/workbench` | 同接口不同过滤 | 修 R14 |
| 模板 | `/g/templates`（模板中心，`project_template`） | `/reports/templates`（报告模板，`report_template`） | **不是同一个东西，只是同名** | 术语区分（O11），不合并 |
| 设置 | `/g/settings`（系统设置 6 项） | `/settings`（项目设置） | 作用域差异 | 保留，统一表单控件与保存反馈 |
| 用户/权限 | `/g/iam/users`（全功能） | `/settings/users`（只读页） | 双轨（项目侧残缺） | 明确「项目侧只读」并在页面说明，或直接链到 IAM |

**结论**：7 组里 3 组是真双轨（用例、用例集、用户），2 组是同名不同物（模板），2 组是合理作用域差异。**先治 3 组真双轨，成本最低、收益最大。**
