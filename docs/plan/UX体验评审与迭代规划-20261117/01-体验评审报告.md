## 一、一句话结论

**平台"能力已经齐了、链路也真的通了"——我确实完成了采集、建集、执行、出报告的完整闭环；但"用户能不能自己走通"还有明显断点：三个人工卡点（报告无法对外交付、大批用例静默跳过、报告无法查看）会让真实用户在半路卡死，而这些卡点的原因后端都算清了，只是没告诉用户。**

打分（5 分制，用户视角）：

| 维度          | 分   | 说明                                         |
| ----------- | --- | ------------------------------------------ |
| 功能完整性       | 4.0 | 六步链路全部具备，环境采集/执行/导出都是真链路，不是壳子              |
| 可发现性（能不能找到） | 2.5 | 菜单两套、标题与菜单名不符、关键入口藏在行内文字链接里                |
| 可理解性（看不看得懂） | 2.0 | 术语密集（需补判 / 不互斥 / D12 双口径 / exit 1），数字缺口径说明 |

| 视觉与排版       | 3.0 | 整体专业，但多处按钮错位、表头错位、右侧大片留白                   |

## 三、短板清单（按对用户的伤害程度分级）

### P0 — 阻断型（用户完不成核心任务，必须修）

**P0-1 执行 → 报告 → 对外导出，这条终点链路是三处断的**

- 现象：发起执行时没有任何 metadata 采集入口 → 产出的报告首屏是「未判定」，并标注「报告当前不可对外交付」 → 想导出时被别人为红线拦住。  
  |  |  |  |  
  | --- | --- | --- |
- 实测：执行报告页「导出 PDF / 导出 Word」是 disabled（这条做对了，且写了缺哪 9 项）；**测试报告页同样的缺项场景直接静默失败**——`/api/test-reports/38/export?format=html|pdf|docx` 全部返回 400，body 写明原因，前端未展示任何提示，我干等了 100 秒。
- 影响：这是"测试报告交给客户"这一**唯一对外交付动作**，当前走不通。而且用户没有任何"我该去哪补"的指引。
- 建议：
  1. 采集前移到**发起执行时**（或在项目设置里一次配好 `CASE_ID/QA_PROJECT/DUT/LINK/SW_BUILD/BASELINE/OPERATOR`），执行产物自动带上，而不是事后逐份报告补 10 项；
  2. 测试报告页的导出失败必须把后端 message 原样弹出（`40001` 的文案已经是给用户看的）；
  3. 测试报告页补「导出内部版」入口（后端已支持 `mode=internal`，前端没暴露），让用户至少有路可走。

**P0-2 61 条用例被静默跳过，平台不解释**

- 现象：我发起 61 条，界面先显示「已完成 0/61」，跑完得到：运行记录「5 / 4 / —」、执行报告「总数 70、失败 4、跳过 61」、报告选择器「70 条用例」。**同一个 run，界面上出现 61 / 9 / 70 三个数**。
- 事后靠 PDF 才看到真相：跳过的用例原因是「本用例未下发外部命令」（fake 模式下没绑定脚本/无命令）。
- 影响：用户第一反应是"我的用例怎么全跳了？"，而界面上**没有任何地方能回答"为什么跳过 61 条"**——最大的数字（61）恰恰是最没解释的。
- 建议：报告/运行记录里把 SKIP 按原因归类（未绑脚本 / 未下发命令 / 环境不允许 / 主动跳过），并提供一条"补齐方式"的链接；口径统一为"应跑 N / 实跑 M / 跳过 K（原因）"。

**P0-3 测试报告"看不见"**

- 现象：测试报告列表里**标题不可点**，行内只有「编辑 软删 [格式▾] 导出」；详情页 `/test-reports/38` 存在但入口缺失。
- 影响：导出又被 P0-1 拦住时，用户**完全没有任何途径看到报告内容**。
- 建议：标题做成链接直达详情；操作列加「查看」。

### P1 — 严重（能走通但很费劲、或容易误操作）

**P1-1 用例集构建效率不可用（对 469 条用例的工程）**

单选、一次加一条、"添加用例"要重复 N 次；候选下拉只能精确搜，滚动条不可见、底部条目被裁掉半行、无"共 N 条"。要给 469 条用例建集，实际操作是"搜一次加一条"×N。  
建议：改为「从用例库勾选 → 批量加入」（复用用例库已有的多选表格），候选下拉加计数与"已选 N 条"。

**P1-2 发起执行无二次确认，误点即跑**

pytest 工程页点「发起执行」立即提交（我这次真实跑了 4 分 01 秒）；而用例集页「立即执行」**有**确认框。同一件事两种安全级别。且确认框（用例集那个）不显示"用哪套脚本、跑在哪台设备、fake 还是 real"。  
建议：统一走确认框，并在确认框里列出模式/设备/用例数/预计时长。

**P1-3 执行完就"失联"**

提交后页面上只有一行易失的状态文字；刷新/离开后完全找不到"我刚发起的那次"。执行协调卡显示"在跑 1"，但那个 1 点不进去。  
建议：提交成功后在原位留一个持久卡片「本次运行 EHT-xxx · 进度 32/61 · 查看 →」，并给运行记录/报告直达链接。

**P1-4 导出成功的反馈等于没有**

内部 PDF 导出实际成功了，但界面上只有按钮下方一行小字「已生成 PDF：571.2 KB，sha256 e71a4525bfe…」+ 一个「下载文件」链接，**不弹提示、不自动下载**，且 64 位 hash 把按钮行挤乱。  
建议：导出完成 toast + 自动触发下载；hash 收进"详情"折叠。

**P1-5 证据层字段粘连（确定的渲染 bug）**

测试报告详情「证据层」每条显示成 `IM-FUN-020IM-FUN-020 junit.xml 已校验`——用例编号重复两遍且无分隔符。70 条全部如此。

## 四、横向问题（比单条更重要）

1. **"后端算清了，前端没说"是系统性毛病。** 测试报告导出 400 的 message 是一段完整可读的中文解释，前端吞了；61 条 SKIP 的原因后端也记了，报告不展示；执行完 run_id 有了，却不在发起页留住。**平台不缺信息，缺把信息送到用户眼前这一层。**
2. **同一件事两套做法。** 执行有确认/无确认、导出有拦截说明/静默失败、报告能看/不能看——用户学到的规则会立刻失效。
3. **口径随页面漂移。** 61 / 9 / 70 三个数；"通过率 7.1%"与"成功率 0%"并存；"近 7 天通过率 —"。任何一个数字被客户追问，现场都答不上。
4. **术语是给实现者写的。** 需补判、不互斥、源表无值、内核返回失败（exit 1）、D12 双口径、缺证据——一个懂测试但不懂本系统的负责人，读不懂 60%。
5. **信息架构双轨。** 全局和项目是两套菜单 + 同名页面（都叫"项目总览"），切模式后顶部仍挂项目选择器。

## 五、值得保留的亮点（别在重构中弄丢）

1. **命令白名单公开**（环境采集把 10 条真实命令摆在页面上，并声明"证据里逐条记着"）——这是同类产品少见的诚意。
2. **"先在界面上看能不能跑，再决定发不发"**（预检四项齐备 + 台架就绪度）——把"跑之前先判"做成了产品动作。
3. **缺项红线**：报告标「不可对外交付」、导出禁用并写明缺哪 9 项——宁可拦也不糊弄，方向完全正确（只是要贯彻到所有页面）。
4. **内部版/对外版分家**，PDF 页眉打「内部版 · 含缺失项，不可对外」，文件名带 `_internal_DRAFT`。
5. **D12 双口径并列**（含待评审 13% / 排除待评审 10.3%）——思路专业，只需换成人话。
6. **AI 叙述的"逐项核对"声明**（"正文数字会与报告证据逐项核对"）。
