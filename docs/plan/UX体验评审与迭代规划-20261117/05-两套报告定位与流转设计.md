# 两套报告的定位、分离与流转（设计依据）

> 文档性质：产品设计依据，上游为大师 2026-11-17 13:18 口径补充 + `01-体验评审报告.md` 实测证据。
> 下游：`v5.23.0/PRD.md`（FR-v5.23-18 定稿）、`v5.28.0/PRD.md`（新增 FR-07/08）。
> 本文回答一个问题：**执行报告与测试报告要不要分离？答案是必须分离，但分离的层次要说清。**

---

## 1. 大师给的口径（原文要点）

| 维度 | 执行报告 | 测试报告 |
|---|---|---|
| 谁看 | **测试人员自己** | **合作伙伴 / 客户**（内部先预览，OK 后导出） |
| 关注什么 | 当前项目、当前用例或用例集的**执行情况** | 这些用例对应的**测试环境、工具**，以及产品的**功能 / 性能 / 稳定性** |
| 用来干什么 | 失败了查原因 → 修复 → 重新执行 | 交付证明 |
| 流转 | 自取自用，随时重跑 | 内部预览 → 审核通过 → 导出发出 |

这两句话已经把产品边界划清了：**一个是工作台，一个是交付物。**

---

## 2. 结论：必须分离，且要分离到底

| 理由 | 说明 |
|---|---|
| 读者不同 | 前者是"我"，后者是"客户 + 我的审核人"。同一份文档不可能同时服务两种读者的信息密度与信任要求 |
| 对象不同 | 前者是**一次运行**（run）；后者是一**批交付内容**（用例范围 + 环境 + 版本 + 时间窗），后者通常由多次 run 支撑 |
| 生命周期不同 | 前者随 run 生随 run 灭，可软删、可重跑；后者要定稿、要版本、要留档、要能追溯"当时用的哪版模板" |
| 合规要求不同 | 后者对外，必须脱敏（执行机路径、内核命令、内部 ID）；前者对内，必须完整（不然没法排障） |
| 失败语义不同 | 前者失败是**工作信号**（去修）；后者失败是**结论**（要写清楚什么没过、影响什么） |

**所以：分离不是"要不要"的问题，是"现在分离得够不够彻底"的问题。**

---

## 3. 当前实现：分离了一半

### 已经分离的（做对了，别动）

| 能力 | 证据 |
|---|---|
| 数据模型分离 | `test_result` / run 级报告 vs `test_reports` 独立表（含快照、版本、状态机） |
| 渲染分离 | `TestReportService.render(id, external)` → `renderer.internal(snapshot)` 与 `renderer.external(...)` 两条路径 |
| 快照自包含 | 冻结后只读快照，不回查 run、不回查当前模板（"冻结后自包含"是硬保证） |
| 状态机 | `DRAFT → FROZEN → REVOKED / ARCHIVED`，冻结后不可回 DRAFT |

### 没分离好的（本次要修）

| 问题 | 表现 | 证据 |
|---|---|---|
| 入口语义没讲清 | 菜单两个都叫"报告"，页面标题一个叫「执行报告」一个叫「测试报告」，但**没有一个地方说清"我该去哪个"** | 评审 P0-3；`10-workbench`/`14-reports`/`27-test-reports` 截图 |
| 名字相近导致误入 | 用户想给客户出报告，却点进了"执行报告"，发现导出是灰的 | 评审故事 A |
| 派生关系不可见 | 从 run 到测试报告没有"由这次执行生成"的显式动作，只能去测试报告页再选一次执行记录 | 评审实测：需手工选 run |
| 状态机缺"审核"语义 | `DRAFT → FROZEN` 一步到位，冻结既当"定稿"又当"审核通过"，**没有"谁批准对外"的记录** | `ReportState.java` |
| 对外视图无预览入口 | `render(external=true)` 能力存在，但界面上没有"看看客户会看到什么"的按钮 | 实测详情页只有「冻结报告」 |

## 4. 目标模型：一条主线 + 三个关卡

```
  一次执行（run）
        │  自动生成
        ▼
  执行报告（run 级）  ──── 读者：测试人员
        │                  用途：排障 / 重跑 / 看日志与命令
        │  「据此生成测试报告」（显式动作，带 runId）
        ▼
  测试报告 · 草稿（DRAFT） ── 读者：报告编写人
        │                  内容：选材（run/用例集）+ 元数据 + 模板
        │  关卡①：内部预览（internal 渲染）
        ▼
  内部预览  ─────────────── 读者：审核人（组长/负责人）
        │                  看的是：结论站不站得住、数字对不对、有没有内部信息
        │  关卡②：审核通过（approve，记录审核人与时间）
        ▼
  已定稿（FROZEN）────────── 快照冻结，内容不可再变
        │  关卡③：对外视图预览（external 渲染，脱敏后）
        ▼
  导出（PDF/DOCX）  ─────── 读者：合作伙伴 / 客户
```

**三个关卡缺一不可**：没有①，编写人不知道客户会看到什么；没有②，无法回答"谁批准发出的"；没有③，脱敏规则失效时无人发现。

## 5. 关键补充：客户报告的对象可能不是"一次 run"

这一点必须提出来，因为它决定 v5.28 的方向。

**现状**：测试报告"按执行记录"创建，或"按用例集"创建（`runId` 传空 = 取该用例集**最近一次**执行）。

**问题**：客户问"这批用例在 EHT 环境、平台 v5.30、7 天内跑得怎么样"，而"最近一次 run"可能是：
- 一次只跑了 9 条的子集（就像我评审时那次 5 通过 / 4 失败 / 61 跳过）；
- 一次调试性质的 fake 运行；
- 一次失败后重跑前的临时记录。

拿它当交付结论，**不严谨也不可控**。

**建议（v5.28 引入"交付批次"）**：

| 项 | 内容 |
|---|---|
| 批次定义 | `用例集 + 环境快照 + 软件版本(SW_BUILD) + 时间窗` 唯一确定一个批次 |
| 取数规则 | 批内每次 run 的结论按用例聚合；**用例级取"最近一次通过"**，并同时展示"运行 N 次 / 通过 M 次" |
| 结论规则 | 全部用例至少通过一次 → 通过；存在从未通过的用例 → 不通过（列出） |
| 可追溯 | 批次报告附"支撑本次结论的 run 清单"（runId + 时间 + 结论） |
| 兼容 | 原"按单次 run 建报告"保留，标记为"单次执行报告（内部用）" |

这样客户报告才是"可复现、可解释、可追溯"的，而不是"碰巧最后一次"。

## 6. 对 FR-v5.23-18 的裁决（定稿）

| 选项 | 结论 |
|---|---|
| A 合并为一条链路 | **否决**。大师的口径明确区分了两种读者与两种用途，合并会同时毁掉两边 |
| B 分工 + 互跳 | **采纳，但不够，需升级为 B+** |
| C 不动 | **否决**。评审已证明用户会迷路 |
| **B+（本次定稿）** | 分离保留 + 入口语义显式化 + 派生动作可见 + 对外视图可预览。**审核态与批次化留到 v5.28** |

**B+ 的具体要求**（落到 FR-v5.23-18）：

1. 两页标题与副标题写明定位（"执行报告：给测试人员看执行过程" / "测试报告：给客户看的交付文档"）；
2. 执行报告详情的每个 run 页加「生成测试报告」按钮，带 runId 直达测试报告新建流程（派生关系可见）；
3. 测试报告详情加「预览客户视图」按钮（`render(external=true)`，脱敏后只读，不可导出）；
4. 两页互加跳转链接（"要找原始执行记录？去执行报告"）；
5. 软删行为对齐（当前 run 级 404、报告级 200 的不一致必须修）。
