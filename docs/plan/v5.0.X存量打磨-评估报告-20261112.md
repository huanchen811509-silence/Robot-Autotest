## 0. 评估结论（先给判断）

**可行，建议按「度量先行 + 局部治理 + 零新增表」执行，不做重构、不换肤、不拆服务。**

理由：v4.12.0 功能面已完整，代码规模 601 主 `.java` + 126 `.vue`，源码 `TODO/FIXME/HACK` 为 0 处，说明本版不存在「靠清标记就能收敛」的低垂果实；真实短板集中在**口径不统一、效果度量缺失、机检未覆盖新判据**三处。因此收益应来自度量补证与机检加固，而不是结构改动。

**本版不可判定的部分已明确排除**：CDP 保持取消（D1）、现场真机不解禁（D2）、RUM / 告警 / 演练不启用（D5）、真实端点不授权（D6）、不落号不判 G 门（D7）。评估不把这些当成「待解决障碍」，而是当成**边界条件**，据此把对应验收项设计为如实 `NOT-RUN` / `BLOCKED`。

## 2. 方案对比与选择

| 方案 | 做法 | 优点 | 代价与风险 | 结论 |
|---|---|---|---|---|
| A 度量先行 + 局部治理（**选中**） | B0 冻结口径与基线，B1/B2 只改被证据定位的模块，机检进门禁 | 回归面可控、每条提升可判定、零数据改动 | 收益依赖证据完备度；无基线项须如实判 `PARTIAL` | **采用** |
| B 借优化期重构 / 换肤 | 重排前端组件、拆服务、统一状态层 | 长期结构更整齐 | 破坏 436 个路由注解与双内核契约；门禁 32 步大面积失稳；与本版「存量打磨」目标相悖 | 否决 |
| C 只补文档与证据，不改代码 | 全部 30 包只产出报告 | 零风险 | 18 处交互目标、i18n 口径、README 旧读数等真实缺陷不收敛，版本无实质产出 | 否决 |

**选择 A 的硬理由**：本版验收要求「同一批存量任务，步数更少、页面更快、失败更快定位，且每一条提升都能拿出前后两份证据」。B 无法在 D1 / D2 边界下完成真实验证，C 无法收敛已定位缺陷。

## 3. 七维度可行性评估

| 维度 | 现状（已核实） | 可行性 | 本版动作 |
|---|---|---|---|
| 系统架构 | 后端五层 + 前端 Vue3 + editor 分包；78 张迁移演进到 `V11_45` | 高 | 不动拓扑；新增能力走开关，默认关闭 |
| 软件设计 | 两层设计令牌、明暗双主题、六预设强调色；280 项对比度机检 | 高 | 只收口本版改动文件的令牌，不扩 px 白名单 |
| 程序实现 | 源码技术标记 0 处；双内核与 `RUN_ID` 契约稳定 | 中 | 局部治理；零新增表、零破坏性 API、执行链零改动 |
| 测试体系 | 门禁 32 步、lint 20+ 项、40 TC；`check_structure` 只断言 13~32 步 | 高 | 新增 33~36 步只增不删；负向自检强制判红 |
| UI / UX | 18 处交互目标 <24×24；暗色下拉、密度、焦点环有历史整改单 | **中偏低** | 静态整改可做；**真实浏览器探针依赖 CDP，D1 下不可采集**，人工项如实 `NOT-RUN` |
| 用户体验 | Top8 成功率 / SUS / 50 查询集 / 跨浏览器 / RUM 均「未测量」 | 低 | 只建采集口径与前后测框架；无基线不写「提升」结论 |
| 运维保障 | 12 个 ops 脚本、6 条硬护栏、dry-run 默认；真实回滚演练未执行、RTO 未计时 | 中 | SLI / SLO 规则成文；演练判 `BLOCKED`；交付包只做准备不落号 |

**最关键的可行性问题**：UI/UX 与用户体验两维度的「效果类结论」在本版**不具备完整取证条件**。评估结论不是降低判据，而是把这两维度的准出判据改为「静态整改可机检部分 + 人工项如实登记 + 无基线项判 `PARTIAL`」，并在测试计划 §1.4、§9 中固定。
