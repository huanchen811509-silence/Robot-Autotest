# GPU 与智能网卡测试：平台演进评估与中长期计划

**评估对象**：现有 `infra-monitor` 资产 + RoboScope 平台 + 目标测试业务（GPU / SmartNIC 全场景）
**评估日期**：2026-10-31 ｜ **版本**：v1.0 ｜ **性质**：内部技术评估，非对外交付物

---

## 0. 结论摘要

现状是一套**可运行的环境巡检脚本**，不是**产品测试平台**。二者差距不在工具，在**测试资产的组织方式**。

三句话概括建议：

1. **用例规格（YAML）做唯一真源**，向上生成用例文档（xlsx/docx）、向下生成执行脚本（.robot）、向右生成测试报告（md/docx/pdf）。这一条同时解决"自动生成用例""文档与执行不一致""对比测试口径不统一"三个需求。
2. **执行层不要押注单一平台**。按用途分两条通道：交互式（RoboScope，点选、演示、单机调试）与流水线式（Git + CI，矩阵、并发、夜间、归档），两者共用同一份结果模型与同一个报告生成器。
3. **报告质量靠"模板语料 + 数据填空"，不靠生成模型自由写作**。给客户看的东西，80% 的文字应当来自固定语料库，机器只负责填数与选分支。

按当前人力（1–2 人兼职），预计：**6 个月形成可交付的最小闭环，12 个月覆盖六类交付形态，24 个月具备对外标准化能力**。

## 1. 需求拆解：五个正交维度

"多功能、能组合、能自动生成"是结果，不是设计。真正要先定的是下面五个维度的解耦方式——它们的组合数就是平台要承载的复杂度。

| 维度 | 取值 | 对平台的要求 |
|---|---|---|
| ① 被测对象 | GPU 服务器 / SmartNIC / RoCE 网络 / 存储 / 智算集群 | 资产与拓扑模型（角色、端口、链路、版本） |
| ② 测试类型 | 功能 / 性能 / 稳定性 / 兼容性 / 对比 | 判定器可插拔（布尔、阈值、相对基线、差异显著） |
| ③ 交付形态 | 内部产品测试 / 生态适配 / 厂验 / 开局 / 验收 / 对比 | 判据来源 + 抽样策略 + 报告模板三件套 |
| ④ 产物 | 用例文档（xlsx/md/docx）、结果（json/xml）、报告（md/docx/pdf） | 单一数据模型，多渲染器 |
| ⑤ 平台能力 | 编排、调度、并发、环境管理、结果库、趋势 | 执行与展示解耦 |

### 一个关键判断

**六类交付形态不是六套系统，而是三件事的不同配置：判据从哪来、抽多少、报告长什么样。**

| 交付形态 | 判据来源 | 抽样策略 | 报告侧重 |
|---|---|---|---|
| 内部产品测试 | 自研基线（上一版本/同型号） | 全量，含稳定性 soak | 缺陷定位、趋势 |
| 生态适配 | 生态方/标准（如 OFED、CUDA 版本矩阵） | 兼容矩阵全覆盖 | 版本兼容结论 |
| 厂验 | 合同/技术协议条款 | 逐条对应条款，抽检比例写死 | 条款符合性逐条对照 |
| 开局测试 | 组网设计与交付规范 | 按拓扑逐链路验证 | 配置正确性 + 可用性 |
| 验收测试 | 客户验收大纲 | 大纲全覆盖 + 见证点 | 结论页与签署页 |
| 对比测试 | 竞品/上代同参数实测 | 同拓扑同参数，等样本量 | 差异分析与归因 |

这条判断直接决定架构：**用例库只有一份，交付形态是"视图 + 判据集 + 模板"的组合**。若按交付形态各建一套用例，半年内必然出现同一测试项六个版本的灾难。

### 2.2 结构性缺口

| 缺口 | 具体表现 | 影响 |
|---|---|---|
| **没有测试项模型** | 用例是"对主机做某事"，不是"验证某条特性"；无 case_id、无前置、无判据字段、无追溯 | 无法做条款对照、无法算覆盖度、无法自动生成文档 |
| **指标无维度** | `metrics.json` 没有 scene_id / build(固件·驱动·OS·NCCL) / topology / round | **对比测试和趋势分析做不了**，这是最致命的 |
| **无基线概念** | `threshold` 是写死的字符串（如 `<100`） | 性能测试只能看"是否跑通"，不能判断"是否达标" |
| **报告是运行快照** | 无封面、无目录、无修订记录、无术语表、无结论页、无附录，无 PDF | 不能作为交付物，客户不会接受 |
| **用例不可组合** | 参数写死在 `common.robot`，PC 地址、账号、端口全硬编码 | 换一套机器就要改代码，无法做场景装配 |
| **执行通道单一** | RoboScope 单 worker 串行、无实时日志、无并发 | 多机矩阵测试（如 8 机 NCCL 扫描）跑不动 |
| **无版本控制** | `~/robot-test/infra-monitor` 不是 git 仓库，改动靠 tar 备份 | 测试资产是公司核心资产，这是最高优先级风险 |

## 3. 架构设计

### 3.1 分层

```
L5  交付层   厂验包 / 开局包 / 验收包 / 对比包       ← 模板 + 判据集 + 封面
L4  报告层   md · docx · pdf 三渲染器               ← 同一 run.json
L3  编排层   场景装配器 (YAML → .robot)             ← 参数矩阵 + 拓扑裁剪
L2  用例层   原子测试项（case_id + 判据 + 采集项）
L1  关键字层 统一记录入口 + 分域关键字库
L0  资产层   设备清单 / 拓扑 / 版本矩阵（YAML，入 Git）
```

**单向依赖**：上层只依赖下层的接口，下层不知道上层存在。这样换报告引擎、换执行平台都不牵动用例。

### 3.2 统一数据模型（最关键的产出物）

一份 `run.json`，所有渲染器都吃它：

```json
{
  "run_id": "R-20261031-001",
  "package": {"type": "factory_acceptance", "contract": "XX-2026-018", "template": "v2"},
  "scene_id": "SC-ROCE-2N2P",
  "product": {"model": "GPU-X8", "serial": ["SN001","SN002"]},
  "build": {"fw": "28.39.1002", "driver": "MLNX_OFED 24.10", "os": "Ubuntu 24.04",
            "cuda": "12.4", "nccl": "2.22.3", "image": "vllm:0.6.3"},
  "topology_id": "TP-2N-2P-DIRECT",
  "round": 1,
  "cases": [{
    "case_id": "RDMA-ROCE-NL-001",
    "verdict": "pass",
    "judge": {"type": "threshold", "expr": "out_of_seq==0 and bw>=baseline*0.95",
              "baseline_ref": "BL-2026Q3-GPU-X8"},
    "metrics": [{"metric": "ib_write_bw", "value": 96.4, "unit": "Gbps"},
                {"metric": "out_of_seq", "value": 0, "unit": "pkt"}],
    "evidence": {"cmd_file": "ev/RDMA-ROCE-NL-001.cmd",
                 "raw_file": "ev/RDMA-ROCE-NL-001.raw"}
  }]
}
```

对比测试 = 两份 `run.json` 同 `case_id` 对齐；趋势 = 按 `build` 维度切；条款对照 = `package.contract` 绑定条款号。

### 3.3 用例规格（YAML）示例

```yaml
case_id: RDMA-ROCE-NL-001
title: RoCE v2 无损链路 incast 场景零丢包验证
domain: roce          # nic | roce | storage | train | infer
type: function        # function | performance | stability | compat
objects: {role: gpu_node, count: 2, ports: [mlx5_0]}
preconditions:
  - PFC 已在交换机与网卡双向使能 (priority 3)
  - ECN 已配置, min/max = 150KB / 1500KB
  - 端到端 MTU 一致 (4200)
steps:
  - cmd: "ib_send_bw -d mlx5_0 -F --report_gbits -Q 1 -q 4 -l 65536"
    collect: [bw_avg, msg_rate]
  - cmd: "ethtool -S mlx5_0 | egrep 'pause|cnp|out_of_seq'"
    collect: [rx_pause, tx_pause, cnps, out_of_seq]
judge:
  type: threshold
  expr: "pfc_pause_frames > 0 and out_of_seq == 0 and bw_avg >= baseline*0.95"
evidence: [cmd, raw, counter_snapshot]
timeout: 300
tags: [roce, lossless, acceptance]
```

**一个规格，三种产物**：
- `spec → .robot`：执行脚本（Jinja2 模板生成，`steps` 逐条落到统一记录入口）
- `spec → xlsx/docx`：用例文档（编号/目的/前置/步骤/预期/判据/工具/耗时/追溯）
- `spec + run.json → 报告`：结果章节

这条链路是"自动生成用例"的正解。反过来做（先写 .robot 再反推文档）会在半年内失控。

### 4.6 性能

| 编号 | 测试项 | 输出指标 |
|---|---|---|
| PERF-IPERF-001 ★ | iperf3：单流/多流/双向、包长扫描(64~9000) | 带宽(Mbps)、重传、CPU |
| PERF-PERFTEST-001 ★ | perftest：write/read/send 的 bw 与 lat（size 扫描 2B~8MB） | 带宽、单向时延、消息率 |
| PERF-XCCL-001 ★ | nccl-tests 规模扫描：1/2/4/8 机 × 卡数 | busbw、算法带宽、扩展效率 |
| PERF-INFER-001 ★ | 大模型推理：并发 1/4/8/16/32 × 输入输出长度矩阵 | tokens/s、TTFT、TPOT、显存 |
| PERF-VERIFY-001 | 性能复现性（同条件 3 次） | CV < 5% |

**性能判据统一写法**（不要写死绝对值）：

```
pass = (value >= baseline * ratio) and (cv < 0.05)
其中 baseline 来自基线库（按 product + build + topology 三元组索引）
```

### 4.7 稳定性

| 编号 | 测试项 | 判据 |
|---|---|---|
| STAB-SOAK-001 | 12/24/72 小时持续流量 | 零错误、时延 P99 不劣化 > 10% |
| STAB-CYCLE-001 | 复位/重启循环 100 次 | 每次可恢复，无挂死 |
| STAB-FWUP-001 | 固件升级与回滚 | 升级后功能全通，回滚成功 |

### 4.8 首批范围建议

一上来全铺会烂尾。**先做一条纵切**：`NIC-LINK / MTU / FW` + `RDMA-BASE / NL / ECN` + `PERF-IPERF / PERFTEST`，共 8 个测试项，覆盖"两台机器 + 两个 RoCE 端口"的最小拓扑。跑通端到端（规格→脚本→执行→报告→交付），再横向复制到存储、训练、推理域。

## 5. 报告体系与"去 AI 味"

### 5.1 客户版报告骨架（固定）

```
封面（项目名/被测对象/委托方/测试方/日期/版本/密级）
修订记录（版本/日期/修订人/变更说明）
目录
1 测试概述
  1.1 测试目的与范围（含"不在范围内"声明）
  1.2 被测对象（型号/序列号/固件/驱动/OS/镜像版本矩阵）
  1.3 测试环境与拓扑（拓扑图 + 端口/IP/交换机配置摘要）
  1.4 测试依据（标准、合同条款、技术协议，逐条列编号）
2 测试方法
  2.1 测试项与判据（表格：编号/项/工具/参数/判据）
  2.2 数据采集与有效性判定（采样次数、剔除规则、CV 阈值）
3 测试结果
  3.1 汇总（通过/失败/阻塞 计数 + 结论一句话）
  3.2 功能结果（按域分节，表格 + 证据引用）
  3.3 性能结果（图：曲线/柱状；表：数值 + 基线对比 + 偏差）
  3.4 异常与偏差说明（每个失败项：现象/复现/根因/建议）
4 结论
5 附录
  A 原始命令与输出（按 case_id 索引，可裁剪）
  B 环境配置快照
  C 术语与缩写表
```

"不在范围内"声明是专业度分水岭——客户最常挑的刺是"你没测 X 却说通过"。

### 5.2 去 AI 味的六条硬规则

这部分不是提示词技巧，是**内容工程 + 审校流程**。判断标准：客户读完不会问"这报告是谁写的"。

| # | 规则 | 反例 → 正例 |
|---|---|---|
| 1 | 禁形容词，只写数与判据 | ✗"性能显著提升，表现优异" → ✓"ib_write_bw 均值 96.4 Gbps，较基线 92.1 Gbps 高 4.7%，3 次测量 CV 1.2%" |
| 2 | 主语必须是具体对象 | ✗"我们对该网卡进行了全面测试" → ✓"mlx5_0（GPU-01, PCI 0000:3b:00.0）在 4200 MTU、PFC 使能条件下…" |
| 3 | 句式统一为"陈述 + 数据 + 依据" | 不排比、不设问、不用"值得注意的是" |
| 4 | 图表必配一句"读图结论"，只陈述事实 | ✓"并发从 8 增至 32，吞吐由 1.2k 升至 1.35k tokens/s 后趋于平台，TTFT 由 210ms 升至 480ms" |
| 5 | 术语首现给全称，全文统一 | RoCE v2（RDMA over Converged Ethernet）、PFC（Priority Flow Control） |
| 6 | 生成后必须过"三查" | 查数值（回读 run.json）、查单位（Gbps vs GB/s）、查结论与数据是否自相矛盾 |

### 5.3 工程实现：模板语料 + 数据填空

```
report/
  templates/
    base.docx            # 骨架：封面/目录/样式/页眉页脚/编号
    sections/
      overview.docx      # 固定语料 + {{ }} 占位
      method.docx
      result_func.docx
      result_perf.docx   # 含图表占位
      appendix.docx
    i18n/zh-CN.yaml      # 术语表、固定句式库
  render/
    render_docx.py       # docxtpl：模板 + run.json → docx
    render_md.py         # Jinja2 → md
    render_pdf.py        # LibreOffice headless: docx → pdf
    charts.py            # matplotlib 静态图（矢量 SVG/EMF 嵌入）
```

**为什么 PDF 走"docx → LibreOffice"而不是 LaTeX/HTML**：一份模板出 docx 和 pdf，客户能自己在 Word 里改版式，中文排版零风险。LaTeX 更美但维护成本高且客户无法改；HTML→PDF（WeasyPrint）在跨页表格和页码上长期出问题。

**报告文字来源比例**：80% 模板固定语料（方法描述、判据说明、结论句式）+ 20% 数据与分支（数值、通过/失败、偏差说明）。这个比例是"去 AI 味"的可量化指标——自由生成的部分一旦超过 30%，风格就会飘。

### 5.4 现状报告的直接问题（`post_report.py`）

| 问题 | 现状 | 改法 |
|---|---|---|
| 标题 | "自动化测试报告" | 带项目/对象/阶段的正式标题 |
| 结构 | 指标表平铺 | 按第 5.1 节骨架重排 |
| 无 PDF | 只有 html/xlsx/md/docx/csv | 加 LibreOffice 转换 |
| 无判据说明 | 只列 threshold 字符串 | 从 spec 取判据并翻译成人话 |
| 无对比 | 单次运行快照 | 引入基线库，出"基线 vs 本次"列 |
| 无证据索引 | 附录缺失 | 按 case_id 索引原始命令与输出 |

## 6. 平台选型

| 用途 | 推荐 | 备选 | 不推荐及原因 |
|---|---|---|---|
| 执行引擎 | **Robot Framework 7.x** | pytest | pytest 缺业务可读语法，报告需另接 Allure，客户看不懂 |
| 交互式执行 | **RoboScope（保留）** | 自研 Web | 现有可用，作为演示/单机调试；但不可作为唯一平台 |
| 批量/矩阵执行 | **GitLab CI**（自带 runner 矩阵、制品、日志流） | Jenkins、Tekton | Jenkins 维护重；Tekton 学习曲线陡 |
| 资产版本 | **Git + 语义化 tag** | SVN | 无版本控制是当前最大风险 |
| 用例规格 | **YAML + JSON Schema**（自建） | Excel 直接做源 | Excel 做源无法做 diff/review，必失控 |
| 结果模型 | **自有 run.json + JUnit 兼容** | Allure | 二选一即可，别双写 |
| 报告 | **docxtpl + Markdown + LibreOffice→PDF** | Pandoc、WeasyPrint、LaTeX | 见 5.3 |
| 图表 | matplotlib（静态矢量） | Plotly | 交互图在 PDF 里无意义 |
| 结果库 | **SQLite（现阶段）→ PostgreSQL（多站点）** | InfluxDB | 测试结果不是时序指标，Influx 查询能力不匹配 |
| 趋势看板 | Grafana（读结果库） | robotdashboard | robotdashboard 数据模型过窄 |
| 环境预约 | 自建轻量表（Git 仓库 + 日历） | 商业 Lab 管理系统 | 现阶段人数不支撑 |

**关于 RoboScope 的定位结论**：保留，但降级为"交互式前端"。它的硬约束（单 worker 串行、无实时输出、补丁升级会丢、并行字段是假的）决定了它不适合承载回归矩阵。GitLab CI 恰好在这三点上是强项。二者共用 `run.json` 与报告渲染器，不构成两套体系。

## 7. 演进路线

### M0 · 止血与规范化（第 1–2 周）

| 事项 | 交付物 |
|---|---|
| 建 Git 仓库，目录重构 | `specs/ keywords/ scenes/ report/ results/` |
| 定 `case spec` schema v0.1 + 3 个样例句 | `schema/case.schema.json` + NIC/ROCE/IPERF 各一条 |
| 定 `run.json` v0.1 | 扩 `metrics.json`，补 scene/build/topology/judge |
| 报告模板 v1（docx + md，含封面/目录/结论/附录） | `report/templates/base.docx` |
| 现有 28 用例迁移为"环境巡检"场景 | `scenes/env-check.yaml` |

**验收**：同一份结果数据，一条命令出 md + docx + pdf；人工写报告时间从 2h 降到 20min。

### M1 · 测试项库成型（第 1–2 月）

- 关键字库分域：`net`(ethtool/ibstat/iperf3)、`rdma`(perftest)、`gpu`(nvidia-smi/nccl)、`storage`(fio/nvme)、`infer`(vllm bench)
- 8.1 节列的首批 8 个测试项落地，逐步扩到 40–60 个原子项
- 判定器三类：布尔 / 阈值 / 相对基线
- 场景装配器：`scene.yaml` → `.robot` → 执行 → 回填 `run.json`

**验收**：一套"2 机 × 8 卡 × 2 端口 RoCE"拓扑，一条命令跑完功能 + 性能，产出客户格式报告；报告里每个数字都能点回原始命令。

### M2 · 交付形态分化 + 对比测试（第 3–6 月）

- 六类交付包的模板、判据集、抽样规则（按第 1 节表格）
- 对比测试：同 `case_id` 双 run 对齐，输出差异表 + 归因（同参数同判据是前提）
- 用例文档自动生成：xlsx（用例表）+ docx（用例说明），与执行脚本同源
- 调度：CI 矩阵 + 夜间回归 + 结果入库趋势

**验收**：厂验包从"拿到机器"到"交付报告"≤ 3 天；任意两份 run 可一键出对比章节。

### M3 · 平台化与规模化（第 6–12 月）

- 多站点/多机柜资产模型，环境预约（GPU 稀缺是主要瓶颈）
- 并发执行（替代单 worker），实时日志（WS 或 SSE）
- **基线库**：每产品/固件一份基线，自动漂移告警
- 失败案例库 → 自动诊断建议（"这次失败上次也出现过，根因 X"）

**验收**：夜间全量回归覆盖 6 类交付包；基线漂移 24h 内可发现。

### M4 · 标准化与对外（第 12–24 月）

- 判据与标准条款对齐（OCP / 信通院 / 客户大纲）
- 测试即服务：对外部合作方开放子集
- 报告多语言、留痕与审计

**验收**：第三方可按公开口径复现我方测试并得到一致结论。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 测试环境稀缺（GPU 排队） | 进度不可控 | 环境预约表 + 轻量冒烟子集（15 分钟）+ 夜间长任务 |
| 客户模板各异 | 报告返工 | 模板分层：骨架固定，章节可插拔；每客户一份 profile |
| 判据争议 | 结论不被认可 | 判据写进用例规格并在测试前与客户确认签字 |
| 平台锁定 | 换平台推翻资产 | 资产以 YAML/Git 为源，平台只做执行 |
| 补丁丢失（RoboScope 升级） | 已修功能回退 | 补丁脚本化 + 升级检查清单 |
| 人力不足 | 铺太宽烂尾 | 先做一条纵切（RoCE 功能 + iperf/perftest），跑通再复制 |
| 报告"AI 味" | 客户信任受损 | 模板语料占比 ≥ 70% + 三查流程 + 人工署名审校 |
