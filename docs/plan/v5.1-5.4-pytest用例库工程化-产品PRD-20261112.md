## 3. 5.1.x 契约适配线（增量修订）

### 3.1 与详版的关系

5.1.0 的功能需求（FR-v5.1-01 ~ 14）、验收（A1–A33）、字段规则、门禁脚本**全部沿用** `RA-PRD-51-001` v1.0，本文件不重复。

### 3.2 本文件对 5.1.0 详版的 6 条修订（冲突时以本节为准）

| # | 修订项 | 原详版 | 修订后 | 理由 |
|---|---|---|---|---|
| M1 | 证据目录不覆盖 | 未定义 | 每次执行使用 `<repo>/artifacts/<RUN_ID>/`；**若目录已存在且非空，先重命名为 `<RUN_ID>.bak-<ts>` 再执行**，并在 `run_metadata` 记 `EVIDENCE_REUSED=true` | 隐藏需求 H10：重跑会覆盖第一次的证据 |
| M2 | 进度心跳 | 未定义 | 任意 stdout/stderr 行刷新 `lastActivityAt`（不只阶段切换），避免 pytest run 被 60s 卡死误判 | §7.3.1 已核实的误判风险 |
| M3 | 覆盖率分母 | 「`lifecycle_status='active'` 且 `source_sheet='详细测试流程'`」 | 保持该分母，但**看板必须并列展示两个数**：含待评审（469 条 / 已实现 61 / **13.0%**）与排除待评审（291 条 / 已实现 30 / **10.3%**，实测值），页脚写明差异与算法 | 待决 D12；避免对外口径争议（H11） |
| M4 | 绑定同步的可重命名跟随 | 三级解析（MANUAL/DOCSTRING/FILENAME） | 同步时先按 `script_sha256` 匹配旧行，命中则**更新 `script_path` 而非新建**；未命中才按文件名重建 | 隐藏需求 H4：目录整理会产生批量假 MISSING |
| M5 | 用例库升版存续 | 未定义 | 导入新版本用例库时，以 `external_id`（库编号）为准做 upsert；`test_case.id` 保持稳定；绑定表不重建 | 隐藏需求 H3：升版后 id 变化会让覆盖率掉到 0 |
| M6 | 执行前拒绝清单 | 三类（未绑定/资源不足/环境不健康） | 增加第四类：**证据目录不可写 / 磁盘不足**（复用 `minFreeBytes`），一并拒绝 | 跑到一半磁盘满会产生半截证据 |

## 4. 5.2.x 执行治理线

### FR-v5.2-01 项目类型 `pytest-suite`

**描述**：在 `project.kind` 增加 `pytest-suite`，作为 pytest 用例库工程的承载类型；与 `standard`、`platform` 并列。

**规则**

| # | 规则 |
|---|---|
| R1 | `kind` 取值域扩为 `standard` / `platform` / `pytest-suite`；`platform` 仍为单例约束 |
| R2 | 新建项目时必须显式选类型；默认 `standard`，不允许「隐式变 pytest 工程」 |
| R3 | `kind=pytest-suite` 的项目，项目级默认内核 = `pytest-nic`（`KernelSelector` 第一优先级） |
| R4 | 切换 `kind` 需 `PROJECT/UPDATE` + 影响面确认（已有 run 的历史结论按 `run.kernel` 快照，不回填） |
| R5 | `kind=pytest-suite` 的项目卡片展示三个工程指标：覆盖率、绑定健康度、基线偏差中位数 |

**边界**：一个项目只绑一个仓库；不复用 `robot_file`。

**验收**：B1、B2、B3。

### FR-v5.2-02 工程配置与必填校验

**描述**：pytest 工程的运行配置统一在「工程配置」页维护，缺失关键项即拒跑并给出定位链接。

**规则**

| # | 规则 |
|---|---|
| R1 | 配置项（`project_setting`，沿用 `pytest.*` 前缀）：`repo_url`、`repo_ref`、`subdir`、`python_bin`、`mode_default`、`exclude_paths`、`baseline.window_days`、`baseline.slow_factor`、`report.auto_generate`、`report.template_id` |
| R2 | 必填项：`repo_url`、`python_bin`。任一为空 → 执行前拒绝（`repo_unbound` / `runtime_unbound`），并在拒绝卡片上给「去配置」链接 |
| R3 | `mode_default` 强制 `fake`（安全默认）；选 `real` 需二次确认并留审计 |
| R4 | 保存配置后自动触发一次健康检查（异步），结果落 `/kernels` 页 |
| R5 | 配置变更写审计（谁、何时、改了哪项、旧值→新值），口令类值只记掩码 |

**验收**：B4、B5、B6。

### FR-v5.2-03 项目执行协调者

**描述**：在项目维度提供「编排—监护—裁决—记账」四类能力，形态为**进程内逻辑角色**（复用 `RunDispatcher`/`LeaseService`/`RunTimeoutMonitor`/`ExecutionOrphanSweeper`），**不新建守护进程**。

**规则**

| # | 规则 |
|---|---|
| R1 | 编排：支持「批内顺序」（按用例集顺序，或按优先级 + 分类）、「执行窗口」（时间窗 + 独占资源）、「资源预约」（双端用例整单预约两端） |
| R2 | 监护：复用现有心跳/超时/孤儿能力；pytest 侧心跳来自 5.2.2 的进度通道；监护事件写 `execution_event`（`event_type` 前缀 `supervisor.`） |
| R3 | 裁决：失败后按规则给出三选一动作——`retry`（同 commit 同资源重跑）/ `stop`（终止剩余）/ `handover`（转人工，5.3.2 落地前只标记） |
| R4 | 记账：项目级执行台账（今日 run 数、成功率、平均时长、当前在跑、排队位次） |
| R5 | 协调者**不改变** `RunDispatcher` 的排队语义；窗口与预约实现为「何时 submit」而非改调度器 |
| R6 | 外置条件：出现「重启丢 run」≥1 次、执行机 >1 台、或吞吐 > `maxParallel×3` 时，另立评估外置（本版不做） |

**边界**：不替人判定「是否产品缺陷」；不做跨项目全局编排。

**验收**：B7、B8、B9。

### FR-v5.2-04 跨内核用例集拆单

**描述**：一个用例集包含 RF 与 pytest 用例时，执行时自动按内核拆成多个 run，报告层合并展示。

**规则**

| # | 规则 |
|---|---|
| R1 | 拆单规则：按 `kernel` 分组，每组一个 run；组内顺序保持用例集顺序 |
| R2 | 拆单后各 run 的 `run_id` 独立生成；父批次用一个 `batch_id`（`execution_job.job_no` 复用）关联 |
| R3 | **单个 run 不允许混内核**（`run.kernel` 单值快照） |
| R4 | 报告层以 `batch_id` 聚合展示；结论按 run 分别呈现，不合并成一个通过率 |
| R5 | 拆单失败（某组资源不足）→ 该组拒绝，其他组照常执行，批次标「部分执行」 |

**验收**：B10、B11。

### FR-v5.2-05 实时进度通道

**描述**：pytest 执行进度通过平台插件写入 `progress.jsonl`，平台增量读取后统一对外（不解析 stdout 中文，不改 RF 正则）。

**规则**

| # | 规则 |
|---|---|
| R1 | 事件模型按评估 §7.3.2（`session_start` / `collect_finish` / `case_start` / `case_end` / `session_finish`） |
| R2 | 文件位置 `<runDir>/kernel-pytest-nic-0/progress.jsonl`，UTF-8，逐行 JSON，追加写 |
| R3 | 平台侧新增**独立通道**读进度；`RunProgressRegistry` 的 RF 正则**零改动**（回归锁 RK-2） |
| R4 | 进度仅用于展示：最终结论一律以 junit 为准；两者不一致时报告标「进度与结论差异」并附两者数字 |
| R5 | 任意新事件刷新心跳，使 `stalled` 判定对 pytest 有效 |
| R6 | 前端展示五要素：阶段、已完成/总数、当前用例编号、已耗时、预计剩余（有基线用基线，无基线显示「估算」） |

**边界**：不保证字节级实时（轮询 3s 沿用）；不伪造百分比（`total=0` 时不确定进度）。

**验收**：B12、B13、B14。

### FR-v5.2-06 错误归因五层与人话摘要

**描述**：把失败从「一个枚举值」升级为可操作的归因结构。

**规则**

| # | 规则 |
|---|---|
| R1 | L1 结论（PASS/FAIL/ERROR/SKIP/PLANNED）、L2 分类（环境/配置/框架/用例/断言/超时）、L3 位置（步骤N + 命令 + endpoint）、L4 原文（日志切片 + 命令回显）、L5 建议（规则匹配，AI 可选增强） |
| R2 | L2 归因规则集扩展：`SSH 认证失败`（`AuthenticationException`/`Permission denied`）与`口令错误`（`Bad authentication type`/`Authentication failed`）**必须区分**，且给出不同修复建议 |
| R3 | 人话摘要：一句话说明「在哪一步、对哪个端点、执行什么操作、得到什么结果」，≤120 字，不含堆栈 |
| R4 | 归因结果写入 `test_result` 的扩展字段（复用 `failure_class` + 新增 `failure_stage` / `failure_endpoint`），并进失败聚类 |
| R5 | 归因为「环境/配置」的失败**默认不进产品通过率的分母**，单列「环境失败」并在报告标注（复用既有分流口径） |

**边界**：不做根因推断（只做归因分层）；不自动改判定。

**验收**：B15、B16、B17。

### FR-v5.2-07 kind 差异化菜单与孤儿页归位

**描述**：pytest 工程使用「工程视图」侧栏；普通项目菜单**零变化**。

**规则**

| # | 规则 |
|---|---|
| R1 | 菜单选择逻辑从「uiMode 二分」扩展为「uiMode × project.kind」；`standard` 项目渲染现有 29 叶，不变 |
| R2 | `pytest-suite` 工程渲染工程视图（组与叶见 §8.1）；叶子集合允许与现有页面复用 |
| R3 | 三个孤儿页归位：`/kernels` → 工程视图「执行」组；`/imports` → 「用例工程」组导入记录；`/groups` → 并入用例集页（不单独设入口） |

**验收**：B18、B19、B20。

### FR-v5.2-08 型号字典与设备标识变更

**描述**：把 `product_model` 从「自由文本」变成「受控字典」，并为设备标识变更提供审计化路径。

**规则**

| # | 规则 |
|---|---|
| R1 | 新增 `nic_model_dict`（厂商 + 型号 + 归一化键 + 是否已知 + 映射的 `device_specs` 键）；资产录入时按字典校验 |

| R3 | 未在字典中的型号：允许保存但标 `unknown_model`，执行前拒绝（`model_unmapped`），并给「补字典」入口 |

| R5 | 字典变更需 `ASSET/UPDATE`，且变更影响面提示（引用该型号的设备数、相关用例数） |

**验收**：B21、B22、B23。

## 5. 5.3.x 监控与智能线

### FR-v5.3-01 执行监视器（内核无关）

**描述**：一个「公共」的监视组件，订阅执行产物与事件，产出统一的可观测数据；**不新建独立进程**。

**规则**

| # | 规则 |
|---|---|
| R1 | 输入四类：进程 stdout/stderr 流、证据目录变化、`progress.jsonl`、平台 `execution_event` |
| R2 | 输出三类：日志切片（脱敏）、结构化事件、命令集合（见 FR-v5.3-02） |
| R3 | 内核无关：RF 与 pytest 走同一组件、同一 schema；差异只在「取材适配器」 |
| R4 | 监视器失败不得影响执行（只降级为「无监视数据」，报告标「监视不可用」） |
| R5 | 监视器自身资源受限：单 run 内存上限、事件速率上限（超限丢弃并计数，不静默） |

**验收**：C1、C2、C3。

### FR-v5.3-02 命令集合

**描述**：把「一个 run 发了哪些命令」变成一等数据，可查、可过滤、可对比。

**规则**

| # | 规则 |
|---|---|
| R1 | schema 按评估 §7.6.1 十一字段（`cmd_id`/`run_id`/`node_id`/`seq`/`endpoint`/`kind`/`argv`/`started_at`/`duration_ms`/`exit_code`/`stdout_sha`/`truncated`/`sensitive`） |
| R2 | `kind` 取值：`collect` / `configure` / `traffic` / `verify` / `cleanup`；无法判定记 `other`，**不猜** |
| R3 | 入库前脱敏（复用 `EvidenceLogWriter.scrub`）；命中敏感词表 → `sensitive=true` 且 `argv` 只存掩码 |
| R4 | 查询入口：按 run / 用例 / endpoint / kind / 退出码过滤；支持「两次 run 同用例命令 diff」 |
| R5 | 原文不入库（只存 `stdout_sha`），原文在证据文件里；库内查询返回「前 200 字符 + 指纹」 |

**验收**：C4、C5、C6。

### FR-v5.3-03 用例时长基线

**描述**：为每条用例建立耗时分位基线，供 ETA、软超时、异常检测使用。

**规则**

| # | 规则 |
|---|---|
| R1 | 新表 `case_duration_baseline`：`(project_id, case_id, kernel)` 唯一；字段 `p50_ms/p90_ms/p99_ms/max_ms/sample_count/window_days/updated_at` |
| R2 | 统计窗口默认 30 天，可配；样本量 < 5 时不写基线（标 `insufficient`），ETA 用分类中位数兜底 |
| R3 | 分母排除：`PLANNED`、`SKIP`、环境失败样本（避免污染） |
| R4 | 基线刷新：每日离线重算（不影响执行）；也可在「工程看板」手工触发 |
| R5 | 基线只用于**估算与告警**，不参与判定 |

**验收**：C7、C8、C9。

### FR-v5.3-04 软超时与异常快检测

**描述**：以基线为参照做双向异常检测：过慢告警、过快可疑。

**规则**

| # | 规则 |
|---|---|
| R1 | 软超时阈值 = `p90 × baseline.slow_factor`（默认 1.5）；超阈值写 `slow` 事件 + 报告标 `slow`，**不中断执行** |
| R2 | **硬超时仍为 run 级**（`runTimeoutSeconds`，默认 3600）；PRD 与界面文案必须写明「逐用例硬中断不在本期范围」 |
| R3 | 异常快：单例耗时 < `p50 × 0.2` 且结论为 PASS → 标 `suspicious_fast`，进报告「可疑通过」清单 |
| R4 | 界面展示三档：正常 / 慢（`slow`）/ 可疑快（`suspicious_fast`），配色与 PASS/FAIL 独立 |
| R5 | 若将来框架引入 `pytest-timeout`，本 FR 的阈值配置可直接复用为插件参数（预留配置项，不实装） |

**边界**：不做用例级进程强杀（技术不可行，见评估 §7.6.4）。

**验收**：C10、C11、C12。

### FR-v5.3-05 AI 归因建议（不参与判定）

**描述**：失败用例可请求 AI 给出「可能原因 + 建议动作」，仅作建议展示。

**规则**

| # | 规则 |
|---|---|
| R1 | 受 `AiFeatureGate` 双闸门控制；关闭时入口隐藏，人工闭环（FR-v5.3-06）完整可用 |
| R2 | 证据包内容固定（评估 §7.6.2）：编号+标题、L2 归因、失败步骤、命令与回显（脱敏+截断）、日志切片 ≤200 行、基线偏差、同类历史次数 |
| R3 | 输出必须标注「AI 建议，需人工确认」；不得写入 `verdict`、不得改 run 状态、不得自动触发重试 |
| R4 | 导出时默认**不包含** AI 建议，需显式勾选才进报告 |
| R5 | 每次请求记审计（谁、哪条用例、消耗、模型标识）；建议内容留存以便复核 |

**验收**：C13、C14、C15。

### FR-v5.3-06 人工处置闭环

**描述**：每条失败可被指派、定级、给结论、留附件、形成时间线。

**规则**

| # | 规则 |
|---|---|
| R1 | 处置字段：`assignee`、`disposition`（用例问题/产品缺陷/环境问题/待查/已知问题）、`note`、`attachments`、`decided_at`、`decided_by` |

| R3 | 处置结果**不影响** run 的历史结论（结论是事实，处置是判断），但在台账与报告中并列展示 |
| R4 | 「已知问题」可登记为豁免规则（用例+归因指纹），命中时报告标「已知问题」并单独计数，不进新产品缺陷统计 |
| R5 | 处置动作写审计；批量处置需二次确认 |

**验收**：C16、C17、C18。

### FR-v5.3-07 环境健康雷达与执行窗口

**描述**：把「环境好不好」与「什么时候能跑长跑」变成可看可排的能力。

**规则**

| # | 规则 |

| R3 | 长跑识别：按分类（稳定性/压力）或基线 p90 > 阈值（默认 30 分钟）自动标记 |
| R4 | 缺口派工：覆盖率看板的缺失项可按分类批量指派责任人（`case_owner`），并跟踪「已派/已交付/已验证」 |
| R5 | 窗口与派工都不改执行语义（只在 submit 时机与看板层面生效） |

**验收**：C19、C20、C21。

## 6. 5.4.x 报告与全量线

### FR-v5.4-01 报告生成策略化

**描述**：报告从「人工点一下」升级为「按策略自动生成」，但默认关闭、只对正式执行生效。

**规则**

| # | 规则 |
|---|---|
| R1 | 触发器三选：`run_finished`（默认）/ `scheduled`（每日汇总）/ `manual`；由 `project_setting.report.auto_generate` 控制，**默认 false** |
| R2 | 生效条件全部满足才生成：run 终态 + `mode=real` + 存在 `test_result` + 项目已绑模板 |
| R3 | 挂载在 `RunCompletionListener`（新增实现），事务提交后执行；自动生成失败**不影响** run 结论，只记事件与页面提示 |
| R4 | 幂等键 `(run_id, template_id)`；重复触发不重复建；重建需显式「重新生成」并留旧版本 |
| R5 | 生成后默认**不自动冻结**（`freeze` 仍需人工或批量策略），冻结动作单独审计 |
| R6 | Fake/PLANNED 执行不自动出正式报告（可手工出「预检报告」，模板不同） |

**验收**：D1、D2、D3。

### FR-v5.4-02 报告 8 章内容模型

**描述**：报告内容固定为 8 章，每章有数据来源与降级规则（数据缺失时标注「无数据」而不是省略）。

| 章 | 内容 | 数据来源 | 缺失时 |
|---|---|---|---|
| 1 结论摘要 | 一句话结论 + 通过率 + 判定建议 | `test_report` + 规则 | 必填，无降级 |
| 2 执行环境 | commit / 框架版本 / 内核 / 运行时 / 资源池顺序 / 模式 | `run_metadata` + 渲染快照 | 标「未记录」 |
| 3 结果分布 | 分类别 / 优先级 / 设备的结果矩阵 | `test_result` + `test_case` | 标「无分类数据」 |
| 4 失败分析 | L2 归因分布 + TopN + L3/L4 下钻 | 归因 + 证据 | 标「无失败」 |
| 5 时间分析 | 偏慢 TopN + 可疑快清单 + 基线覆盖率 | `case_duration_baseline` | 标「基线未建立」 |
| 6 覆盖影响 | 本次覆盖分类 + 缺口变化 | 覆盖率 | 标「未统计」 |
| 7 命令集合摘要 | 命令总数 / kind 分布 / 失败命令 / 敏感计数 | 命令集合 | 标「未采集」 |
| 8 附录与口径 | 证据索引 + 用例清单 + 三条口径声明 | 产物清单 | 必填，无降级 |

**规则**

| # | 规则 |
|---|---|
| R1 | 8 章顺序固定；第 8 章必须含三条声明：覆盖率≠完成度、PLANNED 不计通过率、AI 建议不参与判定 |
| R2 | 每章数据必须可追溯到具体查询（报告内可展开「数据来源」） |
| R3 | 第 1 章「判定建议」为规则推导（有 FAIL→不建议通过；无 FAIL 但 PLANNED 占比 >0→建议复验），**不由 AI 生成** |
| R4 | 章节内容与 `ReportFieldWhitelist` 对齐；新增字段先登记再进导出 |

**验收**：D4、D5、D6。

### FR-v5.4-03 对外报告脱敏

**描述**：同一份报告可导出「对外版」，隐藏内部标识。

**规则**

| # | 规则 |
|---|---|
| R1 | 对外版隐藏：`node_id`、`host_key`、`management_ip`、内部路径、执行机用户名 |
| R2 | 对外版保留：库编号、用例标题、结论、耗时、命令的「业务可读形式」（如 `iperf3 -c <DUT>` 而非真实 IP） |
| R3 | 脱敏是**渲染期**行为，不改库内数据；导出文件不留内部标识（机检：正则扫 IP/路径 0 命中） |
| R4 | 对外版与内部版共用同一模板，仅字段可见性不同（避免两套模板漂移） |

**验收**：D7、D8。

### FR-v5.4-04 非自动化用例编辑与手工执行

**描述**：支持非自动化用例在平台内编辑与执行记录；与自动执行共用同一套用例台账。

**规则**

| # | 规则 |
|---|---|
| R1 | `test_case.exec_mode`：`auto` / `manual` / `hybrid`；由 `source_type` + 绑定情况推导默认值（有绑定=auto），可人工改 |
| R2 | 编辑能力：步骤表（增删改排序）、富文本说明、前置条件、附件（图/日志）、责任人、标签；保存留版本（`case_version` 复用） |
| R3 | 手工执行模型：一次执行 = 一条 `run`（`trigger_type=manual`、`kernel=manual`）+ `manual_execution`（executor/started_at/finished_at/环境备注）+ 每步 `manual_step_result`（verdict/note/attachments） |
| R4 | 手工结果写 `test_result`（`verdict` + `executor`），与自动结果同表但**分列统计** |
| R5 | 手工用例的步骤来自 `test_case_step`（action/expectation），执行时逐条确认；未确认的步骤不能提交结论 |
| R6 | 手工 run 不占资源租约、不出现在「执行队列」、不触发自动报告（除非显式） |

**验收**：D9、D10、D11。

### FR-v5.4-05 手工与自动结果分离统计

**描述**：任何通过率都必须可拆成「自动 / 手工」两列，再给合计。

**规则**

| # | 规则 |
|---|---|
| R1 | `test_result` 增 `exec_mode` 快照（auto/manual），报告与 API 均返回分列字段 |
| R2 | 报告第 1、3 章必须分列展示；合计需标注「含手工 N 条」 |
| R3 | 对外报告默认只报自动结果，手工结果需显式勾选（避免对外口径混淆） |
| R4 | 趋势图分两条线（自动/手工），不合并成一条 |

**验收**：D12、D13。

### FR-v5.4-06 双内核统一视图与规模化收口

**描述**：RF 与 pytest 在同一处被看见，但口径不混。

**规则**

| # | 规则 |
|---|---|
| R1 | 统一视图：按项目/批次展示双内核 run，字段对齐（结论/耗时/证据/归因），**通过率分别算** |
| R2 | 三向一致性机检转正：库编号 ↔ 脚本 ↔ collect 结果，不一致 0 条（或全在豁免清单内） |

| R4 | 规模化保护：单 run node 数上限、证据目录配额、命令集合条数上限，超限截断并标记 |
| R5 | 收口判据：`v5.4.2` 交付时，RF 四锁仍全绿、pytest 样板仍通过、门禁步数只增不减 |

**验收**：D14、D15、D16。
