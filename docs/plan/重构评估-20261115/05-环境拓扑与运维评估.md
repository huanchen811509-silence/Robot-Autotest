## 一、R17 环境与拓扑

### 1.1 现状盘点（可量化）

| 层 | 内容 | 规模 |
|---|---|---|
| 前端页面 | 环境概览 / 环境采集 / 拓扑与快照 / 环境准备 / 采集记录分析 / 连接与拓扑 | 6 个组件，**1348 行** |
| 前端 API | `api/environment.ts` + `api/assetInfo.ts` | 139 + 115 行 |
| 后端控制器 | `EnvController`(74) + `HostInventoryController`(93) + `AssetInfoController`(94) | 261 行，**12 端点** |

|---|---|---|---|

### 1.3 结构性缺口（这是「重写」的理由，不是细节）

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| 1 | **快照只存一行 JSON**，没有版本对象 | `env_profile.snapshot_json`（`V1:233-246`、`V11_27` 改为允许多份）；`EnvController.java:46-56` | 「环境漂移」无法追溯：两次快照差异只能整段文本 diff，不能按项查、不能被执行引用 |
| 2 | **手工拓扑表是死表** | `topology_node`（`V1:248-263`）无任何 Repository/Mapper；`AssetInfoService.java:31-35` 明确「不合并手工拓扑」 | 拓扑图完全由 device/port/link 派生 → 无 LLDP、无条件推断、无「实测 vs 规划」分级 |
| 3 | **采集探针白名单写死在代码里** | `HostInventoryCollector.COMMANDS`（`HostInventoryController.java:78-82`），固定 10 条只读命令 | 想加一项探针要改代码发版；不同设备类型（交换机/GPU 机型）无法差异化 |
| 4 | **环境与执行的闸门断裂** | 执行前不看快照（v5.5 时代的 ADR-0013 只看 `confirmReal` + 绑定） | 环境漂移只能事后追查，不能事前拦住「端口速率不对还去跑 400G 用例」 |
| 5 | 项目侧「环境采集」只能采本机 | `api/environment.ts:65-70` 只传 `host`，无凭证入参 | 与 R9 的「绑定凭证」能力脱节 |

### 1.4 白泽可抄什么（逐条给源码位置，不是概念）

| 机制 | 白泽实现 | 可直接抄的部分 | 我方落点 |
|---|---|---|---|
| 内容寻址快照 | `data/snapshots/<sha256>` + 索引表 `device_snapshot`，读时校验「摘要 + 设备身份」双匹配；`DeviceSnapshotIndex.java`(170 行)、`SnapshotCompare.java`(141 行) | **抄**：快照作为不可变对象、按 hash 寻址、两份快照按项对比 | 新建 `device_snapshot` + `device_snapshot_item`；替代 `env_profile.snapshot_json` |
| 探针包 | Linux 基础 39 项 + 按发现的 netdev/HCA 动态追加 `mlnx_qos`/`qdisc`/`mlxconfig`；交换机按 `show version` 分流 Centec/Ruijie | **抄结构，不抄命令集**：把探针做成「包 = 一组命令 + 解析器」，可配置、按设备类型选包 | 我方 10 条固定命令 → `probe_pack`（YAML/表） |
| 拓扑三源分级 | LLDP 邻居 / 同网段同速率 / 人工规划 / 人工确认，各有 `confidence`；重合时实测优先；`TopologyGraph.java`(498 行)、`TopologyController.java`(56 行) | **抄** confidence 模型与「实测盖规划」的取舍 | `link` 表加 `confidence` + `source`；拓扑图加图例与过滤 |
| SSH 安全细节 | 系统 ssh 客户端 + askpass（口令不进 argv）+ 每设备独立 `known_hosts` + `StrictHostKeyChecking=yes` + 老算法用 `+` 追加 | **抄**（这是安全正确性，不是风格） | 我方 `application/host` 的 SSH Runner（291 行）需逐条核对 |
| 执行前环境闸门 | `require400G` 直接读快照里的 `speed_mbps` | **抄**：执行前按用例要求校验快照 | 与 ADR-0013 安全闸并列成第二道闸 |
| 不抄 | 57 个探针的具体命令、路径强绑定仓库布局、租约无 TTL、1s 轮询、手写 SVG | — | 见 §1.5 的「不抄」 |

### 1.5 白泽自身缺陷（照抄会带过来的）

| 缺陷 | 证据（白泽调研报告章节） | 我方必须避开 |
|---|---|---|
| 租约无 TTL/心跳/自动回收 | §6.6 D-05 | 我方已有 `ExecutionOrphanSweeper`（按 DB 活跃 run 对账 + 60s SIGTERM），**保留我方机制，不抄租约** |
| 无实时推送，运行中看不到日志 | §6.7 D-06 | 我方已有 WebSocket 推送，不退化 |
| 路径强绑定仓库布局 | §6.9 D-08 | 快照内容寻址，但**存储位置可配置**（`data/` 还是对象存储要可切） |
| 无全局异常处理，错误被压平成一句话 | §6.10 D-09 | 我方有 `GlobalExceptionHandler`；新端点必须登记错误码 |
| 前端 1s 轮询代替推送 | §8.10 C-3 | 不抄 |

### 1.6 重写方案（分三期，避免一次改完无法回归）

| 期 | 内容 | 交付判据 |
|---|---|---|
| **P1 快照对象化** | 新建 `device_snapshot`（内容寻址）+ `device_snapshot_item`（按项）；采集写快照；替代 `env_profile.snapshot_json`；保留旧数据只读兼容 | 同一设备两次采集产生两个快照；`GET /snapshots/{id}` 返回按项结构；旧页面仍可读旧数据 |
| **P2 探针包与拓扑分级** | 探针包配置化（表或 YAML）+ 按设备类型选包；`link` 加 `confidence/source`；拓扑图加图例与过滤；导入 LLDP 邻居 | 交换机与服务器采到不同项集；拓扑图上同一对端口只显示一条线且标注最高 confidence |
| **P3 页面重组 + 执行闸门** | 6 页收敛为 4 页（环境概览 / 设备感知 / 环境准备 / 拓扑与连接）；执行前读快照做环境校验 | 执行一条要求 400G 的用例，快照里 `speed_mbps` 不足时被拒并点名原因 |

**工作量**：P1 中（约 2 张表 + 采集写入改造 + 2 页改造）、P2 中大（探针抽象 + 拓扑三源 + 图组件）、P3 中大（页面重组 + 闸门接入）。合计约等于**一个完整版本**（对应总纲 5.15）。

## 二、R18 维护与恢复

### 2.1 现状：菜单名不副实

| 菜单项 | 路由 | 真实能力 | 证据 |
|---|---|---|---|
| 维护原则 | `/maintenance/principles` | 纯只读（3 条静态原则 + 设置键值） | `ExecutionPrinciplesView.vue:5-7` |
| 恢复记录 | `/maintenance/records` | 纯只读（审计日志里 `case.batch.undo.` 开头动作，只取 4 字段） | `RecoveryRecordsView.vue:5-7` |
| 只读找回 | `/maintenance/recover` | 纯只读（搜历史 run，只能跳转） | `ReadOnlyRecoverView.vue:3-7` |
| 存量同步 | `/sync` | 有真实写（预览/冲突/执行/回滚） | `ProjectSyncView.vue`(385) |

而真实运维能力分散在：

| 能力 | 在哪 | 能否界面触发 |
|---|---|---|
| 备份 | `scripts/ops/backup.sh`(66)、`scripts/backup-drill.sh`(146) | ❌ 界面只有一张只读卡（读 `docs/evidence/ops/backup-drill-latest.json`） |
| 归档/恢复 | `/admin/archive` → `ArchiveCenterView.vue`(240) | ✅ 真执行，默认 dry-run |
| 产物清理 | 报告列表页 | ✅ 真执行，默认 dry-run |
| 告警/巡检 | `/admin/ops` → `OpsCenterView.vue` | ✅ 规则/通道/评估可写 |
| 服务启停/日志 | `ctl.sh` / `logs.sh` | ❌ |

**结论**：R18 要做的不是「新写一套维护功能」，而是**把已经存在的四块（归档/清理/告警/备份脚本）收进一个「运维控制台」，并补上缺的三件事**：备份清单可视化、恢复演练、健康体检。

### 2.2 白泽 `/ops` 可抄什么

| 白泽做法 | 我方对应缺口 |
|---|---|
| 备份清单 13 条，每条带**文件大小 / 脚本数 / 恢复包 / SHA-256** | 我方只有一份 JSON 证据文件，无清单 |
| 健康与存储同页（服务状态 + 磁盘 + 库大小） | 我方 `/api/admin/ops/summary` 有部分数据，但页面只展示告警卡 |
| 远端 Runner 列表 | 我方 `nodes`（执行节点）已存在，不重复 |
| 升级演练（白泽自己也是「规划中」灰项） | 我方有 `scripts/ops/update-drill.sh` + `ROLLBACK.md` 演练记录表，**比白泽强**，缺的是界面呈现 |

### 2.3 方案：一个「运维控制台」+ 四条硬护栏

```text
运维控制台（/ops，新一级菜单或并入现有「系统设置」下）
├─ 健康总览   服务/端口/DB/磁盘/最近采集/最近备份（读）
├─ 备份与恢复 备份清单（大小/时间/SHA256/校验状）+「新建备份」+「恢复到演练库」
├─ 归档与清理 复用 archive 策略（已存在，迁入）
├─ 恢复演练   一键跑 backup-drill（只恢复到 _it 库），出比对报告
└─ 升级演练   读 update-drill 的结果与最近 3 个版本保留情况
```

**四条护栏**（写进 PRD，属不可协商项）：

1. **任何破坏性操作默认 dry-run**，界面上「执行」与「预演」是两个按钮，不是勾选框（现状归档中心的做法正确，沿用）；
2. **恢复只能恢复到演练库**（库名必须 `_it` 结尾，复用 `scripts/db-reset.sh:7-20` 的守卫），要恢复生产库必须走 CLI；
3. **备份文件必须带 SHA-256 并在清单里显示校验状态**（照抄白泽，这是唯一能让用户信任备份的展示）；
4. **所有界面触发的运维动作必须落审计**（`audit` 表，含操作人/参数/结果/耗时）。

**工作量**：中（1 个新页约 800 行 + 3 个后端端点：备份清单、创建备份、演练触发）。**难点不在页面，在「备份清单从哪来」**——`backup.sh` 现在把产物写到固定目录，需要补一个 manifest 输出（脚本小改），后端读目录生成清单。

## 三、R19 安装 / 升级 / 维护 / 拆卸

### 3.1 现状：CLI 已经很完整，界面为零

| 能力 | 脚本 | 规模 | 护栏（已具备） |
|---|---|---|---|
| 安装 | `scripts/ops/install.sh` | 135 行 | 默认 dry-run；必须 `--apply`；只认带 `MANIFEST.json` 的包；非空目录需 `--upgrade` |
| 升级 | `scripts/ops/update.sh` | **526 行** | 十步编排（版本比对→包校验→锁/磁盘→doctor→DB 备份→停/覆盖/起→健康抽样→审计→结论→保留 3 版）；输入 `UPDATE`；降级需 `--restore-db`；`--schema=keep` 只允许 expand |
| 拆卸 | `scripts/ops/uninstall.sh` | 122 行 | 默认 dry-run；必须 `MANIFEST.json`；**从不碰数据库**；输入 `UNINSTALL` |
| 启停 | `ctl.sh` | 119 行 | 只认本安装根 pid/unit |
| 体检 | `doctor.sh` | 163 行 | `--ci` 模式 |
| 升级演练 | `update-drill.sh` | — | 4 阶段（dry-run / 负向包校验 / 正序升级 / 失败回滚），不改真实库 |
| 回滚 | `scripts/rollback.sh` | 335 行 | 三步；`--schema=down` 需二次确认 |

**这套东西的质量高于白泽**（白泽的「升级演练」还是灰项）。问题只有一个：**全部在终端里，平台用户（测试工程师/PM）用不到**。

### 3.2 方案：分层界面化，不做「一键安装」

| 层 | 上界面？ | 内容 | 理由 |
|---|---|---|---|
| **L1 只读** | ✅ 必须 | 当前版本 / 上次升级时间与结果 / 安装根 / 数据目录 / 磁盘余量 / 保留的 3 个历史版本 / 最近一次 doctor 结论 | 这些是「运维事实」，只读没有任何风险 |
| **L2 预检与演练** | ✅ 建议 | 「升级预检」（跑 `doctor.sh --ci` + 包校验 + 磁盘检查，只出报告）、「备份」「备份恢复演练」「升级演练」 | 全部非破坏性（演练恢复到 `_it` 库） |
| **L3 受控执行** | ⚠️ 有条件 | 「执行升级」（上传包 → 预检通过 → 生成升级任务 → 二次输入版本号确认 → 后台执行 → 实时进度 → 失败自动回滚） | 有真实收益（PM 也能升），但必须保留「输入确认」这一护栏 |
| **L4 安装/拆卸** | ❌ 不上界面 | 保持 CLI | `uninstall.sh` 的护栏就是「终端里手输 UNINSTALL」；搬上界面等于把护栏拆掉。且安装发生在「平台还没跑起来」的时刻，界面无能为力 |

### 3.3 若做 L3，必须满足的四条

1. **任务化**：每次升级是一个 `ops_task` 记录（id/操作人/起始版本/目标版本/阶段/日志/结果），可断点查看，不能是一个阻塞 HTTP；
2. **进度可观测**：`update.sh` 十步每步输出一行结构化标记（如 `STEP 4/10 db_backup OK`），后端解析成进度；
3. **失败必回滚且可见**：回滚结果与 `rollback.sh` 的结论一起落库；
4. **禁止降级自动执行**：降级需 `--restore-db`，界面上只能「生成命令」，由人在终端执行。

### 3.4 工作量

| 层 | 规模 | 风险 |
|---|---|---|
| L1 只读（版本/历史/磁盘/doctor 结论） | 小（约 300 行前端 + 2 个端点，`/api/admin/ops/*` 已有 summary/releases 可复用） | 低 |
| L2 预检与演练 | 中（任务化框架 + 3 个动作） | 中：`doctor.sh` 输出要结构化 |
| L3 升级执行 | 大（任务化 + 进度 + 与 `update.sh` 契约） | **高**：升级失败会停机，必须先在演练环境跑通 `update-drill.sh` 才允许上线 |
| L4 | 不做 | — |

## 五、验收判据草案（R17/R18/R19）

| 判据 | 可判定形式 |
|---|---|
| 快照对象化 | 同一设备间隔两次采集 → 两个不同 hash 的快照；按项查询某字段的两次值（不靠文本 diff） |
| 探针分包 | 交换机与服务器采集结果项集不同（断言项数与项名）；新增一项探针**不改代码**即可生效 |
| 拓扑分级 | 同一对端口同时有 LLDP 与规划数据时，图上只显示一条线且 `confidence=lldp`；过滤「仅实测」后规划线消失 |
| 执行闸门 | 快照中速率不足时，要求 400G 的用例被拒，返回点名字段（不是泛化 400） |
| 备份清单 | 清单条目数 = 备份目录文件数；每条的 SHA-256 与 `sha256sum` 实算一致 |
| 恢复演练 | 演练后 `robot_it` 关键表行数与源库一致（复用 `backup-drill.sh` 的比对逻辑） |
| 运维动作审计 | 每次界面触发在 `audit` 表有记录，含操作人与结果 |
| 升级预检 | 预检报告能指出「磁盘不足/包不匹配/迁移非 expand」三类问题各一条 |
