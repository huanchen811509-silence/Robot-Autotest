## 一、R1 二级菜单同时高亮

### 1.1 复现路径（代码级，可在真实界面 1 分钟复现）

| 操作 | 现象 | 期望 |
|---|---|---|
| 全局 → 公共用例 → 导入记录（`/g/cases?view=imports`） | 「用例清单」与「导入记录」**同时**高亮 | 只有「导入记录」亮 |
| 全局 → 公共资产 → 凭据（`/g/assets?tab=credentials`） | 「设备」与「凭据」**同时**高亮 | 只有「凭据」亮 |
| 全局 → 项目 → 我参与的（`/g/projects?scope=mine`） | 「全部项目」与「我参与的」**同时**高亮 | 只有「我参与的」亮 |

### 1.2 根因一：无 query 的叶子对任何 query 都成立

`frontend/src/config/navigation.ts:101-110`：

```ts
function queryMatches(leaf: NavLeaf, route: NavRouteLike): boolean {
  if (!leaf.query) return true          // ← 无 query 的叶子恒真
  const actual = route.query ?? {}
  return Object.entries(leaf.query).every(([key, expected]) => ...)
}
```

各组「默认叶子」不带 query（`/g/cases`、`/g/projects`），带 query 的分支不带默认值互斥规则，于是**任一带 query 的分支被点亮时，默认叶子也同时点亮**。`AppNav.vue:120-122` 对每个子项独立渲染 `active` 类，没有任何「至多一个」的收敛。

### 1.3 根因二：`alsoMatch` 尾斜杠被 `normalizePath` 吃掉，退化为全前缀

`navigation.ts:131-134` 的 `normalizePath` 会去掉尾部斜杠：

```ts
function normalizePath(path: string): string {
  if (path.length > 1 && path.endsWith('/')) return path.slice(0, -1)
  return path
}
```

而 `hitsPrefix`（`navigation.ts:117-120`）用 `path === base || path.startsWith(base + '/')` 判前缀。于是：

- `global-assets-devices` 配了 `alsoMatch: ['/g/assets/']`（`navigation.ts:207-211`），归一化后变成 `/g/assets` → **命中所有 `/g/assets*` 路径**，包括 `?tab=credentials` 自己。
- `global-cases-all` 配了 `alsoMatch: ['/g/cases/']`（`navigation.ts:177`），同理命中 `?view=imports`。
- 注释的本意是「详情页 `/g/assets/:id` 保持父项点亮」（`navigation.ts:128-129`），但**详情页与查询页共用同一 path 前缀**，这条 `alsoMatch` 顺带把查询页也点亮了。

### 1.4 项目模式的同类隐患（方向相反）

项目侧 `/assets` 三个页签**都**带 query、都没有默认叶子（`navigation.ts:411-435`）。所以：

- `/assets?tab=links` → 只有 links 亮，正常；
- `/assets`（无 query，或 query 被清掉）→ **三个都不亮**（当前靠页面 `router.replace` 到默认值兜着，`navigation.ts:120-126` 的注释承认了这个约定）。

结论：**全局模式是「多亮」，项目模式是「可能全灭」**，同一套判定逻辑的两个反向症状，必须在同一个修复里一起解决。

### 1.5 修复方案（三选一，建议 B）

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| A 局部补丁 | 给 `queryMatches` 加特例：默认叶子在「同 path 存在带 query 的兄弟且该 query 命中」时不亮 | 小（约 15 行） | 规则藏在特例里，下一个加二级项的人还会踩 |
| **B 规则化（建议）** | 在 `NavLeaf` 上加 `defaultOf?: true`，并明确「同 path 组内至多一个 defaultOf；有 query 且命中的兄弟存在时，defaultOf 不亮」；`alsoMatch` 只允许写**详情段**（如 `/g/assets/detail/`）或显式 `exclude` 查询页 | 中（改数据结构 + 全站 10 处同 path 叶子复核） | 需要同步改 `navigation.spec.ts` 的 7 组/16 叶断言 |
| C 收敛渲染 | `AppNav.vue` 渲染前把命中集合收敛成「路径最具体的一个」 | 小 | 只是掩盖，`aria-current` 与面包屑仍可能给出两个 |

**无论选哪个，必须补一条不变量测试**：遍历 `router.getRoutes()` 全部静态路由 × 各组默认 query 组合，断言「每个 URL 命中的叶子数 ≤ 1」。当前 `navigation.spec.ts:392-449` 只断言了组数/叶数，没有断言互斥，所以这个 bug 一直绿着。

### 1.6 归属

- **v5.8.0 热修**：只做 `queryMatches` 的互斥特例 + 一条不变量测试（判据：任意 URL 命中 ≤1）。
- **v5.9.0 固化**：改成 `defaultOf` 规则 + `alsoMatch` 白名单校验（可加进 `tools/check_navigation.py`，静态扫 `alsoMatch` 是否以 `/` 结尾）。

## 二、R2 我参与的项目只有一个

### 2.1 现状实现

`backend/src/main/java/com/qa/autotest/application/iam/AccessControlService.java:166-173`：

```java
public List<Project> visibleProjects() {
    long userId = TenantContext.requireUserId();
    if (isAdmin(userId)) return projects.page(null, 1, 1000).items();  // admin 全量
    return projects.findByMember(userId);                              // 其他人：只按 project_member
}
```

`ProjectRepositoryJdbc.java:117-125` 的 SQL 只有 `JOIN project_member m ON m.project_id = p.id WHERE m.user_id = ?`。

### 2.2 三类归属被漏掉（不是「数据少」，是口径窄）

| 归属方式 | 数据在哪 | 是否参与 `visibleProjects()` | 后果 |
|---|---|---|---|
| 项目成员 | `project_member` | ✅ | — |
| **项目负责人** | `project.owner_id`（`V2_1:27-31`） | ❌ | 转移所有权时只 `UPDATE project SET owner_id`（`ProjectService.java:137-158`），**不补 `project_member` 行** → 新 owner 打开「我参与的」看不到自己的项目，且直接访问接口 403（`AccessControlService.java:145-154`） |
| **用户组授权** | `project_group_role` + `user_group_member`（`V8_3:18-23`） | ❌ | 在 `/groups/grant` 授了权限，列表看不到、接口 403，但「有效角色」接口显示已提升（见 R10） |
| 创建者 | `project.created_by`（`V1:21`） | ❌ | 该列**从未被写入**（`ProjectRepositoryJdbc.java:131-144` 的列清单里没有），数据上不可追溯 |

### 2.3 「只有一个」的具体成因（按可能性）

1. 该账号确实只有 1 行 `project_member`，其余项目通过组授权或属主身份获得 → 被过滤；
2. `AdminView` 的项目成员区块一次只能给「当前选中的项目」加人（`AdminView.vue:669-711`），默认项目是 `auth.projects[0]`，操作时容易只加进一个；
3. 平台项目按设计排除（`ProjectRepositoryJdbc.java:123` 的 `p.kind <> 'platform'`），属预期；
4. 旧后端无 `own/joined` 字段时前端 `filter(card => card.own === true || card.joined === true)` 会把卡片全滤掉（`SettingsUsersView.vue:36`），表现为 0 而不是 1，可据此区分。

### 2.4 方案

**把「可见项目」改成三源并集**，并把「来源」一并返回给前端：

```sql
-- 目标口径（示意，非最终 SQL）
SELECT p.*, 'MEMBER' AS source FROM project p JOIN project_member m ...
UNION
SELECT p.*, 'OWNER'  FROM project p WHERE p.owner_id = ?
UNION
SELECT p.*, 'GROUP'  FROM project p
  JOIN project_group_role r ON r.project_id = p.id
  JOIN user_group_member m ON m.group_id = r.group_id WHERE m.user_id = ?
```

同步要改的两处：
1. `AccessControlService.requireProjectAccess`（`:145-154`）必须用同一套并集，否则「列表能看到、点进去 403」；
2. `ProjectCardService`（`:81-111`）的 `own/joined` 字段扩成 `source` 枚举 + `roleCodes`，前端「我参与的」列表加「来源」列（成员/负责人/用户组）。

**注意**：这条与 R10 的「组授权参与判权」是**同一处代码**，必须同版本，不可拆。

### 2.5 验收判据草案

- 用 `pm` 账号把项目 A 的 owner 转给 `eng1`，`eng1` 不改成员关系，`GET /api/projects/cards?scope=mine` 必须包含 A，且 `source=OWNER`；
- 把 `eng2` 加入用户组 G，给 G 授 `P_A:ENGINEER`，`eng2` 的 `scope=mine` 必须包含 A 且 `source=GROUP`；
- 未参与任何项目的 `viewer` 账号 `scope=mine` 返回空数组（不是 500）。

## 三、R4 向导类二级菜单

### 3.1 项目向导：**已经存在**，缺的是入口位置与命名

`frontend/src/views/ProjectWizardView.vue`（971 行），六步（`:34`）：

```ts
const ALL_STEPS = ['template', 'basics', 'runtime', 'members', 'content', 'review']
```

已有能力：

| 步骤 | 内容 | 证据 |
|---|---|---|
| template | 选项目模板（决定内核/可见性/编码前缀） | `ProjectWizardView.vue:138-150` |
| basics | 编码 + 名称 + 描述（编码有格式校验与示例） | `:126-133`、`:153-162` |

### 3.2 模板向导：**不存在**，只有一个内联表单

`frontend/src/views/global/GlobalTemplatesView.vue`（568 行）里 `openCreate()`（`:118`）弹出一个表单，硬性要求「至少关联 1 条用例或 1 个用例集」（`:88`、`:305`）。模板的完整能力（`ProjectTemplateService.java:33-50`）其实支持四类明细 + 资产：

即：**后端模型够用，前端表单装不下**（四类明细 + 资产在一屏表单里无法表达「先选什么、后选什么、冲突怎么办」）。这正是需要向导的判据。

### 3.3 公共资产 / 公共用例 是否需要导入向导

| 对象 | 现状 | 是否值得向导化 | 理由 |

| 公共用例 | 已有 Excel 导入 + 批次记录（`GlobalCasesView.vue:257-275`、「导入记录」二级项 `?view=imports`） | 同上，且**已有独立二级项承载结果** | 同上 |

## 四、R10 用户与权限独立一级菜单

### 4.1 现状：三套并行口径，其中一套不生效

| 口径 | 表 | 谁维护 | 是否参与真实判权 |
|---|---|---|---|
| 全局角色 | `user_role`（`V1:97-109`） | `AdminView` 用户区块 | ✅ `AccessControlService.java:55-57` |
| 项目成员角色 | `project_member` + `project_member_role`（`V1:111-124`、`V11_30:3-13`） | `AdminView` 项目成员区块、项目向导 members 步 | ✅ `:58-61`、`:145-154` |
| 用户组授权 | `user_group_member` + `project_group_role`（`V8_3:2-23`） | **只有 API，前端零入口**（`/groups` 是孤儿路由，`router/index.ts:275-278`，导航树无叶子） | ❌ **完全不生效** |

唯一查组的代码在 `EffectiveRoleResolver.java:35-48`，但它的消费者只有 `GroupController.effective` 与 `GroupService.effective` 两个只读接口；真正判 403 的 `AccessControlService.requireProjectAccess`（`:145-154`）**从不查 `project_group_role`**。

**这是逻辑错误，不是取舍**：界面显示「有效角色已提升为 ENGINEER」，实际访问仍 403。同时 `GroupsView.vue:58` 调 `groupsApi.effective(projectId, 0)` 传的 `userId=0`，结果恒为 `NONE`——**连那个唯一显示组角色的界面也是坏的**。

### 4.2 其余确凿缺陷（同属本维度，需一并修）

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| 1 | 删用户不清理 `project_member_role`，而该表对 `app_user` 有 FK 且**无 CASCADE** | `UserRepositoryJdbc.java:150-156`、`V11_30:11-12` | 删有项目角色的用户 → 外键错误 → 500 |
| 2 | 组相关三表**无任何外键** | `V8_3:11-23`、`V8_6:23-44` | 删组/删用户留孤儿行 |
| 3 | `/admin` 无前端能力闸，且 `USER_ROLE:READ` 对 PM/ENGINEER 放行 | `router/index.ts:189-192`、`PermissionMatrix.java:145-146,178-179` | 工程师可枚举全量用户（含邮箱、角色、启停态） |
| 4 | 路由守卫用本地 `capabilitiesForRole` 兜底表，与服务端 `MENU_CAPABILITIES` 双源 | `router/index.ts:546-552` vs `PermissionMatrix.java:41-43` | 两套口径会漂移 |
| 5 | 角色只有只读 UI，后端 CRUD 无界面 | `api/iam.ts:123-127`、`UserController.java:89-110` | 角色配置只能靠 API |
| 6 | `project.created_by` 从不写入 | `ProjectRepositoryJdbc.java:128-147` | 创建者不可追溯 |

### 4.3 方案：一级菜单「用户与权限」，4 个二级

```text
用户与权限（新一级，全局侧）
├── 角色管理    /g/iam/roles        4 内置 + 自定义（增删改查，内置只读）
├── 用户组      /g/iam/groups       组 CRUD + 成员管理 + 授权项目（见 4.4）
├── 用户        /g/iam/users        用户 CRUD + 全局角色 + 所属组 + 参与项目
└── 项目关联    /g/iam/projects     选项目 → 关联用户组/用户（双向同步的唯一写入口）
```

### 4.4 「自动关联 + 幂等 + 显示同步」怎么保证（R10 的核心诉求）

不要靠「两个页面互相写对方」，而是**一个事实 + 一个视图**：

| 层 | 做法 |
|---|---|
| 事实层 | `project_member` / `project_group_role` 两张表是唯一事实；`user_group_member` 只是组→人 |
| 写入口 | 「项目关联」页是**唯一推荐写入口**；在「用户组」页给组选项目、在「用户」页给用户选项目，都调用**同一组端点**（`POST /projects/{id}/members`、`POST /groups/{id}/grant`），不新增第二套 API |
| 幂等 | 组→项目已幂等（`ON DUPLICATE KEY UPDATE`，`GroupService.java:53-61`）；用户→项目单个**非幂等**（409，`ProjectService.java:338-346`），批量幂等（`:357-389`）→ 统一成「批量语义」（重复视为成功跳过） |
| 显示同步 | 「用户组」页显示「已授权项目 N 个」（`SELECT ... FROM project_group_role WHERE group_id`）；「用户」页显示「参与项目 N 个 / 所属组 N 个」（同一并集查询）；「项目关联」页按项目展开组与用户。三处读**同一聚合接口** `GET /api/iam/relations?dimension=user\|group\|project` |

**菜单数量的机检代价**：`tools/check_navigation.py:50-51` 硬编码 `GLOBAL_EXPECTED=5`，加一级后变 6；`navigation.spec.ts:438-449` 断言「全局 5 组 16 叶」也要改。这属**必然改动**，必须与代码同版提交，否则第一道门红（见总纲 §3.1 第 3 条）。

### 4.5 工作量与风险

| 项 | 规模 | 风险 |
|---|---|---|
| 组授权参与判权（含 403 用例复核） | 中（改 1 个服务 + 重跑 `AuthzMatrixTest`/`AuthorizationBoundaryTest`） | **高**：所有越权用例的期望值都可能变，必须逐条复核不是「改绿」 |

| 关系聚合接口 + 幂等统一 | 中（1 个新端点 + 3 处写入改造迁移） | 中：迁移只能追加 |
| 修 4.2 的 6 条缺陷 | 中（其中「删用户 500」必须走迁移补 CASCADE 或补删除语句） | 低 |

### 5.2 通则（建议写成机检可查的 5 条）

1. **凡列表必有「删除」，且删除必须有二次确认**（统一用 `confirmAction`，禁用 `window.confirm`）；
2. **凡删除必须展示影响面**：被引用数、级联项、不可恢复提示（引用 `GET .../impact` 模式，`RunRecordController.java:72-79` 是现成范式）；
3. **批量操作必须有入口**：要么批量删，要么明确「本页不支持批量」的空态说明（不许「有全选但无动作」，`CaseSetsView.vue:673-690` 就是反例）；
4. **删除失败必须给人话**：外键/引用冲突返 409 并点名（当前 `test_case` 被 4 张无 CASCADE 的表引用，删已绑定脚本的用例会 500「服务内部错误」）；
5. **机检落地**：门禁已有 `LIST_CRUD`（v5.7.0 读数 `PASS=114`），把上表「缺」的项作为**待办白名单**登记，新增列表页不进白名单即红。
