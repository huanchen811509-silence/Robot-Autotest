## 一、R9 现状：四个断点，逐个给出证据

### 1.1 断点一：绑定字段存在，但只对「公共资产库」链路可见

`db/migration/V11_45__asset_credential_binding.sql:16-26`：

```sql
ALTER TABLE `device`
    ADD COLUMN `management_credential_id` BIGINT NULL   -- 业务管理面默认凭证
    ADD COLUMN `bmc_credential_id`        BIGINT NULL;  -- BMC/带外面默认凭证
```

| 层 | 是否有这两个字段 | 证据 |
|---|---|---|
| 表 | ✅ | `V11_45:21-24` |
| 领域实体 `Device` | ❌ | `domain/asset/Device.java:15-35` |

| 全局侧 DTO `AssetRow` | ✅ | `GlobalAssetService.java:78-84` |
| 全局侧读取 | ✅（裸 SQL） | `GlobalAssetService.java:226,247-248` |

**后果**：项目模式「测试资产」页**结构上拿不到**绑定关系，只能显示管理 IP。

### 1.2 断点二：采集时根本不读绑定，仍靠前端临时传 `credentialId`

`GlobalAssetService.java:526-552`：

```java
public CollectResult collect(long deviceId, Long credentialId, String username, boolean confirmed) {
    ...
    if (credentialId != null) ensurePlatformCredentialReference(platformId, credentialId);
    HostInventoryRecord record = hostInventory.collect(platformId, host, deviceId, ..., credentialId, confirmed);
```

`management_credential_id` / `bmc_credential_id` **在方法体里一次都没出现**。绑定的作用只剩三处：前端「能不能点采集」的开关、凭据→设备反查、下拉里的 `bound_devices` 计数。

### 1.3 断点三：验证事实从来不写表 → 「已验证可采集」无法表达

| 项 | 证据 | 后果 |
|---|---|---|
| `CredentialVerificationService.recordFromCollect()` 定义存在，但**全仓唯一引用是它自己的单测** | `CredentialVerificationService.java:183-191`；仅 `CredentialVerificationServiceTest.java:151-152` 调用 | 采集成功不写 `credential_verification` |
| `POST /api/global/assets/{id}/credentials/{credId}/verify` **前端零调用** | `GlobalAssetCredentialController.java:54-67` | 表基本恒为空 |
| `CredentialPicker` 的「四级排序 + 自动选中已验证」依赖 `tier=0` | `CredentialPicker.vue:95-142` | `tier=0` 在实际业务流里永不出现 → 排序形同空转 |
| `device_check.credential_id` 采集成功时回填 | `V11_64:30-33` | 这是**唯一真实记录「用了哪条凭证」的地方**，但没被聚合到列表 |

**这是 R9 的核心**：大师要的「已验证可采集的资产自动关联好采集凭证」，技术上等于「把 `credential_verification` + `device_check` + 绑定列三处聚合成一个可查询的『采集画像』」。当前三者互不相通。

### 1.4 断点四：界面用账号名冒充凭证

`AssetDetailController.java:126-132` 用 `device.account` 生成掩码 → 前端 `api/assetDetail.ts:192` 合成**单条** `id=0` 的假凭据：

```ts
credentials: masked ? [{ id: 0, name: 'credential', keyMasked: masked }] : [],
```

`AssetDetailPanel.vue:303-314` 就渲染这条。**详情页永远显示 1 条、名字叫 `credential`、与绑定关系无关**。

### 1.5 余下三处一致性缺陷（同版必修，否则「关联关系」不可信）

| 缺陷 | 证据 | 后果 |
|---|---|---|
| `canCollect` 只看绑定，后端却只认 `management_ip` | 前端 `GlobalAssetsView.vue:222-224`；后端 `GlobalAssetService.java:528-538` 无管理 IP 直接 400 | **只绑了 BMC 凭据的设备：按钮可点、必然失败** |

| `recordFromCollect` 之外，`referenceCount` 接口无人用 | `api/globalAssets.ts:149-151` 定义，全前端无调用 | 「被几处引用」做不了删除前提示（与 R12 通则冲突） |

## 二、R9 方案：一个聚合对象 + 两个采集入口 + 三处展示

### 2.1 数据层：把「采集画像」做成可查询的一行（不新建业务表，先做视图/聚合查询）

```text
DeviceCollectProfile（查询期聚合，或落 collect_profile 表做缓存）
├─ deviceId / projectId / scope(PLATFORM|PROJECT)
├─ managementCredentialId / bmcCredentialId          ← V11_45 绑定列
├─ boundCredentialName / boundCredentialMasked        ← join credential
├─ lastVerifiedCredentialId / lastVerifiedAt / verifyResult ← credential_verification 最新一条
├─ lastCollectAt / lastCollectStatus / collectCount   ← device_host_spec 聚合（已有：GlobalAssetService.java:221-225）
├─ usable（可采集判定）= 有 management_ip 且 有可用凭证
└─ profileState = READY(已验证) / PARTIAL(仅绑定未验证) / BLOCKED(无凭证或无 IP)
```

**为什么先做聚合而不是新表**：`device_host_spec` 已 append-only（`HostInventoryService.java:27-31`），`credential_verification` 也只追加，事实层已经够了；缺的是「读的时候拼起来」。落表只在一处需要——`profileState` 若要在列表排序/筛选中使用（数量大时），再补一张物化表 + 迁移号。

### 2.2 写入侧：三处补齐（这是「永久保存」的实质）

| 要补的写 | 位置 | 做法 |
|---|---|---|
| 采集成功/失败都写验证事实 | `GlobalAssetService.collect()` 与 `verify` 端点 | 调 `credentialVerification.record(...)`；成功写 `OK`、失败写 `failure_kind`；**`recordFromCollect` 从死代码变成主路径** |
| 采集时若未显式传凭证，用绑定 | `GlobalAssetService.collect()` 入口 | `credentialId == null` 时按 `management_ip` 存在与否取 `management_credential_id`，再退 `bmc_credential_id`；两者都空 → 400 并点名「未绑定凭证，请先关联或手工指定」 |
| 自动关联（首次可采即绑） | 采集成功后的同事务 | 若 `management_credential_id` 为空且本次用的是管理面凭证 → 回填绑定；已有绑定则不动（不覆盖人工选择） |

> 「自动关联」的边界要写进 PRD：**只自动填空，不自动改非空**。否则人工指定的凭证会被下一次采集悄悄覆盖，这属破坏性行为。

### 2.3 交互侧：两个采集入口并存（大师原话「发起采集时候可调整关联 或对已经关联好的直接采集」）

| 入口 | 按钮文案 | 行为 |
|---|---|---|
| 直接采集 | 「采集」（主按钮） | 用绑定凭证一键采集；未绑定时按钮禁用并有 `title` 说明缺什么 |
| 调整后采集 | 「采集（指定凭证）」次按钮/下拉 | 弹凭证选择器（`CredentialPicker` 四级排序），选完可勾「同时设为默认凭证」→ 写绑定 |
| 批量 | 「对已关联的设备批量采集」 | 走 `POST /assets/credentials/{credId}/collect`（已存在，`GlobalAssetController.java:99-104`） |

### 2.4 可视化：三处展示（列表 / 关系 / 结果）

| 面 | 展示什么 | 数据来源 |
|---|---|---|
| 设备列表新增列 | 「凭证」列（`mgmt: rd-01 · bmc: bmc-01` 或「未关联」）+「采集」列（`READY 已采集 2 次 / 3h 前`）+「状态」列（可采/不可采 + 原因） | 2.1 的聚合 |
| 关联关系视图 | 双向：设备行展开看「关联的凭证 + 最近验证」；凭据行「关联设备」弹层（已存在，`GlobalAssetsView.vue:720-776`）加「最近验证/失败原因」列 | 同上 + `credential_verification` |
| 采集结果 | 复用 `device_host_spec` 的十类清单详情（`AssetDetailPanel` 四层证据已做），补「历史采集列表 + 两次对比」 | `HostInventoryRepositoryJdbc`（已有 list/detail 分离），对比可参考 `SnapshotCompare` 思路（见 05 报告） |

**「结果持久化」现状是达标的**（append-only 入库），缺的是「可视化里看不出哪次是哪条凭证采的」——把 `device_check.credential_id` 与 `device_host_spec` 关联起来展示即可，不需要新表。

### 2.5 工作量

|---|---|

## 三、R16 项目测试资产：照搬全局形态，仅显授权

### 3.1 现状：两套独立实现，能力互补而非重叠

| 维度 | 项目模式 `/assets` | 全局模式 `/g/assets` |
|---|---|---|
| 组件 | `AssetsView.vue`（1451 行） | `GlobalAssetsView.vue`（1106 行） |
| 页签 | 4 个：devices / links / credentials / leases | 2 个：devices / credentials |
| 端点 | `/api/projects/{id}/devices\|links\|credentials` | `/api/global/assets*` |
| 独有能力 | 批量删除（`BatchController`）、平台资产引用/解除、链路管理 | Excel 导入导出、采集、凭证绑定录入、软失效 |
| 详情页 | 同一个 `AssetDetailPanel`（`source` 后端忽略） | 同上 |

**授权关系**在 `project_asset`（`V7_3:48-63`），可见性拼接唯一来源：

```sql
-- AssetScopeSql.java:22-27
WHERE (d.project_id = ? OR (d.owner_scope = 'PLATFORM' AND pa.id IS NOT NULL))
```

即：**「仅显授权资产」这件事后端已经成立**，前端没做的是「同一套形态 + 同一套列 + 同一套操作」。

### 3.2 方案：一个工作台组件，两种 scope

```text
AssetWorkspace(scope: 'project' | 'global', projectId?)
├─ 页签：设备 / 链路(仅 project) / 凭证 / 授权租约(仅 project)
├─ 列集合：由 scope 决定「是否显示归属/引用数/授权状态」
├─ 动作：采集/绑定（两种 scope 都可用，后端按 owner_scope 决定是否允许写）
└─ 删除：project 侧走「解除引用 or 删除私有」，global 侧仅管理员且被引用 409
```

要点：
1. **不合并后端端点**（两套服务各有权限与审计语义，合并风险大），只合并前端工作台；
2. 列差异用配置表表达（如 `owner_scope === 'PLATFORM'` 时显示「来源：公共资产」+「解除引用」），不要写两套模板；
3. 采集入口在项目侧**必须对项目授权来的平台设备可用**——这要求修 1.5 的第二条缺陷（当前对项目私有设备 404），修法是把采集端点从「只认 `owner_scope='PLATFORM'`」改为「认 `AssetScopeSql` 的可见性，凭证必须是本项目可见的凭证」。

### 3.3 工作量与风险

| 项 | 规模 | 风险 |
|---|---|---|
| 抽 `AssetWorkspace` 组件（约 1200 行，替换 1451 + 1106 两处） | 大 | 两套的列/动作差异多，容易做成「都塞进去」的巨型组件 → 需先列差异矩阵（PRD 阶段做） |
| 采集端点 scope 放宽 | 小 | 权限面变化，需补越权用例 |
| 链路/租约页签保留 | 小 | — |

**建议顺序**：先做 R9 的数据与写入（后端），再做 R16 的合并（前端）。反过来会把「采集入口」在旧组件里实现两遍。
