### 1.2 差距（逐条对大师原话）

| 大师要求 | 现状 | 差距 |
|---|---|---|
| 仅留「列表」一个视图 | 两个视图并列在工具栏 | 删「分类归组」按钮与 `CaseCategoryTree` 的单栏形态；分类下沉为中栏 |
| 中栏分类要按「分类分组」的两级 | 列表视图的分类侧栏是**单级**（只列 L1），且与 `?group=1` 的树是两套渲染 | 需要**一个两级树组件**同时服务：中栏（选中即过滤）、向导内容选择器（勾选用例） |
| 右边工作区是对应用例列表 | 右侧就是表格（无工作区概念，详情走行内展开） | 保留表格，但**详情区固定在工作区底部**（R6） |
| 每个用例能单独打开看全部细节 | 目前只有行内展开（`CasesView.vue:622-629`），且 `GlobalCasesView` **列定义无行内展开** | 全局页需补详情区；另外 `/g/cases/:id` 是**孤儿路由**（`router/index.ts:494-499`，全仓无入口） |
| 与表格严格信息幂等 | `CaseDetailPanel.vue:77-79` 把 `precondition/steps/expected` **硬编码成「源表无此列」**，而库里这两列明明存在（`V2_3:8-11`）且有 `test_case_step` 表（`V1:294-303`） | **当前直接违反幂等**：详情说没有的字段，列表/库里有 |

> 这一条值得单独强调：**「信息幂等」现在是有确凿反例的**。修法不是「让详情少显示」，而是「表格列集合 ⊆ 详情字段集合，且详情必须取真值」。PRD 里应写成可判定的不变量，并加一条单测：遍历表格列配置，断言每个 `key` 都能在详情 DTO 里找到同名或显式映射的字段。

### 1.3 建议布局

```text
┌────────────── 页头（标题 + 计数 + 导入/导出动作）──────────────┐
├───────────────┬────────────────────────────────────────────┤
│ 中栏 240px    │ 右工作区（用例表格）                        │
│ 分类树        │  筛选条 / 列设置 / 分页                     │
│  L1 域        │  ┌──────────────────────────────────────┐  │
│   └ L2 分类   │  │ 用例行（编号/标题/分类/优先级/路径）  │  │
│ 全部 / 未分类 │  └──────────────────────────────────────┘  │
│               ├────────────────────────────────────────────┤
│               │ 详情区（选中行后在此渲染，非弹窗/非跳页）   │
└───────────────┴────────────────────────────────────────────┘
```

- 中栏的「全部/未分类」是必要项：没有它，选中分类后无法回到全集；
- 两级表达：L1 可折叠，L2 可点；点 L1 时右表按整个域过滤（不是只展开树）；
- 分类数据源复用 `GET /api/global/cases/grouped`（`CaseGroupingController.java:20-23`），**无需新端点**。

## 二、R6 详情在「当前列表下方」展开

### 2.1 现状：三种范式并存，只有一种是大师要的

| 范式 | 用例 | 证据 | 是否符合要求 |
|---|---|---|---|
| 表格行内展开（`type: 'expand'`） | 项目用例清单 | `CasesView.vue:622-629`（**全站唯一** `renderExpand`） | 符合（就在行下方） |
| 表格下方面板（选中行 → 面板） | 项目资产端口、运行日志 | `AssetsView.vue:208-219` 注释明确「端口面板独立在表格下方（同 RunsView 的日志面板），不做行内展开」 | 符合（就在列表下方） |
| 弹窗 / 抽屉 / 独立路由页 | 全局资产详情、全局用例详情、资产详情（`/assets/:id`、`/g/assets/:id`、`/g/cases/:id` 三条孤儿路由）、各类导入弹窗 | `router/index.ts:494-510`（无任何 `router.push`） | **不符合** |

### 2.2 方案：抽一个 `DetailDock` 规范 + 组件

| 项 | 约定 |
|---|---|
| 位置 | 列表容器内部、表格之后（不是页面最底部、不是 fixed 浮层） |
| 触发 | 单选行 → 就地渲染；再点同一行 → 收起；切换行 → 原地替换内容 |
| 滚动 | 打开时 `scrollIntoView({ block: 'nearest' })`，**不允许**跳到页面底部 |
| 宽度 | 与表格同宽；内部两列（字段 / 值），不做三栏 |
| 状态 | URL 可选携带 `?detail=<id>`，刷新后能恢复（与「列表筛选可分享」同一目标） |
| 复用 | 用例、用例集成员、资产、凭证、报告行、运行记录统一用它 |

工作量：组件约 200 行 + 4~6 处接入点各 10~30 行改写。**真正的工作量在「改掉弹窗习惯」**，涉及 6 个页面的交互回归。

### 2.3 验收判据草案

- 在 1440×900 视口下点开任意行，详情区**首屏可见**（不需要滚动页面），且表格仍可见（不是整页替换）；
- 详情区与表格同宽（`clientWidth` 差值 ≤ 2px）；
- 刷新后若 URL 带 `?detail=<id>`，详情区自动展开且滚动位置正确。

## 三、R7 全站用例显示「测试文件相对路径 + 文件名」

### 3.1 数据在哪：**在，但没被用**

`db/migration/V11_47__case_script_binding.sql:20-41`：

```sql
CREATE TABLE `case_script_binding` (
  project_id BIGINT NOT NULL,
  case_id    BIGINT NOT NULL,
  kernel     VARCHAR(32) NOT NULL DEFAULT 'pytest',
  script_path VARCHAR(512) NOT NULL COMMENT '相对仓库根的脚本路径',
  node_id     VARCHAR(512) NULL,
  script_sha256 CHAR(64) NULL,
  resolve_source VARCHAR(16) NOT NULL DEFAULT 'FILENAME',
  verified   TINYINT NOT NULL DEFAULT 0,
  UNIQUE KEY uk_binding_case_kernel (project_id, case_id, kernel)
);
```

**文件名不单独存**，从 `script_path` 末段取（后端已有先例：`PytestResultNormalizer.java:249-256` 的 `fileStemOfPath`）。

### 3.2 三个显示面全都没取（这就是 R7 的全部工作）

| 显示面 | 现状 | 证据 |
|---|---|---|
| 用例列表（项目 `/cases`） | 列集合 7 个可配置列，**无路径列** | `CasesView.vue:356-375` |
| 用例详情（`CaseDetailPanel`） | 21 字段 DTO，**无路径** | `GlobalCaseService.java:87-95`、`api/caseDetail.ts:14-35` |
| 用例集成员 | SQL 只 `SELECT c.* FROM test_set_item i JOIN test_case c`，**不 join 绑定** | `TestSetRepositoryJdbc.java:197-215` |
| 全局用例清单 | 同上，无路径 | `GlobalCasesView.vue:133-186` |
| 唯一有路径的地方 | pytest 工作台「绑定覆盖率」表 | `PytestWorkbenchView.vue:52-57` |

### 3.3 方案

1. **后端一次 join，三处复用**：新增聚合查询（或在现有 SELECT 上 `LEFT JOIN case_script_binding b ON b.project_id = c.project_id AND b.case_id = c.id AND b.kernel = c.kernel`），返回三字段：
   - `scriptPath`（相对路径，完整）
   - `scriptName`（末段文件名，后端算，避免前端多套切法）
   - `bindingState`（`BOUND_VERIFIED` / `BOUND_UNVERIFIED` / `UNBOUND`，由 `verified` 与 `script_sha256` 推）
2. **前端统一组件 `CaseScriptLink`**：显示文件名（`mono` 字体，悬浮显示完整相对路径，点击复制）；未绑定时显示「未绑定脚本」灰标签，不隐藏。
3. **列位置**：用例表格在「标题」后插一列「脚本」（默认显示，可在列设置里隐藏）；详情区顶部固定一行「脚本：`cases/net/roce_bw.py` · nodeId `cases/net/roce_bw.py::test_bw` · 已校验」。
4. **多内核**：同一用例可能同时绑 pytest 与 robot（`uk_binding_case_kernel` 允许多行），显示规则是「当前项目内核优先，其余折叠为 `+N`」。

### 3.4 前置依赖与风险

- 依赖 v5.11 的列表改造（同页改，不额外开版）；
- 风险：`case_script_binding` 目前只有 pytest 链路在写（`PytestWorkbench`），RF 用例可能**全部显示未绑定**。需要在 PRD 里定「RF 的路径从哪来」——`robot_file.path`（`V1:336-350`）存在但与 `test_case` 无关联列，属真实缺口，建议**先只接 pytest，RF 标「不适用」并在界面写明**，不做半假的自动匹配。

## 五、R13 项目改为用例/用例集 是否影响全局

### 5.1 代码结论：**物理隔离，仅本地影响**

| 事实 | 证据 |
|---|---|
| `test_case` 只有 `project_id`，**无 `owner_scope`/`tenant`/`scope` 列** | `V1__baseline.sql:269-293`；全库 `grep owner_scope` 只命中 device/credential/link（`V7_3`）、test_set（`V9_3`） |
| 「全局用例库」是一个**特殊项目**（`PLATFORM-LIB`），不是共享行 | `PlatformProjectService.java:14-50` |
| 编辑/删除一律带 `project_id` | `TestCaseRepositoryJdbc.java:186-197`（update + `TenantGuard.requireProjectScope`）、`:200-215`（delete） |
| 用例集才有「平台资产 + 项目副本 + 分叉」三件套 | `V9_3:15-30`（`owner_scope`、`source_asset_id`、`scope_project_id`）、`AssetVersionService.java:271-350` |

**所以「项目里改用例会改坏全局」这个担心不成立**。真正需要提示的是另外两件事：

### 5.2 需要提示的两个真实场景

| 场景 | 机制 | 建议提示 |
|---|---|---|
| **平台用例集的副本同步** | 项目的集合若 `source_asset_id` 非空，就是平台集的副本；`syncFull` 会按 `case_code` 找成员、缺则新建、`ADD_ONLY` 保留本地改写后判 `DIVERGED`（`AssetVersionService.java:271-350`） | 在集合头显示徽章「来源：平台集 #123 · 已同步 / 已分叉（本地有改动）」，同步前弹**影响面预览**（将新增 N 条、覆盖 M 条、保留 K 条本地改写） |
| **存量同步（ProjectSync）按 `external_id` 覆盖** | 相同 `external_id` 视为同一条，非 `local_override` 字段会被覆盖（`ProjectSyncService.java:20-23`） | `/sync` 页已有预览 → 冲突 → 执行 → 回滚四步（`ProjectSyncView.vue`），保持；在用例详情加「来源：存量同步 · 本地已改写（不再覆盖）」徽章 |

### 5.3 一处需要修的契约漏洞（不是 R13 的需求，但同源）

`TestCaseRepositoryJdbc.java:243-256` 的 `writeImportMetadata` 与 `:228-238` 的 `insertImportedSteps` **只按 `id` 更新，不经 `TenantGuard`**。当前调用点紧跟同事务内刚插入的 id，实践安全，但属「跨项目写」的契约漏洞，建议同版加 `project_id` 条件（一行 SQL），并登记到门禁（`check_kernel_decoupling.py` 或新增一条租户校验）。**这属代码缺陷修复，不单独开需求号**。
