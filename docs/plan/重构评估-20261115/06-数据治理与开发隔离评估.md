# 评估报告 06 · 数据治理与开发隔离（GOV）

| 项 | 内容 |
|---|---|
| 覆盖需求 | R3 开发期账号/项目/用例/报告要按阶段清理 + 开发账号与用户项目隔离、R11 的项目编号与属主归属部分 |
| 代码基线 | 提交 `3e14bea` |
| 结论 | **当前没有任何「演示数据」的可识别标记，也没有清理机制**——只能整库重置（且被限制为 `_it` 库）。这意味着「阶段完成后移除」现在只能靠人肉记忆 + 手写 SQL，**而手写 SQL 的顺序错了会撞外键**。R11 的自动编号已经可用，缺的是「前缀注册、并发唯一、删除后不复用」三条保障。 |

## 一、R3 现状：三件事都没有

| 应有能力 | 现状 | 证据 |
|---|---|---|
| 区分「开发/演示数据」与「用户数据」 | **无标记列**（全库无 `is_demo` / `demo_flag`） | `grep is_demo\|demo_flag` 全仓 0 命中 |
| 清理机制 | **无按标记清理的脚本**；只有整库重置 `scripts/db-reset.sh`（强制库名 `_it` 结尾 + 交互确认） | `scripts/db-reset.sh:7-20` |
| 开发账号约定 | 只有一份手写 SQL，用 `INSERT ... WHERE NOT EXISTS` 保证可重复执行，**没有配套 DELETE** | `artifacts/tmp/qa-ui.sql:1-11`（账号 `qa-ui`，注释「仅供本机 UI 验证」） |
| 开发项目 | 无种子、无标记；v2.7 的「双演示项目」是人工通过接口/UI 建的 | `CHANGELOG.md:616-618` |
| 脚本里用的账号 | 多个 UI 探针脚本默认用 `qa-e2e-admin`，只读登录、不收尾 | `scripts/browser-regression.mjs:26`、`scripts/e2e-smoke.mjs:34` 等 |

### 1.1 为什么「阶段完成后移除」现在做不干净

两个硬阻碍：

1. **删除项目被业务数据挡住**：`ProjectService.java:254-311` 的 `busyCounts` 会统计 30+ 张表，有数据就只能停用不能删（这是对的，防误删）；
2. **删除用户的顺序错了会 500**：`UserRepositoryJdbc.delete` 只清 `user_role` / `api_token` / `project_member` / `app_user`（`:150-156`），**没清 `project_member_role`**，而该表对 `app_user` 有 FK 且无 CASCADE（`V11_30:11-12`）。

### 1.2 顺带的三个数据卫生问题

| 问题 | 证据 | 影响 |
|---|---|---|
| `project.created_by` 永远是 NULL | `ProjectRepositoryJdbc.java:128-147` 插入列清单里没有它 | 「谁建的这个项目」不可追溯（与 R2 的归属口径同源） |
| 组相关三表**无外键** | `V8_3:11-23`、`V8_6:23-44` | 删组/删用户留孤儿行，`user_group_member` 会越积越多 |
| 组授权不参与判权 | 见 01 报告 §4.1 | 清理时无法判断「这个组授权是否还有人依赖」 |

## 二、R3 方案：标记 + 隔离 + 分阶段清理，不做「自动删数据」

### 2.1 数据层：一个标记 + 一个专属账号/项目

| 对象 | 标记方式 | 为什么这样选 |
|---|---|---|
| 开发账号 | `app_user.username` 统一前缀 `dev-`（或 `qa-`）+ 可选 `is_demo TINYINT NOT NULL DEFAULT 0` | 前缀可肉眼识别、可用于脚本；`is_demo` 用于界面打标与门禁校验。**两者都要**：前缀防「新账号忘记勾选」，标记防「前缀被合法用户占用」 |
| 开发项目 | `project.kind` 增枚举 `dev`（现有值含 `standard`/`pytest-suite`/`platform`），并置 `is_demo=1` | 用 `kind` 而不是新列，能直接复用现有按 kind 过滤的逻辑（`p`kind <> 'platform'` 已在用） |
| 开发期产生的用例/报告 | **不单独标记**（数量太大），靠「所属项目是 dev」级联识别 | 用例/报告表都有 `project_id`，级联删除即可 |

**迁移**：`V11_65`（追加）——`app_user.is_demo`、`project.is_demo`、`project.kind` 枚举扩展 + 一个 `dev` 专用账号种子（幂等 `INSERT ... WHERE NOT EXISTS`）。

### 2.2 清理脚本：按依赖顺序，默认 dry-run

`scripts/ops/purge-demo.sh`（新增），三条硬规矩：

1. **默认 dry-run**，列出「将删除 N 个用户 / M 个项目 / K 个 run / J 个 test_case」，必须 `--apply`；
2. **只删 `is_demo=1`**，任何 `is_demo=0` 的对象即使名字像演示也不碰；
3. **按外键顺序删**（这个顺序是踩过坑的，必须写死在脚本里）：

```text
project_member_role → project_member → user_group_member → project_group_role
  → test_set_item → test_case_step → case_script_binding → case_requirement
  → case_requirement_version → manual_execution → test_result → keyword_result
  → run_artifact → run → test_report → report_template_field → report_template
  → device_port → link → device → credential → project_asset
  → project → api_token → user_role → app_user
```

4. **删完做一次对账**：断言「`is_demo=0` 的对象数量在执行前后不变」（这条是防「删多了」的唯一硬护栏）。

### 2.3 阶段化：写进每个版本的 TEST-PLAN 收尾项

| 阶段 | 清理对象 | 时机 |
|---|---|---|
| 开发中 | 每轮 UI 取证后的临时项目/用例 | 取证完立即（脚本 `--apply --scope=round`） |
| 版本收尾 | 该版所有 `dev-*` 项目、演示用例集、演示报告 | 05-TEST-REPORT 定稿前 |
| 发版前 | **断言 `is_demo=1` 的对象数为 0**（或仅保留一个「示例项目」并由大师指定） | 打包前 |

**门禁**：新增一条机检 `check_demo_data`——连接当前库统计 `is_demo=1` 的对象，若 >0 且 `VERSION` 已 bump 到发版号，则判红并列出清单。理由：v5.7.0 就出现过「演示数据混在交付证据里」的返工。

### 2.4 边界（这是 D-5，必须大师拍板）

| 选项 | 含义 | 风险 |
|---|---|---|
| **A 标记 + 显式清理（建议）** | 只清理 `is_demo=1`，每次由人（或收尾流程）显式触发 | 低。缺点是需要人记得跑 |
| B 按「N 天未登录的 dev- 账号」自动清理 | 定时任务自动跑 | **高**：等于自动删数据，一旦账号被真实用户复用会造成事故 |

学徒建议 A，并把「跑清理」写进七道流程第 7 道（文档回写）的检查清单。

## 三、R11 编号与属主部分

### 3.1 自动编号：**已有，且规则正确**

`ProjectService.nextCode(prefix, kernel)`（`:191-196`）→ `nextCodeSequence(scope)`（`:196`），格式由 `ProjectTemplateService.java:41` 的正则约束：

```java
private static final Pattern CODE = Pattern.compile("^([A-Z][A-Z0-9]{1,7})-(RF|PYT)-(\\d{6})-(\\d{3,})$");
```

前端在向导里给示例（`ProjectWizardView.vue:126-133`）：

```ts
return `${tpl.codePrefix}-${engineCode(form.testKernel || tpl.testKernel)}-${yearMonth()}-001`
```

即：**前缀（模板定）+ 内核（RF/PYT）+ 年月 + 三位流水**，符合 R11「自动分配项目编号」的要求。

### 3.2 三条缺口

| 缺口 | 现状 | 建议 |
|---|---|---|
| **删项目后编号复用** | `nextCodeSequence` 按 `MAX(序号)+1` 取（`ProjectService.java:196` 附近）→ 删掉最后一个项目后，新项目会拿到同一个号 | 引入 `project_code_sequence`（前缀+年月+内核 → 已发最大号，只增不减）；迁移回填现有最大号。判据：删掉编号末号再建项目，新号必须是 +1 不是复用 |
| **并发唯一** | 靠 DB 唯一键兜底（`uk_project_code` 或 `uk_test_set_scope_code` 同类），并发下会 500 而不是重试 | 捕获 `DuplicateKeyException` 后重试 3 次（每次重新取号）；判据：并发 5 个请求创建，5 个不同编号且全成功 |
| **前缀注册** | 前缀由模板 `codePrefix` 决定，无集中清单；两个模板写同一前缀会撞号 | 前缀表 `project_code_prefix`（前缀/含义/内核/负责人），创建模板时校验；判据：重复前缀被拒并点名 |

### 3.3 属主归属（与 R2 同源）

`project.owner_id` 存在但「转移所有权不补成员行」（`ProjectService.java:137-158`），且 `created_by` 从不写。R11 要求「配置项目属性」，其中「负责人」是必填属性 → 修法：

1. `ProjectRepositoryJdbc.insert` 补 `created_by`（一行 SQL）；
2. 转移 owner 时**同事务**补 `project_member` + `project_member_role`（避免新 owner 看不到项目）；
3. `visibleProjects` 改成三源并集（见 01 报告 §2.4）——**这两条必须同版，否则转了 owner 仍然看不到**。

## 四、工作量与风险

| 项 | 规模 | 风险 |
|---|---|---|
| 迁移（is_demo 两列 + kind 扩展 + 前缀序列表 + created_by 回填） | 小（1~2 支追加迁移） | 低（都是加列/加表，无破坏性） |

| 门禁 `check_demo_data` | 小 | 低 |
| 编号序列 + 并发重试 + 前缀校验 | 中 | 中：并发重试要真并发测（5 线程） |
| 转移 owner 补成员 + created_by | 小 | 低 |

## 五、验收判据草案

| 判据 | 可判定形式 |
|---|---|
| 开发数据可识别 | `GET /api/projects?include=demo` 能筛出全部 `is_demo=1`；界面上打「演示」标签（截图） |
| 清理不误伤 | 造 3 个 dev 项目 + 2 个真实项目 → 跑 `--apply` → 真实项目及其用例/报告数量前后一致（断言） |
| 清理可预演 | 不加 `--apply` 时库内行数不变（断言） |
| 编号不复用 | 删除最大编号项目 → 新建 → 编号为原最大号 +1 |
| 编号并发唯一 | 5 并发创建全部成功且编号互异 |
| 属主可见 | 转移 owner 后新 owner `scope=mine` 可见且 `source=OWNER` |
| 门禁 | `VERSION` 为发版号时，库内 `is_demo=1` 对象数必须为 0，否则门禁红并列出清单 |
