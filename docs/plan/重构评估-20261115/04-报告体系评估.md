## 一、R14 执行报告 / 测试报告

### 1.1 现状：数据层分家，界面口径三套

| 维度 | 执行报告 | 测试报告（对外） |
|---|---|---|
| 数据实体 | `run` 表（**没有独立的执行报告展示表**） | `test_report`（自包含快照） |
| 依据 | `V11_63__report_crud.sql:3-6`：「执行报告 = `run` 表」 | `V8_1__test_report.sql:1-3`：「测试报告（对外）与执行报告（对内）分家」 |
| API | `/api/reports` | `/api/test-reports` |
| 菜单文案 | 报告列表 | **对外报告** |
| 页面标题 | 报告列表 | **测试报告** |
| 代码命名 | `Report*` | `TestReport*` |

**同一入口在界面上有三个名字**：菜单叫「对外报告」、页面标题叫「测试报告」、报告列表页顶部那个跳转按钮**也叫「测试报告」**（`ReportsView.vue:296-300` 用 `t('testReports.open')`，文案在 `locales/zh-CN.ts:1716`）。用户无法从名字判断「这是对内还是对外」。

### 1.2 建议口径（R14 的实质是「改文案 + 加链接」）

| 位置 | 统一为 | 理由 |
|---|---|---|
| 菜单「报告列表」 | **执行报告** | 它列的是 `run`，内容是对内执行事实 |
| 菜单「对外报告」 | **测试报告** | 大师原话「把对外报告改成测试报告」 |
| 页面标题 | 与菜单一致 | 消除「位置区分」代替「名字区分」 |
| 报告列表页顶部跳转按钮 | 「查看测试报告」 | 动作语义而非对象语义，避免与菜单同名 |
| 代码/表名 | **不改**（`run` / `test_report` / `TestReport*`） | 改表名要迁移 + 契约重生成，收益为零；用 i18n 层对齐即可 |

> 对外口径涉及词条，按规矩报大师拍板（属 D 类：口径问题）。

### 1.3 套件数：**当前不存在**

| 检查项 | 结论 | 证据 |
|---|---|---|
| 数据库列 | 无 `suite_count`；`run` 表无套件维度 | `V1__baseline.sql:452-471` |
| 列表 DTO | 只有 `pass/fail/skip` 计数 | `ReportController.java:133-139,177-190` |
| 套件树来源 | **查询期按 `case_key` 现场拼**，不落表 | `ReportTreeService.java:18-26,100-122` |
| 列表页展示 | 三个列表（`/reports`、`/test-reports`、看板）**都不显示** | `ReportsView.vue:56-131`、`TestReportsView.vue:228-243`、`OverviewView.vue:104-136` |
| 深链 | 只能进详情看整棵树，**没有套件级页面/参数** | `ReportDetailView.vue:884-891`、`SuiteTree.vue:163-171` |

### 1.4 方案：套件数怎么算、链接到哪

**算法**：`case_key` 形如 `suitePath.caseName`（`V5_1:22` 注释），套件数 = 按 `/`（RF）或 `.`（pytest 归一后）切分后的**唯一前缀集合大小**。注意两点：

1. 必须与 `ReportTreeService` 用**同一套切分规则**，否则列表数字与详情树对不上（这是最容易出的「数字不一致」投诉）；
2. RF 与 pytest 的 `case_key` 形态不同（RF 是 `/`，pytest 归一后是 `.`），需要在归一化时统一成一种分隔符，或在聚合时按 kernel 分支。

**落点（二选一）**：

| 方案 | 做法 | 代价 | 取舍 |
|---|---|---|---|
| A 查询期聚合 | 列表 SQL 加子查询 `COUNT(DISTINCT prefix)` | 低 | 10000 行 run 的列表会慢（v5.6 已测 fps 项，需回归） |
| **B 入库期落列（建议）** | `run` 表加 `suite_count INT`（迁移追加），`ReportIngestService` 入库时写 | 低（1 列 + 1 处写） | 需要回填历史 run（可置 NULL 并显示「—」，不强行回填） |

**链接**：列表「套件数」列渲染为链接 → `/reports/{runId}/suites`（新页面：左侧套件列表，右侧该套件的用例与日志），或退一步 `/reports/{runId}?suite=<path>` 让详情页展开对应节点。**建议后者**（不新增页面，复用现有 `SuiteTree` 的展开能力），成本约为新增页面的 1/3。

### 1.5 顺带修的 CRUD 缺口（与 R12 通则联动）

| 缺口 | 证据 | 处理 |
|---|---|---|
| `/reports` 无批量删、无影响面预览 | `ReportsView.vue:221-227` 自述「没有预览端点」；而 `/runs/{runId}/impact` 是现成的（`RunRecordController.java:72-79`） | 复用 `impact`，批量删走 `DELETE /api/reports/{runId}` 循环或新增批量端点 |
| 看板报告列表无操作列 | `OverviewView.vue:104-136` | 加操作列（查看/删除），删除走与 `/reports` 同一端点，不另写一套 |
| `run` 与 `report` 删除是同一件事两个入口 | `ReportLifecycleService.java:59-65` 都软删 `run.deleted_at` | 保留两入口但文案统一为「删除执行记录（含报告）」，避免用户以为删了两份 |

## 二、R15 测试报告模板与预览

### 2.1 现状：模板是「DB 配置 + 代码白名单」，没有按内核分支

| 组成 | 位置 | 说明 |
|---|---|---|
| 模板本体 | `report_template`（`V9_2:19-35`） | 项目级/平台级（`project_id=0`） |
| 字段与顺序 | `report_template_field`（`V9_2:37-54`） | `field_key` + `sort_order` + `title_override` |
| 可选字段白名单 | **代码常量**（`ReportFieldWhitelist.java:30-53`） | 未列入默认拒绝 |
| 必填不可删 | 代码常量 `reportId/title/version/frozenAt/disclaimer/watermark` | `ReportFieldWhitelist.java:49-50` |
| 选择规则 | 项目默认 → 平台默认（`project_id DESC`） | `ReportTemplateRepositoryJdbc.java:146-156` |
| 冻结绑定 | 冻结时把 templateId/version/fields 写进快照 JSON | `ReportSnapshotService.java:25-27` |

**关键缺口：没有任何「按工程类型/内核」的分支**。对 `application/report`、`api/report`、模板仓储 grep `projectKind|pytest-suite|PYTEST_SUITE` → **0 命中**。所以 EHT pytest 工程库用的是平台默认的 **21 字段全量模板**，与标准 RF 工程完全一样。

### 2.2 现状：对外报告「能建不能看」（这是 R15 最硬的一条）

| 能力 | 后端 | 前端 |
|---|---|---|
| 渲染（`GET /api/test-reports/{id}?external=`） | ✅ `TestReportController.java:66-72` | ❌ `testReportsApi.render` **零消费者**（`api/testReports.ts:69-73`，全仓 grep 仅命中定义与单测） |
| 导出 html/pdf/docx | ✅ `ReportExportService.java:104-110` | ❌ `exportBlob` **零消费者** |
| 预览 | — | ❌ **没有详情路由**（`router/index.ts:183-187` 只有列表） |
| 打印页（执行报告） | ✅ `POST /api/reports/{runId}/print-token`（`ReportExportController.java:70-77`） | ❌ 无调用方（`printUrl\|print-token` 全仓仅命中定义） |
| 快照 HTML | ✅ 落库 `test_report.snapshot_html`（`V8_1:12`、`ReportSnapshotService.java:117-125`） | ❌ 没有「打开 HTML」的端点与页面 |
| 自动生成开关 | ✅ `report.auto_generate`（`ReportAutoGenerator.java:47-52`） | ❌ 设置页只有 `report.retentionDays`（`SettingsView.vue:44`），该键在 `frontend/src` **零命中** |

**结论**：R15 的「最好可以预览」不是新建能力，是**把已有的后端能力接到界面**——这是本维度性价比最高的一条。

### 2.3 方案（三层，按依赖排序）

#### 第一层：补前端入口（1 个版本内可完成）

| 项 | 做法 |
|---|---|
| 测试报告详情页 | 新增 `/test-reports/:id`，左栏分节锚点、右栏渲染。渲染数据用两种来源之一：① `GET /{id}?external=true` 的 JSON；② `snapshot_html` 直出（iframe + sandbox）。**建议 ②**：冻结语义更真（快照即事实），且不依赖运行期模板变更 |
| 导出 | 列表与详情各一个「导出」下拉（HTML/PDF/DOCX），接 `exportBlob` |
| 打印 | 详情页「打印」按钮，先 `POST print-token` 再开 `/print?token=` |
| 自动生成开关 | 项目设置页加 `report.auto_generate` 开关（后端已有，仅缺 UI） |
| 模板「复制平台模板」 | `ReportTemplatesView.vue:12` 注释承诺、实现没有 → 补一个「复制为项目模板」动作 |

#### 第二层：模板按内核分维度（R15 的「尤其 EHT pytest」）

| 改动 | 说明 |
|---|---|
| 迁移 | `report_template` 加 `kernel VARCHAR(32) NOT NULL DEFAULT 'robot'`；选择规则改为「项目默认(kernel 匹配) → 平台默认(kernel 匹配) → 平台默认(任意 kernel)」 |
| 白名单 | `ReportFieldWhitelist` 加 pytest 专属字段（判据结论、nodeId、参数化 id、junit message、artifact 路径），RF 专属字段（keyword 序列、output.xml 节点路径）保持 |
| 预置模板 | 平台种子新增一份 `EHT-PYTEST 默认模板`（8~10 字段，不是 21 字段全量）：报告编号/被测对象/软件构建/执行环境/用例总数与结论分布/判据未定项/证据索引/免责声明 |
| 兼容 | 旧模板 `kernel` 默认 `robot`；EHT 工程首次打开时提示「当前为通用模板，可一键应用 EHT 预置模板」 |

#### 第三层：EHT pytest 的「编写逻辑」（不只是字段顺序）

现状问题：21 字段全量模板把 pytest 报告写成了「执行台账」，而 EHT 工程的读者要看的是**判据链**。建议按三段式重写（这一层是内容逻辑，不是排版）：

```text
一、结论层（1 页）
   本次执行结论（通过/不通过/缺证据/未执行 四态计数）
   + 判据未定项清单（点名到 nodeId）
   + 与上次同工程执行的差异（新增失败/修复/仍失败）
二、证据层（按用例分组）
   每条：nodeId · 判据行原文 · 实测值 · 证据文件（junit / json-report / 日志）相对路径
   关键：证据路径必须可点到（与 R7 的「文件相对路径」同一套组件）
三、附录
   metadata 十项（CASE_ID/RUN_ID/QA_PROJECT/DUT/LINK/SW_BUILD + 推荐四项）
   执行环境（内核版本、插件版本、仓库 commit、快照引用）
```

> 这一层与 v5.8.0 的 W58-13「判据链端到端打通 + 报告结论统一口径」是同一条线的延伸：**先有判据数据，才有判据报告**。若 5.8 的判据链在 RF 侧确认「无载体」（W58-11 的结论），则三段式里的「判据行原文」在 RF 报告里要标注「不适用」，不许留空装样子。

### 2.4 工作量

| 层 | 规模 | 风险 |
|---|---|---|
| 第一层（详情页 + 导出 + 打印 + 开关 + 复制模板） | 中（1 个新页约 500 行 + 4 处小改） | 低 |
| 第二层（kernel 维度 + 白名单 + 预置模板） | 中（1 条迁移 + 白名单扩展 + 种子） | 中：模板选择规则变更会影响所有项目的默认模板，需回归「已有项目打开报告」 |
| 第三层（三段式编写逻辑） | 大（模板渲染器与前端排版都要改） | 中：属「对外口径」，需大师定稿后才能开发 |

## 三、验收判据草案

| 判据 | 可判定形式 |
|---|---|
| 名称统一 | 全站 grep「对外报告」应为 0 命中（i18n 除外，改后也应为 0）；菜单/标题/按钮三处一致（截图 3 张） |
| 套件数一致 | 列表套件数 = 详情树一级子节点数（对同一 run 断言相等，至少 3 个 run：RF 单套件/多套件、pytest 参数化） |
| 套件可点 | 点列表套件数 → 详情页对应套件节点展开且高亮（真实界面取证） |
| 测试报告可预览 | 建草稿→冻结→详情页能渲染出结论层与证据层，无需下载（截图 + `snapshot_html` 长度断言） |
| 导出可用 | html/pdf/docx 三个格式各下载一次，文件非空且可打开 |
| 模板分内核 | EHT pytest 工程新建报告默认取到 EHT 预置模板（断言 templateId 与字段数）；标准 RF 工程不受影响 |
| 自动生成开 | 开关打开后跑一次执行，报告列表出现「自动报告 」前缀的记录（后端已有该前缀，`ReportAutoGenerator.java:141-155`） |
