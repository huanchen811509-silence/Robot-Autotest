## 三、版本路线

### 3.1 硬约束（决定切分粒度，不是偏好）

1. **一版一 PRD**：`check_release_docs.py` 要求六份齐全 + PRD 的 FR 在 TEST-PLAN 有覆盖 + TC 在 05-TEST-REPORT 有结果。一版塞两个维度会让 TC 编号与证据目录同时翻倍。
2. **迁移只能追加**：每版新增列/表都要新号迁移（当前到 `V11_64`）。R9 的采集画像、R17 的快照表、R10 的授权派生视图各自要吃迁移号。
3. **门禁会锁死菜单数量**：`tools/check_navigation.py:50-51` 硬编码 `GLOBAL_EXPECTED=5`、`PROJECT_EXPECTED=7`。R10（新增一级菜单）、R4（新增向导二级项）**必须同版改机检和 `navigation.spec.ts`**，否则第一道门就红。
4. **组授权参与判权（R10 核心）会影响所有既有 403 用例**：`AuthzMatrixTest`、`AuthorizationBoundaryTest` 需要同版复核，不能延后。

### 3.2 推荐方案（X=16）

| 版本 | 主题 | 交付需求 | 为什么放这一版 |
|---|---|---|---|
| **5.8** | （已在开发）技术债收口 | 既有 12 条 FR + **热修 R1** | R1 是 1 处匹配逻辑 + 1 条不变量测试，插队成本最低、影响全站导航；不插队则整个 5.9 之前用户都在看错误高亮 |
| **5.9** | 导航与权限基座 | R1 固化、R2、R10、R12 通则、R3 机制 | 必须先有「谁属于哪个项目」的正确口径，5.10 的向导成员步才有意义；R10 与 R2 共用 union 逻辑，同版做省一次迁移 |
| **5.10** | 向导 | R4、R11、R3 清理脚本落地 | 依赖 5.9 的组/项目关联；模板向导复用 5.9 的能力码 |
| **5.11** | 用例工作区 | R5、R6、R7、R13 | 一个页面重构 + 一个通用组件（就地展开）+ 一处 API join；R13 只需徽章与提示，与 R5/R7 同页 |
| **5.12** | 用例集与项目资产 | R8、R16 | 都依赖 5.11 的工作区范式与路径组件；R16 抽公共组件时正逢 R8 改三栏，样式一次成型 |
| **5.13** | 资产采集闭环 | R9 | 依赖 5.12 的资产工作台（关系列、采集入口都在同一张表里） |
| **5.14** | 报告体系 | R14、R15 | 依赖 5.13 的采集/执行证据形态（测试报告要引证据） |
| **5.15** | 环境与拓扑重写 | R17 | 独立大改，需要独占一版；白泽快照机制与 5.13 的采集画像对齐 |
| **5.16** | 运维管理 | R18、R19 | 依赖 5.15 的健康/快照口径；界面化运维必须在服务足够稳定后做 |

### 3.3 压缩方案（X=13）

| 版本 | 合并方式 | 代价 |
|---|---|---|
| 5.8 | 同推荐方案 | — |
| 5.9 | IA 基座（R1/R2/R10/R12/R3） | 无 |
| 5.10 | 向导（R4/R11） | 无 |
| 5.11 | UX 全部（R5/R6/R7/R8/R13/R16） | 一个版本 6 条 FR、约 3 个页面重构，TC 会到 60+ 条，证据目录膨胀 |
| 5.12 | 资产采集 + 报告（R9/R14/R15） | 跨两个维度、两套数据模型，回滚粒度变粗：报告出问题要连带回滚采集 |
| 5.13 | 环境拓扑 + 运维（R17/R18/R19） | **风险最高**：重写 + 界面化运维同版，出问题没有干净的上一版可退 |

**取舍建议**：若大师希望 2026 年内看到全量形态，取 X=13；若希望每版都能独立验收、独立回滚，取 X=16。**学徒推荐 X=16**，唯一理由是 5.15/5.16 与 5.12 的「可回滚性」——这两块一旦混版，现场出问题时无法判断是重写引入还是运维界面引入。
