## 0. 结论摘要

### 2.2 自研框架（nic-test-platform V1.2）

`[已核实]` 文件 175 个；`pyproject.toml` `version=1.2.0`、`requires-python>=3.11`；`addopts = "-ra -p nic_platform.pytest_plugin -s"`；`pythonpath=["src"]`；14 个 marker。

对象模型：`SSHConnection → Host → NIC`，`Switch` 独立，`Adapter` 按 `vendor+model+os_family` 选择，`AW` 为能力粒度，`Runtime` 管资源池与证据生命周期。**用例串行，无资源锁**。

| 事实 | 对平台的含义 |
|---|---|
| `first` / `second` 指**资源池列表顺序**，不是设备身份 | 平台必须控制 `resource_pool.hosts` 顺序；顺序即语义 |
| `TRAFFIC_DIRECTION` / `TARGET_SLOT` 是**脚本文本里的常量**，只能 CLI 全局覆盖 | 一个 run 内所有用例共用同一方向/被测端，**无法逐例差异化** |
| `--host` / `--target` 只能**收窄**白名单，不能扩大 | 平台先渲染 run_env，再用 CLI 收窄 |
| 证据根固定为 `<repo>/artifacts/<run_id>/`（`PROJECT_ROOT = parents[3]`） | 平台不能假定证据落在 runDir 下 |
| `run_id` 可由 `run_env.run_id` 注入（`runtime.py:59`） | **平台 RUN_ID 可贯穿到框架证据目录**，是三方关联的天然钩子 |

| 产物 | 路径 | 内容 |
|---|---|---|

`[已核实]` 实测（`python -m pytest tests/nic/base/test_im_fun_020.py --mode fake -q --junitxml=/tmp/j.xml`）：`1 skipped in 0.43s`；产物目录 `artifacts/20261112_192112_594505/cases/tests_nic_base_test_im_fun_020.py_test_im_fun_020_pci_device_info`；junit 为 `classname="tests.nic.base.test_im_fun_020" name="test_im_fun_020_pci_device_info"`。

> 两个细节必须写进实现要求：① 用例目录名是 nodeid 净化串，平台不能按 nodeid 原样拼路径；② junit 的 `classname` 是**点分**，与 json-report 的斜杠 nodeid **不同源**，映射一律走绑定表。

#### 2.4.4 退出码语义

| 退出码 | pytest 语义 | 平台应判为 |
|---|---|---|
| 0 | 全部通过（含 skip） | 执行成功 |
| 1 | 有用例失败 | **执行成功、业务失败** |
| 2 | 用户中断 | 执行中断 |
| 3 | 内部错误 | 执行故障 |
| 4 | 用法错误（参数不认） | 执行故障（**本次实测命中过**） |
| 5 | 未收集到用例 | 执行故障（选择集为空） |

`[已核实]` 现有 `PytestRunAdapter.run()` 把 `exitCode != 0` 统一返回 `pytest_exit_N` 失败——用例失败会被记成执行故障，failure_class 与重试策略都会错。

### 2.5 现有 pytest 支持与本框架的 8 处不匹配

| # | 现有实现 | 本框架要求 | 结论 |
|---|---|---|---|
| M1 | 命令固定带 `--json-report` + `--json-report-file` | 依赖未声明（3 个包） | `[已核实]` **直接失败** |

## 3. 三层结构：适配 / 解耦 / 联动（v2.0 核心）

### 3.1 一条设计公理

> **解耦是约束，适配是手段，联动是价值。三者顺序不可颠倒。**

把它写反的三个典型后果（都在真实项目里见过）：

| 颠倒 | 表现 | 后果 |
|---|---|---|
| 先联动后解耦 | 为了让报告好看，平台去解析 Python AST / 反解 junit 字符串 | 框架一改就崩，且崩在报告层（最不该崩的地方） |
| 先适配后解耦 | 适配代码直接写进 `RunExecutionService` 主流程 | 「加内核」变成「改内核」，RF 回归风险不可控 |
| 只适配不解耦 | 平台与框架共享 venv、共享配置目录、共享 run_id 目录 | 一方升级另一方必挂；证据目录互相覆盖（隐藏需求 H10） |

### 3.2 适配层：窄而厚

**唯一的接触面**（8 个契约点，全部在 §2.4 已列）：

| 方向 | 契约点 | 形态 |
|---|---|---|
| 平台 → 框架 | ① `inventory.yaml` ② `run_env.yaml` ③ argv（8 参数）④ 进程 env（凭据） | 文件 + 命令行 + 环境变量 |
| 框架 → 平台 | ⑤ `junit.xml` ⑥ `artifacts/**` 证据树 ⑦ 退出码 ⑧ stdout/stderr 流 | 文件 + 目录 + 退出码 + 流 |

**「窄」的判据**：新增代码只允许落在 1 个包 `application/kernel/pytestnic/`（下称适配包），且该包**只被 3 个既有类引用**：`KernelRegistry`（注册）、`RunExecutionService`（调用执行）、`ReportIngestService`（归一分派）。

**「厚」的判据**：适配包内部允许复杂（渲染器 / argv 构造器 / 契约探测 / junit 解析 / sidecar 解析 / 步骤解析 / 进度事件解析 / 证据登记），但**对外只暴露 4 个接口**：

| 接口 | 输入 | 输出 |
|---|---|---|
| `EnvRenderer` | 项目 + 选择集 + 资产 | `env/` 目录（两文件 + 脱敏报告） |
| `CommandBuilder` | run + 选择集 + 模式 | argv + 工作目录 + 环境变量映射 |
| `ContractProbe` | python_bin + 仓库路径 | 8 参数存在性 + 版本 + collect 数 |
| `ResultNormalizer` | junit + sidecar + 证据目录 | 用例结果列表 + 步骤树 + 产物清单 |

> **反模式警告**：若适配逻辑开始出现在 `RunExecutionService` 的 if-else 里、出现在前端、出现在报告模板里，就说明「窄」被破坏了。评审时要拿这条卡。

### 3.3 解耦的五个切面（每切面都要有可度量判据）

| # | 切面 | 现状 | 目标 | 可度量判据 |
|---|---|---|---|---|
| D1 | **源码真源** | `robot_file` 存 DB 内容（RF 路径）；pytest 无模型 | pytest 侧只在 DB 存「仓库引用 + commit + 绑定」，不存源码 | `test_case` / `robot_file` 表零新增 pytest 源码列；`git status` 干净 |
| D2 | **运行时** | `venvBin` 单值、`pytestBin` 单值 | 运行时可切换、可多版本并存（项目级配置） | 换 `python_bin` 后 RF 链路零影响；健康检查能识别 3.10 vs 3.11 |
| D3 | **版本** | 框架版本只在 `pyproject.version` | 每次 run 记 `COMMIT_SHA` + 框架版本 + 契约探测结果 | 报告可回答「这次是哪个 commit 跑的」；契约变更会拒跑而非静默错 |
| D4 | **调度** | `RunDispatcher` / `LeaseService` 与内核无关 | 保持无关，pytest 只声明「我要哪些资源 + 并发 1」 | `RunDispatcher` 代码零内核分支；pytest run 与 RF run 可同队列共存 |
| D5 | **报告** | 结果树以 RF `keyword_result` 为骨架 | 报告层只认「归一模型」，不认内核 | 报告渲染代码零 `if (kernel == ...)`；新增内核不改报告层 |
| **D6** | **可移除性（总判据）** | — | 删除适配包后平台仍可完整运行 RF 全链路 | **删除 `application/kernel/pytestnic/` 后，RF 门禁 36 步读数逐字不变** |

`[推断]` D6 是本报告最重要的可执行判据——它把「解耦」从口号变成了一个可以跑的命令。建议直接做成机检脚本 `tools/check_kernel_decoupling.py`（临时移走包 → 跑 RF argv 快照 + 门禁读数 → 还原）。

### 3.4 联动的三条链（以及三条断链检测）

| 链 | 起点 → 终点 | 现状 | 断链检测（机检） |
|---|---|---|---|
| L-A 资产 → 环境 | `device/device_port/credential` → `inventory/run_env` | 缺 NIC 级字段、缺口令注入 | 渲染前后双向校验：渲染失败的资产项必须能定位到具体设备+端口 |
| L-B 用例 → 脚本 | `test_case.external_id` ↔ `node_id` | 无绑定实体 | 三向一致性：库编号 / 脚本文件 / collect 结果三者计数与集合自洽 |
| L-C 结果 → 报告 → 用例库 | junit → `test_result.case_id` → 覆盖率/趋势 | `case_id` 不填 | 每条结果的 `case_id` 非空率 = 100%，或显式标 `ORPHAN_RESULT` |

**联动的三个「不可断」原则**：

| # | 原则 | 理由 |
|---|---|---|
| P1 | 联动必须是**派生**，不能是**复制** | 复制即双真源（资产复制进 env、源码复制进 DB 都会分叉） |
| P2 | 联动必须有**单一关联键** | 本方案用 `RUN_ID` 贯穿 DB / 证据目录 / 报告；用 `node_id` 贯穿库 / 脚本 / 结果 |
| P3 | 联动失败必须**可见** | 渲染失败、绑定缺失、结果孤儿，一律在执行前或报告页显著标记，不静默降级 |

### 3.5 该结构下的三个反模式（明确不做）

| 反模式 | 为什么不做 |
|---|---|
| 平台解析 Python AST 抽步骤 | 静态结构与运行期实际执行必然不一致（条件分支、参数化、fixture skip） |
| 平台接管框架的资源池 / 锁 | 框架明确不做锁；平台做租约已足够，双方都做必然死锁 |
| 为 pytest 单独造一套「用例/执行/报告」页面 | 第五域重复建设，用户体验分裂，且必然与 RF 侧口径打架 |

## 4. 项目化承载：`project.kind = pytest-suite`（需求 2）

### 4.1 结论：扩 `kind` 值，不造新体系

`[已核实]` `project` 表已有 `kind VARCHAR(16) DEFAULT 'standard'`，且已有 `platform`（公共库载体，单例）先例（`V11_31__ui_mode_platform_project.sql`）。

| kind | 语义 | 基数 | 菜单 | 默认内核 | 必填配置 |
|---|---|---|---|---|---|
| `standard` | 普通测试项目 | 多 | 现有 7 组 29 叶 | `robot` | 无额外 |
| `platform` | 公共库载体 | **单例** | 全局模式 5 组 14 叶 | `robot` | 无 |
| **`pytest-suite`**（新增） | pytest 用例库工程 | 多 | **工程视图**（§7.2） | **`pytest`（显式 `testKernel`；kind 不推导内核）** | `pytest.repo_url` / `pytest.python_bin` 缺失即拒跑 |

> **2026-11-13 订正（EHT-04 / D-C 授权 / 授权人：大师）**：本表「默认内核」列原值 `pytest-nic`（称 `KernelSelector` 第一优先级）与代码不符——`ProjectService.normalizeKernel()` 只认 `robot` / `pytest`，`KernelRegistry` 仅注册两个 SPI，全仓源码 `pytest-nic` 字面 0 处。实测值 `pytest`（由显式 `testKernel` 决定并同步 `kernel.default`）。影响：仅新建工程时的内核口径说明；不改 kind 枚举、不注册第二内核码、不动已应用迁移。原表述保留在本文件修订记录行的「原值」栏。

### 4.2 为什么不放在 `standard` 项目的设置里

| 理由 | 说明 |
|---|---|
| 默认内核不同 | `kind` 决定 `KernelSelector` 的项目级默认，避免每建一个 run 都要手动选内核 |
| 必填约束不同 | 普通项目没有仓库时正常运行；pytest 工程没有仓库**必须拒跑**，这是硬前置 |
| 看板口径不同 | 覆盖率分母（469）、时间基线、命令集合只对 pytest 工程有意义 |
| 生命周期不同 | pytest 工程跟随用例库版本演进（`v0.2.9.9` → 后续），需要 commit 快照与升版流程（隐藏需求 H3） |
| 菜单污染 | 若不加 kind，pytest 概念会出现在所有项目侧栏（§7.2 详述） |

### 4.3 「项目」承载的六件事（这就是「长期考虑」的具体含义）

| # | 承载物 | 载体 | 说明 |
|---|---|---|---|
| 1 | 仓库绑定 | `project_setting`：`pytest.repo_url` / `repo_ref` / `subdir` | 引用，不是副本（D1 解耦） |
| 2 | 运行时 | `project_setting`：`pytest.python_bin` / `pytest.venv` | 可换，换后健康检查复验（D2 解耦） |
| 3 | 资源池 | `project_asset` + `execution_selection` 快照 | 顺序即语义，冻结留哈希 |
| 4 | 用例分母 | `test_case`（`source_sheet='详细测试流程'`、`lifecycle_status='active'`） | 口径锁死，含 178 条待评审的归属规则（H11） |
| 5 | 执行基线 | 新表 `case_duration_baseline` | 5.3.1 落地；冷启动用分类中位数（H5） |
| 6 | 报告模板与生成策略 | `project_setting`：`report.template_id` / `report.auto_generate` | 5.4.0 落地 |

### 4.4 一个额外收益：自证（dogfooding）

`[推断]` pytest 工程可以作为平台的**自证项目**：用平台自己的 pytest 通道跑用例库的 Fake 模式（70 tests，全 skip，不连设备），作为每次发版前的平台回归。它同时验证了渲染器、命令构造、契约探测、junit 归一、PLANNED 语义五段代码——这是现成 R6「RF 回归」之外的第二条回归线。

### 4.5 边界（不做）

| # | 不做 | 理由 |
|---|---|---|
| N1 | 一个 pytest 工程绑多个仓库 | 绑定关系一多，「这次是哪个 commit」就说不清；需要多仓库就建多项目 |
| N2 | 自动为用例库新建项目 | 项目创建仍需人确认（`project:create` 权限），避免误建 |
| N3 | pytest 工程复用 `robot_file` | `robot_file` 是 RF 内容真源，混用即破坏 D1 解耦 |

## 5. 方案对比与推荐

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A 契约适配**（推荐） | 适配包 + 渲染 + 绑定 + 归一 + 项目承载 | 单一真源；框架零改动即可 P0 落地；可移除（D6） | 平台不能在线编辑用例；需管 repo/ref | **采用** |
| B 仓库资产化 | py/src/config 全量存 `robot_file`，执行前落盘 | 复用现成 materializer | 丢包结构/git 历史；双真源；上百文件同步成本高 | 不采用 |
| C 平台插件注入 | `qa_platform_plugin.py` 通过 `-p` 注入 | 不改仓库、可版本化、可加钩子（进度/映射/超时） | 需保证 PYTHONPATH 与加载顺序 | **作为 A 的组成部分** |
| **D 独立服务化**（v2.0 新增评估） | 把适配层做成独立 HTTP 服务，平台只调 API | 语言无关、可独立升级 | 多一跳部署与故障点；与现有 Spring 事务/租户/租约割裂；团队维护成本翻倍 | **不采用**（除非将来跨团队复用同一适配） |

> D 案被评估过是因为需求 8 提了「独立进程」——结论见 §7.4：**适配层不需要独立进程，执行协调者也不需要**。

### 7.1 需求 5：改造后能否适配原 Robot Framework 内核

**结论：可兼容，但必须先建 4 把「回归锁」，再动 4 个共享热点。**

#### 7.1.1 冲突面（共享代码热点）

### 7.3 需求 7：执行进度可视化与错误原因展示

#### 7.3.1 现状（精确到行）

| 能力 | 现状 | 缺口 |
|---|---|---|
| 实时日志 | WebSocket 推送 + `LogRingBuffer` 补最近 200 行 + 丢行计数 | 可用，无需改 |
| 进度 | 3 秒轮询 `RunProgressRegistry`，前端 `total=0` 时渲染不确定进度（不伪造百分比） | **pytest 无解析** |
| ETA | `RunEtaCalculator` 平均速度外推 | 冷启动无样本返回 null；样本跨内核混合 |
| 卡死判定 | 心跳 > `progressStalledSeconds(60)` | pytest 阶段不刷新心跳（因为不解析）→ **会误判卡死** |
| 错误原因 | `failure_class`（INFRA/TEST/...）+ 失败聚类 | 粒度粗，无「人话」 |

> `[已核实]` 特别注意：由于 pytest 不产出控制台解析结果，`lastActivityAt` 可能长期不刷新 → **现有卡死判定会对 pytest run 误报**。这是一个「加内核就会踩」的既有 bug 面，必须在 5.1.0 一并处理（把「任意 stdout 行」也算活动）。

#### 7.3.2 方案：平台插件写 `progress.jsonl`（零依赖）

**为什么不用解析 `-q` 输出**：

| 解析 stdout | 写 sidecar |
|---|---|
| 输出格式随 pytest 版本/`-q`/`-v` 变化 | 钩子 API 稳定（`pytest_runtest_logreport`） |
| 中文/编码/locale 依赖（GAP-34） | 结构化 JSON，UTF-8 显式 |
| 拿不到「当前在跑哪条」「已耗时」 | 钩子里有 `when`、`duration`、`nodeid` |
| 与 RF 正则耦合（H-2 风险） | 完全独立通道 |

**`progress.jsonl` 事件模型**（每行一个 JSON）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ts` | ISO8601 | 事件时间（UTC） |
| `event` | enum | `session_start` / `collect_finish` / `case_start` / `case_end` / `session_finish` |
| `node_id` | string | `path::func`（`case_start`/`case_end` 必填） |
| `outcome` | enum | `passed/failed/skipped/error/xfail/xpass`（`case_end` 必填） |
| `duration_ms` | int | 单例耗时（`case_end`） |
| `phase` | string | 平台可映射的阶段名 |
| `collected` | int | 收集总数（`collect_finish`） |
| `reason` | string | skip/fail 摘要（截断 500） |

**消费方式**：`WorkerLogTailer` 已有的 tail 机制复用 → 增量读 `progress.jsonl` → 写 `RunProgressRegistry` 的**新通道**（不动 RF 正则）→ 前端轮询接口返回统一结构（`total` 来自 `collect_finish`，`completed` 来自 `case_end` 计数）。

**收益**：ETA 可用「基线加权」（5.3.1 后）；阶段可视化有真实来源；卡死判定不再误报。

#### 7.3.3 错误原因分层（L1–L5）

| 层 | 内容 | 来源 | 展示 |
|---|---|---|---|
| L1 结论 | PASS / FAIL / ERROR / SKIP / PLANNED | junit + 退出码 | 列表色块 |
| L2 分类 | 环境 / 配置 / 框架 / 用例 / 断言 / 超时 | `failure_class` + 归因规则 | 列表标签 |
| L3 位置 | 步骤 N + 命令 + endpoint | 步骤树 + 命令集合 | 详情抽屉 |
| L4 原文 | 日志切片（`log_offset/log_span`）+ 命令原始回显 | 证据树 | 可展开 |
| L5 建议 | 规则库匹配的修复建议（可选 AI 增强） | 规则 + AI（5.3.2） | 「可能原因 / 建议动作」 |

> L5 的铁律：**AI 建议不参与判定**，只作为「建议」展示，且必须标注来源（规则/AI）。与既有「AI 不得勾选 M 项」口径一致。

### 7.4 需求 8：是否需要协调与监管执行的进程

**结论：需要「项目执行协调者」这个逻辑角色，但不需要新建独立守护进程。**

#### 7.4.1 已有能力盘点（§2.6.1 已列）

| 需求描述的职责 | 现有承载 | 是否够 |
|---|---|---|
| 排队与并发控制 | `RunDispatcher`（项目分道 + `maxParallel` + 位次） | 够 |
| 资源互斥 | `LeaseService` + `resource_lease` 唯一键 | 够（需扩键粒度） |
| 超时与卡死 | `RunTimeoutMonitor` + `stalled` | 够（需 pytest 心跳） |
| 孤儿清理 | `ExecutionOrphanSweeper` | 够 |
| 重启恢复 | `RestartRecoveryService` | 够 |
| 通知与回写 | `RunCompletionListener`（2 实现） | 够（可加第 3 个：自动报告） |

#### 7.4.2 缺的不是进程，是「项目视角的编排与裁决」

| # | 缺的能力 | 为什么现有组件不做 | 归属 |
|---|---|---|---|
| A1 | 一个项目内多个 run 的**先后与资源预约**（如：稳定性 run 夜间窗口、功能 run 白天） | `RunDispatcher` 只看 priority，无「窗口」概念 | 5.2.1 |
| A2 | 用例集跨内核**拆单**（§7.1.3 S2） | 派发层不知道用例内核 | 5.2.1 |
| A3 | 失败**裁决**（重试 / 终止 / 转人工） | `RetryPolicy` 只管重试次数 | 5.2.1 + 5.3.2 |
| A4 | 项目级**执行台账**（今天跑了什么、卡在哪、成功率） | 只有 run 列表，无聚合视图 | 5.2.2 |
| A5 | 长跑用例的**窗口编排**（STB 22 + STR 10 = 32 条） | 无窗口概念 | 5.3.3 |

#### 7.4.3 为什么不做独立守护进程

| 理由 | 说明 |
|---|---|
| 已有进程内恢复机制 | `RestartRecoveryService` + 孤儿清扫已覆盖「平台重启」场景；独立进程解决的是同一问题 |
| 租户上下文会断 | 现有执行线程用 `runAs(projectId)` 包裹；跨进程要重建整套租户/审计上下文 |
| 租约与事务会割裂 | `resource_lease` 唯一键互斥依赖同库事务；外部进程要么共享库连接（更复杂），要么失去原子性 |
| 运维成本翻倍 | 多一个 systemd 单元、多一套日志、多一处部署验证 |
| 与门禁冲突 | 门禁 36 步假设单进程；加进程要重写验证链 |

**触发外置的条件（写进文档，避免以后反复讨论）**：

| 条件 | 阈值 | 一旦触发再评估 |
|---|---|---|
| 平台重启导致在途 run 丢失 | 观察到 ≥1 次 | 外置守护进程 |
| 需要跨机编排多个执行机 | 执行机 > 1 台且需统一排队 | 外置（或扩展现有 node 通道） |
| 单 JVM 无法承载并发 | run 吞吐 > 现有 `maxParallel` 的 3 倍 | 外置 |

#### 7.4.4 「协调者」的职责边界（5.2.1 交付）

| 职责 | 做 | 不做 |
|---|---|---|
| 编排 | 批内顺序、窗口、跨内核拆单、资源预约 | 不做用例内部逻辑 |
| 监护 | 心跳、卡死、超时、孤儿（复用现有） | 不做进程管理（复用 `ProcessRegistry`） |
| 裁决 | 失败归因、重试决策、终止、转人工 | 不替人做「这是不是产品缺陷」的结论 |
| 记账 | 项目级执行台账、成功率、平均时长 | 不做计费/工时统计 |

### 7.5 需求 9：报告自动生成逻辑与内容优化

#### 7.5.1 现状

| 项 | 现状 | 缺口 |
|---|---|---|
| 生成时机 | 人工（`create` / `createFromCaseSet`） | 无「run 完成自动生成」 |
| 模板 | `ReportTemplateService`（内置/自定义，`V11_44`） | 模板与生成策略未绑定 |
| 内容 | 数字 + TopN 失败 + AI 叙事（可选） | 无基线偏差、无归因分布、无覆盖率影响、无结论建议 |
| 冻结 | `freeze` 存在（快照） | 自动生成后是否自动冻结未定 |
| 导出 | PDF/DOCX + 字段白名单 | 新字段需登记 |

#### 7.5.2 生成逻辑优化：策略化

| 维度 | 设计 |
|---|---|
| 触发器 | `run_finished`（默认）/ `scheduled`（每日汇总）/ `manual` |
| 条件 | 项目级 `report.auto_generate`（默认 **关**，开了才自动）+ 仅 `run_status` 终态 + 仅 real 模式（Fake/PLANNED 不自动出正式报告） |
| 挂载点 | `RunCompletionListener` 新增第 3 个实现 `AutoReportListener`（事务提交后执行，与 `RunNotificationListener` 同模式） |
| 幂等 | 以 `run_id + template_id` 为键，重复触发不重复建（复用 `RunIdempotency` 思路） |
| 失败处理 | 自动生成失败不影响 run 结论（只记事件 + 页面提示），绝不因报告失败改 run 状态 |

#### 7.5.3 内容优化：固定 8 章模型

| 章 | 内容 | 数据来源 | 现状 |
|---|---|---|---|
| 1 结论摘要 | 一句话结论 + 通过率 + 判定建议 | `ReportRecord` + 规则 | 部分（数字有，结论无） |
| 2 执行环境 | commit / 框架版本 / 内核 / 运行时 / 资源池顺序 / 模式 | `run_metadata` + 渲染快照 | 缺 commit/顺序 |
| 3 结果分布 | 分类别、分优先级、分设备的结果矩阵 | `test_result` + `test_case` | 部分 |
| 4 失败分析 | 按 L2 归因分布 + TopN + 每条 L3/L4 下钻 | 归因 + 证据 | 部分（无归因分布） |
| 5 时间分析 | 单例耗时 vs 基线（偏慢 TopN、异常快清单） | `case_duration_baseline` | **全新**（5.3.1 后才有） |
| 6 覆盖影响 | 本次覆盖了哪些分类、缺口变化 | 覆盖率 | **全新**（5.1.2 后才有） |
| 7 命令集合摘要 | 命令总数、分类分布、失败命令、敏感过滤 | 命令集合 | **全新**（5.3.0 后才有） |
| 8 附录 | 证据索引、用例清单、免责与口径说明 | 产物清单 | 缺口径说明 |

> 第 8 章的「口径说明」不是套话：要写明「覆盖率≠完成度」「Fake/PLANNED 不计通过率」「AI 建议不参与判定」三条，避免对外误读（这是 v5.0 踩过的坑）。

### 7.6 需求 10：小组会议五项补充需求

#### 7.6.1 公共监控程序（10.1）

**需求原文**：公共监控程序，用来监控 pytest 执行过程、捕获错误、收集日志——需要收集命令集合。

| 项 | 评估 |
|---|---|
| 是否要新进程 | **不要**。做「执行监视器」组件（内核无关），订阅：进程 stdout/stderr + 证据目录 + 平台事件 + `progress.jsonl` |
| 已有基础 | `WorkerLogTailer`（tail）、`LogRingBuffer`（缓冲）、`EvidenceLogWriter`（脱敏）、`CaseCommandExtractor`（命令抽取，含 pytest 路径） |
| 真正缺的 | ① **命令集合**统一 schema ② 错误捕获的结构化（现在只有日志文本） ③ 事件流统一（`execution_event` 已有表，未用于命令级） |

**命令集合标准 schema**（`commands.jsonl`，平台侧归一后写入，同时兼容框架原生格式）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `cmd_id` | string | 是 | run 内唯一，`<case_dir>/<seq>` |
| `run_id` | string | 是 | 平台 RUN_ID |
| `node_id` | string | 是 | 归属用例 |
| `seq` | int | 是 | 用例内序号（从 1） |
| `endpoint` | string | 否 | 执行端点（`host_key` / `host_key/netdev` / `local`） |
| `kind` | enum | 是 | `collect` / `configure` / `traffic` / `verify` / `cleanup`（分类口径 §9 附录） |
| `argv` | string[] | 是 | 命令与参数（**脱敏后**） |
| `started_at` | ISO8601 | 是 | 开始时间 |
| `duration_ms` | int | 是 | 耗时 |
| `exit_code` | int | 否 | 退出码（超时/中断为空） |
| `stdout_sha` | string | 否 | 回显指纹（原文存证据文件，库里不存全文） |
| `truncated` | bool | 是 | 是否被截断（不静默裁剪） |
| `sensitive` | bool | 是 | 是否命中敏感词表（命中则 argv 只存掩码） |

**「公共」的正确含义**：同一套监视器同时服务 pytest 与 RF —— RF 的命令来自关键字树（`CaseCommandExtractor.fromRobotKeywords`），pytest 的来自 `commands.jsonl`。**两个来源，一个 schema，一个查询入口**。这才是「公共」。

#### 7.6.2 错误后对接 AI 或人工（10.2）

| 项 | 评估 |
|---|---|
| 是否可行 | 可行。AI 底座已有（`AiWorkbenchService` / `AiEvidenceService` / `ContextPacker` / `AiFactVerifier` / SSE），双闸门已有 |
| 需要新建什么 | 只有业务连接：**证据包构造器** + **提示词模板** + **建议落地**（不做新 AI 能力） |
| 铁律 | AI 输出不参与判定、不写 `verdict`、不自动改 run 状态；必须标注「AI 建议，需人工确认」 |
| 双闸门 | `ai.enabled` 默认 false → 关闭时该功能整块隐藏，人工处置路径不受影响 |
| 人工闭环 | 每条失败可指派（`case_owner`）、写处置结论（用例问题/产品缺陷/环境问题/待查）、附件、时间线 |

**证据包内容**（喂给 AI 的最小充分集）：用例编号与标题 + L2 归因 + 失败步骤 + 命令与回显（脱敏、截断）+ 日志切片（≤200 行）+ 基线偏差 + 同类历史失败次数。**不给**：完整证据树、整份日志、凭据。

#### 7.6.3 每用例跑通时间预期（10.3）

| 项 | 评估 |
|---|---|
| 现状 | `test_result.duration_ms` 已有单次耗时；无聚合基线 |
| 缺口 | 无 p50/p90、无样本量、无窗口、无分类兜底 |
| 方案 | 新表 `case_duration_baseline`（5.3.1）；ETA 从「平均速度外推」升级为「剩余用例基线之和 × 修正系数」 |
| 冷启动 | 无样本用例用**同分类中位数**兜底，并标注「估算（冷启动）」，不显示精确值（隐藏需求 H5） |

#### 7.6.4 执行时间基线 + 正式测试超时预期（10.4）

**这里必须说清一件做不到的事**：

| 层 | 可做性 | 方案 |
|---|---|---|
| 基线 | **可做** | `case_duration_baseline`：`p50_ms / p90_ms / p99_ms / max_ms / sample_count / window_days / updated_at`，按（project, case_id, 内核）唯一 |
| run 级硬超时 | 已有 | `runTimeoutSeconds=3600` + `RunTimeoutMonitor`（杀进程树） |
| 用例级**软**超时 | **可做** | 平台插件在 `pytest_runtest_call` 前起计时，超 `p90×k` 记 `slow` 事件并告警；**不中断**用例 |
| 用例级**硬**超时 | **做不到（安全）** | pytest 无内置 per-test timeout；用例库无 `pytest-timeout` 依赖；Python 线程无法强杀；`signal.SIGALRM` 只在主线程且 Unix 有效，且被阻塞的 SSH/socket 调用不响应信号 |
| 精确 kill 单用例的路径 | 需框架侧配合 | 要么用例库装 `pytest-timeout`（`--timeout-method=thread` 也不可靠，需 `signal`）；要么框架把长阻塞操作拆成可中断步骤。**均超出平台能力** |

**因此 PRD 的口径必须写成**：

> 「正式测试可按用例设定**预期时长**（基线 p90）与**软超时阈值**；超阈值即告警并在报告中标记 `slow`，**不中断执行**。硬超时仍为 run 级（默认 3600s）。逐用例硬中断需要用例库引入超时插件，不在本期范围。」

这条口径如果不写清，现场一定会提「为什么卡住的用例没被杀掉」。

#### 7.6.5 非自动化用例编辑（10.5）

| 项 | 评估 |
|---|---|
| 现状 | `test_case` 有 `source_type`（`ledger`/`script`）、`test_case_step`（`step_no/action/expectation`）、`lifecycle_status`；**无执行记录模型** |
| 能否编辑 | 用例编辑（台账/步骤）**已有基础**（`CasesView` + 步骤表），但缺少「富文本 + 附件 + 责任人 + 版本对比」 |
| 缺的核心 | **手工执行模型**：一次手工执行 = 一条 `run`（`trigger_type=manual`, `kernel=manual`）+ 每步结果 + 证据附件 + 执行人 |
| 方案 | ① `test_case.exec_mode`（`auto`/`manual`/`hybrid`）② `manual_execution`（run_id, case_id, executor, started_at, finished_at）③ `manual_step_result`（step_no, verdict, note, attachments）④ 手工结果同样写 `test_result`（`verdict` + `executor`），进同一通过率口径 |
| 优先级 | P1，归 **5.4.1**（独立功能线，与 pytest 适配不耦合，可并行） |
| 风险 | 手工结果与自动结果混在同一通过率里会失真 → 报告必须**分列**（自动 / 手工）再给合计 |
