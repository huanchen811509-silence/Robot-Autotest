## 1. 结论摘要

1. 大师补充的 7 项里，**1 / 2 / 5 属交互基座**（同一套顶栏与布局，合并成一个工作包最省回归成本）；
   **3 / 4 属架构解耦**（项目目录化 + 创建向导，是本轮最重、最需要 ADR 的两项）；
   **6 属交付运维闭环**（补齐「升级」这一缺失环节）；**7 是本报告本身**。
2. **最关键的判断**：需求 3 的「按目录组织」**不应**把数据库换成文件系统，也不应做 DB 与磁盘双真源。
   现状 88 张业务表中 56 张带 `project_id`，事务、权限、审计、并发都建立在 MySQL 上；改成磁盘真源会一次性丢掉这些能力。
   建议做法是：**DB 继续做运行时唯一真源，磁盘 `workspace/` 做「可移植交换格式」**——显式导出成目录树、显式导入回 DB。
   这样既满足「一个项目一个目录、目录里分用例/环境/报告」，又天然支持「目录级 / 文件级传递」。
3. 需求 1 的「和 AI 助手弹窗模式一致」有精确技术含义：AI 助手是 `.app-shell` 的 **grid 第三列**（第二行），
   而「关于 / 外观 / 命令面板 / 侧面板 / NModal」全是 `position: fixed; inset: 0` 的全屏遮罩，**从 top:0 起盖住顶栏**。
   改造不是调 z-index，而是引入统一的「工作区浮层」定位层，判据可用 CDP 量 DOM 矩形与命中元素。
4. 需求 6 缺的不是「再写一套安装」，而是**编排 + 自动回滚**：`install.sh --upgrade` 已能覆盖程序文件，
   `docs/ROLLBACK.md §8` 已写人工五步升级，但没有一条脚本把「版本比对 → 备份 → 迁移 → 起服 → 健康抽样 → 失败回滚」串起来。
5. 按「其他拍板项均按学徒建议来」的授权，本报告给出 8 项决策的**建议值并直接采用**（见 §9），
   其中涉及对外口径与破坏性变更的两项仍保持安全默认态，**不擅自启用**。
6. 版本线建议从 **`4.0.0`** 起（架构级变更，不是 3.12 的小步迭代），分 4.0 / 4.1 / 4.2 三批；
   `v3.12+` 的 8 条 FR、18 条 TC、6 条取证缺口**整体并入 4.2**，原三份文档保留为历史并标注「已被收编」。

## 3. 七项需求逐条评估

### 3.1 需求 1 · 顶栏浮层不得遮挡或占用顶栏

**现状证据**：F-02 / F-03 / F-04。AI 助手是 grid 列，其余顶栏入口浮层是 `fixed inset:0` 全屏遮罩，
`SidePanel` 的右抽屉甚至 `top:0` 直接压在顶栏上。因此用户点开「关于 / 外观 / 命令面板」后，
顶栏虽在 DOM 里但被遮罩拦截点击，视觉上「顶栏被吃掉」。

**问题定性**：不是样式瑕疵，而是**两套浮层范式并存**。新增页面越多，不一致越严重；
而且遮罩让「顶栏的项目切换 / 通知 / 登出」在浮层打开期间全部不可用。

| 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| S1-1 只降 z-index / 遮罩透明化 | 顶栏 z-index 抬高 | 改动最小 | 遮罩仍在顶栏之下抢焦点，命中与焦点顺序仍错 | 否 |
| S1-2 浮层整体改为 grid 第三列 | 全部走 AI 抽屉的列模型 | 与 AI 完全一致 | 命令面板 / 确认框需要居中语义；同时开两个浮层会争列 | 部分采纳 |
| S1-3 **统一「工作区浮层」定位层**（采纳） | 新增 `OverlaySurface`：容器锚定在 `.app-main`（顶栏之下），顶栏 `z-index` 高于该层；居中模态与右侧抽屉都在这层内定位 | 顶栏始终可见可点；一套焦点陷阱 / ESC / 窄屏降级；与 AI 抽屉语义一致 | 需迁移 5 类浮层、改全局层级变量 | **是** |

**范围边界（重要）**：仅**顶栏入口触发**的浮层纳入统一范式；
页面内的危险操作确认（`ConfirmModal`）保留模态语义，但其遮罩同样避让顶栏（不允许盖住顶栏），
避免为了统一而弱化二次确认的强提示。

**判据草案**：浮层打开时 `document.elementFromPoint(顶栏中心)` 仍命中顶栏元素；
浮层 `getBoundingClientRect().top >= header.bottom`；顶栏 9 个控件在浮层期间仍可点击；
1280 / 1440 两档视口与窄屏降级分别取证。

### 3.2 需求 2 · 管理员与退出登录收敛为账户下拉

**现状证据**：F-01 / F-05 / F-06 / F-18。顶栏 9 个控件里账户段占 2 个（姓名+角色、退出登录），
偏好段占 3 个（外观、主题、语言），管理员入口在侧栏 /admin，无「切换用户」能力。

**评估**：大师列的「看状态 / 调主题 / 切换用户 / 退出登录」其实覆盖**身份、偏好、会话、管理**四类动作，
正好可以收敛为一个账户触发器，把顶栏从 9 控件降到 ≤5，顺带解决需求 1 的拥挤根因。

| 下拉分区 | 内容 | 数据来源 | 写操作 |
|---|---|---|---|
| 状态 | 用户名、角色、当前项目、后端健康、版本号 | `/api/me`、`/api/health`、build-info | 无（只读） |
| 外观 | 主题三态、6 强调色、密度双档、语言 | 既有 `AppearanceDialog` 逻辑 + `/api/preferences` | 用户显式点击才写 |
| 管理 | 「系统管理」入口（能力门控，非 admin 不渲染） | 既有 `capabilitiesForRole` | 路由跳转 |
| 会话 | 切换账号、退出登录（danger + 二次确认） | `performLogout` | 二次确认后写 |

**关键决策**：「切换用户」**不做 impersonation**（I-07），实现为登出后回登录页并预填用户名；
后端 `AccessControlService` 的「管理员跨项目放行」是既有设计，不得因本需求改成隐式越权。

**实现约束**：`NDropdown` teleport + 虚拟列表在 happy-dom 下量不到选项（I-06）。
因此取数/门控/动作派发抽到 `utils/accountMenu.ts` 做纯逻辑单测，视图层用桩组件，
展开态与命中率由 CDP 真浏览器补证。

**判据草案**：顶栏控件数 ≤5；下拉展开后 4 个分区可见且只读区 0 写请求；
非 admin 看不到管理入口；退出登录仍有二次确认；键盘可达（Tab / Enter / ESC）。

### 3.3 需求 3 · 项目按目录组织与解耦（重点）

**现状证据**：F-08 / F-09 / F-10 / F-12 / F-13 / F-19。
当前「项目」是一个 DB 主键 + 56 张表的 `project_id` 外键；用例脚本是 DB 里的**虚拟路径**；
仓库里没有任何按项目分目录的持久化结构；导出只支持单实体，不支持整项目。

**大师的真实目标拆成三层**：
1. **组织**：`workspace/<project-code>/` 下分 `cases/ case-sets/ assets/ environments/ reports/ runs/ files/`；
2. **解耦**：程序、项目、测试用例、测试资产互不绑定，可独立搬运/替换；
3. **传递**：支持目录级与文件级传递（拷一个目录、拷一个 `.robot` 就能换机/换环境）。

#### 3.3.1 四种方案比较

| 方案 | 做法 | 优点 | 代价 / 风险 | 结论 |
|---|---|---|---|---|
| S3-1 全面文件系统化 | 把 56 张表的数据落成目录文件，磁盘成唯一真源 | 组织最直观、天然可 git | 丢事务 / 权限 / 审计 / 并发；56 张表全量重写；既有 284 端点语义全变；`TenantGuard` 失效 | **否** |
| S3-2 DB 与磁盘双真源 | 两边都写，定时同步 | 看起来两边都有 | 一致性不可证、冲突无仲裁、备份窗口内必然漂移；与「唯一真源」硬规矩冲突 | **否** |
| S3-3 **DB 为运行时唯一真源 + 磁盘为交换格式**（采纳） | 显式 `export` 生成目录树与 `manifest.json`/sha256；显式 `import` 预检后写回 DB | 满足组织 + 解耦 + 传递；不动既有事务/权限/审计；可离线编辑、可版本控制；风险可控可回滚 | 目录不是「实时镜像」，用户手工改文件后需显式导入 | **是** |
| S3-4 工作区挂载执行 | 执行内核直接读磁盘目录跑用例 | 传递后即可执行 | 需引入 sync 引擎、路径与凭据治理、执行链改造；应作为 S3-3 之后的第二阶段 | 4.2 候选 |

#### 3.3.2 建议的目录契约（S3-3）

```
workspace/
  <project-code>/
    project.json            # code / name / testKernel / visibility / 导出版本 / 生成时间
    manifest.json           # 逐文件相对路径 + sha256 + 字节数 + 源实体类型
    cases/                  # 用例定义（JSON，按 case id/编号命名）
    case-sets/              # 用例集及其 items
    assets/                 # 设备 / 链路 / 凭据引用（**只存引用与掩码，绝不存明文**）
    environments/           # env_profile 快照、拓扑节点
    reports/                # 测试报告元数据与导出件索引
    runs/                   # 运行记录索引（不含大日志）
    files/                  # robot_file 虚拟树按原路径落盘（.robot/.py/.yaml…）
    members.json            # 成员与项目角色（仅 id/角色，不含口令）
```

**目录/文件级传递**：三级粒度——整项目目录、单个子目录（如只搬 `case-sets/`）、单文件（如 `files/suites/smoke.robot`）。
导入侧对每级做「预检 → 冲突策略（skip / overwrite / rename）→ 事务写入 → 审计」；
导出侧只读、不改 DB、不产生新 run。

#### 3.3.3 必须写进 ADR 的硬约束

1. **唯一真源**：DB 是运行时真源；磁盘目录是**交换格式**，不是镜像，不做后台自动双向同步。
2. **凭据零落盘**：`credential` 表里的 AES-256-GCM 密文、口令、token 一律不导出；`assets/` 只写引用与掩码。
3. **路径治理**：复用 `FileWorkspaceService.normalize()` 的拒绝规则（绝对路径 / `..` / 控制字符 / 扩展名白名单），
   导入侧额外校验 `manifest.json` 的 sha256 与相对路径，防 zip-slip 类路径穿越。
4. **幂等与冲突**：同一 `project-code` 重复导入不得产生重复实体；冲突必须显式选择策略，默认 `skip` 并逐条报告。
5. **多租户**：新增表必须登记 `TenantGuard.TENANT_TABLES`，SQL 必带 `project_id`；非成员 403。
6. **兼容性**：`project.json` 带导出格式版本；跨大版本导入若无兼容适配器，**拒绝并给出原因**，不猜、不半写。
7. **审计与配额**：导出/导入各记一条审计；单次导出体积上限与超时可配置，避免把整库拖垮。

#### 3.3.4 风险与缓解

| 风险 | 缓解 |
|---|---|
| 用户把目录当真源，手改后以为系统已更新 | 目录内 `README` 与 `project.json` 明示「交换格式」；界面只提供显式「导入」入口 |
| 导入半途失败留下脏数据 | 单事务 + 预检 dry-run + 失败整批回滚 + 逐条冲突报告 |
| 凭据随目录外泄 | 导出器白名单字段；机检负向样本「导出件含 `sk-`/口令」必须判红 |
| 大项目导出拖垮服务 | 体积/条数配额、流式写出、超时取消、审计留痕 |
| 与 `.gitignore` / 卸载脚本冲突 | `workspace/` 明确为**运行数据**，加入 `uninstall.sh` 保留清单与 `backup.sh` 范围，绝不随程序删除 |

### 3.4 需求 4 · 界面支持创建项目（向导 / 模板）

**现状证据**：F-10 / F-11 / F-12 / F-13。后端 `POST /api/projects` 与内核选择**已经可用**，
缺的是「把创建项目 + 关联场景/用例集 + 资产 + 成员」串成一次可复核的操作。

**评估结论**：**建议做**，但定位为「编排层」而非「新实体层」——
向导不新增业务表，只是把已有的 6 个 API 按事务顺序编排，避免又造一套平行数据模型。

| 步骤 | 内容 | 复用的既有能力 |
|---|---|---|
| 1 基本信息 | 项目名称、编码、可见性、描述 | `POST /api/projects` |
| 2 场景与用例集 | 选测试场景、选/建用例集 | `test_scenario` / `TestSetController` |
| 3 测试资产 | 关联设备 / 链路 / 环境快照（只引用，不新建凭据） | `DeviceController` / `LinkController` / `EnvController` |
| 4 执行内核 | `robot` vs `pytest`，并说明会同步 `kernel.default` | `ProjectService.normalizeKernel()` |
| 5 成员与复核 | 项目组人员与角色、总览、一次提交 | `ProjectController` members 三端点 |

**模板**：预置 4 个 JSON 模板（A-05），放 `config/project-templates/`（**版本化文件，不是 DB 表**），
只做「预填 + 批量创建」，不引入模板实体与版本表；模板可被目录化导出，便于传递。

**硬判据**：向导每步可回退且不产生副作用；只有最后「提交」写库；
提交为单事务（任一步失败整体回滚并保留草稿）；创建后项目列表、成员、用例集关联、内核路由四处读数一致；
审计留一条 `project:create`；非 `PROJECT/CREATE` 权限 403。

### 3.5 需求 5 · 菜单栏收起后的留白

**现状证据**：F-07。折叠态 `56px`、内容区 `padding:20px` 且 `max-width:1440px` 居中；
`min-width:0` 是修过折叠按钮命中 bug 的关键约束，改动时不能丢。

**评估**：按 I-03 两种解读同时微调，给可量化判据，避免「感觉」类验收。

| 项 | 现值 | 建议值 | 理由 |
|---|---|---|---|
| 折叠窄轨宽 | `56px` | `64px` | 28px 图标按钮两侧各 18px，视觉不贴边，仍远小于展开 200px |
| 内容区右内边距 | `20px` | `28px` | 收起后主区变宽 144px，右侧需要一点呼吸空间 |
| 响应式断点 | 760px 强制 `56px` | 同步改 `64px` | 否则窄屏与手动折叠口径分叉 |

**回归判据**：4 处 grid 定义 + media query 同步；折叠按钮 `elementFromPoint` 仍命中自身（历史 bug 不复发）；
1280 / 1440 视口下内容右边缘到视口右边缘 ≥ 28px；1280 视口无整页横滚。

### 3.6 需求 6 · 更新部署机制

**现状证据**：F-14 / F-15 / F-17。已有：可覆盖式升级（`install.sh --upgrade`）、人工五步升级文档、
三步回滚脚本、备份脚本、健康探针、CI 产物。缺口是**把它们串成一条可重复、可回滚的命令**。

**建议**：新增 `bin/update.sh`（默认 dry-run，`--apply` 才写），编排如下——

1. 版本比对：读 `MANIFEST.json` / `VERSION`，同版本或降级须显式 `--force` 并二次确认；
2. 校验：sha256 + MANIFEST 逐文件；校验不过立即退出，不碰现网；
3. 预检：`doctor.sh`（含 DB 连通）+ 列出将执行的迁移清单（**只读**，不自动改库）；
4. 备份：`backup.sh --apply`（库 + `env` 键名清单），归档当前程序包到 `releases/<version>/`，保留最近 3 版；
5. 停服 → 覆盖程序文件（保留 `env/logs/var/backups/workspace`）→ Flyway 正序迁移（IT 库名守卫 `_it`）→ 起服；
6. 健康抽样：`:8081 /actuator/health`、`:8001 /_ping`、登录、看报告、跑一条用例；
7. 成功写审计与 `releases/UPDATE-HISTORY.md`；**任一步失败自动按 `--schema=keep` 回滚到上一版**（默认不 down schema）。

**边界**：不在生产库上无人值守执行；`--apply` + 二次确认；凭据文件哈希升级前后必须一致；
升级不碰 `workspace/` 与数据库数据；`status.sh` 增加「当前版本 / 上一可用版本 / 最近一次升级结论」。

**判据草案**：临时 prefix 上真跑一次 `3.11.0 → 4.0.0` 演练，升级前后两处健康均 200、凭据哈希不变、
迁移 checksum 通过；注入一个「起服失败」负向样本，必须自动回滚且数据不丢；全程日志可复核。
