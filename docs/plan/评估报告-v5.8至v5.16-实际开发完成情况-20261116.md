# 评估报告：v5.8.0 ~ v5.16.0 实际开发完成情况

> 评估对象：`robot-autotest`（自动化测试平台）v5.8.0 ~ v5.16.0 共 **9 个版本**
> 评估日期：2026-11-16
> 评估依据：各版 `PRD.md` / `DEV-PLAN.md` / `TEST-PLAN.md` / `05-TEST-REPORT.md`，对照**代码真值**与**机检复跑**
> 评估口径：**文档自述 ≠ 完成**。只有「代码里有、机检跑过、能复现」的才算达成；证据形态缺失（截图/性能采样/真机）单列为 `PARTIAL`，不并入达成
> 判定权限：本报告**不判 G 门**、不主张 GA。G 门与对外口径归大师

## 一、结论摘要

### 1.1 三句话结论

1. **代码交付是完整的**：9 个版本全部有实现并合入 `main`，`VERSION=5.16.0`，HEAD `876da9b` 已打 tag `v5.16.0`，双远程三处 sha 一致，交付包已生成并校验。
2. **验收完成度不是完整的**：448 条 TC 里 **PASS 234（52.2%）/ PARTIAL 159（35.5%）/ BLOCKED 49（10.9%）/ 未达成 6（1.3%）**。PARTIAL 的大头是证据形态缺口（真视口截图、性能采样、真机窗口），但其中夹着 **11 项真功能缺口**（见 §六），性质不同，不能混算。
3. **早期三版（5.8/5.9/5.10）的验收证据层级明显低于后六版**：49 条 BLOCKED 里有 46 条集中在这三版，原因是当时没有运行中的后端与浏览器；5.12 起建立「真实 HTTP + DB 探针」后才补上这条腿。

### 1.2 一句话判定

**「九版代码都在、门禁全绿、文档齐全；但按各版 PRD 自己的 P0/P1 放行口径，只有 5.12 接近完全达成，5.14 与 5.15 有 P0 级未完全达成，其余六版为「P0 落地、P1 有登记缺口」的中间态。」**

### 1.3 不可直接对外宣称的三件事

| # | 不能说的话 | 事实 |
|---|---|---|
| 1 | 「九版全部验收通过」 | 448 条 TC 中只有 52.2% 拿到一级证据；5.14 / 5.15 报告自己写明 P0 有未完全达成 |
| 2 | 「已 GA / 已对外交付」 | G 门未判；各版报告均写「本版不判 G 门」；5.16 只做到内部发版留痕 |
| 3 | 「功能全做完」 | 11 项真功能缺口仍在（5.10 四项、5.13 一项、5.15 三项、5.16 三项安全边界内未执行、5.12 一项 NFR 未达成） |

## 五、横向发现（跨九版）

### F1 早期三版与后六版是两套证据标准

| 版本段 | BLOCKED | 一级证据形态 | 原因 |
|---|---|---|---|
| 5.8 / 5.9 / 5.10 | 46 条（占全部 49 条的 94%） | 以单测 + 真实库为主 | 当时无运行中后端 / 无浏览器自动化 |
| 5.11 | 3 条 | 单测 + 真库 | 过渡期 |
| 5.12 ~ 5.16 | 0 条 | 真实 HTTP + DB 探针（每版 40~63 条断言） | 建立探针脚本与部署自校验 |

**含义**：5.8~5.10 的「验收」结论实质上是「代码级 + 单测级」，与后六版不可直接横比。若要拿这三版对外，需补一轮真实链路复验。

### F2 第七道回写在 5.8 上迟到过一次

5.8 的 `05-TEST-REPORT.md` 成文于 5.9 收口期，期间门禁 `07-release_docs` 持续判 `FAIL 缺产物`。这不是内容造假（读数可复核），但违反了「测试完不回写 = 版本未完成」的流程约定。5.9 起未再复发。

### F3 进度口径三处不同源（5.9）

同一事实有三个数：`总纲 §5.3` 写「约 40%」、`DEV-PLAN §12` 写「未完成」、`DEV-PLAN §10.1` 写「24/28 完成」。前两处是早期快照未更新。**建议**：总纲进度表改为「只放指针」，不复制百分比。

### F4 门禁与真实探针确实抓到了单测抓不到的东西

| 版本 | 抓到的真问题 | 若只跑单测的后果 |
|---|---|---|
| 5.11 | `@Audited` 注解错位到只读 `impact()` | 查影响面被记成删除审计，真删除不留痕 |
| 5.13 | 平台画像端点恒空（`AssetScopeSql` 要求平台项目引用 DEVICE） | 全局资产页采集画像全空，用户以为没设备 |
| 5.15 | `TINYINT(1)` 被 JDBC 映射成 `Boolean`，强转 `Number` 抛 `ClassCastException` | 探针包两个端点恒 500 |
| 5.14 | `?kernel=bogus` 读路径 fail-open | 非法内核静默返回 RF 字段，导出件字段错 |
| 5.16 | dry-run 不落审计行 | 违反 P4 全量审计，审计缺口 |

**含义**：这套「机检 + 真实探针 + 首轮判红留痕」的机制是有效的，且**首轮判红证据被保留而不是删掉重跑**，这一点值得保持。

### F5 证据形态缺口是结构性的，不是偶发

159 条 PARTIAL 里，**真视口截图 / 性能采样 / 真机样本** 三类反复出现，跨 6 个版本。按各版 §5 逐条归类的**估算**区间：真视口类约 55~65 条、性能类约 15~20 条、真机类约 20~30 条（估算值，逐条依据见各版 `05-TEST-REPORT.md §5`，不逐条重算）。根因是环境里没有稳定的「浏览器截图 + 压测样本 + 真机 DUT」三件套，每版只能临时补一部分。

### F6 九个版本只有一个 tag

`git tag` 只有 `v5.7.0`、`v5.12.0-pre-merge`、`v5.16.0`。5.8~5.15 这 8 个版本**没有独立 tag**，`VERSION` 是一次性从 5.7.0 跳到 5.16.0 的（提交 `9fe354c`）。

**影响**：无法按版本回退或按版本取证；若 5.15 的环境拓扑出问题，只能整包回退到 5.16.0 之前。这是本批交付最实在的一处工程风险。

### 7.2 四条改进建议（按性价比排序）

1. **把「真视口截图 + 性能采样 + 真机窗口」三件套做成常设能力**，而不是每版临时补。159 条 PARTIAL 里约 105 条来自这三类；一次投入可让后续每版 PASS 率抬 20 个百分点以上。
2. **首轮判红证据制度化**（已在 5.12 起自发形成）。建议写进 TEST-PLAN 模板：探针首轮必须留档，禁止「重跑一次绿了就算过」。
3. **总纲进度表只放指针**，不复制百分比/WBS 完成数，避免出现 F3 那种三处不同源。
4. **Bump 与 tag 跟着版本走**，或明确宣布「里程碑制」并在 RELEASE-NOTES 写清回退策略——现在是混合态，最容易被误读。

- 九版**没有一版把未做写成已做**：每一处未达成都能在报告里找到原文（本报告 §六 逐条给出了出处）。
