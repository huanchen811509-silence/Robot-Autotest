## 3. 逐项评估

### 3.1 问题 1：全局用例集的中栏与右侧列表

**现象（`shots/01`、`02`、`11`）**

| 观察项 | 1440 视口 | 1920 视口 |
|---|---|---|
| 中栏宽度 | 320px | **320px（不变）** |
| 每个集行可见内容 | `032`、`40条`、`成员/改名/删除` 三按钮竖排 | 同上 |
| 集名称/描述可见像素 | 0（被裁掉） | 0 |
| 单行高度 | 约 150px | 约 150px |
| 成员行高度 | 约 150px（按钮竖排） | **224px** |

**根因（代码级）**

| 位置 | 事实 | 后果 |
|---|---|---|
| `components/CaseSetWorkspace.vue:109` | `grid-template-columns: 320px minmax(0, 1fr)` 写死 | 中栏与视口宽度无关，永远 320px |
| `GlobalCaseSetsView.vue:521` | 集行 grid `8rem 1.2fr 1.4fr 4rem auto` | 8rem+4rem 固定已吃掉 192px，剩 128px 分给名称/描述/按钮 |
| `GlobalCaseSetsView.vue:532` | 成员行 grid `2.5rem 9rem minmax(0,1fr) 8rem auto` | 固定列合计 348px + 3 个按钮，1fr 被压到几十像素 |
| `GlobalCaseSetsView.vue:453-458` | `.row-actions` 是 `flex-wrap: wrap` | 三按钮换行 → 每个按钮再按字换行 → **一字一行** |
| `GlobalCaseSetsView.vue:393-395` | 成员"脚本"列恒输出 `cases.scriptNotApplicable` | 72 行全是「不适用」，是**硬编码**而非按 `bindingState` 渲染 |
| `GlobalCaseSetsView.vue:404-411` | 成员详情只渲染 4 项（编号/标题/分类/脚本） | 与 N3 差距最大的一处 |

**影响**：这是"列表页不可用"级别，不是"不够美观"。32 个公共用例集之间**除 2 位编号外没有任何可区分信息**；用户必须逐个点开才知道是不是自己要的那个（每点一次还要滚过 40×224px 的成员列表）。

### 3.2 问题 2：项目用例打开没有详细信息

**先说结论**：详情面板本身没有坏——同一天、同一组件、换到项目 77（robot 标准工程）就能显示完整的预置条件、4 条步骤、预期结果（`shots/14`）。**空的是数据。**

**实测（`shots/13` 与 DB）**

| 项目 | 用例数 | 无预置条件 | 无步骤 | 无预期结果 | 无用例分类 | 无优先级 |
|---|---|---|---|---|---|---|
| 88 公共库（platform/robot） | 730 | 0 | 0 | 6 | 0 | 0 |
| 77 ED202 公共用例库（standard） | 813 | 0 | 0 | 6 | 0 | 0 |
| **95 EHT pytest 用例库工程** | **485** | **485** | **485** | **485** | **469** | **178** |

```
项目95 用例详情（实拍原文）：内容 / 预置条件：源表无值 / 测试步骤：无步骤记录 / 预期结果：源表无值
项目77 用例详情（实拍原文）：预置条件：1. 大规模集群就绪 2. 可注入单链路… / 测试步骤：4 条步骤（逐条） / 预期结果：…
```

**为什么不能"自动继承"——三条硬事实**

| # | 事实 | 证据 |
|---|---|---|
| 1 | 项目 95 的 485 条里 **414 条与公共库同 `case_code`**，公共库那侧有完整内容 | SQL：`left join test_case g on g.project_id=88 and g.case_code=t.case_code` → `in_global=414` |
| 2 | 但两边是**两批物理行**，`case_code` **没有外键、没有来源列**；公共库是 `project_id=88` 单例，项目库是 `project_id=95` | `V11_31__ui_mode_platform_project.sql`；`test_case` 无 `source_case_id` |
| 3 | 项目 95 的 469 条是 **2026-11-13 从「详细测试流程」这张 sheet 导入**的，`created_by=0`；该 sheet 只带编号/名称/分类/优先级，**没有正文列**。另有 16 条是 2026-11-20 手工建 | `select source,source_sheet,created_by,count(*) … group by` |
| 4 | 公共库的 730 条来自 5 张不同的 sheet（`Import详细测试流程` 414、`HCI` 102、`存储` 86、`AI参数网` 67、`XCCL` 61），字段齐全 | 同上 |

即：**不是"应该继承却没继承"，是"从来没定义过继承这件事"**。平台把公共库与项目库设计成物理隔离（`CaseDetailPanel.vue:60-63` 的"所属提示"就是为此写的），导入只做本行复制，不做跨库关联。

**另一个独立缺口**：pytest 项目的用例名是**分类名**而非用例名。485 条只有 136 个不同标题，`集合通信性能` 重复 28 次、`BMC/BIOS识别` 重复 10 次（`shots/04` 列表里能看到大量同名行）。这跟"详情空"是两个问题，但同一个根：**台账 sheet 的列语义被当成了用例字段**。

**4.2 用例集「立即执行」的三处阻断**

| 序 | 现象 | 回执 | 判据来源 |
|---|---|---|---|
| 1 | 缺 `projectId` 直接 400 | `{"code":40001,"message":"缺少参数：projectId"}` | 该端点是 `@RequestParam long projectId`（`RunController.java:118`），而用例集 id 在路径里——**同一个页面里两套传参习惯** |
| 2 | 补上 projectId 后 403 | `SAFETY_LEVEL_BLOCKED：IM-NIC-002(LX), IM-NIC-004(LX), IM-VIR-001(LX)` | `TestSetRunService.java:67-77` 整单拒绝，不静默剔除（设计正确） |
| 3 | 换成 7 条已判安全级的集（id=108）仍 400 | `存在未绑定脚本的用例（7 条）：IM-FUN-014, … 请在脚本测试的 [Tags] 中写入 case:<用例编号>` | `TestSetRunService` 走 `CaseScriptResolver`，**只读 `.robot` 文件**（`CaseScriptResolver.java:44-70`），完全不看 `case_script_binding` |

第 3 条是本轮最关键的发现：**pytest 用例集在"用例集执行"这条链路上永远跑不起来**，哪怕 `case_script_binding` 里 nodeId 齐全、pytest 工作台同一批用例跑得好好的。报错文案还把人往 RF 的 `[Tags]` 上引。

**4.4 报告可用性实测（同一 run：`EVAL10B-20261121021611`）**

| 观测量 | 值 | 评价 |
|---|---|---|

| 页面表现（`shots/09`） | 通过率 0.0% / 总数 10 / 失败 0 / 跳过 10；顶部"未判定"；风险提示三条 | 页面把矛盾原样呈现给用户 |

**4.5 报告可用性结论**

| 维度 | 判定 |
|---|---|
| 能不能看 | 能：报告页把 runId、计数、风险、metadata 缺项都摆出来了，比"白屏"强 |
| 能不能信 | **不能**：同一份 run，进度说 10 通过、报告说 10 跳过 0 通过、结论说 PASSED。三者任一被引用都会得出相反结论 |
| 能不能交付 | **不能**：`exportable=false` 是硬门禁，且不可达（表单缺 2 个键） |
| 能不能归因 | **不能**：跳过原因已采集到 junit，却在入库时丢弃 |
