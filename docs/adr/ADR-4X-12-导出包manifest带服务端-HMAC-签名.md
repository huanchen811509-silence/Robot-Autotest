# ADR-4X-12 · 导出包 manifest 带服务端 HMAC 签名，导入先验签

- **状态**：已采纳
- **日期**：2026-11-09
- **决策人**：大师（书面批准 2026-11-09，「均按你的建议来」）
- **约束范围**：v4.1.0 起全部工作区导出包（`workspace/<code>/manifest.json`）、导入预检与落库

## 背景

`FR-v4.1-01` 要求 `manifest.json` 逐文件记录相对路径 + sha256 + 字节数 + 格式版本号；
`FR-v4.1-02` 要求「校验 manifest sha256 与服务端 HMAC/签名，篡改或未验签必拒」。

已知事实：sha256 只能证明「文件内容与清单一致」，**不能证明清单本身没被改过**。
目录化方案（`workspace/` 为交换格式）意味着包会被拷贝、邮件传递、放到共享盘，
任何人拿到包都能同时改文件和清单，纯 sha256 校验必然通过。

推断：伪造包的直接后果是把任意 `.robot/.py` 写入可执行源表（`robot_file.content`），
进而被调度执行。这是 4.X 最高危的输入面，不能用「单测绿」放行。

## 选项

| 选项 | 优点 | 代价 | 为何不选 / 为何选 |
|---|---|---|---|
| ① 只做 sha256 | 零密钥管理 | 无法防伪造，误改与伪造不可区分 | 不选：与 PRD 判据直接冲突 |
| ② 非对称签名（Ed25519，公钥内置） | 导入端只需公钥，导出端私钥可离线保管 | 需引入密钥分发、轮换与 JCA Provider 细节；单实例部署收益低 | 暂不选：本期单服务端密钥足够，后续可平滑升级 |
| ③ 服务端 HMAC-SHA256（共享密钥） | 标准算法、无新依赖、实现与验证都简单；密钥不出服务端 | 多实例需共享同一密钥；密钥泄露等于全部包可伪造 | **选**：单实例部署 + 密钥可由环境变量注入，满足当前边界 |

## 决定

导出包 `manifest.json` 增加 `signature` 块：

```json
{
  "formatVersion": 1,
  "projectCode": "DEMO",
  "exportedAt": "2026-11-09T00:00:00Z",
  "generator": "robot-autotest/4.1.0",
  "granularity": "project",
  "rootPath": null,
  "files": [{"path": "project.json", "sha256": "...", "bytes": 123}],
  "signature": {"algorithm": "HMAC-SHA256", "keyId": "server-local-v1", "value": "<64 hex>"}
}
```

边界：

- 签名对象是**去掉 `signature` 后的清单规范形**：键名字典序、无缩进空白的 JSON；
  校验端按同一规范形重算，不做「原文重排」这类脆弱比较。
- 密钥来源：`app.workspace.signing-key`（环境变量 `WORKSPACE_SIGNING_KEY`）优先；
  未注入时在 `<workspace.root>/.signing-key` 生成 32 字节随机十六进制（权限 0600），
  读不到或写不进时**导出失败**，不降级为无签名。
- 导入先验签再谈其它：签名缺失、算法不符、keyId 未知、常量时间比较不相等 → 整包拒绝；
  验签失败不进入隔离区以外的任何写入路径。
- 不做「签名通过即可执行」：验签只解决包的真实性，恶意脚本扫描与人工确认是另一道门（`FR-v4.1-02` ⑩）。

## 后果

- 正面：误改与伪造可区分；导入端的信任判断从「文件哈希一致」升级为「服务端签发的清单」。
- 负面：密钥需要随部署保存与备份；多实例部署前必须先共享密钥，否则 A 实例导出的包 B 实例验不过。
- 触发复核的条件：部署形态从单实例变为多活、或需要把导出包开放给外部组织时，改用非对称签名并补密钥轮换。
