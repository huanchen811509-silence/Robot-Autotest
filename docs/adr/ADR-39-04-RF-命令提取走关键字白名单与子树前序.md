# ADR-39-04 · RF 命令提取走关键字白名单 + 子树前序遍历，不做全文正则盲扫

| 项 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 日期 | 2026-11-09 |
| 约束范围 | v3.9.0 起 RF 报告入库链；v3.12 命令复跑必须复用本提取器 |
| 依据 | RA-PRD-39-001 §3 ADR-39-04；`CaseCommandExtractor` |

## 背景

第一次真实跑双内核演示时，RF 侧 3/3 用例都得到 `NONE`。查 `output.xml` 发现现场套件的写法是：

```
执行命令并记录原始输出
    Log    $ ${cmd}          # ← 命令落在一条**子关键字** Log 的消息里
    ${result}=    Run Process    bash    -c    ${cmd}
```

命令原文不在命中的父关键字自身消息上。另有一条更危险的捷径：对整个 `output.xml` 做 `$ ...` 正则盲扫——那会把断言消息、文档示例里的命令行一起抓进来，报告就变成了假证据。

## 决策

两级判定：① 关键字名命中 8 条白名单（`execute command` / `run process` / `start process` / `ssh 执行命令` / `执行命令并记录原始输出` / `远端执行` / `远程执行` / `执行远端命令`）；② 只在命中的子树内**前序遍历**取第一条命令行（`^\$\s+(.+)$` 或 `命令|执行命令|CMD|argv` 前缀）。
**明确不做**：不对整份 XML 盲扫；不跨关键字取第二条命令。

## 后果与护栏

- 正面：祖先必须是白名单关键字，误识别面可控；命令写在子关键字里也能取到。
- 负面：新的命令封装写法若不进白名单就取不到，需要补白名单（属正常维护）。
- 护栏：白名单变更必须同时补 `CaseCommandExtractorTest$RobotFramework` 用例；`extractsFromNestedLogUnderCommandKeyword` 固定「子关键字」这一场景。
- 复核条件：出现官方关键字库之外的主流封装（如 `SSHLibrary.Execute Command` 之外的第三方库）时补白名单并复核误识别面。

## 验证方式

`mvn -o -B test -Dtest="CaseCommandExtractorTest*"`（16 条）；真实 run `RUN-20261109133212-b70000` 7/7 命中 `RF_KEYWORD`。
