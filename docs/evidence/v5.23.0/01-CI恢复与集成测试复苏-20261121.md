## 二、交付流水线为什么一直红

`delivery.yml` 的顺序是「检查 → 打包」，而检查器优先验 `releases/*.tar.gz`。
CI 上仓库里没有 tar.gz，只能退回验归档证据 `docs/evidence/v3.11.0-delivery/bundle-manifest.json`；
该证据的 version 恒为 `3.11.0`，与当前 `VERSION=5.23.0` 必然不一致 → 每次发版固定判红。

修法两条，缺一不可：

1. **顺序改为「打包 → 检查」**：CI 验本次构建的真包，比归档证据严格（本地门禁本来就是这个顺序）；
2. **归档分支不再与当前 VERSION 比版本号**：归档证据是历史交付的实物记录，拿它证明当前版本是判据错误。
   改为「版本取自证据目录名 + 必须在 CHANGELOG 有对应小节」，保留可证伪性（手写一份假版本仍判红）。
   `--self-check` 同步新增「归档证据结构正常应 PASS」「归档证据版本无出处应 FAIL」两条。

## 三、PR 流水线为什么改成托管 runner

原 `pr.yml` 依赖自托管 runner `rf-lab` + 真 MySQL，该 runner 在本仓库从未注册（运行记录里
`24h0m2s` 后被 cancelled 即为证）。门禁永远排队，等于没有门禁。

改为 GitHub 托管 `ubuntu-latest`：

- 数据库：`docker run` 起一次性 `mariadb:10.11`，口令 `openssl rand -hex 16` 只写进 `$GITHUB_ENV`，
  仓库不留明文；容器每次新建，等价于 `db-reset` 且不依赖交互确认（原 `db-reset` 在非 tty 下会静默取消）。
- 因为 `DB_PASSWORD` 非空，`scripts/test.sh` 会自动追加 `@Tag("it")` 集成测试——不额外加开关，
  避免「CI 里悄悄不跑 IT」。
- `lint` job 先装 `tools/requirements.txt`（openpyxl / fonttools / brotli），否则静态守门缺包即红。
- 测试 job 补一次性 `CRED_MASTER_KEY`：`RunLogWebSocketE2ETest` 拉完整上下文，`SecretCipher`
  强校验该变量（首跑 2277 条里 4 条因此报 Context load 失败）。

## 四、集成测试首次真跑暴露的缺陷

本地 `robot_it` 停在 flyway `11.64`，而 `db/migration` 已到 `11.95`；`mvn -Pit test` 又从未进门禁。
两边叠加，等于这套用例几个月没人真跑过。用空库迁到最新后，65 条里 7 条红，逐条追因：

| # | 位置 | 现象 | 性质 | 处置 |
|---|---|---|---|---|
| 1 | `TenantGuard.TENANT_TABLES` | 删除用例时子表清理抛 500「未配置租户策略」 | 生产缺陷 | 补登记 `case_requirement_version` `case_script_binding` `test_result` `keyword_result` |
| 2 | `ProjectTemplateService.copyCase` | 从模板建项目必报 `Unknown column 'status'` | 生产缺陷 | INSERT 列表去掉 V11_87 已删的 `test_case.status` |
| 3 | 三处 IT seed | INSERT 仍带 `status` 列 | 测试滞后 | 去掉该列；`OVW-OFF`「停用用例」前提随列消失，删掉造数 |
| 4 | `CaseImportTxIT` | viewer 导入不再 403 | 测试前提错 | 判权读 `project_member_role` 三源并集，原用例只写 `member_role`，且被测用户同时是 owner（owner 隐含 PM）→ 改写入 `project_member_role`，viewer 判据换成别人的项目 |
| 5 | `WorkspaceRepositoryJdbcIT.seedSet` | 断言始终对不上 | 测试笔误 | `set_code` 后缀改用与断言同一个 millis stamp |
| 6 | `GlobalCasePreviewForceIT` | 空库里查不到平台库项目 | 测试假设错 | 改走生产同一路径 `PlatformProjectService.id()`（惰性创建） |

第 1 项的静态对账：扫描全部 `requireProjectScope(` 调用点后，现已无「已调用但未登记」的表；
变量表名的调用点只剩三处（`ProjectAssetRepositoryJdbc` / `ProjectRepositoryJdbc` / `TestCaseRepositoryJdbc`），
其中 `ProjectRepositoryJdbc` 自带 `requiresTenant` 过滤，另两处表名来源是 `AssetScopeSql` 与删除子表清单，均已登记。
