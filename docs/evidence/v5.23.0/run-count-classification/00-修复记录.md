# 执行结论口径修复：用例失败不再冒充平台故障

> **缺陷来源**：2026-11-17 演示项目瘦身验收时实测发现——RF 演示项目 10 条用例实际
> `7 通过 / 2 失败 / 1 跳过`，平台却记成 `10 条全失败`、`failure_class=INFRA`、
> `failure_message=分片执行失败: ok`。
> **授权**：大师 2026-11-17 批准「现在就做，按 output.xml 真实统计回填，并把用例失败与执行器失败区分开」。
> **落号状态**：未落号。代码已改、已部署、已实测；版本归属与发版口径归大师。

## 一、根因（两处独立缺陷，一处放大另一处）

### 缺陷 1：计数聚合「一条失败，全部归零」

`RunExecutionService` 原实现：

```java
int passed = result.success() ? total : 0;   // success = 全绿，有一条失败就是 false
int failed = total - passed;
```

`success` 的语义是「整单全绿」，却被拿来当「这一轮是否跑成功」。于是只要有一条用例
失败（RF 退出码非 0），通过数就被清零、失败数记满，`skipped` 根本没有落库。

### 缺陷 2：`reason` 在用例失败时返回 `"ok"`，被当成平台故障

`PabotOrchestrator` 原实现：

```java
String reason = timeoutHit ? "timeout"
        : (!shards.ok() ? shards.reason()
        : (testTimedOut ? "test_timeout" : verified.reason()));   // 产物有效 → "ok"
```

产物校验通过时 `reason = "ok"`，即便 `exitCode != 0`（有用例失败）。随后
`classify("ok", success=false)` 因为 `artifactOk=false` 落到 **INFRA**，
最终落库为「分片执行失败: ok」——一个成功原因冒充失败原因，还带着最误导人的分类。

## 二、改法：把「跑起来了没有」与「是否全绿」拆成两个正交结论

| 概念 | 含义 | 用途 |
|---|---|---|
| `executionOk` | 无整体超时、无启动失败、产物可解析、分片完整 | 决定这一轮结果是否**可用于判定用例质量** |
| `success` | `executionOk` 且退出码 0 且无单用例超时 | 决定 run 是否 **FINISHED**（语义与旧版一致，不动既有调用方） |

组合与落库：

| executionOk | success | run 状态 | failure_class | 文案 |
|---|---|---|---|---|
| true | true | FINISHED | — | — |
| true | false | FAILED | **ASSERT** | 用例未全部通过：N 条失败 / 共 M 条（跳过 K 条） |
| false | false | FAILED | INFRA / ENV | 分片执行失败: <真实 reason> |

### 改动文件

| 文件 | 改动 |
|---|---|
| `OutputXmlProbe.java` | 新增 `stats(xml)` → 逐 `<test>` 取**直接子** `<status>`，给出 total/passed/failed/skipped；`NOT RUN` 计入 skipped |
| `ArtifactVerifier.java` | `VerifyResult` 携带 `Stats`（保留旧构造器）；产物有效与用例全绿解耦 |
| `PabotOrchestrator.java` | `ShardResult` 增 `executionOk` + `stats`；`success` 去掉 `exitCode==0` 之外的含义不变；新增 `reason="tests_failed"`；日志分三支 |
| `PytestRunAdapter.java` | 从 `NormalizedRun` 取三态（不再只取 total）；按 pytest 官方退出码分档：0 全绿 / 1 用例失败 / 2~5 执行器故障 |
| `RunExecutionService.java` | 按真实统计回填（含 skipped）；失败分两类落库，用例失败记 ASSERT |
| `RunRepository(+Jdbc).java` | 新增 `updateCountsDetailed`，7 列一起写（`total = passed + failed + skipped` 硬口径） |
| `RunService.java` | 新增 5 参 `updateCounts` 重载（含 skipped） |
| `PytestNicRunController.java` | ①`passed` 不再写死 0；②`failure_class` 写规范枚举（`PYTEST_EXIT`→ASSERT/INFRA、`USER_CANCEL`→CANCELED） |

> **为什么「只认 test 的直接子 status」**：`output.xml` 里 `<kw>`、`<if>`、`<for>` 内部
> 都各有 `<status>`，用文档级 `getElementsByTagName("status")` 会把一条用例数成十几条。
> 单测 `三态统计只认_test_的直接子_status` 用一条「2 通过 1 失败 2 未执行 + 关键字内也有 status」
> 的样本锁死这条判据。

## 三、验证

### 3.1 单测

| 用例 | 断言 |
|---|---|
| `ArtifactVerifierTest.三态统计只认_test_的直接子_status` | 5 条样本 → `2/1/2`，且 `total = p + f + s` |
| `ArtifactVerifierTest.产物校验把三态统计透传出去` | `success=true`（产物有效）但 `stats.failed=1` 同时成立 |
| `ArtifactVerifierTest.产物缺失时统计为未知而不是全零可信` | `known=false`，防把「没读到」当「跑 0 条全过」 |
| `RunExecutionServiceTest.用例失败按真实三态回填并记为_ASSERT` | `5/2/1` + `ASSERT` + `tests_failed` + `skipped=2` 落库 |
| `PytestRunAdapterTest.runRecordsTestsFailedOnExitOneEvenWithArtifacts` | 退出码 1 → `executionOk=true`、`reason=tests_failed` |
| `PytestRunAdapterTest.runTreatsNonOneExitAsExecutorFailure` | 退出码 3 → `executionOk=false`、`pytest_exit_3` |

## 四、影响面与遗留

1. **历史 run 不会被追溯纠正**：本次只改执行期写入。已存在的错误计数与
   `failure_class=INFRA` 保持原样；若需纠正，应走「重新解析报告」
   （`POST /api/reports/{runId}/parse` → `recountFromResults`），它按 `test_result`
   重算计数，但**不重算 failure_class**——那需要单独的数据修复脚本，本次未做。
2. **节点投递路径未覆盖**：`ShardService.aggregate` 仍用 `total - failed` 估算
   （跳过数缺失）。该路径的 `execution_shard` 表本身没有 skip 列，补齐需加列 + 迁移，
   留作后续。
3. **取消路径的 failure_class 已规范**（`USER_CANCEL` → `CANCELED`），
   若历史数据里有 `USER_CANCEL`，前端需兼容显示——当前前端对未知值回退显示原文，不会白屏。
