## EW310-01 细节：读数与「改前不达标」的证明

同一支探针（项目 29，55 条计划，取首屏 10 行）前后各跑一次：

| 指标 | 改前 | 改后 |
|---|---:|---:|
| 整页可点控件 | 64 | **30** |
| 首屏主操作 | 9 | **5** |
| 每行控件 | 4 | **1** |
| 行内菜单项 | —（无菜单） | **4** |
| 首屏高度（屏） | 2.63 | **1.18** |

`controls-before.json` 的 `verdict=FAIL` 是**预期**——它的用途就是证明改前确实不达标，
不是「跑挂了」。逐项功能的新位置见 `EW310-01/feature-map.md`（16 项，按可点控件拆开，
比 PRD 主文写的 12 项更细）。

**探针在这里测不出的一件事**：计划页分页（判据④「单页 ≤ 50 行」）。演示项目里
计划条数不足一页，`rows=0 / pager=false`，探针给不出结论。该条改由
`frontend/src/views/PlansView.spec.ts` 的两条单测钉住（60 条夹具 → 单页 50 行、
翻页首行 `计划-51`），不假称「已由探针验证」。

## EW310-02 细节：哪些判据是探针判的，哪些只能靠单测

探针在页面里登录 → 打开 `/test-reports` → 真点下拉 → 真选一条，读出：

| 判据 | 探针读数 |
|---|---|
| ①列出本项目 run | 渲染 100 个选项，首项 `RUN-20261109030001-300001 · 2026/11/09 03:00:35 · 失败 · 0 条用例`（四段齐全） |
| ②关键词过滤 | 用该 runId 过滤后**只剩 1 条**；换成不存在的关键词出现空态提示 |
| ③自动带标题 | 选中后标题 = `测试报告 RUN-20261109030001-300001` |
| ④手打降级 | 主路径手打框不可见；点「高级：手输 RUN_ID」后可见，再点回来 |

**两处探针判不了的**（写在这里而不是藏起来）：

1. **时间档 7d/30d 的真实差异**：本库全部 run 落在最近 5 天内（2026-11-04 ~ 11-09），
   切档切不出差别。探针只验证控件存在且可切换；边界（恰好 7 天前保留、早 1 ms 剔除、
   运行中的 run 按 `started_at` 参与排序）由 `frontend/src/utils/runPicker.spec.ts` 用
   注入的 `now` 钉住。
2. **「点选一条」这个动作本身**：naive-ui 用虚拟列表，happy-dom 下量不出宽度、选项不渲染，
   单测点不到。所以视图单测把 `RunPicker` 换成桩组件（只验「选中之后页面做了什么」），
   真点由本探针覆盖。两者互补，谁都不替代谁。

另：`RunPicker` 只加载最近 100 条，更早的 run 靠时间档或「高级」手输——这是接口能力
限制（后端 `RunPageQuery` 只有 `state/page/size`），已记入 `DEV-PLAN.md` 偏差。

## EW310-03 细节：用例集来源与那次撞键

契约验证（真 HTTP + 真库，夹具一次性、跑完即删）逐条：

| # | 判据 | 结果 |
|---|---|---|
| ① | 按用例集建草稿（不传 runId）→ 取该集最近一次执行 | `200`，`runId=CT-…-NEW`，`sourceType=CASE_SET` |
| ② | 传该集内的 runId → 用指定的那一次 | `200`，`runId=CT-…-OLD` |
| ③ | 传**别的集**的 runId → 拒绝 | `400` |
| ④ | 旧路径（按 run 建）零回归 | `200`，`sourceType=RUN`，`caseSetId=null` |
| ⑤ | 列表带 `sourceType` / `caseSetId` | 命中 2 条 |
| ⑥ | 冻结后删掉源 run，渲染逐字不变；快照里记得源 runId | 长度 566 前后一致；`snapshot_json` 含 runId |

`snapshot-case-set.json` 是这次冻结件的真实快照（`snapshot_json` 原样导出）：
它里面既有 `runId`、`state`、计数与元数据——**删掉 `run` 表那一行之后仍然渲染得出**，
这就是判据③「自包含」的实质，不是「引用式快照 + 恰好源还在」。

**顺手抓到并修掉的一个真 bug**：`uk_report_run_version (project_id, run_id, version)`
唯一键下，同一个 run 上有多份报告时（按 run 建的 + 按用例集建的），
`freeze` 原本按「本报告版本 + 1」分配版本号，先冻结第 1 份会占掉第 2 份刚用过的号
→ 唯一键冲突 → **HTTP 500**（首次契约验证实测）。改为按 run 全局 `maxVersion + 1`
分配后通过。这条不是本次需求引入的问题，但「按用例集建报告」让它变得容易撞上。

`down-up.log`：`V11_25` 的 down→up 真实演练——两列摘掉再装回、索引重建、
类型/可空性逐一比对一致、`test_report` 行数不变，末行 `RESULT PASS fails=0`。

> 演练脚本本轮被**参数化**（目标表与列从 up 脚本里解析）：v3.9.0 初版把
> `test_result` / `command%` 写死在脚本里，拿去演练 `V11_25` 会「通过」一个它
> 根本没看的表——那种假绿比没有演练更危险。现在两条迁移都能跑，且都会打印它实际检查了什么。
