## 2 为什么之前会出现两套数字

`run` 表有**两个时期、两条链路**各写一半的计数列：

| 列组 | 引入 | 谁写 | 缺什么 |
|---|---|---|---|
| `total_tests` / `passed_tests` / `failed_tests` | V4_1 | 执行期 `updateCounts` | `passed_tests` 在 pytest 路径**恒写 0**（`PytestNicRunController` 传字面量 `0`）；robot 路径 `passed = total - failed` 是二元估算；**没有 SKIP 位置** |
| `pass_count` / `fail_count` / `skip_count` | V5_1 | 报告入库 `reports.replace` | 只有走过 `/api/reports/ingest` 的 run 才有真值 |

两者叠加的结果就是 L-19-06 的形状：`EHT-FAKE-1794805219801` 明细 5/4/61，
`run` 表读作 `70 / 0 / 4`——执行页与报告页各显示一套，且哪套都不完整。

## 3 口径：一个真源，两组镜像

**真源只有一个：`test_result` 的逐用例结论。** 两组列都是物化镜像，用**同一段聚合 SQL** 一起写：

```sql
UPDATE `run` r
  JOIN (SELECT `run_id` AS `rid`,
               SUM(`verdict` = 'PASS') AS `p`,
               SUM(`verdict` = 'FAIL') AS `f`,
               SUM(`verdict` = 'SKIP') AS `s`
          FROM `test_result` GROUP BY `run_id`) agg ON agg.`rid` = r.`id`
   SET r.`total_tests` = agg.`p` + agg.`f` + agg.`s`,  r.`passed_tests` = agg.`p`,
       r.`failed_tests` = agg.`f`,                      r.`skipped_tests` = agg.`s`,
       r.`pass_count` = agg.`p`,                        r.`fail_count` = agg.`f`,
       r.`skip_count` = agg.`s`
 WHERE r.`project_id` = ? AND r.`id` = ?
```

三个刻意的选择：

1. **一条 UPDATE 写 7 列**，不分两条。分两条就有中间态，第二条失败时又多一个「两套数字」的 run。
2. **`total = p + f + s` 由 WHERE 之外的三列自然成立**：`DISPATCHED` 不是 PASS/FAIL/SKIP，
   天然落在三列之外，不需要额外排除条件——写进 WHERE 反而容易漏一个分支。
3. **没有明细就不写 0**。JOIN 不产生行 → 影响 0 行 → 调用方保留执行期估值。
   把「没跑过」写成「跑了 0 条」，这个区别就永久丢了（本库 34 个这类 run 保持 `skipped_tests IS NULL`）。

写入侧挂在 `ReportIngestService.ingest()` 的 `reports.replace(...)` **之后**，同一事务内。
顺序是硬约束：重算必须发生在明细落库之后，否则只会把计数清零——
`ReportIngestServiceTest.入库后按明细重算计数` 用调用时间线 `["replace", "recount"]` 钉住这一点。

读路径（`OverviewRepositoryJdbc.recentRuns`）同时拆掉了旧的兜底：

```java
// 旧：pass > 0 ? pass : passed_tests   ← 「哪个非零用哪个」，在两个真源之间反复横跳
// 新：有明细用明细，没明细才退到列上的执行期估值
int rows = rs.getInt("case_rows");
boolean detailed = rows > 0;
```

旧写法失效的场景恰好就是 L-19-06：明细 0 PASS、列里存着 5 时它会挑错的那个。

## 4 幂等怎么证明（不是「跑两次没报错」）

摘要行只报**回填后的状态**，不含「本次改了多少行」，所以两次可直接 `diff`：

```
[backfill] SUMMARY runs=550 withDetail=516 backfilled=516 pending=34 dispatched=4 \
           total=794 passed=165 failed=497 skipped=132 mismatch=0
```

「修掉多少差异」单独打一行 `[backfill] repaired mismatchBefore=… mismatchAfter=…`，不参与比对。

另外做了一次**破坏性自证**（不是只看摘要自洽）：

| 步骤 | 读数 |
|---|---|
| 取明细最多的 run | `EHT-FAKE-1794661209912`，原始 `70/5/4/61/5/4/61` |
| 蓄意改坏 | `total_tests=9999`、`skipped_tests=NULL` |
| 破坏后差异行 | `1` |
| 跑回填 | `repaired mismatchBefore=1 mismatchAfter=0`，`SUMMARY` 回到原值 |
| 修复后该 run | `70/5/4/61/5/4/61`，`total-(p+f+s)=0` |

教训一条：**别用「改了多少行」当幂等证据**。mysql CLI 默认带 `CLIENT_FOUND_ROWS`，
`UPDATE` 回报的是**匹配行数**，幂等的第二次跑照样报 `516`，看起来像完全没生效。
初版脚本正是这么写的，已改成用差异行数收口。
