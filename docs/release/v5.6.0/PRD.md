# v5.6.0 产品需求文档（PRD）· 可见性版本

> 流程位置：③ PRD。每条需求必须可判定 —— **写不出判据的不算需求**。
> 上游：`v5.6.0-01-评估报告-可见性版本-20261113.md`（结论 C-1~C-7、D-01~D-05）。
> 版本号 v5.6.0 暂定；本文件**不修改 `VERSION`**，落号以 G 门判定为准。

---

## 1. 版本定位

**一句话**：不新增业务功能，把已经能跑的能力**摆到台面上**、把「发起了但看不见」的流程**变成看得见**、把「能导出但不好读」的报告**变成能评审**，并把「两套菜单」收敛成**一套**。

**菜单口径（D-01 已拍板）**：pytest 工程与标准工程**共用全量菜单**，不再维护第二棵树。业务事实是「先配台架才能跑」，pytest 工程同样要先登记 DUT、配凭据、拉环境——因此资产 / 环境 / 维护这些入口对它不是噪音，而是前置条件。

**为什么这么定**：v5.5.0 已用 59 条真机用例证明链路是通的（57 PASS / 1 FAIL / 1 ERROR），但同一次评估也证明——界面上发不起执行、GPU 资产表里没有实体、报告命令列恒 `NONE`。能力不缺，**缺的是「被看见、被用上、被信任」**。

**范围三分法**：

| 类别 | 含义 | 条数 |
|---|---|---|
| 本版必做 | 不做则本版目标不成立 | 23 |
| 本版尽力 | 依赖外部条件，可降级登记 | 1 |
| 后续版本 | 方向已定，本版不排期 | 12 |

## 2. 约束与术语

| 术语 | 定义 |
|---|---|
| 工程类型 `kind` | `standard` / `platform` / `pytest-suite`；本版**只扩充它的语义用途**（驱动可见性规则），不新增取值 |
| 菜单增量项 | 在本版单一菜单之上唯一的工程类型专属叶子，即 `/pytest-workbench`；除此之外不保留任何「某工程看不到某项」的规则 |
| 空态自解释 | 页面在当前工程无数据时，不用空白或报错回避，而是说明「为什么没有、能做什么」 |
| 可用性验证项 | 入口已确定可见，需实测「点进去能不能用」的需求；不可用按缺陷登记 |
| 假绿 | 门禁在缺少采样/证据时默认通过，导致「没测」看起来像「测过」 |

**硬约束**（违反即打回）：

1. 不破坏既有契约：已有端点语义不变；新增能力走新端点并标注 deprecated 迁移路径（对应 D-04）。
2. 已应用迁移不可改，只追加新号（`db10f39` 后首个空号）。
3. 安全闸不得放松：`real` 仍须 `confirmReal=true` + ADR-0013 双通过 + fail-closed。
4. 元数据十项门禁不放宽（`CASE_ID/RUN_ID/QA_PROJECT/DUT/LINK/SW_BUILD/BASELINE/OPERATOR/STARTED_AT/CASE_KIND`）。
5. 本版**不得**出现「为通过门禁而改证据」的改动。
