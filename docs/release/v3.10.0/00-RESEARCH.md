# v3.10.0 需求调研（RA-RES-310）

> 目的：在动手之前把「现在到底长什么样」量出来。全部读数带命令与文件，推断必标 `[推断]`。
> 标注口径：`[已核实]` = 有命令输出或数据库读数；`[推断]` = 由已核实事实推导，未直接观测；`[假设]` = 无法验证、按经验取值。

## 1. 计划页「一屏到底有多挤」

| # | 结论 | 标注 | 依据 |
|---|---|---|---|
| 1 | 计划页首屏可点控件 **64 个**，其中页面级主操作 **9 个** | [已核实] | `scripts/plan-controls-probe.mjs` → `EW310-01/controls-before.json`（项目 29，55 条计划） |
| 2 | 每行 **4 个**文字按钮（编辑 / 暂停·恢复 / 立即触发 / 删除） | [已核实] | 同上 `rowControls` |
| 3 | 首屏高度 **2.63 屏**（`.app-main` 滚动高 / 视口高） | [已核实] | 同上 `screens` |
| 4 | 冲突处理区默认**展开**，跳过事件区默认收起 | [已核实] | 同上 `conflictCollapsed=false` / `skippedCollapsed=true` |
| 5 | 「计划组 / 依赖图 / 返回运行列表」三个跳转占了工具条的 3 个按钮位 | [已核实] | `PlansView.vue` 工具条 DOM |
| 6 | 主操作里 3 个是「跳走」（离开本页），不产生本页动作 | [推断] | 由 #5 推导：这 3 个按钮在首屏占用与「新建计划」同级的视觉权重 |
| 7 | 把 3 个跳转与 4 个行内动作收进菜单后，首屏主操作可降到 5 个 | [推断] | 按 #1 − 3（跳转）+ 1（「更多」）推得；实测 5，见 `controls-after.json` |

## 2. 报告草稿「建报告要先知道 runId」

| # | 结论 | 标注 | 依据 |
|---|---|---|---|
| 8 | 对外报告草稿原来只有一个手打 `RUN_ID` 输入框 | [已核实] | `TestReportsView.vue` 旧版模板 |
| 9 | `RUN_ID` 形如 `RUN-20261109030001-300001`（22 字符，含 14 位时间戳 + 6 位序列） | [已核实] | 库表 `run.run_id` 取样 |
| 10 | 本项目 run 数量：项目 29 有 **470 条**、项目 1 有 8 条 | [已核实] | `select project_id, count(*) from run group by project_id` |
| 11 | 后端 `RunPageQuery` 只有 `state / page / size` 三个参数，没有关键词与时间过滤 | [已核实] | `backend/.../RunPageQuery.java`、`frontend/src/api/execution.ts` |
| 12 | 用户手里通常只有「上周二那次回归」这类信息，没有 22 位 id | [假设] | 无用户访谈数据；按「报告标题靠人记、id 靠拷」的常识假设 |
| 13 | 因此「手打 id」是主要失败点：打错一个字符 → 建不出来 → 回头重新找 | [推断] | 由 #9 + #12 推导 |
| 14 | 一次加载 100 条 run 足够覆盖「最近几次回归」，更早的靠时间档或高级入口 | [假设] | 无使用频次数据；100 条 ≈ 本项目 5 天的量（#10 ÷ 天数） |

## 3. 用例集来源（FR-v3.10-03）

| # | 结论 | 标注 | 依据 |
|---|---|---|---|
| 15 | `test_report` 现有列：`project_id / run_id / title / state / version / snapshot_hash / snapshot_json / snapshot_html / source_summary / frozen_at …`，**没有来源类型字段** | [已核实] | `show columns from test_report` |
| 16 | 冻结后渲染读的是 `snapshot_json`，因此「用例集来源」只要在冻结时把事实写进快照，就不需要运行时回查 run | [已核实] | `TestReportService.freeze` + `ReportReadRepositoryJdbc` |

## 4. 与本次改造无关但影响验收的事实

| # | 结论 | 标注 | 依据 |
|---|---|---|---|
| 19 | 本库全部 run 落在最近 5 天内（2026-11-04 ~ 11-09），「近 7 天 / 近 30 天」切不出数据差异 | [已核实] | `select min/max(coalesce(finished_at, started_at, enqueued_at)) from run` |
| 20 | 因此时间档过滤无法在真实浏览器里产生可观测差异，只能由单测钉边界 | [推断] | 由 #19 推导 |
| 21 | naive-ui 的 `NSelect` 下拉 teleport 到 `document.body` 且用虚拟列表，happy-dom 量不出宽度 → 选项不渲染 | [已核实] | 本次 `RunPicker.spec` 首次尝试即失败；改为桩组件 + 纯函数单测 |

## 5. 调研结论

1. **计划页的问题是「权重平铺」而不是「功能太多」**：9 个主操作里 3 个是跳转、4 个是逐行动作，收进菜单即可，不需要删功能（对应 ADR-310-01/03）。
2. **报告页的问题是「要求用户记住系统内部标识」**：必须在界面里把 run 摆出来给用户选，而不是让用户去别处抄（对应 ADR-310-04）。
3. **用例集来源是数据模型问题，不是界面问题**：`test_report` 缺来源字段，冻结快照已自包含 → 加两列即可，不用新表（对应 ADR-310-07/08）。
4. **验收必须靠探针 + 单测两条腿**：交互在虚拟列表下测不到（#21），纯逻辑又测不出接线错 → 两者分工，各自写明缺口（#20）。
