## 0. 结论先行

1. **这批需求不是「从零做功能」，而是「把已经建好的模型接到界面上」**。R1/R2 的字段基线已经入库（同一份 `基本功能导入测试v0.5.0.0.xlsx` 的 730 条用例、2779 步骤、32 个一级分类，`CHANGELOG.md:21`），R3 的 SSH 采集链路已经跑通（`HostInventoryService` + `SystemSshClient` + 10 类只读命令），R5 的「项目转模板」后端已实现（`ProjectContentController#saveAsTemplate`）。**真实缺口集中在「详情视图 / 内容编辑入口 / 编排接口 / 权限粒度」四处**，不在数据建模。
2. **R6 里藏着一个必须优先修的真 Bug**：全局模式系统设置是 8 张卡片，目标路由全部**不带 `meta.global`**，按 `router/index.ts:354-358` 的守卫，点击后会被强制切回项目模式。即「全局模式下进系统设置」这条路径当前根本走不通，不只是视觉形态问题。
3. **R1 有一个数据损失点**：导入器 `CaseImportService.java:134-160` 的 `HEADER_ALIASES` 只认 12 类列，参考表的 **A端命令 / B端命令 / 交换机配置 / 测试结果** 四列**没有别名、导入即丢弃**；「测试资源」与「ED202覆盖情况」被合并进同一个 `ed202_coverage` TEXT 列，语义混装。需求 1 要「详细信息」，必须先补这四列，否则详情页面无内容可展示。
4. **R4/R5 是同一条链的两个断点**：后端 `project_template_item` / `project_template_asset`（`V11_36`）已建，`TemplateDetail / TemplateItem` 前端类型已定义，但全 `frontend/src` 无任何视图消费；`templateApi.get` 与 `saveAsTemplate` 定义了却无调用点；「通过模板建项目」后端**完全没有接口**（`ProjectController#CreateProjectRequest` 无 `templateId`，全库检索零命中）。现有 `applyContent` 只能往**已存在**的项目里灌内容。
5. **R7 的权限是「半截」**：项目模式系统设置 6 个二级项只有 3 个带 `capability` / `adminOnly`；能力表 `ROLE_CAPABILITIES` 硬编码在前端 `config/navigation.ts:463`；后端 `PermissionResource` 无 MENU 维度、无菜单权限表、无 `@PreAuthorize` 类注解。**只做前端隐藏是「假权限」**，直接 URL 仍能访问 `/admin`、`/settings/ai`。
6. **R8 有现成轮子**：`composables/useTheme.ts:108-114` 已实现 `cycle()`（system→light→dark→system），但全 `src` 无组件调用；当前主题是账户菜单里的三态按钮组、语言是 `<select>`（`AppearanceControls.vue:80/:134`）。改造量很小。
7. **R9 可删，低风险**：目录名是 `E\uf03a\uf05cworkspace\uf05c自动化测试\uf05cRobot-Autotest` 这**一个**文件夹（U+F03A/U+F05C 是 Symbol 字体 PUA 映射，低位即 `:` 与 `\`），42 个文件 / 29,464 B / 全部 14~16 行，2026-11-10 19:03:30~31 一秒内批量生成，是套模板时把整条 Windows 路径当成目录名写错位置的产物。正牌仓库既无 `4.4.0~4.9.0` 目录也无 CHANGELOG 小节（这些只是 v4.9.2 收口前的工作包），真源全在 `docs/release/v4.9.2/` 与 `docs/plan/v4.4-v4.9-*` 三件套。**不在 git 版本控制内、不在机检扫描范围内**。学徒只给判定，**未执行删除**。
8. **R10 的结论被一条更高优先级的事实改写**：`测试自动化demo程序/04 8001平台/AGENTS.md` 明确记载「02 智能网卡实测-CX7 仅为尚待吸收的来源」「旧 02 迁移已终止，不继续吸收剩余代码」，以及 2026-10-25 收口令「本轮为最后一次代码合入，剩余代码不再需要……不再以『全部迁移完成』为前提无限开发」。**即这轮移植已经做过一轮并被叫停**。因此答案不是「能不能充分借鉴」，而是「按已叫停的边界做定点补移，且优先复用 8001 平台已验证的实现而非原始素材」。

10. **综合评分 3.60 / 5（72 分）：建议立项，分三波实施**（详见 §9.1）。波次一修 R6 Bug + 补 R1/R2/R8 呈现层，波次二打通 R4/R5 模板链，波次三做 R7 权限与 R3 资产详情。**R10 不进开发波次**，单列为技术债/知识沉淀议题。

## 2. 逐项需求评估（R1~R8）

> 每条统一给：现状 → 差距 → 方案对比（≥2，含「不自己做」）→ 建议 → 可判定验收判据 → 影响面 → 估算与风险。估算一律 `[假设]`。

### 2.1 R1 公共用例 / 项目用例 / 分配用例打开详情

**现状与差距**：见 §1.4。三类用例实际落在同一张 `test_case`，靠 `project_id` 区分——公共库 = 单例平台项目 `PLATFORM-LIB`（`V11_31:12-17`），分配语义是**快照复制 + 手动重同步**（`ProjectSyncService`、`PlatformCaseSetController:17-18` 注释明确「避免在平台库里改一条、所有副本静默变」），副本靠 `sync_job_item.external_id/local_id/remote_id` 追溯（`V11_37`）。**市场上并不存在独立的「分配用例」实体**，需求里的第三类其实是「带来源标记的普通项目用例」。

| 方案 | 做法 | 优点 | 代价 / 否决理由 |
|---|---|---|---|
| A（推荐） | 统一 `CaseDetail` 契约 + 三个入口（公共库详情抽屉、项目用例行内展开升级、副本详情显示来源徽章）；先补 4 列导入映射 | 一套组件覆盖三类；不改数据域语义；副本来源可追溯 | 需新增 4 列（或 JSON 扩展列）+ 导入回归 |
| B | 为「分配用例」新建独立实体与表 | 语义最直白 | **否决**：与现有 `sync_job_item` 追溯链重复，且要改同步/导入/执行三条链，破坏 `local_override` 语义 |
| C（不自己做） | 只做公共用例详情，项目用例沿用现有行内展开 | 成本最低 | **否决**：需求明确要求三类一致，且项目用例详情只展示 4 项、连分类都不显示 |

**建议**：A。分两步——(a) 补 `HEADER_ALIASES` 与 `ED202_EXPECTED_COLUMNS`，把 A端命令/B端命令/交换机配置/测试结果落成独立列或 `case_extra_json`，并**补导一次 730 条**（幂等依据已有 `external_id` + `content_sha`）；(b) 统一详情面板，字段分组为「标识 / 分类 / 内容 / 执行 / 溯源 / 版本」六组，公共库与项目域共用组件，副本额外渲染「来源公共用例 `external_id` + 同步作业号 + `local_override` 标记」。

**验收判据**（可判定）：① 对 `/g/cases` 任一行点开详情，14 列基线字段中至少 12 项可见且有值（缺失须显式显示「源表无此列」，不得留白）；② 项目用例行内展开与公共库详情字段集一致；③ 由同步作业生成的副本详情显示来源 `external_id` 与 `sync_job.id`，点击可跳公共用例；④ 用样本 xlsx 重新导入后 `SELECT COUNT(*) FROM test_case WHERE external_id LIKE 'IM-%' AND a_side_command IS NOT NULL` > 0；⑤ 详情接口不得返回 `secret`/口令类字段。

**影响面**：DB 加列（1 次新迁移）、`CaseImportService`/`GlobalCaseService`/`ProjectSyncService` 三处 SQL、`CaseDetailPanel` + 新增公共库详情组件、i18n 双语、导入回归用例。

**估算 `[假设]`**：M（约 4~6 人日，含补导回归）。**风险**：补导会改 `content_sha` 与 `version_no`，可能触发存量同步作业的误判「远端有更新」——须在预演库先跑一遍 `sync/preview`，确认 `action` 不出现非预期 UPDATE。

### 2.3 R3 资产 + 登录凭证登录设备获取详情（硬件 / 软件 / 状态）

**现状与差距**：**后端能力已具备且是真链路**——`credential` AES-256-GCM（`SecretCipher`、`CipherConfig`）、`GlobalAssetService#collect` 要求操作者选凭据并 `confirm=true`、`HostInventoryService#resolveMaterial` 解密、`SystemSshClient` 用 `ssh` + `sshpass -e`（口令只走 `SSHPASS` 环境变量）、`HostInventoryCollector` 10 类只读命令（OS/KERNEL/CPU/MEMORY/DISK/GPU/NIC/IP/ROCE/ROUTE）落 `device_host_spec.spec_json`；`device` 表已含型号/厂商/序列号/操作系统/内核/BMC/登录方式/账户/状态。**缺的是「详情视图」和「信息架构」**。

参考表 `当前测试环境` 的 12 字段里，主程序已有 8 个，**缺「角色 / 网口数 / 网卡配置汇总 / VF测试虚拟机 / 凭据引用展示」**；其中「网口数 / 网卡配置汇总」可由 `device_port`（`V11_29` 加 `nic_name/nic_index`）与 `device_host_spec.nic_count/roce_ports/roce_max_gbps` 派生，不必新增列。

| 方案 | 做法 | 优点 | 代价 / 否决理由 |
|---|---|---|---|
| A（推荐） | 新增资产详情路由 `/assets/:id` 与 `/g/assets/:id`，三分区渲染「硬件 / 软件与带外 / 状态」，把已有 `collect` 按钮放进详情页并展示采集时间、命令原文、原始输出、结构化值四层；公共/项目共用组件 | 复用已跑通的 SSH 链路；与 demo 平台证据链同构；改动集中在呈现层 | 需在 `spec_json` 到三分区之间加一层字段映射；大表分页 |
| B | 新增 Redfish / SNMP / 专用 agent 采集通道 | 覆盖带外、少依赖 SSH | **否决（本轮不做）**：现无实现，属于新执行能力，须单独走评估与实机验证；与「详情」需求不同层 |
| C（不自己做） | 沿用现有环境采集页通用渲染 | 零成本 | **否决**：需求明确要求「硬件 软件 状态」，通用 `category` 表格不满足 |

**建议**：A，并把「采集状态」显式化为四态：`未采集 / 采集中 / 部分成功(PARTIAL) / 失败(FAILED)`，与 `HostInventorySpec.status` 已有枚举对齐；详情页必须展示 `credentialId` 的**掩码名**与 `keyMasked` 前缀，**不得返回任何明文口令**（沿袭既有密钥泄漏断言教训：逐条校验 `keyMasked`，不要对整段响应查 `sk-`）。

**验收判据**：① 公共资产与项目分配资产均能从列表点进详情，URL 稳定可分享；② 三分区字段与 `当前测试环境` 表 12 字段逐项对照，缺失项显式标「未采集」；③ 选凭据点采集后，详情页出现 `collectedAt`、命令原文、原始输出折叠区、结构化值；④ 全链路响应体不含 `secret`/明文口令，逐条校验 `keyMasked`；⑤ 采集失败时保留上次成功快照并标 PARTIAL，不清空历史。

**影响面**：前端新增 1 组件 + 2 路由 + 1 个只读聚合接口；**后端零新增采集实现**；DB 零迁移（可选加 `role` 列）。

**估算 `[假设]`**：M（约 4~6 人日）。**风险**：CDP 门禁未恢复，真实浏览器链路取证受限；须至少用 HTTP 级集成测试补齐，不能只靠单测。

### 2.4 R4 模板卡片包含用例信息 + 全局模式进入模板编辑

**现状与差距**：模板卡片只有 `itemCount` 一个聚合数（`GlobalTemplatesView.vue:149-176`、`api/globalTemplates.ts:5-17` 无 `cases/caseSets` 字段）；后端 `project_template_item`（`V11_36:15-28`）已可存 `CASE/CASE_SET/SCENARIO` + `mode=reference/copy` + `snapshot_json`；`TemplateDetail/TemplateItem` 前端类型已定义但**全 src 无视图消费**；`templateApi.get` 无调用点；无 `/g/templates/:id` 路由；新建表单 `TemplateRequest` 只有 name/code/kernel/visibility/description，**不要求关联用例或用例集**。

| 方案 | 做法 | 优点 | 代价 / 否决理由 |
|---|---|---|---|
| A（推荐） | 模板卡片按项目卡片规格重做（独立 `TemplateCard.vue`），展示「用例数 / 用例集数 / 场景数 / 资产数 / 内核 / 最近更新」；新增 `/g/templates/:id` 模板工作台，复用项目模式「用例库 / 用例集 / 资产」的只读+编辑组件；新建模板第 2 步强制关联用例或用例集 | 与需求「类似项目卡片、可全局进入编辑」逐字对齐；`project_template_item` 直接承载 | 组件复用需先做参数化（去 `projectId` 硬绑定） |
| B | 只在卡片上把 `itemCount` 拆成三个数字 | 极小 | **否决**：不满足「进入模板编辑用例/用例集」 |
| C（不自己做） | 模板只当元数据，内容在创建项目时用向导现挑 | 现状即如此 | **否决**：需求 4、5 明确反对 |

**建议**：A。**关键设计约束**：模板不是项目，`project_template_item.mode=reference` 指向的是公共库对象，因此模板工作台必须明确「此处编辑的是模板内容清单，不是公共用例本体」；若允许直接改用例内容，须定义「写回公共库 / 写模板快照」二选一并走权限。新建模板的「关联用例或用例集」应做成**硬校验**（提交时 `itemCount=0` 拒绝并提示），否则 R5 的「模板建项目」会产出空项目。

**验收判据**：① 模板卡片显示四类内容计数且与 `GET /api/global/templates/{id}` 明细逐项相等；② 全局模式可从卡片进入 `/g/templates/{id}`，增删改用例项/用例集项后刷新不丢；③ 新建模板未关联任何用例或用例集时提交被拒、错误文案可见；④ 内置 `builtin` 模板的内容只读（或复制后才可改），行为有断言；⑤ 模板卡片与项目卡片共用同一套栅格与视觉 token。

**影响面**：前端为主（新组件、新路由、新视图、列表接口扩字段）；后端 `TemplateController#get` 需在返回里带 items 汇总。

## 3. 专项评估 R9：乱码目录成因与可删除性

### 3.1 成因（字节级已核实）

目录名 `E\uf03a\uf05cworkspace\uf05c自动化测试\uf05cRobot-Autotest` 是**单一文件夹名**，不是嵌套路径：

| 码点 | 字符 | 说明 |
|---|---|---|
| `U+0045` | `E` | 盘符 |
| `U+F03A` | `` | Unicode 私用区，Symbol 字体 PUA 映射，低位 `0x3A` = `:` |
| `U+F05C` | `` | PUA，低位 `0x5C` = `\` |
| `…` | `workspace` / `自动化测试` / `Robot-Autotest` | 原路径各段，被 `\uf05c` 连接 |

即某次操作把 `E:\workspace\自动化测试\Robot-Autotest\...` 整条路径字符串经 Symbol 编码转换后，**当作一个目录名**创建在工作区根下。

**佐证**：42 个文件、合计 29,464 B、每个 547~933 B / 14~16 行；最早与最晚时间戳 `2026-11-10 19:03:30.54` ~ `19:03:31.70`，**1.2 秒内批量写完**；结构为 `docs/release/4.4.0~4.9.0/` 各 6 件套 + `docs/evidence/4.4.0~4.9.0/README.md`。抽读 `4.4.0/00-RESEARCH.md`（16 行）与 `4.4.0/01-ASSESSMENT.md`（14 行）：只有「现状 / 关键决策 / 未决与假设」「影响面 / 数据与迁移 / 风险 / 回退」等通用套话，**无机检必备的「前置条件」「不做」「修订记录」段，无 `[已核实]/[推断]/[假设]` 标注，无证据清单**；`docs/evidence/4.4.0/README.md:14` 甚至引用了并不存在的 `docs/release/4.4.0` 路径。`[已核实]`

### 3.2 是否唯一副本

### 3.3 判定与建议动作

**结论：可删除，数据丢失风险低。** 依据见 §3.2 六项——它是批量套模板的误生成产物，内容无独有事実，与仓库「不逐版本复制目录」的明令相冲突，且既不在 git 里也不在机检里。

**但学徒未执行删除**，按个人文件安全规则只做只读评估。建议动作（须大师明确确认后才可执行）：

1. 先留存一份**目录清单 + 2 个抽样文件内容**作为审计痕迹（几 KB，成本为零）；

### 4.5 结论

**不建议「充分/整包移植」，建议「定点补移 + 方法论沉淀」，且以 8001 平台已验证实现为第一参考源。`[已核实]`**

- **最大价值**：`checks.py` 判据库、`conftest.py` 安全闸门、`build_cases.py` 生成链、以及四层证据链与反伪造复核方法，可低改造补齐主程序 pytest 侧；其中「反伪造复核」应直接升为门禁规则，价值高于任何代码。
- **最大风险**：整包移植会一并带入 CX7/400G 硬件绑定、内网信息、Windows 运行时、专有包依赖，以及已被复核判定不成立的历史证据——**这些恰好与仓库「只认真实链路、机检必须进门禁」的纪律相冲突**。
- **优先顺序**：① 先比对 8001 平台 `backend/niclab/` 已吸收了什么（§1.6 V6）；② 只补主程序确实缺、且 8001 也没有的 A 类能力；③ 代码搬运前先做脱敏与去硬件常量，任何进入主程序的片段不得含内网 IP、设备名、门限常量与绝对路径。
- `[假设]` **需求原文「深圳移植」按输入误差理解为「深度 / 充分移植」**；若指「在深圳实验室环境内移植」，则还需评估实验室网络与设备可达性，本文 §4 的边界结论需重评（§9.3 P7）。
