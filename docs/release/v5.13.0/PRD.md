## 1. 版本定位

| 项 | 内容 |
|---|---|
| 一句话 | 把「设备 ↔ 采集凭证」的绑定从**界面上的开关**变成**采集链路真正读取的事实**：采集时自动用绑定、采集后自动写验证事实、列表里能看见关联关系与采集结果，手工关联可永久保存 |
| 性质 | **断链修复版**：不是缺表，是四处断点（项目侧读不到、采集不读、验证不写、界面拿账号名冒充凭证） |
| 上游需求 | R9 |
| 目标产出 | 一条可查询的「采集画像」（`READY/PARTIAL/BLOCKED`）+ 三处写入补齐 + 三处展示 + 两个采集入口 |
| 不追求 | 不做资产工作台合并（5.12 已完成）、不做环境快照对象化（5.15）、不做探针包（5.15）、不改报告（5.14） |

### 1.1 四个断点，逐个给证据

| # | 断点 | 证据 | 用户看到什么 |
|---|---|---|---|
| 1 | 绑定列存在，但项目侧读不到 | `V11_45:16-26` 有 `management_credential_id`/`bmc_credential_id`；`Device.java:15-35` 与 `DeviceRepositoryJdbc.java:25-31` 的列清单**都不含** | 项目模式「测试资产」结构上拿不到绑定关系 |
| 2 | 采集不读绑定 | `GlobalAssetService.java:526-552` 的 `collect()` 方法体里，两个绑定列**一次都没出现** | 绑了凭证还要每次手选 |
| 3 | 验证事实从不写表 | `CredentialVerificationService.recordFromCollect()`（`:183-191`）**全仓唯一引用是它自己的单测**；`/verify` 端点前端零调用（`GlobalAssetCredentialController.java:54-67`） | `credential_verification` 表基本恒空 → `CredentialPicker.vue:95-142` 的「已验证优先」排序形同空转 |
| 4 | 界面用账号名冒充凭证 | `AssetDetailController.java:126-132` 用 `device.account` 生成掩码 → `api/assetDetail.ts:192` 合成单条 `id=0` 假凭据 | 详情页永远显示 1 条、名字叫 `credential` |

**唯一真实记录「用了哪条凭证」的地方**是 `device_check.credential_id`（`V11_64:30-33`），但它没被聚合到列表。

### 1.2 「永久保存」的实质是什么

大师要求「已验证可采集的资产自动关联好采集凭证（并永久保存）」。技术上等于三件事：

1. **事实层已有**：`device_host_spec` 是 append-only（`HostInventoryService.java:27-31`）、`credential_verification` 也只追加、绑定列已建；
2. **缺的是「读的时候拼起来」**：一个聚合查询把三者合成一行「采集画像」；
3. **缺的是「写的时候补上」**：采集成功后把验证事实与绑定（仅填空）写进去。

因此本版**先做聚合查询，不新建业务表**。

## 2. 约束与术语

| 术语 | 含义 |
|---|---|
| 采集画像（collect profile） | 查询期聚合出的一行：绑定凭证 + 最近验证 + 最近采集 + 可用判定 + 状态 |
| `profileState` | `READY`（已验证可采）/ `PARTIAL`（已绑定未验证）/ `BLOCKED`（无凭证或无管理 IP） |
| 自动填空 | 采集成功且本次用的是管理面凭证时，**仅当** `management_credential_id IS NULL` 才回填；**非空一律不改** |
| 验证事实 | `credential_verification` 的一行：用了哪条凭证、结果（`OK`/`FAIL`+`failure_kind`）、时间、来源（`COLLECT`/`VERIFY`） |
| 两个入口 | 直接采集（用绑定，一键）/ 指定凭证采集（可改绑定）；批量采集走凭证维度端点 |

**硬约束**：

1. **只自动填空，绝不自动改非空**：人工指定的凭证被下一次采集悄悄覆盖属破坏性行为，明令禁止。
2. **验证事实必须来源于真实采集或真实验证**：不许为了「让列表好看」写假 `OK`。
3. **不新增业务表**：先用聚合查询；只有当 `profileState` 需要参与排序/筛选且性能不达标时才补物化表（登记遗留）。
4. **项目侧采集的权限面**：采集端点从「只认 `owner_scope='PLATFORM'`」改为「认 `AssetScopeSql` 的可见性」，凭证必须是**本项目可见**的凭证；这会改变权限面，必须补越权用例。
5. **迁移只能追加**：从 `V11_72` 起（5.12 预留到 `V11_71`）。

## 3. 角色与关键场景

| 角色 | 场景 | 本版变化 |
|---|---|---|
| 环境管理员 | 一批新机器上线，逐台绑凭证再逐台采集 | 首次采集自动记住凭证；下次一键采集，不用再选 |

| 审计/复核 | 这次采集用的是哪条凭证 | 采集历史每条带凭证名与验证结果 |

## 5. 需求详述

### FR-v5.13-01 采集画像聚合与状态判定【P0】

**描述**：新增查询期聚合：

```text
DeviceCollectProfile
├─ deviceId / projectId / scope(PLATFORM|PROJECT)
├─ managementCredentialId / bmcCredentialId                 ← V11_45 绑定列
├─ boundCredentialName / boundCredentialMasked              ← join credential
├─ lastVerifiedCredentialId / lastVerifiedAt / verifyResult ← credential_verification 最新一条
├─ lastCollectAt / lastCollectStatus / collectCount         ← device_host_spec 聚合
├─ usable = 有 management_ip 且 有可用凭证
└─ profileState = READY / PARTIAL / BLOCKED
```

`BLOCKED` 必须带**原因枚举**：`NO_MANAGEMENT_IP` / `NO_CREDENTIAL` / `CREDENTIAL_REVOKED`。

**验收判据**

| # | 判据 | 证据形态 |
|---|---|---|
| 1 | 三台设备分别构成 `READY`（有 IP + 已验证）、`PARTIAL`（有 IP + 绑定未验证）、`BLOCKED`（无凭证）→ 接口返回三个不同状态 | 真实响应 + DB 状态 |
| 2 | `BLOCKED` 的原因枚举与实际缺失项一致（无 IP 的不能报 `NO_CREDENTIAL`） | 真实响应 |
| 3 | `lastVerifiedAt` 取 `credential_verification` 的**最新一条**（按时间倒序取第一条，允许并列时取 id 最大） | DB 比对 |
| 4 | 聚合查询在 500 台设备下 ≤ 800ms（列表首屏） | 性能记录 |
| 5 | 不新增业务表（`db-audit` 表数与上版一致） | 机检输出 |

**降级预案**：若判据 4 不达标，允许补一张物化表 `device_collect_profile`（迁移追加）+ 采集后刷新，但**不得**改成「采集时不同步刷新导致状态滞后」——状态滞后会让用户以为是 bug。

### FR-v5.13-02 采集结果写验证事实【P0】

**描述**：`GlobalAssetService.collect()` 与 `/verify` 端点在成功/失败时都调用 `credentialVerification.record(...)`：
成功写 `OK`，失败写 `failure_kind`（认证失败 / 连接超时 / 命令不受支持 / 其他）。
`recordFromCollect()` 从死代码变为主路径。

**验收判据**

| # | 判据 | 证据形态 |

| 1 | 采集前 `SELECT count(*) FROM credential_verification` = N → 采集成功一次 → N+1，且该行 `result=OK`、`credential_id` = 实际使用的凭证 | DB 查询 |
| 2 | 用错误密码采集失败 → 仍写一行，`result=FAIL` 且 `failure_kind` 非空 | DB 查询 |
| 3 | `source` 字段能区分 `COLLECT` 与 `VERIFY` 两种来源 | DB 查询 |
| 4 | 反向判据：在 v5.12 收口 commit 上执行判据 1 → 行数不变（复现原断点） | 回放日志 |
| 5 | `CredentialPicker` 的「已验证优先」排序在真实数据下生效（tier=0 的凭证排第一） | 截图 + 真实响应 |

### FR-v5.13-03 采集时使用绑定凭证【P0】

**描述**：`collect()` 入口：`credentialId == null` 时，按「有 `management_ip` → 取 `management_credential_id`；否则取 `bmc_credential_id`」回退；

**验收判据**

|---|---|---|
| 1 | 设备已绑管理面凭证，调用采集**不传** `credentialId` → 200 且实际使用绑定凭证（验证事实里 `credential_id` 一致） | 真实请求 + DB |
| 2 | 只绑了 BMC 凭证、无 `management_ip` → 用 BMC 凭证采集（或明确 400 说明不支持无 IP 采集），行为与文案一致 | 真实请求 |
| 3 | 两者都未绑 → 400，错误信息含「未绑定凭证」与设备标识 | 真实请求日志 |
| 4 | 显式传 `credentialId` 时**优先于**绑定（不被绑定覆盖） | 真实请求 + DB |
| 5 | 安全闸不回退：`confirmed=false` 仍 400（与 v5.8 的安全闸口径一致） | 真实请求日志 |

### FR-v5.13-04 自动填空绑定【P0】

**描述**：采集成功后，若本次使用的是管理面凭证且 `management_credential_id IS NULL` → 回填；
若 `management_credential_id` 非空 → **不动**（即使本次用了另一条凭证）。

**验收判据**

| # | 判据 | 证据形态 |
|---|---|---|
| 1 | 未绑设备首次采集成功 → `management_credential_id` 自动填为本次凭证 id | DB 查询 |
| 2 | 已绑凭证 A 的设备用凭证 B 采集成功 → 绑定**仍为 A**（不被覆盖） | DB 前后比对 |
| 3 | 采集失败 → **不填空**（失败不能形成「已验证可采」假象） | DB 前后比对 |
| 4 | 「自动填空」在界面上有可见说明（列表或详情 tooltip：「首次采集会自动记住凭证」） | 截图 |

**说明**：判据 2 是本条的核心——自动关联的边界是「只自动填空，不自动改非空」。若实施时想改成「总是更新为最近使用」，必须先改本 PRD 并由大师确认，否则视为违反。
