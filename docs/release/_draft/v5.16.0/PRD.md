## 1. 版本定位

| 项 | 内容 |
|---|---|
| 一句话 | 把已经很强但**只在终端里**的运维能力（安装/升级/拆卸/体检/备份/恢复演练）做成**分层界面**：只读事实与预检演练上界面，安装与拆卸留在 CLI；同时把散落四处的归档/清理/告警/备份收进**一个运维控制台** |

## 2. 约束与术语

| 术语 | 含义 |
|---|---|
| L1 只读层 | 当前版本 / 上次升级时间与结果 / 安装根 / 数据目录 / 磁盘余量 / 保留的 3 个历史版本 / 最近 doctor 结论 |
| L2 预检与演练层 | 升级预检（doctor + 包校验 + 磁盘检查，只出报告）、备份、备份恢复演练、升级演练（全部非破坏性） |
| L3 受控执行层 | 上传包 → 预检 → 生成任务 → 二次输入版本号 → 后台执行 → 实时进度 → 失败自动回滚 |
| L4 安装/拆卸 | **不上界面**，保持 CLI |
| 演练库 | 库名以 `_it` 结尾的库；恢复只允许恢复到演练库（沿用 `scripts/db-reset.sh:7-20` 的守卫） |
| ops_task | 一次运维动作的任务记录：操作人 / 类型 / 参数 / 阶段 / 日志 / 结果 / 起止时间 |
| 四条硬护栏 | dry-run 默认 / 只恢复演练库 / 备份带 SHA-256 / 全部动作落审计 |

**硬约束**：

1. **破坏性操作默认 dry-run**：界面上「预演」与「执行」是**两个独立按钮**，不是一个勾选框（沿用归档中心的做法）。
2. **恢复只能恢复到演练库**：库名不以 `_it` 结尾一律拒绝；恢复生产库必须走 CLI，界面只显示命令原文供复制。
3. **备份必须带 SHA-256 并在清单里显示校验状态**：这是唯一能让用户信任备份的展示。
4. **所有界面触发的运维动作必须落审计**（`audit` 表，含操作人/参数/结果/耗时）。
5. **不改 `update.sh` 的十步编排**：只在脚本输出里补结构化标记（`STEP 4/10 db_backup OK`）供后端解析进度；编排逻辑一行不改。
6. **迁移只能追加**：从 `V11_78` 起（5.15 预留到 `V11_77`）。

## 5. 需求详述

### FR-v5.16-01 运维控制台骨架与任务化框架【P0】

**描述**：

```text
运维（一级，方案 A）
├─ 健康总览      /ops/health
├─ 备份与恢复    /ops/backup
├─ 归档与清理    /ops/archive
└─ 升级与演练    /ops/upgrade
```

任何可能超过 3 秒的运维动作（备份、演练、预检、升级）都必须建 `ops_task`：
`{id, type, operator, params, phase, log, result, startedAt, finishedAt}`，界面可查历史与阶段进度。
**禁止**用阻塞 HTTP 请求承载长动作。

**验收判据**

| # | 判据 | 证据形态 |
|---|---|---|
| 1 | 四个二级页可达；导航项数与门禁常量一致（方案 A 为 7 组 / 方案 B 相应调整） | 截图 + `check_navigation.py` |
| 2 | 触发备份 → 返回 `taskId`（HTTP 在 2s 内返回），页面显示阶段进度 | 真实响应 + 截图 |
| 3 | 任务历史页可看到历史任务（状态/耗时/操作人），刷新后仍在 | 截图 + DB |
| 4 | 任务失败时 `result` 含失败阶段与人话原因（不是「未知错误」） | DB + 截图 |
| 5 | 同一类型任务并发触发 → 第二个被拒并提示「已有同类任务在运行」 | 真实请求 |

## 9. 本版不做的事

| 不做 | 理由 |
|---|---|
| 一键安装 / 一键拆卸上界面 | `uninstall.sh` 的护栏就是「终端里手输 UNINSTALL」；搬上界面等于拆护栏。且安装发生在「平台还没跑起来」时，界面无能为力 |
| L3 受控升级执行 | 升级失败会停机；必须先有两轮 `update-drill` 通过 + 任务化框架稳定（本版只建框架） |
| 改 `update.sh` 的十步编排 | CLI 质量已高于对标件，动编排风险大于收益 |
| 自动清理演示数据 | D-5 已定「标记 + 显式触发」 |
| 备份到对象存储 | 需先定存储选型；本版只做本地目录清单 |
| 环境漂移告警 | 属 5.15 的快照能力 + 告警规则，跨版依赖，登记遗留 |
