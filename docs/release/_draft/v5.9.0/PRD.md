## 1. 版本定位

| 项 | 内容 |
|---|---|
| 一句话 | 把「谁能看到哪个项目」收敛成**一套三源并集口径**，把用户与权限从「三套并行且有一套不生效」收口成**一个一级菜单 + 4 个二级页**，并把导航高亮固化成**可机检的不变量** |
| 性质 | **基座版**：本版不新增业务对象，只修口径与架构。5.10 向导的成员步、5.11 起所有页面的人员可见性都建立在本版口径上 |
| 上游需求 | R1（固化）、R2、R10、R12（通则）、R3（机制部分） |
| 目标产出 | 归属口径从 1 源变 3 源并集；组授权从「不生效」变「参与判权」；用户与权限从 0 个正式入口变 4 个；列表 CRUD 从「参差」变「通则 + 机检白名单」；演示数据从「无法识别」变「可标记 + 可预演清理」 |
| 不追求 | 不做向导（5.10）、不改用例/资产页面布局（5.11~5.13）、**不执行**演示数据清理（只建机制与脚本）、不改表名与 API 路径 |

### 1.1 为什么这一版必须先做

三条硬依赖，任何一条不成立，后面的版本都会返工：

1. **R2 与 R10 是同一处代码**：`AccessControlService.visibleProjects()`（`backend/.../iam/AccessControlService.java:166-173`）只按 `project_member` 取，而 `requireProjectAccess`（`:145-154`）同样不查 `project_group_role`。评估报告 01 §2.4 已写明「这两条必须同版本，不可拆」——分开做等于同一个 SQL 改两遍、403 用例重跑两遍。
2. **5.10 向导的「成员步」要有正确口径可写**：向导 `members` 步（`ProjectWizardView.vue:487-530`）现在加的是 `project_member`，若 5.9 不做组授权与并集口径，向导里加进去的人仍然「加完看不到」。
3. **菜单数量是门禁常量**：`tools/check_navigation.py:50-51` 硬编码 `GLOBAL_EXPECTED = 5`。R10 新增一级菜单必须在同版把常量与 `navigation.spec.ts:439/444/445` 的「5 组 16 叶」断言一起改，否则第一道门就红——这种改动不能延后到「以后的某版」。

|---|---|---|---|

## 2. 约束与术语

| 术语 | 含义 |
|---|---|
| 三源并集 | 可见项目 = `project_member`（成员）∪ `project.owner_id`（负责人）∪ `project_group_role`+`user_group_member`（组授权） |
| 来源（source） | 并集里每条记录的归属来源，取值 `OWNER` / `MEMBER` / `GROUP`；同一项目多源命中时取优先级 `OWNER > MEMBER > GROUP`，**只出现一次** |
| defaultOf | `NavLeaf` 上的标记，表示「同 path 组内的默认叶子」（如 `/g/cases` 之于 `?view=imports`） |
| 命中唯一性 | 任意一个 URL，导航树中被判定为「选中」的叶子数 ≤ 1 |
| 事实层 / 视图层 | 事实层 = `project_member`、`project_group_role`、`user_group_member` 三张表；视图层 = 界面上的「参与项目数 / 已授权项目数」。**视图层不得有独立写入口** |
| 演示数据 | `is_demo=1` 的账号与项目（含其下属用例/用例集/报告）。**不单独标记用例与报告**，靠「所属项目是演示项目」级联识别 |
| 通则（R12） | 所有列表必须满足的 5 条：有删除、删除有二次确认、删除有影响面、批量有入口或有明确说明、失败给人话 |

**硬约束**：

1. **不新增第二套写入 API**：界面上的三种「关联」动作（项目关联页、用户组页选项目、用户页选项目）必须调用同一组既有端点（`POST /projects/{id}/members`、`POST /groups/{id}/grant`）。
2. **不改表名、不改 API 路径**：`project_member` / `project_group_role` / `/api/iam/*` 保持；新增能力用新端点，不重命名旧端点。
3. **迁移只能追加**：从 `V11_65` 起（当前最大 `V11_64`），每支迁移配 `.down.sql`；不得修改既有迁移文件。
4. **门禁只增不减**：新增机检必须带 `--self-test`（真注入 → 判红 → 还原）；`GLOBAL_EXPECTED` 的变更必须与代码同 commit。
5. **清理脚本默认 dry-run**：任何删除动作不加 `--apply` 时必须零写入。

## 3. 角色与关键场景

| 角色 | 场景 | 本版变化 |
|---|---|---|
| 项目负责人（owner） | 把项目转给同事后，同事打开「我参与的」 | 转交后立刻可见，且有来源列标「负责人」；不再需要人工补成员行 |
| 工程师（被组授权） | 被加入 `gpu-组` 并授予项目 A 的 ENGINEER | 能看到 A、能进 A、界面显示的角色与真实权限一致 |
| 平台管理员 | 季度审计：这个用户到底参与哪些项目、通过什么方式 | 一个「项目关联」页按项目展开组与用户；三处读数一致，不再靠猜 |
| 平台管理员 | 删掉一个已经退场的账号 | 不再 500；删除前能看到该账号在哪些项目有角色 |
| 平台管理员 | 删除一个演示项目 | 看板报告列表即可删报告；删除前看到影响面（N 条用例、M 条报告） |
| 开发/交付同学 | 阶段完成后清理开发期账号与项目 | `purge-demo.sh` 先列出清单（dry-run），确认后 `--apply`；真实数据零变化 |
| 只读访客（viewer） | 没有参与任何项目 | 「我参与的」返回空列表与空态说明，不是 500 或空白 |

## 5. 需求详述

### FR-v5.9-01 叶子命中唯一性固化为不变量【P0】

**描述**：`NavLeaf` 增 `defaultOf?: true`；`queryMatches` 改为「同 path 组内若存在带 query 且命中的兄弟叶子，则 `defaultOf` 叶子不亮」；
`alsoMatch` 的取值限定为「详情段」（如 `/g/assets/detail/`）或显式 `exclude` 列表，**禁止**用裸前缀表达详情页。
新增机检项：静态扫描 `navigation.ts` 中所有 `alsoMatch` 是否合法；新增单测：任意 URL 命中叶子数 ≤ 1 且 ≥ 1。

**验收判据**

| # | 判据 | 证据形态 |
|---|---|---|
| 1 | 三条复现路径各只亮 1 个：`/g/cases?view=imports`、`/g/assets?tab=credentials`、`/g/projects?scope=mine` | 3 张截图 + DOM 断言（`aria-current` 计数 = 1） |
| 2 | 不变量单测：遍历 `router.getRoutes()` 全部静态路由 × 各组默认 query 组合，断言命中叶子数 **≤ 1 且 ≥ 1**（后者守住项目模式「三页签全灭」的反向症状） | `navigation.spec.ts` 新增用例 |
| 3 | 机检 `check_navigation.py` 新增 `alsoMatch` 校验，`--self-test` 能真注入一条非法 `alsoMatch` 并判红 | 机检输出（含注入前后的红/绿对照） |
| 4 | 反向判据：在 v5.8 收口 commit 上跑判据 2 的单测 → 必须红（至少 3 条路径命中 2 个叶子） | 回放日志 |

**降级预案**：若某页面确实无法用 `defaultOf` 表达（例如同一 path 下两个都不带 query 的叶子），允许改为「一个带 query 的显式默认值 + 页面 `router.replace`」，但必须在 `navigation.ts` 注释里写明理由，且判据 2 仍须通过。

**说明**：v5.8.0 已按 D-2 插队做了「互斥特例 + 一条不变量测试」。本版是把特例**换成规则**，并把机检补上——特例能修现象，规则能防下一次。

### FR-v5.9-02 可见项目改为三源并集并返回来源【P0】

**描述**：`AccessControlService.visibleProjects()` 由「只查 `project_member`」改为三源并集（`UNION` 或 `OR EXISTS`），
且 `requireProjectAccess` 复用**同一段可见性 SQL**（抽成常量或同一个 `ProjectVisibilitySql` 类，禁止两处各写一遍）。
`GET /api/projects/cards?scope=mine` 的每条记录新增 `source` 字段与 `roleCodes`。

**验收判据**

| # | 判据 | 证据形态 |
|---|---|---|
| 1 | 把项目 A 的 owner 转给 `eng1`（不改成员关系）→ `eng1` 的 `scope=mine` 含 A 且 `source=OWNER` | 真实 HTTP 响应 + DB 查询 |
| 2 | 把 `eng2` 加入组 G 并给 G 授 `A:ENGINEER` → `eng2` 的 `scope=mine` 含 A 且 `source=GROUP` | 真实 HTTP 响应 |
| 3 | 三源同时命中同一项目 → 结果中该项目**只出现一次**，`source=OWNER`（优先级最高） | 单测 + 真实响应 |
| 4 | 无任何归属的 `viewer` 账号 → `scope=mine` 返回 `[]`（HTTP 200），不是 500/403 | 真实请求日志 |
| 5 | `visibleProjects` 与 `requireProjectAccess` 共用同一可见性片段：单测断言「并集里出现的项目，`requireProjectAccess` 必不抛 403」，对 3 个账号 × 5 个项目做矩阵 | 单测矩阵输出 |
| 6 | 平台项目（`kind='platform'`）仍不出现在「我参与的」 | 真实响应 |

**降级预案**：若 `UNION` 写法在某数据库方言下无法走索引导致列表超时（>2s/1000 行），允许改为「三次查询 + 应用层去重」，但判据 3/5 仍须通过，并在 DEV-PLAN 记录实测耗时。

### FR-v5.9-06 关联写入统一为幂等批量语义【P1】

**描述**：用户→项目单个添加当前非幂等（409，`ProjectService.java:338-346`），批量幂等（`:357-389`）；组→项目已幂等（`GroupService.java:53-61`）。
统一为：**重复添加视为成功跳过**（HTTP 200，响应含 `added/skipped` 计数），不返回 409。

**验收判据**

| # | 判据 | 证据形态 |
|---|---|---|
| 1 | 同一用户对同一项目连续添加 2 次 → 两次都 200，第二次 `added=0 skipped=1`，`project_member` 行数不变 | 真实请求 + DB 计数 |

| 4 | 响应体含 `added` / `skipped` 字段，前端据此提示「已存在 N 项，未重复添加」 | 界面截图 |

**降级预案**：若既有前端依赖 409 做「已存在」提示，允许保留 409 但**必须同时**在响应体里给 `code=ALREADY_EXISTS`，并在前端改为按 code 提示；判据 1 的「200」可放宽为「幂等状态码 + 行数不变」。
