## 3. 为什么不是「未注册前缀即拒绝」

PRD W60-03 原判据②写的是「未注册前缀被拒」。评估后改成「首用自动登记，**已占用**才拒」，理由：

1. 前缀注册表如果只能靠 SQL 增长，新业务线上线一个新前缀就要发一版数据库脚本——把产品能力锁在发布流程里；
2. 真正的风险不是「用了没人登记的字母」，而是**两个模板用同一个前缀**（人分不清编号出处），这一条仍然硬拒且点名前缀；
3. 登记动作写审计（`template.prefix.register`），事后可查谁在什么时候引进了这个前缀。

这条差异已登记为 DEV-PLAN 推翻项 A1，不静默改判据。

## 4. 为什么导入向导本版不做

DEV-PLAN W60-12/13/14 原计划把资产/用例导入升到五步并统一 `WizardContentPicker`。评估后推迟：

- `WizardContentPicker` 的分类树在 **5.11 用例清单三栏**里要被换成树组件（DEV-PLAN 风险 R4 已预判）。本版改一遍、5.11 再改一遍，等于花两次钱买同一个东西；
- 导入五步的真实收益在「字段映射」，而字段映射的正确性只在真实 CSV 上才看得出来；本版没有导入侧的采样数据，做了也只能是空壳。

**降级处理**：保留既有两步弹窗（功能不缺，只是不叫「向导」），把五步列为 5.12 资产工作台的输入项。
这是**未达成**，不是「已完成但简化」，登记在 TEST-REPORT §降级项。
