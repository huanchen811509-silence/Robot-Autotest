# v5.21.0 评估报告：角色可用性与工程同构

> 流程位置：② 评估报告。上游：`00-RESEARCH.md`（26 条事实 / 4 条该保留 / 4 条缺口）。
> 本文决定"做不做、做什么、不做什么"；需求写进 `PRD.md`。

---

## 1. 目标与范围

**目标**：让"除管理员以外的角色"在真实界面上**能被创建、能登录、能看到该看的、不能做不该做的**；并确认同一套页面在四类工程（RF ×2 / pytest ×2）上表现一致。

**范围**：6 条需求（`FR-v5.21-01 ~ 06`），其中 3 条 P0 落在"角色数据 + 能力集 + 前端表达"，2 条 P1 落在"工程矩阵 + 偶发遮挡"，1 条 P1 落在数据口径。

**不追求**：不重写权限模型（现有 4 角色矩阵是对的）、不做细粒度字段级权限、不做 SSO/LDAP、不做审计合规、不做视觉重设计。

## 2. 结论

**必须做，且必须排在 v5.20.0 之后作为独立的第三个版本**。三条理由：

1. **这是"整类用户不可用"**：库里只有 1 个角色（F-21-01/06），界面角色下拉只有"管理员"（F-21-02）。一个团队要么全员 admin，要么新建的人什么也看不到——平台的多角色设计在交付形态上等于不存在。
2. **前端不设防会教坏用户**：viewer 能点开新建表单填完再失败（F-21-12），能直达执行计划页（F-21-13），能看到 403 后一片空白（F-21-14）。这三条合起来给人的结论是"这系统权限是坏的"，而实际后端判定完全正确（F-21-15/16）——**改造成本低、认知收益高**。
3. **工程同构是"复现面"问题**：四个工程的用例库 100% 同缺陷（F-21-19/20），说明 v5.19 的修复必须是通用布局修复而不是"给 EHT 打补丁"；同时 ED202 用例集的行内按钮**随右栏状态偶发遮挡**（F-21-22/23），这是 v5.19 FR-04 的漏网分支，必须在本版收口，否则永远有人能复现。

## 3. 方案比较

| 方案 | 做法 | 成本 | 风险 | 结论 |
|---|---|---|---|---|
| **A. 只补数据**（迁移 seed 4 角色） | 只加 `role` 表 3 行 + 前端下拉自动变 4 项 | 小 | 角色可选了，但能力集仍空（F-21-07）、写按钮仍全开、直达仍不拦 → 建出来的 engineer 依然是"半个 admin" | 不选 |
| **B. 数据 + 能力集 + 前端表达（推荐）** | A + 修能力集兜底 + 菜单/按钮按角色渲染 + 403 页 + 角色矩阵探针 | 中 | 改动面跨三层（迁移 / 后端能力 / 前端渲染），需要契约机检兜住 | **选** |
| **C. 重做权限模型**（RBAC + 资源树 + 字段级） | 引入权限表、角色继承、策略引擎 | 大 | 与当前"资源+动作"矩阵不兼容，回归面覆盖全站；本版无此必要 | 不选（登记 v5.23 候选） |

**选 B 的理由**：现有 `RoleCode` 4 角色 + `PermissionMatrix` 资源动作矩阵已经是合格模型（K-21-04），缺的是**数据（角色行）+ 兜底（空能力不放大）+ 表达（前端显隐与 403 页）**。C 会把一个"数据缺失"问题升级成"架构重写"。

## 4. 可行性与风险

| 项 | 判定 | 依据 | 主要风险 | 量级 |
|---|---|---|---|---|
| 四角色落库 | 可行 | `role` 表结构已支持 `built_in`；只需 `V11_80` 幂等插入 3 行 | 已有环境重复插入 → 必须 `INSERT ... ON DUPLICATE KEY UPDATE` / `WHERE NOT EXISTS` | 小 |
| 能力集兜底 | 可行 | `MenuCapabilityController` 已走 `AccessControlService`；空集来自"无角色"分支 | 改成"无角色→最小集"可能与"无角色应无权限"冲突 → **采用 fail-closed + 显式提示**，不放大 | 中 |
| 菜单按角色渲染 | 可行 | `navigation.ts` 已有 `capability` 字段，只覆盖少数叶子 | 给每个叶子补 capability 会动全站菜单 → 先建"叶子→capability"映射表并机检，**不改分组**（D-01） | 中 |
| 写按钮显隐 | 可行 | 前端已有 `usePermission`/角色信息（待核） | 各页自己写 `v-if` 会漏 → 统一用指令 `v-can="'CASE:WRITE'"` | 中 |
| 403 页与错误态 | 可行 | 路由已有 `meta.capability` 机制与 403 页 | 直达路由漏配 `meta.capability` → 需要"每个路由必须有 capability 或 public 标记"的机检 | 中 |
| 工程矩阵回归 | 可行 | 4 工程已存在且都有数据（demo 用例集为 0） | demo 用例集 0 条 → 该格只能验空态，需在报告中标注 | 小 |
| 偶发遮挡收口 | 可行 | 遮挡根因是右栏宽度变化挤压表格 | 只修一种状态会留下其他状态 → 需按 4 种右栏状态矩阵验 | 中 |
| 角色口径规范化 | 可行 | 存量 2 种写法（`viewer` / `ENGINEER`） | 一次性 UPDATE 需可回滚；读路径要兼容大小写直到迁移完成 | 小 |

## 5. 前置条件

1. **v5.19.0 与 v5.20.0 已发版**：本版判据依赖"列表可见、操作可达、四态与反馈已统一"，否则角色视角看到的还是空白表，无法判定"能看到该看的"。
2. `PROJECT_ID=29`（qa-e2e-fixture）保留为非管理员验证夹具，且 4 个 E2E 账号可用（口令由 `QA_E2E_PASSWORD` 提供）。
3. 角色矩阵的"期望码表"必须由**产品确认**（哪个角色对哪个接口应 200/403），不能由实现方自定。
4. 迁移只能追加，不改历史脚本；新迁移从 `V11_80` 起。
5. 本版允许改后端（白名单/兜底/迁移），但**不允许改 `RoleCode` 枚举语义**。

## 6. 不做清单（明确划界）

| 不做 | 理由 | 归属 |
|---|---|---|
| 字段级权限（同一页面不同字段可见性） | 当前无业务诉求 | 未立项 |
| 角色继承 / 自定义角色 | `role.permissions` 字段虽在，但无 UI 与语义定义 | v5.23 候选 |
| SSO / LDAP 角色映射 | 部署形态未定 | 未立项 |
| 审计日志的角色变更留痕内容 | 只做"有记录"，不做内容规范 | NFR 覆盖 |
| v5.19 / v5.20 范围内的任何缺陷 | 避免验收责任不清 | 回对应版本 |

## 7. 拆分与发布口径

| 项 | 口径 |
|---|---|
| 版本形态 | **单版发布**，不拆：6 条需求共享同一套角色夹具，拆开会导致"角色建了但界面还不认"的中间态 |
| 不可降级 | `FR-01` / `FR-02` / `FR-03` 三条（任一未达成 → 本版未完成） |
| 可降级 | `FR-04` 的 demo#1 用例集格（0 数据，只能验空态）、`FR-06` 的历史数据修正（可延后一个版本，但读路径必须已兼容） |
| 与 v5.19/5.20 的关系 | 本版**不回改**前两版的判据；但前两版的门禁断言必须在本版继续 PASS（见 NFR-02） |
