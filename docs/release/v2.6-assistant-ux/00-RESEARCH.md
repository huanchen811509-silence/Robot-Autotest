## 1. 现状（改之前到底是什么样）

### 1.1 「宽度可调」是假的

| 事实 | 分级 | 来源 |
|---|---|---|
| `useAiDrawer` 有 `width` 状态、有 `setWidth`、抽屉里还显示这个数字 | [已核实] | `composables/useAiDrawer.ts` |
| 但 `.app-shell.has-drawer` 的第三列**硬编码 `340px`**，与 `width` 无关 | [已核实] | `styles/main.css` 改前 |
| 所以点「宽度」按钮只是把数字从 340 变 360…再回到 280，**布局一动不动** | [已核实] | 代码路径推断 + 改前 CSS 硬编码 |
| 可调范围常量是 280–520，靠按钮 +20 循环，没有拖拽，也不能精确调到想要的宽度 | [已核实] | 同上 |

**结论**：这不是「宽度不好用」，是**这个功能从来没接上**。用户看到的数字是装饰。

### 1.2 抽屉与布局的两种既有形态

| 事实 | 分级 | 来源 |
|---|---|---|
| ≥1000px：抽屉是 grid 第三列，**推挤**主内容（主区变窄，不遮挡） | [已核实] | `main.css` `.app-shell.has-drawer` |
| ≤999px：抽屉变 `position: fixed` **悬浮**覆盖在主内容上，宽度固定 340px | [已核实] | `main.css` `@media (max-width: 999px)` |
| 两种形态已经共存，不是二选一 | [已核实] | 同上 |

### 1.3 Agent 与模型

| 事实 | 分级 | 来源 |
|---|---|---|
| 7 条 CLI 候选已实现，设置页可逐个配端点/密钥/模型（v2.5） | [已核实] | `AiAssistantConfigService` |
| 但**抽屉里选不了**：`AiPanelService.invoke()` 固定用 `probe.primaryCli()`，模型固定用配置里那一个 | [已核实] | `AiPanelService` 改前 |
| 设置页接口 `requireAdmin()`，普通用户看不到清单 | [已核实] | `AiAssistantController` |

## 2. 三种宽度方案的取舍（大师要求先评估）

| 方案 | 用户体验 | 代价 | 结论 |
|---|---|---|---|
| **A. 固定档位**（现状修好版：340/420/520 三档按钮） | 简单，但调不到「正好」；长表格与长对话的合适宽度因人而异 | 最低 | 不够 |
| **B. 全悬浮**（抽屉脱离布局，浮在内容上，可拖宽） | 主内容不被压缩，但**被抽屉盖住的部分看不见也点不到**；抽屉一宽就等于遮住半个页面 | 中；要处理遮罩、层级、Esc 关闭 | 不适合主用法 |
| **C. 推挤 + 可拖拽**（桌面端占第三列、拖动边界改宽度；窄屏仍悬浮） | 打开助手时主内容自动让位，不遮不挡；宽度随手调到合适值 | 中；需要拖拽交互、边界钳制、持久化 | **采用** |

**为什么选 C**：

1. 这是「边看内容边问 AI」的场景，遮挡式抽屉会把要参照的内容盖掉，等于逼用户来回开关；
2. 窄屏本来就放不下并排两栏，悬浮是对的——**两种形态按视口分工**，不是二选一；
3. 推挤的代价只是主区变窄，而主区在 1440 视口下最窄仍有 480px，表格可用。

**上限为什么是 760**：1440 − 200（侧栏）− 760 = 480，这是主区还能用的底线；再宽就该开独立页面。
**下限为什么是 340**：再窄对话每行放不下 20 个汉字，读起来一直换行。
