# 版本开发标准流程

**文档编号** RA-PROC-2026-001 ｜ **版本** v1.0 ｜ **定规日期** 2026-11-02 ｜ **定规人** 大师
**效力**：本项目及后续所有项目的**每个大版本开发**均须依照本流程。与任何排期冲突时，**排期可调，流程不可跳**。

---

## 0. 一句话

**每个大版本 = 七道环节 × 六份产物。缺任一环，该版本不算完成，不得对外称已交付。**

```
需求调研 → 评估报告 → PRD → 开发计划 → 测试计划 → 测试执行 → 文档回写
   ①          ②        ③        ④          ⑤          ⑥          ⑦
```

七道是**单向串行**的：不做完上一道，不进下一道。允许在下一道中回头修订上一道（发现调研遗漏就该回去补），但**不允许跳过**。

---

## 1. 为什么必须串行

这七道分别回答七个不同的问题，任意两道合并或倒置，都会让问题失去答案：

| 环节 | 回答的问题 | 跳过它的后果（本项目真实发生过） |
|---|---|---|
| ① 需求调研 | 用户到底怎么干这件事？ | 按想象写需求，做完没人用 |
| ② 评估报告 | **做不做**？值不值？有没有更省的路？ | 直接开工，做到一半发现路走不通 |
| ③ PRD | **做什么**？做到什么程度算够？ | 范围随开发漂移，永远差一点 |
| ④ 开发计划 | **怎么做**？先做哪一步？ | 大爆炸式提交，无法评审、无法回退 |
| ⑤ 测试计划 | **怎么验**？验到什么程度？ | 只测 happy path，缺陷上线才暴露 |
| ⑥ 测试执行 | 到底过没过？ | 拿"代码写完了"当"能做" |
| ⑦ 文档回写 | 之前的判断还成立吗？ | 文档变成愿望，与系统两张皮 |

**最容易偷懒的是 ② 和 ⑦**：②跳过了没人立刻发现（要等三个月），⑦跳过了文档从此失真。所以这两道在本流程里门槛最硬。

## 2. 七道环节明细

### 2.1 ① 需求调研

| 项 | 内容 |
|---|---|
| **目的** | 把"用户说想要"变成"用户实际怎么做"，把"我知道"变成"我核实过" |
| **产物** | `00-RESEARCH.md` |
| **必含** | 使用场景与真实动作序列；现有系统（含上游开源件）的能力边界与不可改之处；环境与数据约束；术语表；**证据分级清单** |
| **完成判据** | 每条关键事实标注了 **`[已核实]`（有命令输出/文件行号）/ `[推断]`（有依据未验证）/ `[假设]`（凭经验）** 三档之一；所有 `[推断]` `[假设]` 汇成待验证清单，交给 ② 或 ⑥ 关闭 |
| **谁做 / 谁批** | AI 起草；大师或技术负责人确认范围无误 |

**硬规矩**：**不许把 `[假设]` 写成结论。**

> 反面教材（本项目 v4.0）：当时测试环境内存沿用旧运行记录写成 3,350 MB，据此得出"撑不住 4 并发、必须扩内存"的硬结论并列进前置条件。实际登录实测是 7,376 MB，结论完全反转。**一个未标注来源的数字，能让整份评估报告的结论作废。**

### 2.2 ② 评估报告

| 项 | 内容 |
|---|---|
| **目的** | 决定**做不做、做成什么样**，以及明确**不做什么** |
| **产物** | `01-ASSESSMENT.md` |
| **必含** | 结论与评分（分维加权，每维给依据）；方案对比（≥2 个，含"不自己做"）；风险登记册（含概率/影响/对策）；前置条件清单（每项带验收方式）；**证据附录（可复现命令）** |
| **完成判据** | 每条量化结论都能用附录命令复现；评分每一维都有扣分理由；**明确写出"不做"的清单** |
| **谁做 / 谁批** | AI 起草；**大师拍板立项**。未经拍板不得进入 ③ |

**硬规矩**：**缺少评估报告的版本，不许开 PRD。**

**允许的结论**：可行 / 有条件可行 / 需改方案 / 不建议。**"有条件可行"必须把条件写成前置条件清单，不许模糊成"注意风险"。**

### 2.3 ③ PRD

| 项 | 内容 |
|---|---|
| **目的** | 把评估结论翻译成**可验收的需求** |
| **产物** | `PRD.md` |
| **必含** | 范围（含**明确的"不做"**）；FR 清单（编号 + 用户动作 + **验收判据** + 对应 WBS）；非功能指标（性能/并发/安全）；数据模型与接口影响；版本退出标准 |
| **完成判据** | **每条 FR 都能直接写成一条测试用例**；写不出判据的，不算需求 |
| **谁做 / 谁批** | AI 起草；技术负责人评审；范围变更需大师批 |

**硬规矩**：**形容词不是判据。**「快速」「友好」「稳定」一律退回重写，必须换成数字或可观察现象（如"日志延迟 P95 < 2 s"）。

### 2.4 ④ 开发计划

| 项 | 内容 |
|---|---|
| **目的** | 把 PRD 拆成**可独立验收**的执行单元 |
| **产物** | `DEV-PLAN.md` |
| **必含** | WBS 任务包（编号 + 参考体量 + 依赖 + **验收命令** + AI 自主度 A/B/C）；推进顺序与依赖图；降级预案；风险预判 |
| **完成判据** | **每个任务包都有可执行验收命令**。无命令的包视为未定义，不得认领 |
| **谁做 / 谁批** | AI 起草；技术负责人确认依赖与命令可行 |

**硬规矩**：**一个任务包 = 一次可评审的改动。** 超过两个包并行即违规（规划 §7 四条纪律）。

### 2.5 ⑤ 测试计划

| 项 | 内容 |
|---|---|
| **目的** | 在写代码前就定死"怎么算过" |
| **产物** | `TEST-PLAN.md` |
| **必含** | L1-L7 分层与覆盖范围；**FR → TC 映射矩阵**；证据形态（日志/XML/截图/命令输出路径）；失败判据；**独立裁判方案**；故障注入清单 |
| **完成判据** | 每条 FR 至少 1 条 TC；关键需求必须有**反例**（不只 happy path）；证据形态可留存、可复查 |
| **谁做 / 谁批** | AI 起草；技术负责人评审 |

**硬规矩**：**不接受实现方自证。** 判定"对不对"的不能是被测的那个东西本身——编辑器往返保真用 Python `robot.api` 做裁判，并发正确性用独立压测脚本验，而非看业务日志自述。

### 2.6 ⑥ 测试执行

| 项 | 内容 |
|---|---|
| **目的** | 用真实运行给出"过/没过"，而不是"应该能过" |
| **产物** | `05-TEST-REPORT.md` + `docs/evidence/<version>/` 下的证据文件 |
| **必含** | 每条 TC 的结果（PASS/FAIL/BLOCKED）+ 证据路径；失败项归属（代码缺陷 / 用例缺陷 / 环境问题）；遗留缺陷清单与等级；**关键指标实测值 vs 目标值** |
| **完成判据** | 无"未执行"项（BLOCKED 必须写明原因与解除条件）；P0/P1 清零或经书面豁免 |
| **谁做 / 谁批** | AI 执行并留证、按检查单核验门禁并出书面结论；**关键项人旁路抽验**（往返保真抽 10 样本、并发现场看一次、导出抽 3 份）（2026-11-06 口径） |

**硬规矩**：**BLOCKED 不等于 PASS。** 环境不通、用例写错，一律如实记 BLOCKED 并追因，不许改成"跳过"。

### 2.7 ⑦ 文档回写

| 项 | 内容 |
|---|---|
| **目的** | 让文档反映**实际做出来的系统**，而不是当初的设想 |
| **产物** | 上述四份文档各自更新 + 本文件 §7 的回写记录表 |
| **完成判据** | 四份文档都有本次版本的修订记录；① 的三档证据已按 ⑥ 的实测**重新标注** |
| **谁做 / 谁批** | AI 起草并自行判定状态（机器门 + 证据核对通过即置 `已完成`，行内留 `AI 验收 <日期>` 戳）；技术负责人旁路复核、可改判（2026-11-06 口径） |

**回写清单（逐项做，不许合并成一句"已更新"）**：

| 文档 | 回写什么 | 特别要求 |
|---|---|---|
| `00-RESEARCH.md` | `[推断]` `[假设]` 按实测改为 `[已核实]`，或标注"已被推翻" | 被推翻的**保留原文并划掉**，不许直接删 |
| `01-ASSESSMENT.md` | 被实测推翻的假设逐条改掉；评分若变化写明原因；前置条件状态更新 | **不许悄悄改数字**——必须留修订记录，写清"原值 / 实测值 / 影响" |
| `PRD.md` | 每条 FR 的验收状态：达成 / 未达成 / 降级 | 降级必须写理由与**授权人** |
| `DEV-PLAN.md` | 各包实际完成情况、偏差原因、未做项去向 | 未完成的包不许从表里删掉，标 `延后` 并写去向 |
| `TEST-PLAN.md` | 实测结果、与计划的差异、新增用例 | 计划外新增的用例要补编号 |
| `CHANGELOG.md` + `frontend/public/CHANGELOG.md` | 本版四类小节（新增/变更/修复/破坏性变更）写全并同步副本 | **两份副本的当前版本小节必须逐字一致**——版本迭代页读的是 `public` 副本，不同步就是对外说旧内容 |
| 关于页 / 版本迭代页 | 版本号、构建提交、当前版变更摘要 | 两处都由构建产物与 `CHANGELOG` 驱动，**每次版本收口后必须复核**：`python3 tools/check_version_consistency.py` + `node scripts/about-changelog-probe.mjs` |

**硬规矩**：**测试完成后不回写 = 该版本未完成。** 这条比"测试没过"更常被违反，因为它不报错。

## 3. 目录与命名

每个大版本一个目录，六份产物固定命名、固定顺序（数字前缀即流程顺序）：

```
docs/release/<version>/
├── 00-RESEARCH.md      ① 需求调研      （证据分级清单）
├── 01-ASSESSMENT.md    ② 评估报告      （结论 + 评分 + 前置条件）
├── PRD.md              ③ 需求文档      （FR 编号 + 判据）
├── DEV-PLAN.md         ④ 开发计划      （WBS + 验收命令）
├── TEST-PLAN.md        ⑤ 测试计划      （TC 编号 + 证据形态）
└── 05-TEST-REPORT.md   ⑥ 测试报告      （结果 + 证据 + 遗留）
```

⑦ 回写不新增文件，直接改上述五份 + 在本文件 §7 记一行。

`PRD.md` / `DEV-PLAN.md` / `TEST-PLAN.md` 沿用既有命名（已有七个版本在用，不制造无意义改名）；两端的调研与评估、末尾的测试报告用数字前缀标顺序。

## 4. 与其他文档的关系

| 文档 | 管什么 | 与本流程的边界 |
|---|---|---|
| 技术基线报告 | 为什么这么设计（架构、选型） | 是 ② 的**输入**，不是 ② 的替代 |
| 中长期工作规划 | 任务包怎么推进（§7 AI 七步循环） | 管**单个任务包**粒度；本流程管**一个版本**的完整生命周期 |
| `docs/release/README.md` | 版本怎么划分、包含哪些包 | 管**划分**；本流程管**每版怎么走完** |
| `docs/plan/WBS-STATUS.md` | 现在到哪了 | 管**状态**；本流程的 ⑦ 完成后才允许把版本标为完成 |

**粒度对照**：规划 §7 的七步是「认领一个任务包 → 提 PR」；本流程的七道是「一个版本从想法到发版」。前者嵌套在后者之内。

## 5. AI 与人的分工

| 环节 | AI | 人 |
|---|---|---|
| ① 调研 | 起草、核实、标证据档位 | 确认调研范围没跑偏 |
| ② 评估 | 起草、算分、列风险 | **拍板立项**（不可代决） |
| ③ PRD | 起草、写判据 | 评审范围与优先级 |
| ④ 开发计划 | 拆包、写验收命令 | 确认依赖与可行性 |
| ⑤ 测试计划 | 起草、建 FR→TC 映射 | 评审充分性 |
| ⑥ 测试执行 | 执行、留证、如实记 BLOCKED、**按检查单出书面门禁结论** | **机器门留证 + AI 核验；关键项人旁路抽验** |
| ⑦ 回写 | 起草、按实测重标、**自行判定并改状态** | 旁路复核与改判 |

**人守两道硬闸门**（决策 / 授权），评审与门禁转为 AI 核验 + 人旁路，其余时间不必在场。
但**发版、破坏性变更、对外口径，以及需要真机 / 外部凭据的授权，闸门仍不能由 AI 自己开**（2026-11-06 口径，见 `docs/plan/决策纪要-20261106.md`）。

## 6. 例外与不可裁项

### 6.1 允许裁剪的情形

| 情形 | 可裁 | 不可裁 |
|---|---|---|
| **Hotfix**（线上故障紧急修复） | ① 调研与 ② 评估合并为一页（写明故障现象、根因、影响面）；③ PRD 可省（改的是已有需求，在原 FR 下记变更） | ④ 开发计划（至少写清改什么、怎么回滚）、⑤ 测试计划（至少写清回归范围）、⑥ 测试执行、⑦ 回写 |
| **纯文档 / 纯配置版本** | ⑥ 可裁为"校验脚本通过 + 人工抽查" | ① ② ③ ⑦ |
| **版本内单个补丁迭代** | 若 FR 未变，③ 可只记变更行 | ⑤ ⑥ ⑦ |

### 6.2 任何情况都不可裁

> **⑥ 测试执行 与 ⑦ 文档回写，没有任何例外。**

理由：⑥ 是唯一能证伪前面所有判断的环节；⑦ 是唯一能让下个版本不重复踩坑的环节。裁掉这两个，整个流程就退化成"写文档给自己看"。

## 8. 机检项

以下项可脚本化，**能脚本化的不许靠人记得**：

| # | 检查 | 判定 |
|---|---|---|
| 1 | 每版目录六份产物齐全 | 缺一即 FAIL |
| 2 | PRD 的每条 FR 在 TEST-PLAN 有对应 TC | 有孤儿 FR 即 FAIL |
| 3 | TEST-PLAN 的每条 TC 在 TEST-REPORT 有结果 | 有未执行 TC 即 FAIL |
| 4 | TEST-REPORT 无 `BLOCKED` 未写明原因 | 有即 FAIL |
| 5 | 评估报告含"不做什么"与"前置条件"章节 | 缺即 FAIL |
| 6 | ⑦ 回写：评估报告有修订记录段 | 缺即 FAIL |
| 7 | 版本收口：`VERSION` / 根 `CHANGELOG` 当前小节 / `public` 副本当前小节 / 关于页运行期版本 / 版本迭代首条 —— 五处同版本 | 任一不符即 FAIL（`tools/check_version_consistency.py`，门禁 23 步） |
| 8 | 关于页存在「最近更新」区块，且首条版本标题含当前版本 | 缺或对不上即 FAIL（`scripts/about-changelog-probe.mjs`） |

校验脚本：`tools/check_release_docs.py`（用法见脚本头注释）。

## 9. 违反的后果

| 情形 | 后果 |
|---|---|
| 无 ② 评估报告就开 PRD | 停工补 ②，已写的 PRD 作废重审 |
| 无 ④ 开发计划的包就编码 | 该改动不计入版本，不进 `main` |
| 无 ⑤ 测试计划就进开发后期 | 门禁不过，版本不推进 |
| ⑥ 有 BLOCKED 未追因 | 版本不判定通过 |
| ⑦ 未回写 | **版本标记为"未完成"**，不得对外称已交付，不得作为下一版基线 |
